# How Fuse works

This page explains what happens between an agent's edit and Fuse's answer, and why Fuse is built that way, for someone starting on the project. [Commands](commands.md) lists what each command prints, and [architecture.md](architecture.md) maps this behavior to the code.

Fuse answers two questions for a coding agent in a .NET repository: which compiler errors did the changes introduce, and which tests can the changes break. It answers both by comparing the working tree, the files as they are on disk, with HEAD, the commit you have checked out. An error is introduced when the working tree has it and HEAD does not, so an error that already existed at HEAD is never reported.

## Surfaces

Three surfaces run the same three operations (check, test and build) and print the same text.

- **Hooks.** A harness is an agent host, such as Claude Code or Cursor, that runs a command when an event happens. `fuse hook <harness> <event>` is that command. The post-edit hook checks the files an edit wrote, the pre-shell hook rewrites `dotnet build` and `dotnet test` in a shell command to `fuse build` and `fuse test`, and the stop hook checks every change before the agent finishes. The agent does not have to decide to call anything. OpenCode runs JavaScript plugins instead of commands, so `fuse init` writes a plugin that forwards the same events to `fuse hook opencode`.
- **The command line.** `fuse check`, `fuse test` and `fuse build`, for people and for agents that run shell commands.
- **The MCP server.** `fuse mcp` serves the three operations as the tools `fuse_check`, `fuse_test` and `fuse_build` to an MCP host (the application that runs an MCP client) that has no hooks, such as VS Code agent mode.

`fuse init` registers the hooks with each harness the repository uses; [Harnesses](harnesses.md) lists what it writes.

## Process model

`dotnet build` starts MSBuild, evaluates every project and compiles what changed, on every call. Fuse keeps the evaluated and compiled projects in a long-lived process, the engine, and answers each request from it. Every command and hook runs in a short-lived client that sends one request to the engine and prints the answer.

- **One engine per repository.** The engine is `fuse engine <root>`. The first client that finds no engine for its repository starts one and waits up to 15 seconds for its pipe. The engine exits after 30 minutes without a request, when the repository directory disappears, or when a client of another build connects.
- **Identity.** The root is the nearest directory that holds `.git` (a directory, or a file in a worktree or submodule), resolved through junctions, symbolic links, `subst` drives and 8.3 short names, so every spelling of a path reaches the same engine. A hash of the root's path names the engine's pipe, a mutex that lets one engine run per root, and the state directory.
- **Protocol.** Each pipe connection carries one request and one response, each a line of UTF-8 JSON. A request names its case in a `request` property, such as `CheckFiles` or `PlanAffectedTests`, and a response names its case in a `status` property, such as `CheckAnswered` or `Unanswered`. Every request carries the client's build id: the product version and the module id of the assembly, which changes with every build. The engine reads the build id before the rest of the request. When it differs, the engine answers `Restart` and exits, and the client starts an engine of its own build and sends the request again. Client and engine therefore always run the same code, and the protocol needs no version negotiation.
- **Isolation.** The engine runs from a private copy of the tool's files in `<local application data>/fuse/engine/<version>-<module id>`, so a running engine never locks the installed tool and `dotnet tool update` works while engines run. When a client makes a copy, it deletes the copies of other builds last written more than seven days earlier. On Windows the engine starts without inheriting the client's handles and outside the client's job object, so a harness that ends its hook's processes does not end the engine, and an inherited output handle does not keep the hook's pipe open. On Linux and macOS it gets its own standard streams and calls `setsid` to leave the client's session. The pipe accepts connections from the current user only.
- **State directory.** Fuse's files for a repository live in `<local application data>/fuse/repos/<id>`, where `<id>` is the first 16 hexadecimal digits of the SHA-256 of the root path: `engine.log`, `hook.log`, the build lock, test results, the copies used for test runs without MSBuild, and the copies of the repository's own analyzers. Fuse writes nothing inside the repository except the settings `fuse init` writes. [Troubleshooting](troubleshooting.md#where-the-logs-are) gives the path on each operating system.
- **Requests.** The engine answers checks and test plans one at a time, behind a request lock, because each one brings the shared compilations up to date before it reads them. `engine.log` names every request and gives one line of per-phase times ([reading a phase line](troubleshooting.md#reading-a-phase-line)).
- **Guard.** A client starts an engine only in a repository where git knows a `.csproj` file (tracked, or untracked and not ignored). In any other repository a command or hook costs at most two `git ls-files` calls and starts nothing.

## Projects and compilations

- **Evaluation.** At start the engine lists every `.csproj` git knows about and evaluates each with MSBuild, without running targets, using the .NET SDK the repository's `global.json` selects. A multi-targeted project is evaluated once per target framework and the results are joined. The result, the project graph, says which projects own a source file, which projects depend on a project (its dependent projects), which projects hold tests (an `IsTestProject` property or a reference to a test framework package), and which are applications (an `Exe` or `WinExe` output type, or the Web SDK).
- **Loading on demand.** Nothing compiles at start. A request loads the projects it needs with Roslyn's `MSBuildWorkspace`, used only as a loader: its `TryApplyChanges` writes to disk, so Fuse never calls it. Before loading, the engine checks that every project in the closure has been restored (its `project.assets.json` exists) and answers `restore needed` with the command to run when one has not; it never restores on its own. After each request the engine loads, in the background, the dependents of the projects with uncommitted changes, one project at a time and outside the request lock, so a later check that has to reach them does not wait for the load.
- **Analyzers.** Roslyn keeps an analyzer assembly open while it is loaded, and the engine runs for up to 30 idle minutes. An analyzer or source generator the repository builds itself (a project referenced with `OutputItemType="Analyzer"`) would stay locked in its `bin` folder, and the next real build of that project would fail with MSB3021 or MSB3027. The engine therefore loads every analyzer inside the repository from a copy of its directory in the state directory, and a rebuilt analyzer gets a fresh copy when projects next reload. Package and SDK analyzers load from where they are, because no build writes them.
- **Two views.** The engine holds two immutable Roslyn solutions of the loaded projects: the current one, with every file as it is on disk, and the baseline, with every changed file at its HEAD content. Both use the project files as they are on disk. The baseline changes only when HEAD moves or projects load, so its compilations and errors stay cached from one edit to the next.
- **Staying current.** A file watcher marks changed paths, and every request also reads the files its client names (the hooks name the files an edit wrote), before the watcher reports them. A path counts as changed when its content differs from the file at HEAD, ignoring line endings; `bin`, `obj`, `.git` and `node_modules` are skipped. A change to a `.csproj`, `.props`, `.targets`, `.editorconfig`, `.globalconfig`, `global.json` or `packages.lock.json` file re-evaluates the projects. A commit or branch switch, an overflow of the file watcher, or more than 300 changed paths in one sync makes the engine read `git status` again and reload the projects it had loaded, because patching that many files one at a time costs more than reloading.

## Check

1. **Targets.** A check covers the files its client names, or every source file (`.cs`, `.razor`, `.cshtml`) that differs from HEAD. A file no evaluated project owns is skipped. Each target is bound, compiled with Roslyn, in the current view, and when it has errors, in the baseline too. An error is introduced when the baseline has no match for it: the same file, id and message, counted, with line numbers ignored, so an error that only moved is not reported.
2. **Declaration changes.** Each target's declarations are compared with HEAD from syntax alone: types, members, delegates, using directives and file-level attributes, with bodies, formatting, comments and the initializers of fields that are not constants left out. An edit that changes no declaration, such as a body edit or an added `using`, cannot break another file, and the check ends there.
3. **Reach.** Otherwise the dependents of the projects with declaration changes are loaded, and each changed declaration is resolved to its symbol in the baseline. Roslyn's `SymbolFinder` finds the files that reference it, implement or override it, or derive from its type, across the owning project and its dependents.
    - A removed or changed constructor also reaches every type that derives from its type, because a derived constructor calls it without naming it.
    - An added member reaches the users of same-named members of its type and its base types, because an added overload can make a call ambiguous, and for an interface or abstract type, every implementation.
    - An added type reaches every file that mentions its name, because it can clash with a type of the same name, and a changed Razor file (`.razor`, `.cshtml`) reaches every file that mentions the file's name.
    - An added, changed or removed conversion operator also reaches every file that mentions its type's name, because the reference search does not return the places an implicit conversion is applied.
    - A removed `using` directive can change what the file's type names resolve to without changing their text, so it reaches every file that names one of the file's types.
    - A changed type header (attributes, modifiers, kind, type parameters, primary constructor, constraints or base types), a delegate, a global using or an assembly attribute can break code that never names it, so it reaches every file in the owning project and its dependents.
4. **Candidates.** The reached files, the candidates, are bound the same way as the targets, in parallel. Past 500 candidates the check binds the reached projects whole instead, and the summary says `checked whole projects`.
5. **What counts as an error.** Compiler errors, warnings the project treats as errors, and analyzer diagnostics whose configured severity is error (through `.editorconfig`, `.globalconfig`, `WarningsAsErrors` or `TreatWarningsAsErrors`). Only the analyzers that can report an error under the project's configuration run, so an analyzer whose diagnostics are all warnings costs nothing. Warnings are never reported.
6. **Causes.** An error in a candidate is followed by one line naming the declaration change that put its file in the check: `changed:` and the declaration as the working tree has it, or `removed:` and the declaration as HEAD had it. The line holds the declaration's header on one line, without its body, members or initializer. An agent that reads an error in a file it did not edit sees which of its edits caused it without tracing it back. An error in a target, an analyzer error and an error reached by a broad change get no cause line. Each answer holds at most ten, and the summary says how many were left out.

The engine returns at most 200 errors per answer, ordered by file and position, and the client prints the first 20.

## Test selection

A missed failing test is the one outcome selection must avoid; running extra tests only costs time. Each step therefore selects more when it cannot decide.

1. **Changed code.** Each changed file is compared with HEAD from syntax, bodies included. That gives the changed declarations: added and changed members, types whose header changed or that lost a member, changed top-level statements, and every type in a file whose usings or file-level attributes changed. A changed declaration inside a test project selects its test, or its whole class when it is not a test method.
2. **Type walk.** A graph of which types name which, built from syntax with extension methods matched by method name, is walked backwards from the types that hold the changed declarations to every test class that can reach them. It binds nothing: it costs a parse of each file, and each file's part of the graph is cached by text version. Matching by name can only select extra tests.
3. **Member walk.** When at most 40 test classes are reachable, a second walk refines the selection to test methods. It follows Roslyn references backwards from each changed member, through callers, overridden members and the interface members a member implements, and stops after 300 symbols or 8 seconds, in which case the type walk's answer stands. A reference in a test method selects that test; a reference elsewhere in a test class selects the class and the classes that derive from it.
4. **Application hosts.** An application host or a framework calls some code in an application, not the repository's own code: a controller, a message handler, a hosted service, an entry point. Neither walk can follow such code to a test by name, so reaching it selects every test project that depends on the application, whole, because an integration test reaches it through HTTP, a mediator or the host. Changed top-level statements and changed Razor files (`.razor`, `.cshtml`) select every test project that depends on their project the same way.
5. **Filter.** Each selection becomes a VSTest filter, `FullyQualifiedName~` per test or class. A filter longer than 8,000 characters is collapsed to class prefixes, and then to no filter, so it can run more tests than selected but never fewer.

The summary counts tests from source, by test attribute (xUnit, NUnit, MSTest and TUnit), without running test discovery. A test project on Microsoft.Testing.Platform (opted in through `global.json`) runs whole and builds with MSBuild, because its filter syntax differs per test framework.

## Running tests without MSBuild

`dotnet test` on a project runs MSBuild to build it first. When the test project already has build output and only C# sources changed since, Fuse skips that step: it copies the test project's build output into the state directory, emits the changed assemblies (and the assemblies in the test project's closure that depend on them) from the warm compilations into that copy, and runs `dotnet test` on the copied test assembly. In the code this is a shadow run. The emitted assemblies carry the embedded resources of their last built assembly, because the compilation Roslyn loads does not include the resources MSBuild adds.

An assembly counts as changed when its project has a source file newer than the project's build output, or when the copy in the test project's build output is not that build output: missing, or different in length or write time. MSBuild keeps the write time when it copies an assembly into a test project's output, so the copy differs when the project was built on its own after the test project, as `dotnet build Lib` does when `Lib.Tests` references `Lib`. The emitted assembly then replaces that older copy.

A run without MSBuild needs every project the test assembly loads to have build output, no project file or import newer than that output, and no file other than a source file newer than it in the project directories, such as a resource or content file the emitted assembly would not carry. Freshness is judged by timestamps. When a condition fails, or a changed project does not compile, Fuse runs `dotnet test` on the project, which builds it with MSBuild and reports the build errors.

Runs without MSBuild write no build output, so they run in parallel, one process per target framework. Runs with MSBuild share `obj` and `bin` folders across projects, so they run one after another. A run without MSBuild that produces no results goes through MSBuild instead. Results are read from the TRX files `dotnet test` writes.

## Builds and the build lock

Every process that builds a repository writes the same `obj` and `bin` files. Two at once make one of them fail with MSB3021 or MSB3027 on a file the other holds open, or with CS2012 on an output both are writing. Several agents in one repository build at overlapping times, and each such collision fails a build that would have succeeded on its own.

`fuse build` and `fuse test` therefore take a per-repository lock for as long as they write build output: `fuse build` around its `dotnet build`, and `fuse test` from before it asks the engine for a plan until its last `dotnet test` process exits, because preparing the plan writes the copies for runs without MSBuild. The lock is the file `build.lock` in the state directory, opened exclusively, and the operating system releases it when the client that holds it exits or is killed. A client that finds it held retries every 200 ms for as long as it is held and says once on standard error that it is waiting. A client that cannot open the state directory runs without the lock and says why on standard error, so a build is never refused because of the lock.

The arguments `fuse build` passes to `dotnet build` are the caller's, unchanged, including the implicit restore, so a package reference added a moment earlier still resolves.

The engine takes no lock: it writes nothing into the working tree, a check does not build, and it loads the repository's analyzers from copies. A `dotnet build` that does not go through Fuse takes no lock either; the pre-shell hook rewrites an agent's `dotnet build` and `dotnet test` so that they do.

## Failure handling

When Fuse cannot answer, the answer carries one of seven codes and a message that names the fix: not a repository, no projects, loading, restore needed, load failed, timeout, internal. Commands print the message and exit with code 2, and the MCP server marks the result as an error. [Commands](commands.md#messages-and-fixes) lists every message.

A hook must never break the agent's session. It reports introduced errors and a missing restore, and nothing else: every other outcome exits 0 with no output, and an exception or a payload that is not valid JSON is written to `hook.log` in the state directory. A post-edit hook that a harness runs inline, which is every harness except Claude Code, does not wait for an engine that is still loading, so the stop hook reports the first edits after the engine starts.
