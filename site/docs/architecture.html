Architecture

All documentation pages

Fuse's code is organized into layers, and each layer is a set of namespaces. This page states which namespaces each namespace may use, the order you read them in, the types each feature is built from, and the words those types are named with.

This page is for contributors and coding agents changing Fuse. Read it before adding a namespace, a type that other namespaces use, a step to the check or test pipeline, or a word to the output.

Read first How it works, which describes what Fuse does. This page describes where that behavior lives and what it is called.

In short

  • Fuse is one project whose namespaces are its layers, and dependencies point down with no cycles.
  • Each feature declares its concepts as model types first, and features never know the wire.
  • The client runs short-lived commands while the engine alone loads MSBuild and Roslyn.
  • Vocabulary is the authority for names, and two tests hold the code to this page.

Fuse is one project, src/Fuse, and its namespaces are its layers. Two tests hold the code to this page: tests/Fuse.Tests/Architecture/NamespaceDependencyTests.cs for the layers and PathComparisonTests.cs for how paths compare. When your change contradicts a rule on this page, change the page, the tests and the code together, and record a decision in Decisions.

Principles #

  1. Abstractions come first in reading order. Each feature declares its concepts as small model types (records and their variants) before any class that computes them. You learn what a check is from its model, and how the code computes it from its steps.
  2. Dependencies point down. A namespace uses only the layers below it. No cycle exists between namespaces. When one appears, a test fails the build.
  3. One responsibility per type. A class holds one step, one rule or one piece of state. A class that needs several paragraphs to describe is several classes.
  4. Each abstraction takes the form that states it most directly. A model record, a variant hierarchy, a class per step, an abstract class and an interface are all abstractions. Add an interface for a seam or a contract even when it will have one implementation. The one role Fuse implements several times is the harness (Harnesses).
  5. Variants replace nulls that change control flow. When code branches on whether a value is null, that value holds 2 concepts, so give each a named case. A null that is only printed, such as an optional message on a wire record, can stay.
  6. Features do not know the wire. Check and Testing return domain results. The engine maps them to Protocol records in one place.
  7. One word per concept. Vocabulary is the authority for names, and Naming rules decide the next one.

A stage folder is not a layer: the stages of one layer may use each other, and cycles are compared between rows. The row Fuse holds only the namespace Fuse itself.

Three of these rules matter most:

  1. Features never use Fuse.Engine, Fuse.Protocol or anything above them. A check is testable without a pipe, and the wire can change without touching the algorithm.
  2. No client namespace uses Microsoft.CodeAnalysis or Microsoft.Build, directly or through a Fuse namespace that uses them. The client-side namespaces are Fuse.Cli, Fuse.Hooks, Fuse.Mcp, Fuse.Harnesses, Fuse.Operations, Fuse.Client, Fuse.Protocol, Fuse.Check.Model, Fuse.Repo, Fuse.Dotnet and Foundation. The engine-side namespaces are Fuse.Graph, Fuse.Workspace, Fuse.Changes, the features and Fuse.Engine. A hook pays for every assembly it loads, and the runtime loads one as soon as a method that uses it runs, so a single client call into an engine namespace would load Roslyn into every hook. The test follows every namespace a client namespace uses, directly or through others, and fails when that reaches Roslyn, MSBuild or an engine-side namespace.
  3. Program is the only type that references both the client and the engine, because it tells fuse engine apart from the client commands.

tests/Fuse.Tests/Architecture/NamespaceDependencyTests.cs enforces the table and rule 2. It reads every .cs file under src/Fuse and takes the file's namespace from its namespace line. It then collects every Fuse.X, Microsoft.CodeAnalysis and Microsoft.Build name from the using directives and from fully qualified references.

A type a file names from an enclosing namespace without a using, such as a Fuse.Check type in Fuse.Check.Pipeline, counts too. The test also fails when it finds a cycle between namespaces. Each failure names the file, the namespace it used and the rule it broke.

When you add a namespace, the test fails until you give it a row. That row is where you decide its layer. Change the table on this page and the test together.

Reading order #

If you are new to the code, read in this order:

  1. How it works: what Fuse does and why.
  2. Fuse.Protocol: the questions the engine answers and the shape of each answer. It is small and is the product's contract.
  3. Fuse.Check.Model, then the steps in Fuse.Check in the order Check lists them.
  4. Fuse.Testing.Model, then the steps in Fuse.Testing.
  5. Fuse.Changes.Model, then Fuse.Changes, Fuse.Workspace and the Sources layer, when a change needs them.
  6. Fuse.Engine, Fuse.Client, Fuse.Cli, Fuse.Operations and the surfaces, for how a request travels.

Model types sit in a Model folder and namespace inside their feature (src/Fuse/Check/Model, namespace Fuse.Check.Model; src/Fuse/Judge/Model, namespace Fuse.Judge.Model). A model type uses only other model types of its feature, Fuse.Changes model types and Foundation, so you can understand the folder without opening anything else. Every other folder under a feature is a stage of its pipeline: it belongs to the feature's row, never to a row of its own.

RepoPath is a readonly struct that holds the root, the absolute path and its hash, which it computes once. It compares the way the file system does (ignoring case on Windows, ordinally elsewhere), so every set and dictionary of paths takes no comparer. Relative gives the repository-relative path with forward slashes, FileName gives the last segment, IsUnder tells whether the path lies in a directory, and Matches tells whether a path Roslyn or MSBuild reports is the same spelling, which needs no canonicalization.

You make one only through RepoRoot.PathOf. It takes a path, absolute or relative to the root, and canonicalizes any spelling that is not under the root's own spelling (a junction, a symlink, a subst drive), so each file has one value. A path outside the root, such as a project in a sibling folder, is a value too; its relative form starts with ../. The wire, command-line arguments and the Roslyn and MSBuild APIs keep strings. RequestRouter turns the files a request names into values, and answers an empty or invalid one with ErrorCode.InvalidPath. ResponseMapper writes them back as absolute strings.

tests/Fuse.Tests/Architecture/PathComparisonTests.cs fails when a string comparison chosen by the operating system appears outside RepoPath, when code outside Fuse.Paths uses RepoPath.Comparison, or when Fuse.Protocol names RepoPath.

Changes #

Fuse.Changes answers one question for both features: which declarations differ between a file at HEAD and the same file on disk, decided from syntax. The features ask that question in 2 forms: whether a file's visible declarations changed (Check), and whether any declaration's code changed (Testing). Each form is one function. Both functions read a file the same way, into the same declarations under the same key.

Model (Fuse.Changes.Model) #

It uses only Foundation and no Roslyn, so a feature's model may use it.

TypeCases or fields
DeclarationKeyUsing(directive), GlobalUsing(directive), AssemblyAttribute(attributes), TopLevelStatements, NamedType(name) for a type or delegate, Member(NamedType container, signature)
DeclarationChangeAdded(after), Removed(before), Changed(before, after), each with its key and the names other code reaches it by; the texts are the header as written
FileChangesthe declaration changes of one file, and HasBroadChange

A key is read from syntax alone. A member's signature holds its kind, name, explicit interface, arity and parameter types with their modifiers, checked for a checked operator, and a conversion's target type. Overloads, a static constructor, an explicit implementation, a checked operator and 2 conversions to one type therefore each have their own key.

An extension block has no name, so its key is its receiver's type. A field has one key per variable.

When a file declares one key more than once (the parts of a partial type or member, or 2 extension blocks for the same receiver), the parts form one declaration. Its surface holds every part's surface, so a change to any part is a change to the declaration. CodeDiff compares the parts one by one.

Steps (Fuse.Changes) #

  1. FileDeclarations reads one version of a file into its declarations. Each declaration is a DeclarationNode with its key, its syntax node, its surface (what other files can observe, with bodies and trivia removed; none for a finalizer or top-level statements), the names other code reaches it by, and its containing type. It is the one walk of namespaces, types and members that both functions use.
  2. DeclarationHeader is a declaration's header as written, on one line. DeclarationChange carries it, and a cause quotes it.
  3. SurfaceDiff answers Check's question. It compares the surfaces of 2 FileDeclarations and returns FileChanges, which is broad when a type header, a delegate, a global using or a file-level attribute list changed.
  4. CodeDiff answers Testing's question. It compares the code of the same declarations: a type by its header (its surface), and anything else by its whole syntax. It returns the nodes the test walks start from: each added or changed declaration; the type of each removed member; the compilation unit when top-level statements change; and every type, and the compilation unit of a file with top-level statements, when the file's usings (at file level or inside a namespace) or file-level attributes change.

Steps (Fuse.Check) #

  1. TargetResolver turns a CheckScope into the source files that have an owning project. ScopeExpansion expands a scoped check's directories, files and glob patterns against the files that differ from HEAD, and keeps the C# sources a project owns. A spec that matches nothing is refused instead of answering clean. For a check of every change sent with SessionCheckMode.Stop, it excludes the files only other sessions wrote, so the stop checks only its own files and what they reach.
  2. IntroducedErrors binds files or whole projects in both views, and keeps the errors that have no match at HEAD. It uses DiagnosticCollector, AnalyzerSelector and ErrorDelta, and matches a file renamed since HEAD with its old name.
    • AnalyzerSelector also makes each project's AnalyzerPlan, which names its compilation-wide analyzers, shared by concurrent callers under no one caller's token. DiagnosticCollector runs those once per compilation through CompilationAnalyses. Each run outlives the check that started it. A run is reference-counted by the pins that wait on it: a newer compilation or StopAll stops it only when no pinned check waits on it, and takes the pending stop when the last pin goes. Its newest wrapper per project is held weakly, so it does not root its compilation after both views move on.
    • Each check's AnalyzerRun and the rest of its per-check state (its reuse mode, timings, unfinished and left-out counts) live on its own CheckContext, so concurrent checks never overwrite each other's. The run says whether analyzers run and when they must stop, on the working tree and the baseline alike. When a file's baseline analyzers did not finish, the check leaves its working-tree analyzer errors out.
    • DiagnosticCollector keeps each working-tree file's compiler and per-file analyzer errors under a key of its text's checksum, its project's dependent semantic version and the configuration generation, in concurrent dictionaries. It reuses them while the key holds. Its baseline results are keyed by baseline generation and path or project, and a newer baseline generation drops only older keys.
    • BaselineStore keeps HEAD's finished baseline results on disk under the shared directory keyed by the git common directory, keyed by commit, Roslyn build, project inputs, restore output with worktree paths masked in names and values, analyzer assemblies and config files, so worktrees on the same commit compute HEAD's errors once and the first check after an engine restart reads them instead of binding HEAD again. Writes take a per-key lock. It also supplies each project's HEAD summary through the workspace's SummaryCache. A check reads HEAD from the store first, builds a HEAD compilation only for a store miss or for the files reach must search, and releases what it built when the check ends. Past 500 candidates, whole-project binding streams one document at a time and drops each model.
  3. SpanChecker answers a post-edit hook's check from the edited member spans alone. When a .cs file holds only method or accessor body edits, it binds only those spans and runs the per-file analyzers on them, skipping whole-file binding; any declaration, using, directive, syntax or non-body change, or a check that runs compilation-wide analyzers, falls back to full-file binding. Checker tries it first when the request sets InteractiveFast, which only the post-edit hook does.
  4. ChangeReach turns the declaration changes of the targets, as SurfaceDiff finds them, into a Reach.
  5. CandidateBinding binds the reached files, or whole projects past 500 candidates.
  6. SessionAttribution leaves out, for a check answered to a session, the errors that other sessions' edits caused without it. DeclarationFilter runs first: it decides an error only when exactly one bound or candidate symbol traces to a changed declaration in a file exactly one session wrote, and declines analyzer errors, conversions, overloads, inference, constructors, operators, extension methods, added or removed declarations, usings, broad changes and files several sessions wrote. The rest are decided by looking the files with errors up in the session's view, kept by the writer in SessionViews, which SolutionViews holds (the tree view with the files only other live sessions wrote at HEAD, bounded at 8, least recently used first out; a shed or evicted session derives its view again through RepoWorkspace.CurrentWithHeadContentAsync and gets the same answer). No session is settled by its stop (D15): only a stopped subagent's edits count as its parent's.
    • It reads SessionEdits, the record of which sessions wrote each changed file, which RequestRouter fills from CheckFiles.Session and keeps in sessions.tsv in the state directory.
    • An external writer a launcher registered with fuse session begin is a RegisteredSession, kept in registered-sessions.tsv with a trailing pid:<id> field a line without it reads past. Files under its path patterns count as that session's until the registration ends, 4 hours pass, or the process it is tied to exits, checked each time the registrations are read. A session a caller names in FUSE_SESSION needs no registration: the client passes it on CheckChanges, CheckFiles, CheckPaths and the test plan, and a check that names files credits them to it. fuse build passes none.
    • A stop hook's CheckChanges with Mode SessionCheckMode.Stop marks its session stopped there, and SessionEdits.IsOwnEdit counts a stopped subagent's edits as its parent's.
    • For a test plan for a session, RequestRouter passes the files only other sessions wrote in TestScope.Affected.LeftOut, because Fuse.Testing may not use Fuse.Check.
  7. CauseLines attaches causes to errors in candidate files: each error gets the cause whose declared name its message quotes, and CausedBy from the one session that wrote the file that cause's declaration sits in, with the registered: prefix taken off. Every candidate error carries its cause. The client prints at most 10 cause lines and counts the rest itself, and writes CausedBy only in --json.
  8. For each reported error, GeneratedSource names the generated file (one in a bin or obj folder of its project) that declares the symbols bound at the error, or the type whose member is accessed there.
  9. RepairPackets attaches a RepairPacket to each reported error when the request sets IncludeRepairBrief (fuse check --brief), with MemberCandidateLookup, UsingSuggestionLookup and InterfaceStubGenerator building the candidates, usings and stubs. Every error gets the source window; candidates, usings and stubs are built only for missing members (CS1061, CS0117), overloads (CS1503, CS7036, CS1501, CS1729), missing types (CS0246) and unimplemented interface members (CS0535), at most 5 each.
  10. Checker answers one check request and is safe to call concurrently: each attempt creates its own CheckContext, begins from a writer sync pin and reads only that generation. It loads the owners of the targets and later the dependents of the projects with declaration changes through pin-returning writer calls, runs steps 1 to 9 in order, records each as a Phase, and returns a CheckResult. Coverage recovery asks the writer to load the missing projects and restarts on the newer generation at most twice. After the sync it first answers from KeptCheck when an earlier check of the same scope, session and analyzer run was keyed by the same changed files' contents, HEAD, configuration and baseline generations and session record. An answer whose analyzers did not finish is never kept. ClearKeptAnswers drops every kept answer for the memory shed order. ChangeReach keeps its reference sets in a concurrent dictionary keyed by baseline generation, symbol and searched projects, capped at 128 with least-recently-used eviction.

Steps (Fuse.Testing) #

These steps follow How it works. The steps live in stage folders by what they do: Selection selects the tests (TestSelector, SelectionBuilder, TypeGraph, TypeWalk, MemberWalk, BodyEquivalence, HostRule, NamedTestProjects, TestAttributes, ProjectFiles/ (PackageVersionChanges, ProjectFileChanges, ProjectFileSelection), WalkOutcome), Filtering turns selections into runner arguments (TestFilter, PlatformFilter, TestCounter), Shadow prepares shadow runs (ShadowEmitter, ShadowCopyAllocator, ShadowSafetyInspector, ShadowEmitCaches, EmitCache), Caching reuses earlier verdicts (SliceTestCache, DynamicTestMap, CoverageMapStore), and Planning turns selections into a plan (TestPlanner, PendingTestPlan).

  1. TypeGraph records which types name which, built from syntax with each file's facts cached by text version in a concurrent dictionary, and its reverse closure. TypeWalk drops facts for document ids no reached project holds before it builds the graph, so a replaced document's facts do not stay.
  2. TypeWalk gives the class-level answer. It walks TypeGraph back from the types that declare a changed declaration and selects each test class it reaches. A reached test file without classes selects its project whole, and a reached application applies HostRule.
  3. MemberWalk gives the member-level refinement within its budget of 300 symbols and 8 seconds, ending in a WalkOutcome. It also seeds both walks. It finds each changed file's changed declarations with CodeDiff, seeds nothing for one that compiles to the same code as HEAD (see BodyEquivalence), selects the ones in test projects at once, and selects the test projects behind an application whole when its top-level statements change.
  4. BodyEquivalence decides whether a changed declaration compiles to the same code as HEAD's. A declaration qualifies when its header reads the same without bodies, and its bodies read the same after every local, parameter and range variable name is replaced with the order it is first seen in and every local type with the type it names. A local rename and var against the explicit type therefore qualify. Anything else, and anything undecidable, counts as changed.
  5. HostRule says that application code reached through an application host selects every test project that depends on the application. It decides which members an application host or a framework calls (IsEntryPoint, IsFrameworkInvoked, IsCalledByHost) and which test projects that selects (DependentTestProjects).
  6. TestSelector chooses between the walks and merges their selections into a SelectionResult. The class-level answer is the projects the seeds selected whole, overlaid by the type walk, whose whole selections replace the seeds' reasons. The member walk's answer replaces it only when at most 100 test classes are reachable and the walk finishes. In that case a project the seeds selected whole keeps the class-level answer's reason, so the summary does not depend on which answer was returned. SelectionBuilder holds one walk's selections while it runs.
  7. TestFilter builds the VSTest filter for a TestSelection as a RunFilter, and collapses it when the selection has more than 2,000 patterns, to class prefixes and then to no filter (FilterCollapse). The client writes it into a runsettings file with Dotnet.RunSettingsFile. PlatformFilter builds a Microsoft.Testing.Platform run's arguments for xUnit v3 and TUnit, bounded at 200 names the same way. MSTest and NUnit take the VSTest filter there. Graph.TestFramework tells which framework a project uses, from its packages.
  8. ShadowEmitter prepares a shadow run and returns RunMode.Shadow, or returns RunMode.Build when a shadow run is not safe.
    • Each plan prepares with its own emitter over shared concurrent caches. EmitCache keeps each emitted image (EmittedImage) per build output path, and reuses it while the project's dependent version and the write time of its build output stay the same. The emitter does not copy build output over a shadow file it is about to emit, or write an image that is already in place.
    • Each test project has numbered copies (g1, g2 and so on). The emitter prepares the newest one no test run holds (LocalState.HoldTestCopy, LocalState.IsInUse), starts a new one otherwise, and deletes the older ones no run holds.
    • A dependent is emitted again only when a project it depends on changed its declarations. Otherwise the shadow folder keeps its image.
  9. TestPlanner turns the selections into a TestPlanResult in 2 parts. TestCounter counts tests from source for the summary.
    • SelectAsync syncs through SyncAndPinAsync and reads only the pinned generation, records the sync and selection phases, and returns a PendingTestPlan that holds that generation and the plan's own ShadowEmitter. It holds no request lock, because there is none.
    • PrepareAsync prepares the shadow runs from that generation with the plan's own emitter over shared concurrent caches (EmitCache capped at 32 images, the emitter's written and fingerprint maps capped too, TypeWalk facts and TestCounter counts in concurrent dictionaries), so plans for different sessions prepare at the same time. A plan holds the shadow copy it writes until its preparation ends. It records the mirror and emit phases.
    • Paths a command named limit the plan through NamedTestProjects, and a named configuration or framework leaves every run to MSBuild.
    • When no container runtime answers, the plan leaves out the test projects that need one, and names them.
    • A rerun selects the recorded failures still in their projects and names the projects that are gone.

Two types hold state between test runs. SliceTestCache stores each test project's verdict after a test run that finishes with complete results, under the slice's content-addressed key in the shared state directory. An identical later plan reuses a stored passing verdict without starting a process, and runs a stored failure again. When an input cannot be read nothing is cached. fuse test --no-cache neither reads nor writes the cache, and fuse test --clean clears it. DynamicTestMap persists per-method, per-type and per-file coverage mappings from recorded runs; a selection adds the tests those mappings name and never drops a test the static selection found.

Workspace and sources #

Fuse.Repo finds which files differ from HEAD, and Fuse.Workspace keeps the current and baseline solutions in step with them. Every request starts with a sync. ChangeTracker folds what changed into concurrent sets and returns sorted snapshots and a SyncResult, and WorkspaceSync acts on it. RepoGraph evaluates each project once, or reads the stored graph GraphStore keeps under the shared directory, keyed by the project files and the Fuse build and validated against every evaluation input and auto-import, so a new engine evaluates nothing when the graph is kept. A graph with an evaluation failure is never stored. Each ProjectNode also holds its NonSources (the files MSBuild names for it: embedded resources, content, None with copy to output, additional files) and its BuildOnlyReferences (references with ReferenceOutputAssembly false). GitStatus.IgnoredPathsAsync asks git once per sync, with NUL-separated paths on standard input, which reported paths git ignores, so an ignored non-source is never counted.

Sources and the workspace hold stage folders the same way features do. Fuse.Repo splits into Git (reading HEAD and the working tree: HeadResolver, GitHead, GitStatus, GitBlobReader, HeadComparison) and Tracking (folding changes: ChangeTracker, WatchedPaths, WatchedChanges, RepoProbe, SyncResult, TreeStamp). Fuse.Workspace splits into Generations (Generation, RepoWorkspace, WorkspaceSync, WorktreeOverlay), Views (SolutionViews, ViewDocumentPatcher, ViewSummaryApplicator, TransientBaseline, SessionViews, SummaryCache, AnalyzerShadow), Blueprints (ProjectLoader, CompilationBlueprint, Projects/ with the split project records, BlueprintEvaluator, BlueprintWorkspace, BlueprintResourceCache, LoadedWorkspaceState, LoadFailure, BlueprintFiles, AssetsStamp, RestoreCheck) and Indexing (SyntaxTokenIndex, SyntaxDocumentScanner, TokenIndexStore). Fuse.Dotnet splits into Processes (child processes through IProcessRunner), Build (build output parsing) and Test (test output and summaries such as TestRunSummary).

Change tracking (Fuse.Repo) #

  1. HeadResolver resolves the commit HEAD points at and whether git can read it. GitHead reads the ref files, loose or packed, without starting git. Git answers when they do not (reftable refs, unusual layouts). The resolver checks a new HEAD with git cat-file, so a broken commit cannot pass as clean. HeadResolver.GitFailure words the failure when git cannot read the repository, and GitStatus reports that failure too.
  2. GitStatus produces the seed. It reads the NUL-separated records of git status --porcelain=v1 -z and takes each path exactly as git wrote it, since a name may begin or end with a space, hold a quote or not be ASCII.
  3. WatchedPaths is the file watcher and what it recorded since the last sync. Drain hands that over as WatchedChanges: the sources, the directories that are gone, the project files that changed and the watcher's errors. It also decides which paths are ignored (git's own directory, and bin, obj, .git and node_modules folders).
  4. HeadComparison decides whether a file on disk differs from HEAD. It skips every carriage return on both sides, so a checkout that converts line endings is no change, and a file on one side only always is.
  5. ChangeTracker composes them. It holds HEAD and the set of changed sources, and reads a file at HEAD through GitBlobReader. After HEAD moves, after a watcher error, or when more than 300 sources changed (MaxPatchedPaths), it seeds the set again from GitStatus, because the recorded events are not the whole change. Otherwise it compares each reported path with HEAD.

SyncResult has one case per response, and ChangeTracker chooses them in this order:

The engine log names the case and the trigger, as in reloading: Reevaluate trigger=HEAD moved to <commit> and reloading: Reload trigger=<count> changed files.

TreeStamp is the tree stamp: a short hash of what the changed files hold. A summary uses it to name the tree its command saw. The engine stamps a check from its tracker, and a build stamps from git. Both hash the same way, so the same tree stamps the same.

Workspace (Fuse.Workspace) #

  1. ProjectLoader evaluates every project into the RepoGraph and opens the ones requests need from a CompilationBlueprint in an AdhocWorkspace, falling back to direct MSBuild loading only for exotic projects. It refuses a project that is not restored (RestoreNeeded, naming the dotnet restore to run) or that did not load (LoadFailed, with LoadFailure telling a real failure from a restore warning). It increments ConfigurationGeneration whenever it closes every project. A background load (PreloadAsync) opens a project outside a request. Neither view holds it until the next request derives them again.
  2. Generation is one published, immutable state: its number, HEAD, the current and baseline solutions, the graph, the sorted changed and non-source snapshots, and the configuration and baseline generations. A request pins the newest generation and reads only it. RepoWorkspace is the single writer: sync, ensure-loaded, patch and rebuild each hold the writer lock for the whole round and publish a generation only when a held value changed. Background preload uses only the loader lock and is folded in by the next writer round.
  3. SolutionViews holds the current and baseline solutions, both derived from the loader's solution with the repository's own analyzers loaded from a copy (AnalyzerShadow, under the shared directory, pruned past 7 days), and BaselineGeneration, which changes only when the baseline's content does. It supplies each reference to a project outside the change cone (the owners of changed files plus their transitive dependents) from that project's summary in both views, and holds the session views: at most 8, keyed by the set of files they hold at HEAD, in least-recently-used order. A patch applies a file's disk content to every kept view that does not hold that file at HEAD, preserving document ids, and takes the view's references from the patched tree view. Its shed calls are ClearSessionViews, ClearHeadCompilations and ClearIdleConeProjects, wired through RepoWorkspace under the writer lock.
  4. SummaryCache emits an image of a project's HEAD compilation, private members included and generated documents with it, never from obj/ref, validates it by reading it back as metadata, and keeps it as a .dll under the shared directory's summaries folder, keyed by HEAD, the Roslyn build and the project's inputs. Any doubt returns null, so the caller binds source. RepoWorkspace.UseSummaries (default true) is the differential proof's switch, read by no surface.
    • It applies a file's disk content to the current solution and its HEAD content to the baseline, adding or removing documents as needed. It remembers every path it applied, so that a rebuild from the loader applies them again.
    • It also remembers the loader solution it last finished deriving both views from, so HoldEveryOpenProject says whether the loader has opened a project since.
    • Its RefreshGeneratedAsync, which WorkspaceSync calls on every sync, reads each generated file (a document in a bin or obj folder of its project) again when its length or write time changed, and applies it to both views.
  5. WorkspaceSync acts on each SyncResult, and folds the projects the loader opens into both views (EnsureLoadedAsync).
    • It keeps a result it did not finish acting on, such as a re-evaluation after HEAD moved that was cancelled or failed. The next sync acts on it, followed by its own result (SyncResult.Then, where the case that does more wins), because the tracker has already taken the new HEAD and does not report the move again.
    • A rebuild at a HEAD other than the one the baseline was read at increments BaselineGeneration.
    • It rebuilds both views whenever HoldEveryOpenProject is false, which covers a request's own load, a background load, and a load that a cancelled or failed request cut short after some projects opened, all in one rebuild.
  6. RepoWorkspace is the entry point the features use. It composes the tracker and the 3 classes above, and adds no rule of its own.

These types support the one engine a repository shares across its git worktrees. WorktreeOverlay is one worktree's pair of solutions, its changed-file deltas against HEAD and its own generation pin, mounted under that engine and sharing its immutable HEAD base. SyntaxTokenIndex is a persistent syntax-only inverted index from identifier tokens and declared base types to documents, keyed by path and preprocessor configuration, so a reference search narrows to candidate documents without loading a semantic model. The blueprint types, CompilationBlueprint, BlueprintEvaluator and BlueprintWorkspace, hold the compiler inputs MSBuild evaluated for each project, extract them once into serializable form, and load projects from them into a lean AdhocWorkspace, so the engine keeps no resident MSBuild workspace and an unrestored worktree maps its sources onto a restored worktree's blueprint.

SDK capabilities (Fuse.Dotnet) #

SdkCapabilities probes dotnet --version once per repository and names what the active SDK can do: multithreaded MSBuild (-mt), --maximum-failed-tests, and --collect-test-map with --affected-tests, each on .NET 11 and later. The answer is cached per repository root and read again when global.json changes; when the probe fails the capabilities read as unknown and every flag reads as unsupported.

Harnesses #

A harness is an agent host that runs Fuse's hooks: Claude Code, Cursor, Gemini CLI, Codex, GitHub Copilot CLI, OpenCode and Muse Code. Fuse.Harnesses holds a Harness base class with 7 implementations: ClaudeCode, Cursor, GeminiCli, Codex, CopilotCli, OpenCode and MuseCode. To add a harness, add one class and list it in SupportedHarnesses. The namespace holds stage folders: Adapters with the 7 harness types and the embedded plugin, and Setup with init, uninit, settings and instructions. Each implementation owns everything about its harness:

  • its Name on the command line (claude, cursor, gemini, codex, copilot, opencode, muse). Every registration already written into users' settings contains that name, so it never changes.
  • how to detect it in a repository (IsUsedIn, from its settings directory or instructions file), and where and how its hooks are registered (RegisterHooks). That includes the permission allowances Claude Code gets for fuse build and fuse test, the OpenCode plugin (Harnesses/Adapters/opencode-plugin.js, which the tool embeds), and the Muse Code plugin bundle with what the user runs once after fuse init so the harness loads it (NextStep).
  • how it answers a pre-shell, post-edit and stop event: ReplaceShellCommand, ReportAfterEdit, and AllowStop or BlockStop, each returning a HookAnswer with the standard output, standard error and exit code the harness reads;
  • whether it runs the post-edit hook in the background (RunsPostEditInBackground), and whether Cursor also runs the hooks in its settings (IsAlsoRunByCursor). Both are true for Claude Code only.
  • whether its answer to a pre-shell event approves the command (ApprovesRewrittenCommand, true for Cursor, GitHub Copilot CLI, Codex and Muse Code), and which of its tools write files (WritesFiles), for a harness such as Muse Code whose post-edit hook runs after every tool.

The base class holds only that contract and the helpers the 7 share. Those are the hook command for an event, detection from paths in the repository, and replacing Fuse's handler in the nested hook format Claude Code, Gemini CLI and Codex use. Each harness's hook configuration keeps the harness's own event and tool names (Claude Code's PreToolUse with a Bash matcher, Gemini CLI's BeforeTool). Only the command it runs names Fuse's event.

HookEvent names the 3 events once, for the commands RegisterHooks writes and the events fuse hook accepts. SupportedHarnesses lists the harnesses in the order fuse init registers them, and finds one by its name on the command line, for fuse hook and its usage line. SettingsFile reads and writes the files fuse init writes. It replaces a file through a temporary file beside it, and tries that move up to 5 times, 50 ms apart, while it fails with IOException or UnauthorizedAccessException. That is how Windows reports a file a virus scanner or the search indexer is holding.

InitCommand registers every harness it detects, or Claude Code when it detects neither a harness nor VS Code, plus the VS Code MCP server in .vscode/mcp.json, which is not a harness because VS Code runs no hooks. It also has GitIgnore add the reserved .fuse folder to .gitignore. HookCommand in Fuse.Hooks reads the event and the payload (HookPayload), does the work that is the same for every harness (rewriting the command with CommandRewriter, running the check), and asks the harness for the answer. An unknown harness or event, pre-bash included (D12), gets the usage line on standard error and exit code 0. BlockedStops holds each session's last blocked answer and its writes since, so a repeat block on unchanged errors lets the stop through; StopMessage builds the blocked text with its delta line first and its registration guidance last; SessionRoots records the roots a session's post-edit hooks touched, so its stop checks each one. Every block logs its summary line to hook.log.

Engine and client #

Fuse.Client holds EngineClient, which finds, starts and calls the engine through IEngineTransport, EngineLauncher, which starts it detached from the caller, and EngineStopper, which stops it. EngineVersion is in Fuse.Protocol, because the build id it defines is part of every request.

The build id is the product version and the module id of fuse.dll. The native client is compiled separately from the same sources and has a module id of its own, so it reads the module id of the fuse.dll installed with it (EngineVersion.ManagedDirectory) instead. The engine it starts from that fuse.dll reports the same id (D14).

EngineVersion.IsNativeClient is RuntimeFeature.IsDynamicCodeSupported negated. Program reads that feature switch directly for fuse engine, because the native compiler treats it as a constant only there, and so leaves the engine, Roslyn and MSBuild out of the native client.

The engine process is EngineServer, the pipe server, and the classes behind it, in stage folders: Server (the server and shared state), Routing (one route per request family), Scheduling (admission and memory), and Background (stored answers and warming):

  • RequestRouter handles initialization and routes each request to its route through the Scheduler: CheckRoute for checks, TestPlanRoute for test plans, SessionRoute for sessions and guards, and InspectionRoute for status, judge, graph and impact, with FeatureReports mapping the judge, graph and impact answers to Protocol records beside ResponseMapper for check and test plans. Checks and plans take a reader lease in their lane; status, ping and session registrations bypass the scheduler (status syncs under the workspace writer and reads the newest generation, a registration goes through SessionEdits under its own lock). It answers from the AnswerStore by content key before the scheduler and keeps each answer after it, coalesces identical checks through the scheduler, and at a memory boundary sheds in the budget's order and answers Busy past the ceiling. A changed-build plan pins a generation and never loads a project.
  • Scheduler admits requests to a bounded reader pool, as many as the machine has cores minus one for the writer, in lanes (SchedulerLane: Interactive, then Command, then Background, arrival order inside a lane; an inline post-edit check and a stopping check are Interactive). A request's wait and analyzer budget start when a reader takes it. Admission refuses at once with SchedulerBusyException (queue position and estimated wait from the lane's recent median) when a request will not start before its wait ends. Identical checks in flight share one reference-counted computation, and background work runs on a token a newer generation cancels.
  • AnswerStore keeps check answers by content key (32, least recently used first out; an answer whose analyzers did not finish is kept for nothing), serves them by key and by session, and writes each session answer as sessions/<name>.json. BackgroundCheck re-checks each live session's fresh files after a generation, debounced by 500 ms at the Background lane, and is cancelled by a newer generation and by a Background shed. WatchOperation in Operations streams the session files.
  • MemoryBudget reads the engine's own working set at request boundaries against a decided 2 GB ceiling and sheds in a fixed order (Background, KeptAnswersAndCaches, SessionViews, HeadCompilations, IdleConeProjects); machine load at 90 percent sheds background work, kept answers and caches, and session views, at 92 percent HEAD compilations, and at 95 percent idle cone projects. Each reading is an Assessment. Past the ceiling the answer is Busy, never a narrowed check. Engines record their working set in engine-memory.txt; IdleClock holds the 30-minute idle, the 5-minute shortened idle and the release time, and the idlest engine exits first when the machine runs short. EngineClient retries a Busy answer within the caller's wait and answers Unanswered with ErrorCode.Busy past it, so a hook, which reports only ProblemsFound and RestoreNeeded, stays silent.
  • RequestGate is the gate the first evaluation and the background load hold while they choose work. No request serializes on it. It admits one holder at a time, with priority waiters in arrival order before normal ones, and tells each waiter what held it longest: Preload or Initialization. Priority among requests is the scheduler's lane order, not this gate.
  • Preloader loads dependents in the background, one load at a time from one pinned generation, and tracks the projects that failed to preload. It tries each one again once the projects reload or a restore writes a project.assets.json in its closure. It builds no compilation: a check builds what it binds.
  • After HEAD moves, BaselineWarmer fills the baseline disk store in the background, one project at a time between requests, reading the baseline and graph from pins and holding no baseline compilation. The first check that needs HEAD then reads the store instead of binding it.
  • ChangedBuildPlanner builds the plan behind fuse build --changed in Fuse.Inspection: the projects that own the files changed since HEAD and their dependents, reduced to the highest projects, or the whole solution with the reason when the selection cannot be trusted.
  • RequestLog writes the log line and the phase line per request. Both name the request by its case, which the phase line writes as its kind. The phase line records the queue time as its gate phase apart from the total from dequeue. It also logs every Unanswered and Busy answer, and a cancelled request as Timeout, with the request kind, the code name (a Busy with its position and estimate) and the session.
  • ResponseMapper maps CheckResult and TestPlanResult to Protocol records, including CausedBy on each error, and FuseException to an unanswered response.
  • EngineServer drains on a build mismatch instead of exiting at once: it answers Restart, stops accepting connections, lets queued and running requests finish within a 10-second grace, then exits, and logs the mismatched build and the client process. A ShutDown stays immediate. Its idle watch records the engine for the machine budget every 15 seconds. On cleanup it prunes the baseline store in the shared directory, the summaries and the stored graphs.
  • CandidateJudge scores candidate unified diffs for fuse judge in Fuse.Judge: it applies each to a fork of the current solution in memory, checks the fork for introduced errors with ForkChecker, and either ranks the candidates (--race) or applies them together and reports overlaps (--combine), answering a JudgeVerdict from Fuse.Judge.Model.
  • UnifiedDiff parses git-style unified diffs and applies them to file text as PatchResult values (Applied or Conflicted) without writing disk, so the judge can fork a solution from the patched texts.
  • SurfaceGuardStore holds the frozen declaration patterns a fuse session guard --freeze registered, in guards.tsv in the state directory, and returns one guard_violation event per guard and changed declaration under one, which the router publishes after each check.
  • WatchHub holds the engine's live watch events and their subscribers. Each subscription reads the events published after it subscribed, for every session or one, and drops the oldest event when a reader falls behind.
  • GraphAnalysis builds the project graph, coupling clusters and test ownership that fuse graph returns, in Fuse.Inspection.
  • ChangeImpact builds the owning projects, candidate files and affected test projects that fuse impact returns, for the named paths or for every changed file, in Fuse.Inspection.

EngineRequest and EngineResponse are variants, which System.Text.Json source generation writes through [JsonPolymorphic] and [JsonDerivedType] with the case in a property written first. Every request carries BuildId and RequestId on the base record. A request line that leaves out an optional field reads it as its default (an empty build id or request id, an empty file list, not waiting for the load), because the source-generated reader would otherwise set it to null. RequestRouter releases its reader lease in a finally of its own around the request log.

Fuse.Protocol holds stage folders by what the records describe: Transport (EngineVersion, framing and line reading), Requests (the request cases with SessionCheckMode and WatchScope), and Check, Testing and Analysis (the report, plan and status records each answer carries).

Only a check can ask not to wait.

  • A status answer carries an EngineStatus: the engine's process id and working set, the changed file count, HEAD and the tree stamp, the changed sources a project owns, the touched count, the last reload's duration, what holds a reader, the memory ceiling and GC memory load, the tree-size limits (Limits) and the live sessions (Sessions of ReportedSession). A test plan carries the tests and projects left out for want of a container runtime. Each run names why it skips the shadow copy when it does (ShadowSkipReason).

The engine's failure word is the operation's: an Unanswered response becomes the Unanswered outcome.

The engine reads BuildId from the request line before the case (ProtocolJson.ReadBuildId), so a client of any other build gets Restart, whatever shape that build gives its requests. The case properties are named so that an engine of an earlier build can answer too. It reads kind into its own enum and drops a request whose value it does not know, so no request has a kind property. It writes Restart as {"status":"Restart"}, which this build reads as EngineResponse.Restart. Because a mismatched engine restarts, changing these records needs no compatibility code.

OperationResult carries an Outcome (Clean, ProblemsFound, Unanswered) and derives the exit code from it (0, 1, 2). MCP marks isError on Unanswered, and the hooks treat ProblemsFound as a reason to wake the agent.

Naming rules #

These decide a name the vocabulary does not list yet. Each exists because breaking it once made two things share a name.

  1. A word in the vocabulary is reserved. A second concept gets a different word, and the collision is added to the "Do not write" column. Without it, "failed" would mean both a test failure and Fuse not answering.
  2. One concept, one word. Review rejects a synonym, in code, docs and output alike. Without it, one concept collects several names, as the cause once had 4.
  3. Output uses only words marked yes. Compiler and implementation words (bind, shadow, surface, reach) stay in code and contributor docs. A reader of the output does not know what "bound" or "fast path" mean.
  4. No Fuse type shares a simple name with a BCL, Roslyn or MSBuild type. An alias to resolve a clash is the signal, as a Fuse Diagnostic next to Roslyn's would need.
  5. A domain type and the wire record it maps to never share a name. Features return *Result types (CheckResult, TestPlanResult); Protocol records are named for what the client receives (CheckReport, TestPlan).
  6. A boolean reads as a yes-or-no question: Is, Has, Uses, or a verb phrase such as WaitForLoad or FromAnalyzer.
  7. A request is a verb; a result is a noun; a variant case names the state. CheckFiles, PlanAffectedTests; CheckResult; AllChanges, Whole, Unanswered.
  8. A namespace is named for what it owns, which is also its layer on this page, not for one of its callers.
  9. A class is named for its one responsibility. A nested or private helper type gets a real name too (MemberWalk), never a placeholder such as Walk. Native, the .NET convention for P/Invoke declarations, is the exception.
  10. A number with a unit carries the unit in its name (TotalMs) or is a TimeSpan.

Decisions #

When a later change contradicts a decision, record a new decision here rather than editing the old one.

IdDecisionWhy
D1Foundation is 3 namespaces: Fuse.Paths, Fuse.Failures, Fuse.Telemetry.Naming rule 8. A single Fuse.Core would name nothing and collect unrelated types.
D2Each feature keeps its model types in a Model sub-namespace.It makes the reading order visible in the tree. The cost is one using per step file.
D3Fuse stays one project. Layering, including keeping Roslyn and MSBuild out of the client, is enforced by NamespaceDependencyTests.The test catches every edge a project split would, including the Roslyn ban, without extra projects, packing or internal-visibility wiring. Revisit only if the test is worked around.
D4The output says "introduced", as the code does.One word per concept in code and output. "fuse: 2 error(s) introduced in 2 file(s)" and "fuse: no errors introduced" read as plainly as "new" does.
D5The shell event is pre-shell. fuse init writes it, and fuse hook also accepts pre-bash. Replaced by D12."pre-bash" names one harness's tool. An unknown event gets a usage line on standard error and exit code 0, so dropping pre-bash would not break a session.
D6Fuse's error record is CompilerError, with FromAnalyzer.Analyzers run inside the compilation, and the docs call what they report compiler errors. Diagnostic would clash with Roslyn's type (naming rule 4).
D7HEAD is the only name for the comparison point, in code, output, MCP descriptions and docs.It is git's term, and "the last commit" is wrong on a detached HEAD or an older checkout (git glossary).
D8Every failure has an ErrorCode, including NotARepository, and each message is written once, in ErrorMessages when it does not depend on the request.The command line, fuse init and the MCP server each detect some failures on their own, and one wording keeps them saying the same thing.
D9Domain results and wire records are named apart (naming rule 5).ResponseMapper needs no aliases, and a reader always knows which side of the pipe a type is on.
D10An operation's outcome is an enum, Clean, ProblemsFound, Unanswered, and the exit code derives from it."Failed" is the word for a test, so Fuse not answering needs another.
D11CompilerError lives in Fuse.Check.Model, and Fuse.Protocol may use that one type.The wire carries it unchanged, and features may not use Fuse.Protocol, so it cannot live there. A second record with the same fields would only add a copy step. Fuse.Check.Model has no Roslyn or MSBuild reference, so a client that uses Fuse.Protocol still loads neither.
D12fuse hook accepts only pre-shell. This replaces D5's accepted pre-bash alias.Fuse carries no compatibility code for earlier builds, and one alias is one more thing to remove later. A user who does not rerun fuse init after updating loses the dotnet rewrite until they do, and the changelog says so.
D13The documentation lives in site/docs/ as static HTML pages that share site/assets/style.css with the home page. Only the files GitHub and the release workflow read stay Markdown: the README, CONTRIBUTING.md, SECURITY.md and CHANGELOG.md in the root, and CODE_OF_CONDUCT.md and SUPPORT.md in .github/. CHANGELOG.md is the list of changes the release workflow publishes; the changelog page explains each release with its upgrade steps.One copy of each page, on the site where readers find it, with diagrams, callouts and navigation that Markdown on GitHub cannot show. The pages need no build step, so the site deploys from main as it is.
D14The client ships as native code for win-x64, linux-x64, linux-arm64 and osx-arm64, and the engine always runs fuse.dll on the .NET runtime. One project builds both: a native publish also publishes fuse.dll beside the native client, and the build id is the module id of that fuse.dll on both sides. The Linux and macOS packages are native tool packages; the win-x64 package is framework-dependent with the native client as its packaged shim, because the SDK puts a native tool behind a .cmd file on Windows, which Git Bash cannot run. The musl RIDs and every other platform install fuse.dll.A check of an unchanged tree spends almost all its time in the client: on NodaTime it took 313 ms with the managed client and 37 ms with the native client on the same runner (evals/results/managed/latency-NodaTime-20261125-1507.json and evals/results/latency-NodaTime-20261125-1505.json), and every check gains about the same (Benchmarks). The engine cannot be native, because it loads MSBuild and analyzers at run time. Keeping one project keeps D3.
D15No session is settled by its stop. A stopped top-level session keeps its errors from every other session; only a stopped subagent's edits count as its parent's.A harness fires a top-level session's stop at the end of every turn while it keeps working, so settling on stop would hand every agent's half-written files to every other agent after one turn.
D16fuse build carries no session, and FUSE_SESSION is the one environment variable, for identity only.A build has no session-filtered answer to give, and a behavior that needs a setting is a behavior to decide: identity from the orchestrator is data, not a knob. The reader pool size, the session view count, the debounce and the memory ceiling are decided defaults for the same reason.
D17Checks pin generations and run on readers; the writer alone mutates, and projects outside the change cone are supplied from project summaries.One lock made callers wait while the engine's own work stayed small, and holding every project as source made memory follow the repository instead of the change. Summaries ship behind the differential proof that answers with and without them are identical.
D18Discovery honors an optional .fuseignore at the repository root with path patterns only, and skips .template.config trees and unrestored tokenized project files with no configuration. Fuse never writes the file.Exclusions are data about the tree, not behavior settings: a behavior that needs a setting is a behavior to decide. Template fixtures need no setup to stay out of discovery.
D19Foundation is 4 namespaces: Fuse.Identity joins Fuse.Paths, Fuse.Failures and Fuse.Telemetry from D1. Fuse.Identity, Fuse.Failures and Fuse.Telemetry use nothing in Fuse; Fuse.Paths may use Fuse.Identity.Session and value identities are used by every layer and depend on nothing in Fuse, so they sit below Fuse.Paths with their own row rather than inside it.
