Benchmarks

All documentation pages

On four open-source repositories, Fuse checked an edit 7.0x to 31.0x faster than dotnet build at the median, took 2.5x to 5.3x less time than the build over all 30 edits of each, and ran the affected tests 1.3x to 3.7x faster than dotnet test. It missed 1 compiler error in 120 generated cases (162 edits).

This page is for anyone deciding whether to rely on Fuse, and contributors comparing a change with the published numbers.

After reading it you know how fast and how accurate Fuse was, on what, how much the times spread, and where each number comes from. Evals explains how the numbers are produced and how to reproduce them.

The four repositories are FluentValidation, a validation library, the small one; NodaTime, a date and time library; Jellyfin, a media server; and the .NET Community Toolkit, a set of libraries with one source generator for each supported compiler version. The evals in evals/Fuse.Evals run the fuse executable the way an agent does, and compare every answer with a real dotnet build or dotnet test. Each job ran on its own GitHub Actions windows-latest runner, with 4 logical processors and 16 GB of memory, that ran nothing else (Evals). On Windows x64 the fuse command is the native client, so the evals measure it.

Speed and accuracy #

A warm check runs on an engine that is already running and has loaded the edited project. A body edit changes the inside of a method. A signature edit renames a method, so Fuse also checks the dependent projects that use it. P50 and P95 are explained under Reading the numbers.

The native client #

On Windows x64, Linux x64, Linux Arm64 and macOS Arm64 the fuse command is the native client, compiled ahead of time to native code, and elsewhere it runs fuse.dll on the .NET runtime (How it works). The same jobs ran the checks a second time with the managed client, on the same runner and the same engine code, so the difference between the two is the client alone. Every hook and command pays it.

Outside the engine, a body-edit check took 188 to 267 ms with the managed client and 28 to 45 ms with the native client (outsideEngine in bodyEditPhases): the managed client spends that time starting the .NET runtime and compiling its own code before it sends its request. A check of an unchanged tree is almost all client time, so it became 6.7x to 8.0x faster, and a check with more work in the engine gained about the same number of milliseconds. fuse test rounds are dominated by the test run and are not compared here.

The managed client's numbers come from the four files in evals/results/managed: latency-FluentValidation-20261002-1330.json, latency-NodaTime-20261002-1334.json, latency-Jellyfin-20261002-1341.json and latency-CommunityToolkit-20261002-1345.json, which record build 5.2.2/806c99444b87489186345535930bfb1c, the managed build of the same commit. The native client's numbers come from the latency files listed above.

Reading the numbers #

What the accuracy rows count #

  • Missed and contradicted. The correctness suite makes generated edits that change declarations, 162 edits over the 120 cases, runs fuse check on the edited files, and compares its errors with the errors a real dotnet build reports beyond the ones HEAD already has. An error the build reports and Fuse does not is missed. An error Fuse reports that the build does not have, and that the suite cannot account for, is contradicted.
  • Deferred and unverifiable. The build reports fewer errors than exist in two situations, and the suite counts Fuse's extra errors there apart. When a project has a declaration error, the compiler stops before it binds method bodies or runs analyzers, and after any compiler error it skips its documentation checks (CS1570 to CS1592). Fuse reports those errors at once, and the build reports them only once the first errors are fixed, so they are deferred. When a project fails to build, MSBuild skips every project that references it; an error Fuse reports in such a project is unverifiable, because the build has no answer there.
  • NodaTime's missed error. One edit made DateAdjusters.AddPeriod private. The build compiles dependent projects against reference assemblies, which leave out private members, so it reported CS0117 "'DateAdjusters' does not contain a definition for 'AddPeriod'" at five places and the follow-on CS1503 "Argument 1: cannot convert from 'T'" in NodaTime.Demo/DateAdjustersDemo.cs. Fuse compiles against the source and reported CS0122 "'DateAdjusters.AddPeriod(Period)' is inaccessible due to its protection level" at the same five places. The CS1503 error is the one it missed.

What the time rows measure #

  • Medians and speedups. A median is over the 30 correctness cases or the 10 selection cases. The speedup in parentheses is the dotnet median divided by the Fuse median, rounded half up to one decimal, as in the chart.
  • Totals. The total row adds up the 30 correctness cases' times of each command (total in fuseStats and dotnetStats), and divides the build total by the Fuse total. It is lower than the median ratio because the slowest checks are slower than the build they replace: the first check after the engine starts, and signature edits that load dependent projects. The slowest single check took 14,231 ms on FluentValidation, 15,061 ms on NodaTime, 64,590 ms on Jellyfin and 48,934 ms on the Community Toolkit. The total is closer to the time an agent saves over a whole task.
  • P50 and P95. Both use the nearest-rank method. P50 is the 8th fastest of the 15 body edits, which is their median, and the 5th fastest of the 10 signature edits. P95 is the slowest check of each kind.
  • The signature-edit P95. The slowest signature edit is the one that loads the dependent projects and searches them for the first time; the median edit loads nothing. In the signature-edit runs, the slowest loadDependents phase took 22,502 ms on Jellyfin, which checked 27 dependent projects, and 13,022 ms on the Community Toolkit, which checked 12; the slowest referenceSearch phase took 33,487 ms and 21,120 ms.
  • An unchanged tree. A check of a tree with no changes does almost nothing in the engine, so its time is the client's: starting the fuse process, sending the request and reading the answer. The native client needs no .NET runtime to start, which is why it is 21 to 32 ms on every repository.
  • NodaTime's body edits. NodaTime builds with TreatWarningsAsErrors, so every check there also runs the analyzers that can report a warning. That is why its body-edit check is slower than FluentValidation's and Jellyfin's.
  • Several agents at once. In the latency suite's writers scenario, up to four clients edit and check different projects while a fifth runs fuse test three times. The longest wait for the request lock was FluentValidation 478 ms; NodaTime 1,035 ms; Jellyfin 5,313 ms; Community Toolkit 7,211 ms. A test plan now holds the lock only while it syncs and selects tests, not while it emits the changed assemblies; a check still waits for a plan's selection, which loads the test projects the first time.

What the test rows mean #

  • The dotnet test time. The truth side of each selection case runs one dotnet test of the whole solution, as a user runs it after an edit, which builds what changed and runs the test projects in parallel. Before 5.2.2 it ran the test projects one after another, which made dotnet test slower and the speedups larger.
  • Share of tests run. The share is the mean, over the 10 selection cases, of the tests fuse test ran divided by the tests in a full run. Every FluentValidation test uses the library, so each case ran 2,661 of its tests and the other 3 are skipped in a full run too; the time saved there comes from running without MSBuild. In 8 of the 10 NodaTime cases the change reached code that NodaTime.TzdbCompiler, an application, uses behind its application host. Fuse cannot follow code that runs behind an application host to a test by name, so every test project that depends on it ran whole: 42,549 tests ran and 11 were skipped. On the Community Toolkit each change reaches one area of the code, and the cases ran between 148 and 3,621 of the 12,449 tests.
  • How the tests ran. FluentValidation: 9 without MSBuild, 1 with MSBuild; NodaTime: 9 without MSBuild, 1 with no affected test; Jellyfin: 10 without MSBuild; Community Toolkit: 10 without MSBuild.
  • The Community Toolkit's missed tests. In 3 cases the full dotnet test run also failed one MVVM test that fuse test did not report as failing: Test_AsyncRelayCommandOfT_ThrowingTaskBubblesToUnobservedTaskException, Test_ObservableObject_ThrowingTaskOfTBubblesToUnobservedTaskException. These tests wait with Task.Delay and then for the garbage collector to report an unobserved task exception, so they depend on timing, and a full run of every test project on a 4-core runner can fail them. 2 of these cases changed CommunityToolkit.HighPerformance, which no MVVM test project references, so fuse test did not run the test. The other changed CommunityToolkit.Mvvm; there fuse test ran the MVVM test projects, and the result file does not say whether it selected the timing-dependent test or ran it and saw it pass.
  • Cases too large to match name by name. In 2 NodaTime cases 126 and 252 tests failed by name in a full run. fuse test prints details for the first 10 failures and the names of the next 100, then counts the rest, so the suite could not match those cases name by name.

The other rows #

  • Lock collisions. The latency suite runs three fuse build at once, five times, and counts output lines with MSB3021, MSB3026, MSB3027 or CS2012, the errors of two builds writing the same files.
  • Engine memory. The working set of the engine process, read after the latency suite's checks and test rounds, when the engine has loaded every project they reached. The .NET runtime sizes its heap to the memory the machine has, so on a machine with more than the runners' 16 GB the engine keeps more.

How it was measured #

  • Correctness: the suite makes generated edits, some that break the build and some that do not, and compares Fuse's errors with the errors a real dotnet build reports beyond the ones HEAD already has. Each case makes one edit, or two or three in different projects: 162 edits in the 120 cases.
  • Test selection: the suite makes generated changes to behavior, some of which make tests fail. It compares the failing test names exactly with a full dotnet test run.
  • Latency: the suite builds HEAD, then runs the fuse executable after 15 generated body edits and 10 signature edits, and times each warm check. It also times 10 checks of the unchanged tree, five fuse test rounds, and three scenarios for several agents in one repository: up to four clients editing and checking at once, three fuse build runs at once five times, and three fuse test rounds over two projects.
  • The truth side, the real dotnet build and dotnet test, does not change while the repository and the eval code stay the same, so it is cached and measured once; each result file names where its truth was measured in truthOrigins.
  • Every result file records the commit of the repository it measured and the Fuse build that measured it, so each number can be traced to the source and to the executable behind it.

The evals are in evals/Fuse.Evals, every result file is in evals/results, and Evals describes each suite in detail.
