Benchmarks

All documentation pages

On four open-source repositories, Fuse checked an edit 8.1x to 27.7x faster than dotnet build at the median, took 3.1x to 5.6x less time than the build over all 30 edits of each, and ran the affected tests 1.2x to 2.9x faster than dotnet test on three of them; on NodaTime, where most tests run and one project goes through MSBuild, it was 1.4x slower. It reported no edit as clean that the build failed, and missed 2 compiler errors in 120 generated cases (161 edits).

This page is for anyone deciding whether to rely on Fuse, and contributors comparing a change with the published numbers.

After reading it you know how fast and how accurate Fuse was, on what, how much the times spread, and where each number comes from. Evals explains how the numbers are produced and how to reproduce them.

The four repositories measured here are FluentValidation, a validation library, the small one; NodaTime, a date and time library; Jellyfin, a media server; and Polly, a resilience library. The evals in evals/Fuse.Evals run the fuse executable the way an agent does, and compare every answer with a real dotnet build or dotnet test. Each job ran on its own GitHub Actions windows-latest runner, with 4 logical processors and 16 GB of memory, that ran nothing else (Evals). On Windows x64 the fuse command is the native client, so the evals measure it.

Speed and accuracy #

A warm check runs on an engine that is already running and has loaded the edited project. A body edit changes the inside of a method. A signature edit renames a method, so Fuse also checks the dependent projects that use it. P50 and P95 are explained under Reading the numbers.

The native client #

On Windows x64, Linux x64, Linux Arm64 and macOS Arm64 the fuse command is the native client, compiled ahead of time to native code, and elsewhere it runs fuse.dll on the .NET runtime (How it works). The same jobs ran the checks a second time with the managed client, on the same runner and the same engine code, so the difference between the two is the client alone. Every hook and command pays it.

Outside the engine, a body-edit check took 177 to 310 ms with the managed client and 35 to 50 ms with the native client (outsideEngine in bodyEditPhases): the managed client spends that time starting the .NET runtime and compiling its own code before it sends its request. A check of an unchanged tree is almost all client time, so it became 5.5x to 7.7x faster, and a check with more work in the engine gained 130 to 365 ms. fuse test rounds are dominated by the test run and are not compared here.

The managed client's numbers come from the four files in evals/results/managed: latency-FluentValidation-20261029-1858.json, latency-NodaTime-20261029-1900.json, latency-Jellyfin-20261029-1909.json and latency-Polly-20261029-1908.json, which record build 5.7.0/f0c4d92bf6e840c6820ae7fa1f3a312e, the managed build of the same commit. The native client's numbers come from the latency files listed above.

Repeated checks and tests at once #

Two of the latency suite's multi-agent scenarios measure what several agents in one working tree do most (Evals). Stops is a stop hook checking every change again after a small fix: a body edit in one file of each code project, up to 20, a fuse check of every change, then five more, each after another body edit in the first file. A repeat binds the file that changed and can keep the errors of the others from the earlier check (errors kept from an earlier check); the files kept are counted per compiled document, one per target framework, so the count can exceed the changed files. Tests is one fuse test on its own and then two started together, each after another body edit; when two runs only take turns, the pair takes twice as long as one.

A slow analyzer #

The analyzers suite measures a generated 300-file project whose analyzer spends two seconds reading the whole project each time it starts, with its rule at error severity. The engine measured it at 4,001 ms on one file and ran it compilation-wide. The post-edit hook, which leaves it out and names it, took 46 ms at the median. fuse check took 2.14 s for one edited file and 2.12 s for twenty, one run of the analyzer each, and reported its error. The engine peaked at 338 MB and held 218 MB once idle.

These numbers come from analyzers-analyzer-fixture-20261029-1937.json in evals/results, measured in GitHub Actions run 40941018665 (build 5.7.0/e61235320b09466ba67a805c5c71bfb0).

A large tree #

The scale suite measures one cold check of 1,500 changed files in a generated tree of 6,002 files in 31 projects. The check answered in 39.2 s, checked all 1,500 files, peaked at 294 MB and held 273 MB once idle, which scales to about 98 s for a tree of 15,000 files at the recorded factor of 2.5.

These numbers come from scale-scale-fixture-20261029-1940.json in evals/results, measured in GitHub Actions run 40941018665 (build 5.7.0/e61235320b09466ba67a805c5c71bfb0).

Another writer's errors #

The attribution suite measures whether an agent that shares a working tree with another is told the other's errors. Over 9 pairs on the four repositories, writers without sessions were told 20 of each other's errors; with sessions they were told all 64 of their own and none of the other's. A writer that registered its directory instead of sending a hook had its errors left to it in all four repositories.

These numbers come from attribution-FluentValidation-20261029-1937.json, attribution-NodaTime-20261029-1938.json, attribution-Jellyfin-20261029-1939.json and attribution-Polly-20261029-1938.json in evals/results, measured in GitHub Actions run 40941018665 (build 5.7.0/e61235320b09466ba67a805c5c71bfb0).

Reading the numbers #

What the accuracy rows count #

  • Missed and contradicted. The correctness suite makes generated edits that change declarations, 161 edits over the 120 cases, runs fuse check on the edited files, and compares its errors with the errors a real dotnet build reports beyond the ones HEAD already has. An error the build reports and Fuse does not is missed. An error Fuse reports that the build does not have, and that the suite cannot account for, is contradicted.
  • Deferred and unverifiable. The build reports fewer errors than exist in two situations, and the suite counts Fuse's extra errors there apart. When a project has a declaration error, the compiler stops before it binds method bodies or runs analyzers, and after any compiler error it skips its documentation checks (CS1570 to CS1592). Fuse reports those errors at once, and the build reports them only once the first errors are fixed, so they are deferred. When a project fails to build, MSBuild skips every project that references it; an error Fuse reports in such a project is unverifiable, because the build has no answer there.
  • NodaTime's missed error. One edit made DateAdjusters.AddPeriod private. The build compiles dependent projects against reference assemblies, which leave out private members, so it reported CS0117 "'DateAdjusters' does not contain a definition for 'AddPeriod'" at five places and the follow-on CS1503 "Argument 1: cannot convert from 'T'" in NodaTime.Demo/DateAdjustersDemo.cs. Fuse compiles against the source and reported CS0122 "'DateAdjusters.AddPeriod(Period)' is inaccessible due to its protection level" at the same five places. The CS1503 error is the one it missed.
  • Polly's missed error. One edit deleted src/Polly.Core/CircuitBreaker/CircuitBreakerResiliencePipelineBuilderExtensions.cs. The build reported 42 errors beyond HEAD's, 34 of them CS1061 at the places that call AddCircuitBreaker. Fuse found 41 of them: it printed 3 under the cause they share and wrote all 41 to its results file, which the suite compares. It missed the call at line 221 of src/Snippets/Docs/CircuitBreaker.cs.

What the time rows measure #

  • Medians and speedups. A median is over the 30 correctness cases or the 10 selection cases. The speedup in parentheses is the dotnet median divided by the Fuse median, rounded half up to one decimal, as in the chart.
  • Totals. The total row adds up the 30 correctness cases' times of each command (total in fuseStats and dotnetStats), and divides the build total by the Fuse total. It is lower than the median ratio because the slowest checks are slower than the build they replace: the first check after the engine starts, and signature edits that load dependent projects. The slowest single check took 7,896 ms on FluentValidation, 17,394 ms on NodaTime, 68,892 ms on Jellyfin and 49,733 ms on Polly. The total is closer to the time an agent saves over a whole task.
  • P50 and P95. Both use the nearest-rank method. P50 is the 8th fastest of the 15 body edits, which is their median, and the 5th fastest of the 10 signature edits. P95 is the slowest check of each kind.
  • The signature-edit P95. The slowest signature edit is the one that searches the dependent projects for the first time; the median edit searches almost nothing. In the signature-edit runs, the slowest referenceSearch phase took 36,655 ms on Jellyfin, which checked 27 dependent projects, and 6,063 ms on Polly, which checked 14; the loadDependents phase took 0 ms even at its slowest on both.
  • An unchanged tree. A check of a tree with no changes does almost nothing in the engine, so its time is the client's: starting the fuse process, sending the request and reading the answer. The native client needs no .NET runtime to start, which is why it is 27 to 44 ms on every repository.
  • NodaTime's body edits. NodaTime builds with TreatWarningsAsErrors, so every check there also runs the analyzers that can report a warning. That is why its body-edit check is slower than FluentValidation's and Jellyfin's.
  • Several agents at once. In the latency suite's writers scenario, up to four clients edit and check different projects while a fifth runs fuse test three times. The longest wait for the request lock was FluentValidation 563 ms; NodaTime 485 ms; Jellyfin 13,447 ms; Polly 12,600 ms. A test plan now holds the lock only while it syncs and selects tests, not while it emits the changed assemblies; a check still waits for a plan's selection, which loads the test projects the first time.

What the test rows mean #

  • The dotnet test time. The truth side of each selection case runs one dotnet test of the whole solution, as a user runs it after an edit, which builds what changed and runs the test projects in parallel. Before 5.2.2 it ran the test projects one after another, which made dotnet test slower and the speedups larger.
  • Share of tests run. The share is the mean, over the 10 selection cases, of the tests fuse test ran divided by the tests in a full run. Every FluentValidation test uses the library, so each case ran 2,661 of its tests and the other 3 are skipped in a full run too; the time saved there comes from running without MSBuild. In 8 of the 10 NodaTime cases the change reached code that NodaTime.TzdbCompiler, an application, uses behind its application host. Fuse cannot follow code that runs behind an application host to a test by name, so every test project that depends on it ran whole: 42,585 tests ran and 11 were skipped. On Polly each change reaches one area of the code, and the cases ran between 8 and 8,524 of the 12,329 tests; 3 cases ran no test.
  • How the tests ran. FluentValidation: 9 without MSBuild, 1 with MSBuild; NodaTime: 1 without MSBuild, 8 with two runs without MSBuild and one run with it, 1 with no affected test; Jellyfin: 10 without MSBuild; Polly: 7 with MSBuild, 3 with no affected test.
  • Polly's missed test. In 1 case the full dotnet test run also failed one hedging test that fuse test did not report as failing: AddHedging_AttemptNumbers_Are_Incremented. The case dropped ResilienceContextPool.Shared.Return(resilienceContext); in src/Polly/Utilities/Wrappers/ResilienceContextFactory.cs, and fuse test reported 0 failed after running the 11 affected tests out of 2,634.
  • Cases too large to match name by name. In 2 NodaTime cases 129 and 252 tests failed by name in a full run. fuse test prints details for the first 10 failures and the names of the next 100, then counts the rest, so the suite could not match those cases name by name.

The other rows #

  • Lock collisions. The latency suite runs three fuse build at once, five times, and counts output lines with MSB3021, MSB3026, MSB3027 or CS2012, the errors of two builds writing the same files.
  • Engine memory. The working set of the engine process, read three ways: right after the latency suite's checks and test rounds, when the engine has loaded every project they reached; the largest it reached during them, which Windows records for the process; and 50 seconds later, after the engine has returned the memory its requests freed, which is what an idle engine holds. A long test run leaves the engine idle for more than 30 seconds, so the first reading can already be after a release. The .NET runtime sizes its heap to the memory the machine has, so on a machine with more than the runners' 16 GB the engine keeps more.

How it was measured #

  • Correctness: the suite makes generated edits, some that break the build and some that do not, and compares Fuse's errors with the errors a real dotnet build reports beyond the ones HEAD already has. Each case makes one edit, or two or three in different projects: 161 edits in the 120 cases.
  • Test selection: the suite makes generated changes to behavior, some of which make tests fail. It compares the failing test names exactly with a full dotnet test run.
  • Latency: the suite builds HEAD, then runs the fuse executable after 15 generated body edits and 10 signature edits, and times each warm check. It also times 10 checks of the unchanged tree, five fuse test rounds, and five scenarios for several agents in one repository: up to four clients editing and checking at once, three fuse build runs at once five times, three fuse test rounds over two projects, a check of every change repeated after small fixes, and one fuse test against two at once.
  • The truth side, the real dotnet build and dotnet test, does not change while the repository and the eval code stay the same, so it is cached and measured once; each result file names where its truth was measured in truthOrigins.
  • Every result file records the commit of the repository it measured and the Fuse build that measured it, so each number can be traced to the source and to the executable behind it.

The evals are in evals/Fuse.Evals, every result file is in evals/results, and Evals describes each suite in detail.
