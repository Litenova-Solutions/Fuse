Benchmarks

All documentation pages

On four open-source repositories, Fuse 7.1.0 checked an edit 2.9x to 25.6x faster than dotnet build at the median. Over all 30 edits of each repository, it took 1.9x to 6.2x less time than the build. It ran the affected tests 1.4x to 2.4x faster than dotnet test on 3 of the 4, and 1.2x slower on NodaTime, where most tests run (59.4 s against 48.5 s). It reported no edit as clean that the build failed, and it missed 3 compiler errors in 120 generated cases (161 edits). Test selection missed no failing test in the 40 selection cases.

This page is for anyone who is deciding whether to rely on Fuse, and for contributors who are comparing a change with the published numbers.

After reading it you know how fast and how accurate Fuse was, which repositories it ran on, how far the times spread, and where each number comes from. Evals explains how the suites produce the numbers and how you reproduce them.

These benchmarks measure 4 repositories: FluentValidation, a validation library and the small one of the 4; NodaTime, a date and time library; Jellyfin, a media server; and Polly, a resilience library. The evals in evals/Fuse.Evals run the fuse executable the way an agent does. They compare every answer with a real dotnet build or dotnet test. Each job ran on its own GitHub Actions windows-latest runner with 4 logical processors and 16 GB of memory, and that runner ran nothing else (Evals). On Windows x64 the fuse command is the native client, so that is what the evals measure.

The native client #

On Windows x64, Linux x64, Linux Arm64 and macOS Arm64, the fuse command is the native client, compiled ahead of time to native code. Elsewhere it runs fuse.dll on the .NET runtime (How it works). The same jobs ran the checks a second time with the managed client, on the same runner and against the same engine code. The difference between the 2 runs is therefore the client alone. Every hook and every command pays that difference.

Outside the engine, a body-edit check took 284 to 446 ms with the managed client and 42 to 54 ms with the native client (outsideEngine in bodyEditPhases). The managed client spends that time starting the .NET runtime and compiling its own code before it sends its request. A check of an unchanged tree is almost all client time, so it became 6.5x to 8.8x faster. A check with more work in the engine gained 238 to 455 ms at the median on a body edit. On NodaTime a signature edit was faster with the managed client at the median (3,078 ms against 3,087 ms), which the table above shows as it stands. fuse test rounds are dominated by the test run, so this section does not compare them.

The managed client's numbers come from these 4 files in evals/results/managed: latency-FluentValidation-20261128-0035.json, latency-NodaTime-20261128-0043.json, latency-Jellyfin-20261128-0050.json and latency-Polly-20261128-0049.json. They record build 7.1.0/00f1c81428e24e6e8ca79e64978767fc, the managed build of the same commit. The native client's numbers come from the latency files listed above.

Repeated checks and tests at once #

Two of the latency suite's multi-agent scenarios measure what several agents in one working tree do most often (Evals). Stops is a stop hook that checks every change again after a small fix. It makes a body edit in one file of each code project, up to 20, then runs a fuse check of every change and 5 more, each after another body edit in the first file. A repeat binds the file that changed, and it can keep the errors of the other files from the earlier check (errors kept from an earlier check). The kept files are counted per compiled document, one per target framework, so their count can exceed the changed files. Tests is one fuse test on its own and then 2 started together, each after another body edit. When 2 runs only take turns, the pair takes twice as long as one.

Callers at once #

The concurrency suite waves 1, 4, 10 and 20 simultaneous callers from distinct sessions at one engine. No caller timed out at 4, 10 or 20 callers on any of the 4 repositories: timeouts is 0 in every wave, and no wave answers Busy or leaves a caller unanswered. That is the change from the one-lock engine, where callers took turns. The engine's peak working set at 20 callers was 433 MB on FluentValidation, 650 MB on NodaTime, 906 MB on Jellyfin and 990 MB on Polly. Status probes fired with each wave timed out in no wave at 4, 10 or 20 callers on any of the 4 repositories.

These numbers come from concurrency-FluentValidation-20261128-0033.json, concurrency-NodaTime-20261128-0039.json, concurrency-Jellyfin-20261128-0048.json and concurrency-Polly-20261128-0044.json in evals/results (build 7.1.0/6cf989c25a664e37b1db4f777c7e2bf3).

Compilation-wide analyzer #

The analyzers suite measures a generated 300-file project. The project's analyzer spends 2 seconds reading the whole project each time it starts. Its rule reports at error severity. The engine measured the analyzer at 4,001 ms on one file, so it ran it compilation-wide. The post-edit hook leaves that analyzer out and names it, and it took 56 ms at the median. fuse check took 2.12 s for one edited file and 2.24 s for 20, with one run of the analyzer each time, and it reported the analyzer's error. Engine memory peaked at 278 MB and held 221 MB once idle.

These numbers come from analyzers-analyzer-fixture-20261128-0032.json in evals/results (build 7.1.0/6cf989c25a664e37b1db4f777c7e2bf3).

Large tree #

The scale suite measures one cold check of 1,500 changed files. The generated tree holds 6,002 files in 31 projects. The check answered in 54.0 s and checked all 1,500 files. Engine memory peaked at 437 MB and held 271 MB once idle. At the recorded factor of 2.5, that scales to about 135 s for a tree of 15,000 files.

These numbers come from scale-scale-fixture-20261128-0032.json in evals/results (build 7.1.0/6cf989c25a664e37b1db4f777c7e2bf3).

Another session's errors #

The attribution suite measures whether an agent that shares a working tree with another agent is told the other agent's errors. Over 9 pairs on the 4 repositories, writers without sessions were told 20 of each other's errors. With sessions, they were told all 64 of their own errors and none of the other's. In all 4 repositories, registering a directory instead of sending a hook left a writer's errors to that writer.

These numbers come from attribution-FluentValidation-20261128-0030.json, attribution-NodaTime-20261128-0032.json, attribution-Jellyfin-20261128-0035.json and attribution-Polly-20261128-0032.json in evals/results (build 7.1.0/6cf989c25a664e37b1db4f777c7e2bf3).

Reading the numbers #

Accuracy rows #

  • Missed and contradicted. The correctness suite makes generated edits that change declarations: 161 edits over the 120 cases. It runs fuse check on the edited files and compares the reported errors with the errors a real dotnet build reports beyond the ones HEAD already has. An error that the build reports and Fuse does not is missed. When Fuse reports an error that the build does not have and that the suite cannot account for, that error is contradicted.
  • Deferred and unverifiable. In 2 situations the build reports fewer errors than exist. The suite counts Fuse's extra errors in those situations separately. When a project has a declaration error, the compiler stops before it binds method bodies or runs analyzers. After any compiler error it also skips its documentation checks (CS1570 to CS1592). Fuse reports those errors at once, but the build reports them only once the first errors are fixed. Errors in this group are deferred. When a project fails to build, MSBuild skips every project that references it. An error that Fuse reports in such a project is unverifiable, because the build has no answer there. An answered check the engine logged nothing for is unmeasured, so a logging regression cannot silently zero the counts. That was 0 in 30 cases on FluentValidation, 1 in 30 on NodaTime, 1 in 30 on Jellyfin and 3 in 30 on Polly.
  • NodaTime's missed error. One edit made DateAdjusters.AddPeriod private. The build compiles dependent projects against reference assemblies, which leave out private members. It therefore reported CS0117 "'DateAdjusters' does not contain a definition for 'AddPeriod'" at 5 places, and the follow-on CS1503 "Argument 1: cannot convert from 'T'" in NodaTime.Demo/DateAdjustersDemo.cs. Fuse compiles against the source instead, and it reported CS0122 "'DateAdjusters.AddPeriod(Period)' is inaccessible due to its protection level" at the same 5 places. The CS1503 error is the one Fuse missed.
  • Jellyfin's missed error. One edit added an int parameter to VideoResolver.IsStubFile. The build also reported SA1001 "Commas should be followed by whitespace" at Emby.Naming/Video/VideoResolver.cs (131,79), which Fuse did not report. That is the 1 error Fuse missed on Jellyfin.
  • Polly's missed error. One edit deleted src/Polly.Core/CircuitBreaker/CircuitBreakerResiliencePipelineBuilderExtensions.cs. The build reported 42 errors beyond HEAD's. Of those, 34 were CS1061 at the places that call AddCircuitBreaker. Fuse found 41 of them. It printed 3 under the cause they share and counted 41 in its answer. It missed the call at line 221 of src/Snippets/Docs/CircuitBreaker.cs.

Time rows #

  • Medians and speedups. A median runs over the 30 correctness cases or the 10 selection cases. The speedup in parentheses divides the dotnet median by the Fuse median and rounds half up to one decimal, as in the chart.
  • Totals. The total row adds up each command's times over the 30 correctness cases (total in fuseStats and dotnetStats). It divides the build total by the Fuse total. That ratio is lower than the median ratio because the slowest checks run slower than the build they replace: the first check after the engine starts, and signature edits that load dependent projects. The slowest single check took 11,577 ms on FluentValidation, 19,036 ms on NodaTime, 60,603 ms on Jellyfin and 38,160 ms on Polly. The total is closer to the time an agent saves over a whole task.
  • P50 and P95. Both use the nearest-rank method. P50 is the 8th fastest of the 15 body edits, which is their median. For the 10 signature edits it is the 5th fastest. P95 is the slowest check of each kind.
  • The signature-edit P95. The slowest signature edit is the one that searches the dependent projects for the first time. The median edit searches almost nothing. In the signature-edit runs, the slowest referenceSearch phase took 17,173 ms on Jellyfin, which checked 27 dependent projects, and 6,104 ms on Polly, which checked 14. The loadDependents phase took 33,918 ms at its slowest on Jellyfin and 35,404 ms on Polly.
  • An unchanged tree. A check of a tree with no changes does almost nothing in the engine, so its time is the client's. That time goes to starting the fuse process, sending the request, and reading the answer. The native client needs no .NET runtime to start. That is why the check is 31 to 53 ms on every repository.
  • NodaTime's body edits. NodaTime builds with TreatWarningsAsErrors. Every check there therefore also runs the analyzers that can report a warning. That is why its body-edit check runs slower than FluentValidation's and Jellyfin's.
  • Several agents at once. In the latency suite's writers scenario, up to 4 clients edit and check different projects while a fifth runs fuse test 3 times. The longest gate wait was FluentValidation 710 ms; NodaTime 456 ms; Jellyfin 964 ms; Polly 1,519 ms. Checks and test plans run on readers in parallel instead of taking turns behind one lock, and one reader stays free for interactive requests, so a post-edit or stop does not wait behind every command ahead of it.
  • Cold checks. A check of the clean tree with a cold engine took 2.06 s on FluentValidation, 3.57 s on NodaTime, 5.01 s on Jellyfin and 6.84 s on Polly. A cold check after a body edit took 10.6 s on FluentValidation, 12.8 s on NodaTime, 17.6 s on Jellyfin and 14.8 s on Polly. These are coldCleanMs and coldBodyEditMs in the latency files listed above.

Test rows #

  • The dotnet test time. The truth side of each selection case runs one dotnet test of the whole solution, as a user runs it after an edit. That run builds what changed and runs the test projects in parallel. Before 5.2.2 it ran the test projects one after another. That made dotnet test slower and the speedups larger.
  • Share of tests run. The share is the mean over the 10 selection cases of the tests fuse test ran, divided by the tests in a full run. Every FluentValidation test uses the library, so each case ran 2,661 of its tests. The other 3 are skipped in a full run too. The time saved there comes from running without MSBuild. In 8 of the 10 NodaTime cases, the change reached code that NodaTime.TzdbCompiler, an application, uses behind its application host. Fuse cannot follow code that runs behind an application host to a test by name. Every test project that depends on it therefore ran whole. In those runs 42,585 tests ran and 11 were skipped. On Polly each change reaches one area of the code. The cases selected between 0 and 1,821 of the 12,329 tests, and in 3 of them no test ran.
  • How the tests ran. Over the 10 cases of each repository, the runs split by mode as follows, as shadowRuns, msbuildRuns and wholeProjectRuns sum them:
    • FluentValidation: 9 without MSBuild, 1 with MSBuild, 0 whole.
    • NodaTime: 17 without MSBuild, 8 with MSBuild, 9 whole.
    • Jellyfin: 42 without MSBuild, 0 with MSBuild, 27 whole.
    • Polly: 0 without MSBuild, 7 with MSBuild, 0 whole, and 3 cases with no affected test.
  • No missed test. In the 40 selection cases, 23 of which made a test fail, fuse test missed no failing test: missedTests and missedCases are 0 in all 4 files.
  • Cases too large to match name by name. In 2 NodaTime cases, 129 and 252 tests failed by name in a full run. fuse test prints details for the first 10 failures and each failure past the first ten on its own FAILED line under also failed (N):, counting names past 100 as ... and N more. The suite therefore could not match those cases name by name.

The other rows #

  • Lock collisions. The latency suite runs 3 fuse build runs at once, 5 times, and counts output lines with MSB3021, MSB3026, MSB3027 or CS2012. Those codes are the errors of 2 builds writing the same files.
  • Engine memory. Engine memory is the working set of the engine process, read 3 ways. The first reading comes right after the latency suite's checks and test rounds, when the engine has loaded every project they reached. The second is the largest working set reached during them, which Windows records for the process. The third comes 50 seconds later, after the engine has returned the memory its requests freed, which is what an idle engine holds. A long test run leaves the engine idle for more than 30 seconds. The first reading can therefore already come after a release. The .NET runtime sizes its heap to the memory the machine has. On a machine with more than the runners' 16 GB, the engine therefore keeps more.

How it was measured #

  • Correctness: the suite makes generated edits, some that break the build and some that do not. It compares Fuse's errors with the errors a real dotnet build reports beyond the ones HEAD already has. Each case makes one edit, or 2 or 3 in different projects. The 120 cases hold 161 edits.
  • Test selection: the suite makes generated changes to behavior. Some of them make tests fail. It compares the failing test names exactly with a full dotnet test run.
  • Latency: the suite builds HEAD. It then runs the fuse executable after 15 generated body edits and 10 signature edits, and it times each warm check. It also times 10 checks of the unchanged tree, 5 fuse test rounds, and 5 scenarios for several agents in one repository. The scenarios are: up to 4 clients editing and checking at once; 3 fuse build runs at once, 5 times; 3 fuse test rounds over 2 projects; a check of every change repeated after small fixes; and one fuse test against 2 at once.
  • The truth side, the real dotnet build and dotnet test, does not change while the repository and the eval code stay the same. It is therefore cached and measured once. Each result file names where its truth was measured in truthOrigins.
  • Every result file records the commit of the repository it measured and the Fuse build that measured it. You can therefore trace each number to the source and to the executable behind it.

The evals are in evals/Fuse.Evals, and every result file is in evals/results. Evals describes each suite in detail.
