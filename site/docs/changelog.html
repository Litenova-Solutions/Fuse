This page lists what changed in each Fuse release, newest first, and what to do when you upgrade to it. Only Fuse 5 is supported; every version before 5.0.0 is deprecated.

This page is for someone upgrading Fuse, or deciding whether to, who wants to know what will behave differently.

After reading it, follow the upgrade steps of each release between the version you have and the latest one. fuse --version prints the version you have.

Supported versions #

Fixes, security fixes included, ship in patch releases of the latest 5.x minor version, as the security policy says.

VersionStatus
5.2.xSupported. The latest release.
5.1.xNo longer fixed. Upgrade to 5.2.2 with the steps below.
5.0.xNo longer fixed. Upgrade to 5.1.0 with the steps below, then to 5.2.2.
1.0.0 to 4.4.0Deprecated and unsupported. These versions are a different program under the same name; Moving from 4.x says what to remove.

To upgrade the tool itself to the latest release:

dotnet tool update -g Fuse

5.2.2 #

Not released yet. Compared with 5.2.1.

5.2.2 makes fuse test run only the selected tests when the selection is large, keeps a test plan from making other agents' checks wait, rewrites dotnet test commands that start with variable assignments, and corrects the speedups the README and the home page quote.

Upgrading to 5.2.2 #

Update the tool with dotnet tool update -g Fuse. Nothing else needs to change, and fuse init does not need to run again. A script that reads the engine log's phase lines finds a test plan's preparation in two phases, mirror and emit, where 5.2.1 had mirror alone.

  • fuse test passes the test filter to dotnet test in a runsettings file, as RunConfiguration/TestCaseFilter with --settings, instead of on the command line. A selection of up to 2,000 test names runs only those tests. 5.2.1 cut a filter above 8,000 characters back to whole test classes, and a longer one to the whole project, without saying so. Past 2,000 names the filter still collapses, and the summary says so and the engine log names the project.
  • A run without MSBuild uses the test project's own runsettings file (RunSettingsFilePath), with the filter added, as dotnet test on the project does. 5.2.1 ignored that file on such runs.
  • A test plan holds the engine's request lock only while it syncs and selects tests, and prepares the copies for runs without MSBuild after releasing it, so a check from another agent no longer waits while a test plan emits assemblies; it still waits for the plan's sync and selection. An assembly that has not changed since the previous plan is not emitted again. The engine log's phase line splits that preparation into mirror and emit, and gateHolder names what a request waited behind for the request lock.
  • A check whose reference search reaches a project that uses an analyzer the repository has not built yet, such as Jellyfin's own analyzer before its first build, leaves that analyzer out and answers. 5.2.1 answered internal error: Unexpected value 'Microsoft.CodeAnalysis.Diagnostics.UnresolvedAnalyzerReference'.
  • The pre-shell hook rewrites dotnet build and dotnet test after variable assignments, so DOTNET_CLI_UI_LANGUAGE=en dotnet test becomes DOTNET_CLI_UI_LANGUAGE=en fuse test. An assignment counts when its value has no whitespace, quote, backtick, separator, redirection or parenthesis; for Codex, only plain values count. 5.2.1 left such a command as it was.
  • A Microsoft.Testing.Platform run that exits with 8, the platform's code for a run in which no test ran, prints fuse: no test matched the dotnet test arguments (exit code 8) for fuse test with arguments, or fuse: the test run of <project> ran no test (exit code 8). 5.2.1 printed that the run exited with code 8 and produced no results.
  • A second fuse init prints unchanged <file> for a settings file that already holds what it would write, and leaves the file as it was. 5.2.1 printed wrote <file> and wrote it again.
  • The README, the home page and the sharing image quote the check speedup on the three open-source repositories, 7.2x to 22.6x at the median, instead of the generated fixture's 24.6x, and the README quotes the measured test speedup, up to 4.4x, instead of 5.7x, which was a time in seconds. The benchmarks page adds the total time over all 30 edits of each repository, 2.5x to 4.2x on the open-source repositories, and the chart shows the open-source repositories only.
  • fuse check no longer reports CS8795 for a [GeneratedRegex] method that names a culture, such as "en-US". The engine runs with invariant globalization, where the Regex source generator could not look the culture up and wrote no implementation. The same failure sent test projects that depend on such a project through MSBuild instead of running them without it.
  • The check summary counts every error the check found, in every file it found them in. 5.2.1 counted only the 200 errors the engine sends, so a change that broke 602 call sites in 3 files printed 200 error(s) introduced in 2 file(s).
  • A file whose only difference from HEAD is CRLF line endings inside a multi-line string constant, as a checkout with core.autocrlf writes it, has no declaration change, so the check stays within the file.
  • For a test project on Microsoft.Testing.Platform, which runs whole, the fuse test summary counts every test in the project, not only the tests the selection named.
  • The stop hook sends the agent back for a missing restore with the restore message alone, without the line that says the changes introduced errors. A stop payload whose loop_count is not a whole number that fits 32 bits no longer makes the hook fail and let the agent finish unchecked.
  • A state directory that fuse build or fuse test created records its repository, so the daily cleanup removes it once the repository is gone, as it does the directory of a repository an engine served.
  • A client that finds an engine copy without its completion marker, such as one a cleanup deleted part of, makes the copy again, or runs the engine from a fresh copy beside it when the old one cannot be replaced. 5.2.1 ran the engine from the incomplete copy, so the engine could not start until the copy was deleted by hand.

5.2.1 #

Released 2026-10-01. Compared with 5.2.0.

5.2.1 makes Fuse installable from NuGet again. 5.2.0 could not be installed from NuGet: nuget.org refused its per-platform packages, so dotnet tool install and dotnet tool update found the Fuse package but not the package for the platform. Everything 5.2.0 describes below ships in 5.2.1.

Upgrading to 5.2.1 #

Update the tool with dotnet tool update -g Fuse, from 5.1.0 as the 5.2.0 steps describe, or from a 5.2.0 installed another way. Nothing else needs to change. A mirror or offline feed that copies the Fuse package needs the per-platform packages it points to as well: Litenova.Fuse.win-x64, Litenova.Fuse.linux-x64, Litenova.Fuse.linux-arm64, Litenova.Fuse.osx-arm64, Litenova.Fuse.linux-musl-x64, Litenova.Fuse.linux-musl-arm64 and Litenova.Fuse.any.

  • The per-platform packages are named Litenova.Fuse.win-x64, Litenova.Fuse.linux-x64, Litenova.Fuse.linux-arm64, Litenova.Fuse.osx-arm64, Litenova.Fuse.linux-musl-x64, Litenova.Fuse.linux-musl-arm64 and Litenova.Fuse.any. The SDK names them after the tool, Fuse.win-x64 and so on, and nuget.org reserves the Fuse. prefix without an owner, so it refused every one of them as "The package ID is reserved". The Fuse package points to the new names, and dotnet tool install -g Fuse stays the only command.
  • The Fuse package on nuget.org shows the Fuse icon.
  • The publish workflow fails when nuget.org refuses a package, with nuget.org's reason. It passed 5.2.0 although only the Fuse package was pushed, because --skip-duplicate reports every refusal with status 409 as a package that already exists.

5.2.0 #

Released 2026-10-01. Compared with 5.1.0.

5.2.0 makes the fuse command native code on Windows x64, Linux x64, Linux Arm64 and macOS Arm64, so a hook no longer starts the .NET runtime. It also reads the results of test projects on Microsoft.Testing.Platform, fixes fuse test with arguments in repositories that use it, stops a check of files it cannot check from reading as a pass, keeps errors HEAD had in a renamed file from counting as introduced, and removes the engine copies and state directories that nothing uses any more.

Upgrading from 5.1.0 #

  1. Update the tool: dotnet tool update -g Fuse. It installs the package for your platform, and on the four platforms above the fuse command becomes the native client.
  2. Do nothing else. The hook commands fuse init wrote are unchanged, so it does not need to run again. The first request from the 5.2.0 client reaches the running 5.1.0 engine, which answers with a restart and exits, and the client starts a 5.2.0 engine and sends the request again. No request fails.

Then check whether anything you run depends on these changes:

  • Microsoft.Testing.Platform output. A script or agent instruction that matched fuse: tests passed in T s for a test project on Microsoft.Testing.Platform now gets fuse: 0 failed, P passed in T s, as for VSTest, and a failing run gets its failures instead of exited with code E and produced no results.
  • Your own packaging. A mirror or offline feed that copies the Fuse package needs the per-platform packages it points to as well; 5.2.1 names them.

The native client #

  • On Windows x64, Linux x64, Linux Arm64 and macOS Arm64, the fuse command is the native client: the client compiled ahead of time to native code, so a hook or command starts no .NET runtime and compiles no code before it sends its request to the engine (How it works). The engine still runs on the .NET runtime, from the fuse.dll installed with the native client, because it loads MSBuild and the repository's analyzers at run time. On every other platform, Windows Arm64, macOS x64 and Alpine included, fuse runs fuse.dll as in 5.1.0, and so do dotnet tool run fuse and tool manifests everywhere.
  • The Linux native clients run on glibc 2.27 and later. On Windows the native client is the fuse.exe in the tools directory, so Git Bash, PowerShell and cmd all run it.
  • The build id a request carries is the product version and the module id of fuse.dll, which the native client reads from the fuse.dll installed with it, so the native client and the engine it starts always agree.
  • fuse engine <root> in the native client prints that the engine runs from fuse.dll on the .NET runtime and exits with 2.
  • A client that starts the engine looks for the dotnet host on the PATH when neither DOTNET_HOST_PATH nor DOTNET_ROOT names one and it has no runtime directory of its own.

Test runs #

  • For a test project on Microsoft.Testing.Platform, fuse test reads the counts from the run summary and each failed test's message and stack frames from the run's output, and answers as it does for VSTest (Commands). 5.1.0 printed fuse: tests passed in T s for a passing run and, for a failing one, the last 30 lines of the output and exited with code E and produced no results.
  • In a repository whose global.json selects Microsoft.Testing.Platform, fuse test with arguments, such as the fuse test --filter-class Name the pre-shell hook writes for dotnet test --filter-class Name, passes the arguments without VSTest's --logger, --results-directory, -nologo and -tl:off. 5.1.0 added them, so every such run failed with exit code 5 and ran no test.
  • Whether dotnet test runs on Microsoft.Testing.Platform is read from the test.runner value of the global.json nearest to the working directory, up to the repository root, as the dotnet CLI reads it. 5.1.0 read only the root global.json and took any mention of the platform's name in it.

Checks #

  • fuse check and the fuse_check tool with named files answer fuse: none of the files named in the check is a C# source file of a project in this repository: <files> and exit with 2 when every named file is one Fuse cannot check, such as a path with a typo or a file of another language (InvalidPath). 5.1.0 answered fuse: no errors introduced (0 file(s) checked) and exited with 0, which read as a pass.
  • A file renamed since HEAD is compared with the errors HEAD had under its old name, so an error that existed before the rename is not reported as introduced. Git status reports a rename as a deleted file and a new one, and the new file is taken as a rename of the deleted file that shares at least half of its lines. 5.1.0 reported every error HEAD had in a renamed file as introduced.

Local state #

  • A starting engine deletes the engine copies of other builds that no running engine holds and that are more than ten minutes old; each engine marks its copy with a lock file while it runs. 5.1.0 deleted only copies last written more than seven days earlier, so every build of the tool left a copy behind for a week.
  • Each state directory holds a root file with its repository's path. Once a day a starting engine deletes the state directories whose repository no longer exists and that nothing wrote to for a day, such as those of deleted temporary repositories, which 5.1.0 kept for good (Where the logs are).

5.1.0 #

Released 2026-09-29. Compared with 5.0.0.

5.1.0 renames the shell hook event, makes Codex approve only the commands Fuse rewrites whole, adds a cause line to errors in files the agent did not edit, lets two agents build in one repository without breaking each other's build, and fixes checks and test selection that missed or over-selected in 5.0.0.

Upgrading from 5.0.0 #

  1. Update the tool: dotnet tool update -g Fuse.
  2. Run fuse init again in each repository where you use Fuse. The hook event that rewrites dotnet build and dotnet test is now pre-shell, and settings written by 5.0.0 call fuse hook <harness> pre-bash, which 5.1.0 answers with a usage line on standard error and exit code 0. Until you run fuse init, the harness runs dotnet build and dotnet test unchanged. fuse init replaces Fuse's own hook entries and keeps everything else (Running fuse init again). It also adds .fuse/ to .gitignore, so commit that change with the settings.
  3. Do nothing about the engine, the background process that answers every command. The first request from the 5.1.0 client reaches the running 5.0.0 engine, which answers with a restart and exits, and the client starts a 5.1.0 engine and sends the request again. No request fails (details).

Then check whether anything you run depends on these changes:

  • Codex approvals. For Codex, the pre-shell hook now rewrites and approves only a command that is one dotnet build or dotnet test with plain arguments, and gives any other command no answer, so Codex asks you about it as usual. 5.0.0 rewrote dotnet build and dotnet test after any separator and approved the whole command line, so a command such as dotnet build && curl x | sh ran without your approval.
  • fuse test --all with other arguments now prints an error, runs nothing and exits with 2. 5.0.0 dropped --all and ran what the other arguments named. Pass the arguments without --all to choose the scope.
  • Output text. A script or agent instruction that matches Fuse's output has to match the new wording:
Command5.0.0 printed5.1.0 prints
fuse checknew error(s)fuse: N error(s) introduced in M file(s)
fuse checkno new errorsfuse: no errors introduced
fuse checkwhole projects boundchecked whole projects
fuse testfast pathwithout MSBuild, or without MSBuild for N of M project(s)
fuse testno test reaches the changed codeno test is affected by the changes
fuse testran the tests you selectedran the tests your dotnet test arguments name
fuse testtest build failed (exit code E)fuse: the test run of <project> exited with code E and produced no results

Hooks and harnesses #

  • The hook event that rewrites dotnet build and dotnet test is pre-shell, and fuse init writes it for Claude Code, Gemini CLI, Codex and the OpenCode plugin.
  • For Codex, whose answer to the pre-shell hook also approves the command, the hook rewrites only a command that is one dotnet build or dotnet test with plain arguments (Codex).
  • A hook and the MCP server read their input as UTF-8, so a repository whose path or file names are not ASCII is checked from a harness whose console uses another code page. 5.0.0 failed to parse the payload and reported nothing.
  • A hook whose payload names an empty working directory runs in the harness's own working directory, where 5.0.0 crashed. A payload that is valid JSON but not an object exits 0 with no output and a line in hook.log, as every other internal failure does.
  • fuse init adds .fuse/ to the root .gitignore, creating the file when there is none, unless a line already names the folder. The .fuse folder is reserved for files Fuse may keep in a repository, such as an index; 5.1.0 writes nothing there (The .fuse folder).
  • fuse init and fuse mcp outside a git repository say fuse: not inside a git repository; Fuse compares your changes with HEAD, so it needs one, the message fuse check gives.

Checks #

A check compiles the edited files and the files that use a declaration the edit changed, and reports the errors HEAD did not have (How it works).

  • An error in a file the agent did not edit is followed by a cause line: changed: or removed: and the header, on one line, of the declaration change that put the file in the check, as the working tree has it or as HEAD had it. An answer holds at most ten cause lines, and the summary ends with N cause(s) left out when a printed error lost its cause to that cap.
  • A check compares declarations with each project's own preprocessor symbols, once per target framework, so a declaration change inside #if DEBUG or #if NET8_0_OR_GREATER checks the files that use it. 5.0.0 read such a region as inactive and reported no errors in its callers.
  • Removing a using directive checks the files that use the edited file's types, because the declarations' text is unchanged while what their type names resolve to is not. An added using still checks only the edited file.
  • Adding a constructor with parameters to a class that had only the implicit one checks every file that constructs the class, so each broken new C() is reported. 5.0.0 checked no other file.
  • A check finds a change to a type's parameterless constructor, such as making public C() internal, when a static constructor follows it in the file, which 5.0.0 missed. A formatting-only edit inside an explicit interface name no longer counts as a declaration change.
  • When a whole project is checked because more than 500 files are in reach, an analyzer error in an edited file is reported once, where 5.0.0 reported it twice, and file(s) checked counts each source file once, without generated files or a second target framework.
  • A file named to fuse check in another letter case than it has on disk, on Windows, is checked as the file git knows. 5.0.0 read it at HEAD under the other spelling, found nothing, and reported the errors HEAD has as introduced.
  • A file a hook names outside the repository, or under bin or obj, is left out of the change set. In 5.0.0 the first made git fail and dropped the edits of that request, and the second removed the generated file from the HEAD side of the check.
  • A project with a NuGet restore warning, such as a package advisory, is no longer reported as a project Fuse could not load, so Fuse answers in a repository whose restore logs a warning.
  • A restore needed answer names the project to restore in its command, so it also works for a project the solution leaves out.

Test selection and test runs #

Test selection picks the tests the changed code can reach (How it works).

  • Test selection selects the tests that reach an edit it missed in 5.0.0: a body edit to an explicit interface implementation that shares its name and parameter types with another member; a changed parameter modifier (ref, out, in, params or this), which also selects the tests that reach the member's type; a change from class to struct or from record to record struct; and an edit to a delegate declared at namespace level.
  • A change to the usings inside a namespace, and not only at the top of the file, selects the tests that reach the file's types.
  • Test selection selects fewer extra tests. Splitting a field declaration into two, or adding a variable to one, selects the tests that reach those fields and no longer every test that reaches the type. A formatting-only or comment-only edit inside a type header, a parameter type or a conversion, and an edit above a nested delegate, no longer count as a change to that declaration.
  • A run without MSBuild emits a project the tests load when the test project's build output holds another build of it, as after dotnet build Lib when Lib.Tests references Lib. 5.0.0 ran the test project's older copy, so a test the working tree fails could pass.
  • fuse test prints the errors of a test project that does not build, and exits with 1, when other test projects ran too; their results come first and the failed build is the last line. 5.0.0 printed only the other projects' results, so a passing project hid the failed build.
  • fuse test --all with other arguments prints fuse: --all runs every test and cannot be combined with other arguments; pass the arguments without --all to choose the scope on standard error, runs nothing and exits with 2.

Builds #

  • fuse build and fuse test take a per-repository lock for as long as they write build output, so two agents building or testing through Fuse run one after the other instead of making MSBuild fail with MSB3021, MSB3027 or CS2012 on a file the other holds. A client that has to wait says so once on standard error, and a client that cannot take the lock says why and runs anyway (The build lock). The arguments fuse build passes to dotnet build, the implicit restore included, are unchanged.
  • An analyzer or source generator the repository builds itself is loaded from a copy in the state directory, so a running engine no longer holds its file open and a real build that rebuilds it no longer fails with MSB3021 or MSB3027.

Engine #

  • The engine's pipe requests and responses have a different shape. An engine of another build, a running 5.0.0 engine included, answers the first request with a restart and exits, and the client starts an engine of its own build.
  • engine.log names every request by its kind, such as CheckFiles Calc.cs took 15 ms, and writes one line of per-phase times for it, so a slow check or test run can be traced to its phases (Reading a phase line).
  • A check that arrives just as the engine finishes loading a dependent project in the background checks that project too. In 5.0.0 such a check could find the project loaded but leave it out, and miss the errors in it.
  • A request that a hook gives up on while projects load no longer leaves those projects out of later checks. In 5.0.0 every later check of their files said no errors introduced until the next reload.
  • After a commit or branch switch, a re-evaluation that a cancelled or failed request left undone is finished by the next request, and the baseline is read at the new HEAD. In 5.0.0 later checks compared with the old HEAD and reported errors HEAD has as introduced.
  • When git status fails while the engine reads the changes again, after HEAD moved, a watcher error or more than 300 changed files, the engine keeps HEAD and the changed files it knew, and the next request asks git again. 5.0.0 had already taken the new HEAD and emptied its list of changed files, so later checks left out the files changed before the failure.
  • Git's file list and status are read NUL-separated, so a file whose name holds a quote, a backslash or a control character is found and checked under its own name.
  • Renaming, moving or deleting a folder whose name holds a dot, such as Company.Feature, is followed like any other folder, and a project file that moved with it re-evaluates the projects.
  • A project that fails to load in the background is tried again after the projects reload or a restore, and only one background load runs at a time.

5.0.0 #

Released 2026-09-25.

5.0.0 is a complete rewrite. It shares the name and the NuGet package with Fuse 4.x and nothing else. No command, file, setting or MCP tool of 4.x carries over, 5.x reads nothing 4.x wrote, and there is no migration path. Treat 5.0.0 as a new tool: remove what 4.x left in your repositories (Moving from 4.x) and set Fuse up again with fuse init.

Fuse 5 keeps a warm Roslyn compilation of a .NET repository and gives coding agents the compiler errors their edits introduced, affected-test runs, and compact build output, through agent hooks and a three-tool MCP server.

  • fuse init registers hooks with Claude Code, Cursor, Gemini CLI, Codex and GitHub Copilot CLI, a plugin with OpenCode, and the MCP server with VS Code, for the harnesses the repository uses.
  • fuse hook <harness> <event> runs a post-edit check that reports only introduced errors, rewrites dotnet build and dotnet test to their Fuse equivalents, and runs a stop check that sends the agent back once while its changes leave errors that were not at HEAD.
  • fuse check reports the errors the working tree has that HEAD did not, including breaks in dependent projects, with analyzers that can report an error.
  • fuse test runs the tests the changes can reach, from a shadow copy of the last build with changed assemblies emitted in memory when that is safe; fuse test --all runs everything; with dotnet test arguments it runs exactly that scope. Output lists failures only.
  • fuse build runs dotnet build and prints only errors.
  • fuse mcp serves fuse_check, fuse_test and fuse_build.
  • One engine runs per repository, starts on demand, runs from a private copy of its binaries, and exits after 30 idle minutes. Nothing is configured, and nothing is written inside the repository except the hook settings fuse init creates.

Moving from 4.x #

Fuse 4.x was an indexer: it kept an index of the repository in a .fuse folder and served its own MCP tools. Fuse 5 uses none of what 4.x wrote. Most of it is only unused files, but two entries still act on your agent, so remove all of it:

  1. Update the tool: dotnet tool update -g Fuse.
  2. In each repository, remove what 4.x wrote, as the table below lists.
  3. Run fuse init in each repository to register the 5.x hooks (Connect your agent).
What 4.x wroteWhereWhat to do
The .fuse folder, which held the 4.x index fuse.dbThe repository rootDelete the folder. Fuse 5 neither reads nor writes it; left in place, it is residue that takes disk space and does nothing. Keep the .fuse/ line in .gitignore: from 5.1.0, fuse init adds it when it is missing, because the folder is reserved for files a later Fuse may keep there.
fuse.jsonThe repository root, usually committedDelete it. Fuse 5 has no configuration file.
Claude Code hooks running fuse check --delta --fast and fuse gate.claude/settings.jsonDelete both entries. fuse init does not, because it replaces only commands that start with fuse hook. Under Fuse 5, fuse gate prints the usage text and exits with 2, which Claude Code takes as a stop hook refusing to let the agent finish.
A guidance block that starts with <!-- fuse:begin and a 4.x version, such as <!-- fuse:begin v4.4 -->, and ends with <!-- fuse:end -->CLAUDE.md, AGENTS.md or .github/copilot-instructions.md, and for a user-scope install ~/.claude/CLAUDE.md or the AGENTS.md in the Codex, OpenCode or Kilo Code configuration folder; for Cursor, the file .cursor/rules/fuse.mdcDelete the block, markers included, and delete .cursor/rules/fuse.mdc whole. It tells the agent to call 4.x tools, such as fuse_workspace, fuse_find and fuse_impact, that Fuse 5 does not have.
An MCP server named fuse that runs fuse mcp serve.mcp.json, .cursor/mcp.json and .vscode/mcp.json, or the same clients' user-level filesDelete the entry, except in .vscode/mcp.json, where fuse init replaces it with the 5.x entry. Fuse 5 ignores serve and starts its own MCP server, so a leftover entry gives the agent fuse_check, fuse_test and fuse_build next to the hooks, which answer the same questions.

A script or CI step that runs a 4.x command has to be rewritten against Commands. Fuse 5 has no fuse index, fuse find or fuse mcp install, and its fuse check and fuse test take other arguments and print other output than the 4.x commands of the same names.

Versions before 5.0.0 #

Fuse 1.0.0 to 4.4.0, released from 2026-04-09 to 2026-07-30, are deprecated. They get no fixes, security fixes included, and no support, and this documentation does not describe them. Their release notes stay on the GitHub releases page and in CHANGELOG.md at v4.4.0. To leave one, follow Moving from 4.x.
