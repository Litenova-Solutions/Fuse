This page lists what changed in each Fuse release, newest first, and what to do when you upgrade to it. Each release groups its changes as Added, Changed, Removed, Fixed, Security and Documentation. Only Fuse 5 is supported; every version before 5.0.0 is deprecated.

This page is for someone upgrading Fuse, or deciding whether to, who wants to know what will behave differently.

After reading it, follow the upgrade steps of each release between the version you have and the latest one. fuse --version prints the version you have.

5.7.0 #

Released 2026-10-29. Compared with 5.6.0.

Check and test answers have new output shapes, and the engine does more work in the background and keeps new state files. fuse check scopes to directories and patterns, sessions can be registered for external writers, and the stop hook checks only the stopping session's files. fuse test reruns the tests that failed last time and runs them first. fuse build grows --changed and --warnings, and fuse status is new.

Upgrading to 5.7.0 #

Update the tool with dotnet tool update -g Fuse. The hook settings fuse init writes are unchanged, so it does not need to run again. If you ran fuse init --instructions, run it again to refresh the Fuse section in AGENTS.md with the container pre-flight and C# scope bullets. The first command after updating restarts the engine for the new protocol, and no request fails.

What behaves differently:

  • Check and test output shapes. Check errors that share a cause print under one header, test failures that share their message's first line print under one header, and fuse build and fuse check summaries end with a tree stamp. A script that parses that output must accept the header lines and the stamp suffix, as well as the whole-projects segment, the non-C# parenthetical, and the skipped-container clause.
  • Scoped checks. fuse check with a directory or a pattern checks that scope instead of every change, and a spec that matches no changed C# source is refused. To check every change, run fuse check with no arguments.
  • Container-gated test projects. A test project that references Testcontainers is left out of the plan when no container runtime answers, and when no test can run fuse test starts no process and exits 1. Start Docker or Podman to run those tests.
  • Stop hook scope. A stop answered to a session checks only its own files and what they reach. Run fuse check, which reports every error, once all agents have finished.
  • Rewritten commands print a notice. A dotnet test or dotnet build the pre-shell hook rewrites prints a notice on standard error first. A command you type yourself prints none.

Added #

  • Every command takes --help and -h, which print that command's usage to standard output and exit 0, running nothing. fuse hook --help prints its usage to standard error and exits 0 without reading stdin. An unknown option is refused with exit 2 and the command's usage; for fuse build and fuse test only a near miss of a Fuse option is refused (fuse: '<token>' is not a fuse build option; did you mean '<option>'? for builds, and the same form for tests), and every other token goes to dotnet unchanged. Commands shows each usage.
  • fuse build and fuse check take --max-errors <n>, --all-errors and --json. The default answer shows 20 errors; --max-errors takes 1 to 100000, and --all-errors shows every error. --json prints one JSON object per error (file, line, column, code, message, with line and column left out for a general error; a check adds cause and generated when present, and a locked build error adds lockedBy) with the text summary as the last line, and a JSON summary never names a file. A capped build summary ends with ; all N in <state>/last-build-results.txt; that file holds every error and warning, and in JSON mode the errors are also in last-build-results.json. A failed build with no parseable error prints the output tail before the summary, as text mode does. The fuse_check tool takes max_errors (1 to 100000, default 20). Commands shows the check forms and the build forms.
  • fuse test --failed reruns the tests that failed in the last recorded run. It is refused with --all or any other argument, exiting 2 and running nothing, as are the runs with no record: fuse: no test run is recorded yet; run fuse test first and fuse: the last test run was from dotnet test arguments, so its failures cannot be rerun; run fuse test exit 2, while fuse: the last test run had no failures exits 0. A rerun prints reran N test(s) that failed last time in M test project(s), names each dropped project with ; left out X, which is not a test project in this repository, and says when the rerun widened past the failures; when none of the recorded tests still exists it prints fuse: none of the N test(s) that failed last time ran; they may have been renamed or removed and exits 1. After --, every token goes to dotnet test unchanged, even --all and --failed. The fuse_test tool takes failed, refused together with all. The record is last-test-results.json beside the text file in the state directory, holding the last run's per-test verdicts and durations for at most 20,000 tests; a corrupt file counts as no record. Commands shows the forms (#125).
  • fuse build --warnings lists the build's warnings after its errors, at most 20 of them, each indented; the rest are counted as ... N more warning(s) in <state>/last-build-results.txt, and the file holds every warning under ## warnings. A warning that is also an error prints once, as an error, and the warning count in the summary stays MSBuild's. fuse check has no --warnings: it is refused, since warnings come from the build. Commands shows the form.
  • fuse build --changed builds only the projects that own files changed since HEAD and their dependents, reduced to the highest projects, passing the same extra arguments to each dotnet build. It first prints which projects it builds (fuse: building M project(s) for N changed file(s) (tree H): names), then one build (<name>) summary per project, and F of M project(s) failed when several build. With no C# changes it builds nothing and prints fuse: no C# changes since HEAD; nothing to build (tree <hash>). When the selection cannot be trusted, because project files changed or no project owns the changes, it says so and builds the whole solution instead. Commands shows the form.
  • fuse status shows the engine and the changed files: whether an engine runs and its memory, how many files differ from HEAD with their tree stamp and HEAD, and the large-tree limits. It never starts an engine; past a short wait it reads the tree from git instead. fuse status --json prints one object with engine, pid, memoryMB, changedFiles, head, tree, reloadAt and wholeProjectAt. It exits 0 in a repository and 2 outside one. Commands shows both forms.
  • fuse session begin <name> --paths <pattern> [<pattern>...] registers an external writer a launcher starts as a session for its path patterns, so a judge's stop leaves that writer's half-written errors to it. It prints fuse: session <name> registered for N path pattern(s); files under them count as that session's until fuse session end <name> or 4 hours pass; beginning the name again replaces its patterns and restarts the 4 hours. fuse session end <name> prints fuse: session <name> ended; its files now count as no session's, and an unknown name is refused with fuse: no registered session named <name> and exit 2. A name holds 1 to 64 letters, digits, -, _ or .; a pattern is repository-relative with ** as a whole segment and * and ? inside a segment, at most 256 characters and 32 per session, with 64 sessions live at once. Registrations live in registered-sessions.tsv in the state directory, survive an engine restart, and are deleted by fuse uninit but kept by fuse stop. A plain fuse check still reports every error. Commands shows both forms, and Subagents and parallel agents explains external writers (#129).
  • fuse check takes directories and glob patterns as well as files. Any existing directory or argument with * or ? scopes the whole call; files, directories and patterns can be mixed. An error summary adds ; checked <paths> and what it reaches, and a clean answer reads fuse: no errors introduced in <paths> and what it reaches (N file(s) checked). A spec that matches no changed C# source is refused, as is a scope expanding past 2000 source files, each with exit 2 and running nothing; the fuse_check tool stays files-only. Commands shows the forms (#127).
  • fuse test leaves out test projects that need a container runtime when none answers. A project is gated when any of its package references is Testcontainers or starts with Testcontainers.; Fuse probes docker info then podman info, 2 seconds each, cached 5 minutes per engine process. Gated tests are named in the summary as ; skipped N test(s) in P1, P2 (no container runtime), and when no test can run Fuse starts no process and prints fuse: no test ran: N test(s) selected in P need a container runtime, and none is running; start Docker or Podman and run fuse test again, exiting 1. A run that passes arguments to dotnet test runs without that check. Commands shows the lines, and Limits covers which projects are gated.
  • When the pre-shell hook rewrites an agent's dotnet test or dotnet build, the rewritten command prints a notice on standard error first: fuse: dotnet test routed to fuse test (tests affected by your changes; fuse test --all runs every test) and fuse: dotnet build routed to fuse build (first 20 errors; fuse build --all-errors for every error). A command you type yourself prints none. Connect your agent explains the rewrite.
  • When a build error says a file is locked (MSB3021, MSB3026 or MSB3027), the error is followed by an indented line naming the file and the process that holds it (locked: <file> is held by <name> (pid <n>); stop that process, then run the build again), or dotnet build-server shutdown when the holder is a build server. In JSON mode the line is left out and the holder is carried in lockedBy. Commands shows the line, and Troubleshooting covers the fix.
  • fuse check names the changed files in other languages that it does not check. The summary ends with ; N non-C# file(s) changed, which Fuse does not check: <paths>, naming the first five and counting the rest, on clean and error answers alike; with named files it covers the whole tree's delta, not the named scope. The post-edit hook never shows it, and the stop hook shows it only when it already blocks. Commands shows the line, and Limits covers what a check does not see.
  • The evals gain a scale suite and a stale suite. scale measures one cold check of 1,500 changed files in 6,000 over 30 projects plus one test project on a generated fixture, resizable with --projects, --files and --changed; full-scale numbers are extrapolated with the result's factor, never quoted as measured. stale breaks one file through the post-edit hook, fixes it, and checks whether the stop hook delivers a stale error. The selection suite takes --failed-rounds for fix-and-rerun rounds with fuse test --failed, and the result files record kept answers, reused errors, result-file completeness and member-walk scope. Evals describes the suites and fields.

Changed #

  • Check errors that share a cause print under one header naming it once: changed: <declaration> (N error(s)), or (N error(s), first M shown) when the cap cuts the group. Member error lines keep their shape at column 0, and last-check-results.txt stays flat with every error. A script that reads check output line by line must accept the header lines. How it works explains the groups (#126).
  • Test failures that share their message's first line print under one header: N failure(s) with the same first message line: ..., with the first line cut at 160 characters in the header only. Members keep their full FAILED detail, and past 10 failures in detail the rest are names under also failed (N):. last-test-results.txt stays flat and full. Commands shows the form (#126).
  • On the command line, when the last run recorded 1 to 100 failures inside a VSTest method selection, those tests run first as their own stage, and their failures print before the rest runs; the final summary counts each test once. Platform runs, whole-project runs, selections with no recorded failure, and projects whose recorded failure is a theory row run unchanged in one stage. The MCP answer arrives once with the full text. How it works explains the stages (#115).
  • A stop answered to a session checks only its own files and what they reach: it binds the files the session wrote alone or together with another session, and files no session wrote, then attributes as before. N error(s) from other sessions' edits left out now counts only in-reach errors from other sessions. fuse check, the MCP check, and a stop whose harness names no session are unchanged. How it works and Subagents and parallel agents explain the scope (#104).
  • When a check binds whole projects, the summary names the projects and the changed files that forced it: checked whole projects: Lib because Lib/Calc.cs (removed: ...); App because ..., at most 3 projects and 2 files per project, sorted, with ; and N more in the engine log past that. The check: line in engine.log holds the full list after whole projects:. A dependent that owns no candidate is named with its forcing files and no per-cause lines. Commands shows the form (#128).
  • An edit whose declarations compile to the same code as HEAD's selects no tests: a local rename or var against the explicit type seeds nothing. Anything Fuse cannot read counts as changed. When every changed declaration compiled to the same code, fuse test runs nothing and prints fuse: no test is affected by the changes (out of T); the changes compile to the same code as HEAD; fuse test --all runs everything; partial drops are engine-log only. How it works explains the comparison (#109).
  • Member-level selection now applies when at most 100 test classes are reachable, up from 40. Each plan logs its walk statistics and which level it selected at. How it works explains the walks (#80).
  • A shadow run emits a dependent again only when a project it depends on changed its declarations; otherwise the shadow folder keeps its image. Each skipped dependent is named in engine.log. How it works explains the runs (#74).
  • The first fuse check after an engine restart reuses HEAD's finished baseline results from the state directory instead of binding HEAD again, keyed by the commit and the inputs the result depends on. There is no output change; engine.log gains baseline: <n> stored result(s) read for HEAD <12 hex>; <m> computed per check that reads the store. How it works explains the store (#96).
  • After HEAD moves, the engine warms the baseline compilation-wide analyzer results in the background between requests. There is no output change; engine.log gains baseline warm: <project> compilation-wide analyzers done in <ms> ms and baseline warm: skipped, HEAD moved again. How it works explains the warming (#99).
  • The background load of dependents also builds their compilations, so the next check reuses them. There is no output change; engine.log gains preloaded <project> compilation in <ms> ms per project. How it works explains the preload (#67).
  • fuse build and fuse check summaries end with ; tree <12 hex> over N changed file(s), naming the tree the command ended on; last-check-results.txt and last-build-results.txt headers carry the same stamp. Hook and MCP answers carry no stamp. Commands shows the stamp.
  • On large uncommitted trees Fuse bounds two costs. Past 500 changed files a check skips hashing for a kept answer and answers fresh; past 2000 touched paths the next sync re-evaluates the projects and resets the set. The check: line in engine.log gains per-session file counts. Limits covers the bounds, and Troubleshooting the log lines.
  • fuse init prints the version that registered the hooks: fuse: hooks registered by Fuse <version>; ..., or fuse: MCP server registered in .vscode/mcp.json by Fuse <version>; .... Re-running after an upgrade prints the new version even when every file is unchanged. The --instructions section gains the container pre-flight bullet and the C# scope bullet; run fuse init --instructions again to get them. Connect your agent shows the section.

Fixed #

  • A background post-edit answer with errors is confirmed by a second check against the current tree before the hook returns it; when the tree no longer reports the errors, the hook exits 0 silent instead of delivering an already-fixed error. Deliveries and drops are logged in hook.log. The hook wait now covers at most two checks: the first answer plus one confirmation. How it works explains the confirmation.
  • When a reached project is missing from the engine's views after one recovery rebuild, the check fails with fuse: could not load <project>: the check reached <name> but the engine's view does not hold it (the projects the view holds are named in engine.log) and exit 2, instead of answering without that project's errors. Hooks stay silent on it. engine.log gains a check coverage: line naming which reached projects each view held. Troubleshooting explains the line (#82).
  • In a scoped check, a file spec that is not a C# source of a project is refused even when mixed with checkable specs, with "<spec>" in the check matches no changed C# source file of a project in this repository. Without the refusal the mixed case would silently check only the other specs. Commands and Messages cover the refusal.
  • When fuse test passes the command through to dotnet test, a positional directory stays positional on VSTest, which refuses --project; only on Microsoft.Testing.Platform is a first argument naming a project, solution or directory spelled as --project or --solution. In 5.6.0 the spelling applied on VSTest too. Commands describes when arguments pass through (#122).
  • For a Microsoft.Testing.Platform project with a .NET Framework target in a repository without the global.json opt-in, fuse test runs that target through dotnet test --framework and starts the other targets directly, at the same time. A .NET Framework target builds an assembly with no runtimeconfig.json, which dotnet exec cannot start; in 5.6.0 every target started directly, so the project produced no results. A target whose output path does not name its framework still sends the whole project through dotnet test. Commands describes the runs, and How it works explains application hosts.
  • A Microsoft.Testing.Platform project that Fuse runs through dotnet test in a repository without the global.json opt-in now gets the project positionally and reports to TRX, reading the filter from the run settings; a framework's own filter arguments are left out, so an xUnit v3 or TUnit project runs whole. In 5.6.0 the fallback passed --project, which only the platform's dotnet test accepts, so VSTest's refused it and the project produced no results. Commands describes when a run goes through dotnet test.

Documentation #

  • Commands documents every new flag, command and output form. How it works explains grouping, container gating, the stop scope and same-code selection. Limits covers the new bounds and the files a check does not see. Troubleshooting adds the new engine-log lines, the locked-file holder and the missing container runtime. Messages covers the new refusals. Evals documents the scale and stale suites, the failed rounds and the new result fields. Connect your agent and Subagents and parallel agents cover the refreshed instructions and external writers.
  • The evals measure Polly in place of the .NET Community Toolkit: a layered library whose six xUnit v3 test projects run on Microsoft.Testing.Platform. Its first results ship with this release, and Benchmarks quotes them. Evals lists the pinned repositories.

5.6.0 #

Released 2026-10-18. Compared with 5.5.0.

Fuse narrows more test runs to the tests a change can affect. Microsoft.Testing.Platform projects use their framework's filters, and fuse test commands that only name projects or build switches plan within that scope. Repeated checks of an unchanged tree can reuse a previous answer, and capped check and test output points to a file that holds the full result.

Upgrading to 5.6.0 #

Update the tool with dotnet tool update -g Fuse. If you use Cursor or Copilot CLI, run fuse init again so their pre-shell hooks rewrite dotnet build and dotnet test; the other harnesses need nothing.

What behaves differently:

  • Scoped test commands. fuse test tests/Foo.Tests, fuse test --no-build and similar commands run the affected tests in the named scope instead of every test. To pass a command to dotnet test exactly as written, include an argument that chooses the tests or controls reporting, such as a filter.
  • Platform projects without the global.json opt-in. Fuse builds an xUnit v3, MSTest, NUnit or TUnit project and runs its test application directly. Failures that 5.5.0 hid behind a problems answer, or behind an xUnit v3 pass that ran no tests, can surface.
  • Capped output. A capped check or test summary can end with ; all N in <path>. Scripts that match the whole summary line should allow that suffix.

Added #

  • For a test project on Microsoft.Testing.Platform, fuse test runs only the affected tests. Fuse identifies the framework from the project's packages and passes the filter in that framework's form. xUnit v3 and TUnit receive their own filter arguments. MSTest and NUnit receive the VSTest filter in a runsettings file. If Fuse does not know the framework, the project runs whole and the summary gives that reason. Commands describes the runs, and Limits covers the projects that stay whole (#57).
  • fuse test tests/Foo.Tests runs the affected tests in Foo.Tests instead of every test. The same applies to project and solution paths and to commands whose other arguments only control the build, such as --no-build. The summary names the projects included. A path that names no test project is refused rather than treated as an empty run. Commands lists the arguments that count as scope only (#69).
  • When a check or test answer leaves out errors or failures to stay short, its summary ends with ; all N in <path>. last-check-results.txt in the state directory holds every error the engine returned. last-test-results.txt holds every failure, grouped by project. Fuse replaces both files on every check and test run, including clean ones, so the path in the latest answer does not lead to an older result. Commands shows the check form and the test form (#123).
  • fuse init registers the pre-shell hook in Cursor and Copilot CLI. The hook rewrites dotnet build to fuse build and dotnet test to fuse test, as it already did in Claude Code. Run fuse init again in either harness to get the entry. Connect your agent shows each harness's settings (#71, #142).
  • The latency suite's multi-agent results include stopsUnchangedRepeat: three checks of the same tree with no edit in between. The field records how long those repeats take now that an unchanged check can reuse a previous answer. Evals describes the field (#66).

Changed #

  • A repeated check can reuse an earlier answer when its scope, session and analyzer run are the same and nothing that answer depends on has changed. Fuse then returns that answer without binding the files again. It keeps the last eight answers in memory and forgets them when the engine exits. It never reuses an answer whose analyzers did not finish. How it works explains what the answer depends on (#97).
  • A passing fuse build summary includes the build's warning count. You can see warnings creeping up without running another build. Commands shows the line (#121).
  • The engine log's phase line breaks binding into bindUpdate, bindCompiler, bindAnalyzers and bindFrameworks, alongside the bindTargets total. bindFrameworks is a count of the documents bound, one per target framework. Scripts or notes that read the phase line can see which part of binding took the time. Troubleshooting says how to read it (#66).

Fixed #

  • For a Microsoft.Testing.Platform project in a repository without the global.json opt-in, Fuse builds the project and runs its test application directly, with the same framework filter. In 5.5.0 it treated the project as a VSTest project. MSTest, NUnit and TUnit runs reported problems, and an xUnit v3 run could read as a pass after running no tests. A filtered run that matches no test is reported as having run no test. Commands and Limits describe both forms (#57).
  • When other arguments make fuse test pass the command through to dotnet test, a first argument that names a directory, project file or solution file is passed as --project or --solution, as Microsoft.Testing.Platform requires. In 5.5.0 dotnet test rejected the directory form and Fuse could report only that the run exited with code 1 and produced no results. Commands describes when arguments pass through (#122).
  • A --results-directory value is passed to dotnet test as a full path. On Windows, a Git Bash spelling such as /c/... is read as the equivalent Windows path. If a run then produces no results, the answer names the directory Fuse read. In 5.5.0 the POSIX form could produce no TRX file and no explanation (#124).
  • When a test runner colors its output, as the platform runners do on Linux and macOS, Fuse reads the run's counts and failures from it and answers in its own form. In 5.5.0 it could not read colored output: a passing run said only that the tests passed, and a failing run printed the runner's own output (#57).

Documentation #

  • Commands and Limits explain framework-specific platform filters, direct test application runs without the global.json opt-in, and which fuse test arguments only set the scope. How it works explains when a check answer can be reused. Messages covers a path that names no test project, Connect your agent adds the Cursor and Copilot CLI setup, and Evals documents the unchanged-repeat measurement.

5.5.0 #

Released 2026-10-17. Compared with 5.4.0.

Slow analyzers can no longer make a hook run out of time without answering. Fuse keeps the hook wait inside the harness limit, gives the HEAD side of a check the same analyzer deadline as the working tree, and keeps unfinished whole-project analyzer work for the next check. This release also adds fuse uninit for removing Fuse from a repository.

Upgrading to 5.5.0 #

Update the tool with dotnet tool update -g Fuse. The hook settings fuse init wrote need no change. If you ran fuse init --instructions, run it again to replace the Fuse section in AGENTS.md, CLAUDE.md and GEMINI.md; until you do, the old section tells agents to run fuse check before they finish, which repeats the stop hook's check.

What behaves differently: on a repository whose analyzers are slow, a check can leave out analyzer errors in a file whose HEAD analyzers did not finish, and its summary counts that file among those whose analyzers did not finish in time; fuse build runs every analyzer. An engine stays up for 30 minutes without a request, so it keeps its memory longer; fuse stop gives it back at once (Limits).

Added #

  • fuse uninit removes the entries that fuse init and fuse init --instructions wrote for every harness. It keeps entries that are not Fuse's. It then stops the repository's engine and deletes its state. Commands lists what it removes (#94).

Changed #

  • The stop hook and Claude Code post-edit hook wait 280 seconds for an answer. That leaves 20 seconds of the harness's 300-second limit to deliver it. In 5.4.0 the hook could use all 300 seconds, so the harness might end it before the answer arrived. How it works describes the waits (#93).
  • A check gives the analyzers at HEAD the same deadline as the analyzers in the working tree. If HEAD's analyzers do not finish in a file, Fuse leaves the working tree's analyzer errors in that file out of the answer. It counts the file among those whose analyzers did not finish. In 5.4.0 HEAD's analyzers always ran to the end, even after the client had stopped waiting and the check could answer nothing. How it works describes the deadline (#93).
  • An analyzer that reads the whole project keeps running after a check stops waiting for it. The next check of the same code can use its finished errors instead of running it again. How it works describes which errors are kept between checks (#93).
  • The engine exits after 30 minutes without a request instead of 10 minutes. A command after the longer idle period can still use the loaded projects and HEAD analyzer work. The engine also holds its memory for longer while it stays running. Limits describes that trade-off (#93).
  • The section that fuse init --instructions writes says the stop hook checks every change when the agent finishes. It presents fuse check as the same check run sooner. The old section told every agent to run fuse check before finishing and every subagent to run fuse test before handing back work. Subagents and parallel agents shows the current section (#93).
  • When more than 40 files with errors would need a decision about which session caused them, the check summary counts the files reported without that decision. In 5.4.0 it said nothing about those files, so the reader could not tell that attribution had stopped there. How it works describes the limit (#93).

Documentation #

  • How it works and Limits explain the analyzer deadline at HEAD, the hook waits and the engine's idle time. Commands documents removing Fuse from a repository, and Troubleshooting and Messages cover a hook that runs out of time.

5.4.0 #

Released 2026-10-17. Compared with 5.3.0.

Several agents can share one working tree with less interference. The stop hook holds a session to the errors its own edits caused, test runs without MSBuild from different agents can run at the same time, and slow or failed builds show more of what happened.

Upgrading to 5.4.0 #

Update the tool with dotnet tool update -g Fuse. If you use Claude Code, run fuse init again, so .claude/settings.json also runs the stop hook for SubagentStop; until you do, a subagent's stop is not checked, and its edits never count as its parent's. The other harnesses need nothing, and the pre-shell hook passes the session to fuse test without running fuse init again.

To use Muse Code, run fuse init in a repository with a .muse/ folder, then muse plugins install .muse/plugins/fuse --scope project and muse plugins approve fuse once (Muse Code).

What behaves differently: a stop hook whose harness names the session no longer blocks on errors another session's edits cause on their own, so run fuse check, which reports every error, once all agents have finished. A fuse test that an agent's dotnet test became runs the tests its own session's edits affect, and test runs from several agents run at the same time, so integration tests that share a fixed port or database name can collide (Limits).

Added #

  • Muse Code is a supported harness. fuse init writes a plugin bundle with the post-edit, pre-shell and stop hooks. You install and approve that bundle once in Muse. Connect your agent shows the bundle and the commands.
  • In Claude Code, fuse init registers Fuse's stop hook for SubagentStop as well as the main stop. A subagent is sent back for errors its own edits caused before it hands work back. Connect your agent shows the settings.
  • When the pre-shell hook turns an agent's dotnet test into fuse test, the run covers the tests that session's edits affect. The summary says how many changed files only other sessions wrote and were left out. How it works describes session-scoped selection.
  • When a build target's command fails with error MSB3073, fuse build and a failed test build print the last lines that command printed. That can show a code generator's exception instead of only the command's exit code. Commands shows the output.
  • A build that takes 10 seconds or more ends its summary with its slowest tasks and projects. Troubleshooting explains how to read that line.
  • When the type or member behind an error is declared in a file generated during the build, the error names that generated file. If the file is generated from changed code, the message tells you to run fuse build. A generated API client is one example. How it works describes when Fuse adds that note.
  • fuse stop stops the current repository's engine. If the engine has not exited within 10 seconds of being asked, Fuse kills it. fuse stop --all stops every engine. The next command starts a new engine. Commands describes both forms.
  • fuse init --instructions also writes a marked Fuse section into AGENTS.md. It writes the same section into CLAUDE.md and GEMINI.md when those files exist. A later run replaces the section between the markers. Commands shows the section.
  • The latency suite's multi-agent scenario records stops, for repeated checks of every change, and tests, for two fuse test clients running at once. Evals describes both fields.

Changed #

  • The stop hook blocks only on errors caused by the stopping session's edits, whether those edits caused them alone or together with another session's edits. It also blocks on errors in changes no session is credited with. It counts the errors it leaves to other sessions. Once a subagent stops, its edits count as its parent's. In 5.3.0 the stop hook blocked on every error in the working tree. How it works describes how a session's errors are decided.
  • Test runs without MSBuild from several agents run at the same time. Each run uses its own copy, and fuse test releases the build lock while those runs execute. In 5.3.0 every fuse test waited for the run before it. How it works describes the copies, and Limits lists integration tests that can still collide.
  • When a check covers every change, it can keep a file's errors from an earlier check if nothing that file depends on has changed. A stop hook that checks many files again after a small fix therefore repeats only the work affected by that fix and its dependents. How it works describes when errors are kept.

Fixed #

  • After a build writes a generated file again, the next check reads the new contents. In 5.3.0 the engine kept the version from when the project loaded and could report errors the build had already fixed. How it works describes how generated files are refreshed.
  • If another agent moves a source file while fuse build is running and the build fails because that file is gone, Fuse runs the build once more and says that it did. The second run uses the file list as it stands then. Commands describes the retry.
  • A test run without MSBuild no longer keeps files in the repository's bin folder open. A build running at the same time no longer fails because Fuse holds one of its outputs. How it works describes the copy it runs from.

Documentation #

  • Subagents and parallel agents is a new page about several agents in one repository. The documentation explains session attribution at the stop hook, concurrent test runs, generated files that change during a build, and the build's slowest tasks and file log. Troubleshooting adds sections for a slow build, a failing command in the build and an error about generated code. Benchmarks quotes the 5.4.0 eval runs and adds repeated checks and tests at once.

5.2.2 #

Released 2026-10-02. Compared with 5.2.1.

Large test selections run only the selected tests instead of collapsing silently to whole classes or projects. A test plan also makes other agents' checks wait for less of its preparation. The benchmarks move to four open-source repositories and report the spread of every measured time.

Upgrading to 5.2.2 #

Update the tool with dotnet tool update -g Fuse. Nothing else needs to change, and fuse init does not need to run again. A script that reads the engine log's phase lines finds a test plan's preparation in two phases, mirror and emit, where 5.2.1 had mirror alone.

Changed #

  • A test plan holds the engine's request lock only while it syncs the tree and selects tests. It prepares copies for runs without MSBuild after releasing the lock. A check from another agent therefore no longer waits while a plan emits assemblies, although it still waits for that plan's sync and selection. An assembly unchanged since the previous plan is not emitted again.
  • The engine log's phase line splits test-plan preparation into mirror and emit. It also records gateHolder, which names what a request waited behind for the request lock. A script that read the old single preparation phase needs the new names.

Fixed #

  • For a large selection, fuse test passes the filter to dotnet test in a runsettings file, as RunConfiguration/TestCaseFilter with --settings, instead of on the command line. A selection of up to 2,000 test names runs only those tests. In 5.2.1 a filter longer than 8,000 characters was silently cut back to whole test classes, and a longer one to the whole project. Past 2,000 names the filter still collapses, but the summary says so and the engine log names the project.
  • A run without MSBuild uses the test project's own runsettings file, named by RunSettingsFilePath, with Fuse's filter added. That matches dotnet test on the project. In 5.2.1 a run without MSBuild ignored the project's file.
  • When reference search reaches a project that uses an analyzer the repository has not built yet, such as Jellyfin's own analyzer before its first build, a check leaves that analyzer out and answers. In 5.2.1 it answered internal error: Unexpected value 'Microsoft.CodeAnalysis.Diagnostics.UnresolvedAnalyzerReference'.
  • The pre-shell hook rewrites dotnet build and dotnet test after leading variable assignments. For example, DOTNET_CLI_UI_LANGUAGE=en dotnet test becomes DOTNET_CLI_UI_LANGUAGE=en fuse test. An assignment counts only when its value has no whitespace, quote, backtick, separator, redirection or parenthesis. For Codex, only plain values count. In 5.2.1 such a command was left unchanged.
  • A Microsoft.Testing.Platform run that exits with 8, the platform's code for a run in which no test ran, prints fuse: no test matched the dotnet test arguments (exit code 8) for fuse test with arguments, or fuse: the test run of <project> ran no test (exit code 8). 5.2.1 printed that the run exited with code 8 and produced no results.
  • A second fuse init prints unchanged <file> for a settings file that already holds what it would write, and leaves the file as it was. 5.2.1 printed wrote <file> and wrote it again.
  • fuse check no longer reports CS8795 for a [GeneratedRegex] method that names a culture, such as "en-US". The engine runs with invariant globalization, where the Regex source generator could not look the culture up and wrote no implementation. The same failure sent test projects that depend on such a project through MSBuild instead of running them without it.
  • The check summary counts every error the check found, in every file it found them in. 5.2.1 counted only the 200 errors the engine sends, so a change that broke 602 call sites in 3 files printed 200 error(s) introduced in 2 file(s).
  • A file whose only difference from HEAD is CRLF line endings inside a multi-line string constant, as a checkout with core.autocrlf writes it, has no declaration change, so the check stays within the file.
  • For a test project on Microsoft.Testing.Platform, which runs whole, the fuse test summary counts every test in the project, not only the tests the selection named.
  • When the stop hook sends an agent back for a missing restore, it sends the restore message alone. It no longer adds the line saying the changes introduced errors.
  • A stop payload whose loop_count is not a whole number that fits in 32 bits no longer makes the stop hook fail. In 5.2.1 the hook could fail on that value and let the agent finish unchecked.
  • A state directory that fuse build or fuse test created records its repository, so the daily cleanup removes it once the repository is gone, as it does the directory of a repository an engine served.
  • A client that finds an engine copy without its completion marker, such as one a cleanup deleted part of, makes the copy again, or runs the engine from a fresh copy beside it when the old one cannot be replaced. 5.2.1 ran the engine from the incomplete copy, so the engine could not start until the copy was deleted by hand.

Documentation #

  • The benchmarks measure four open-source repositories. FluentValidation, a small library, replaces the generated fixture beside NodaTime, Jellyfin and the Community Toolkit. In those results a check is 7.0x to 31.0x faster than dotnet build at the median and 2.5x to 5.3x faster over all 30 edits in each repository. fuse test is 1.3x to 3.7x faster than dotnet test. The dotnet test baseline is one run of the whole solution, as a user runs it, rather than one test project after another; that change lowered the test speedups.
  • The benchmarks page and chart give each command's fastest and slowest case, mean, standard deviation and P95 beside its median. The README, home page and sharing image quote the new ranges. They replace the fixture's 24.6x check figure and a 5.7x test figure in the README, which had been a time in seconds.

5.2.0 #

Released 2026-10-01. Compared with 5.1.0.

On Windows x64, Linux x64, Linux Arm64 and macOS Arm64, the fuse command is native code, so a hook does not start the .NET runtime before it sends its request. This release also reads results from Microsoft.Testing.Platform test projects. Two false passes are closed: fuse test with platform arguments no longer fails before running the tests, and a check that checked no files no longer reads as clean.

Upgrading from 5.1.0 #

  1. Update the tool: dotnet tool update -g Fuse. It installs the package for your platform, and on the four platforms above the fuse command becomes the native client.
  2. Do nothing else. The hook commands fuse init wrote are unchanged, so it does not need to run again. The first request from the 5.2.0 client reaches the running 5.1.0 engine, which answers with a restart and exits, and the client starts a 5.2.0 engine and sends the request again. No request fails.

Then check whether anything you run depends on these changes:

  • Microsoft.Testing.Platform output. A script or agent instruction that matched fuse: tests passed in T s for a test project on Microsoft.Testing.Platform gets fuse: 0 failed, P passed in T s, as for VSTest, and a failing run gets its failures instead of exited with code E and produced no results.
  • Your own packaging. A mirror or offline feed that copies the Fuse package needs the per-platform packages it points to as well; 5.2.1 names them.

Added #

  • On Windows x64, Linux x64, Linux Arm64 and macOS Arm64, the fuse command is the native client. It is compiled ahead of time to native code, so a hook or command starts no .NET runtime and compiles no code before it sends a request to the engine. The engine still runs on the .NET runtime from the fuse.dll installed with the client. On other platforms, including Windows Arm64, macOS x64 and Alpine, fuse runs fuse.dll as it did in 5.1.0. So do dotnet tool run fuse and tool manifests everywhere. How it works explains the two parts.
  • Each state directory holds a root file containing its repository's path. Once a day, a starting engine deletes state directories whose repository no longer exists and that nothing wrote to for a day. That removes state left by deleted temporary repositories, which 5.1.0 kept indefinitely. Where the logs are shows the state directory.

Changed #

  • The Fuse package points to one package per platform, and dotnet tool install and dotnet tool update choose the package for your platform: Fuse.win-x64, Fuse.linux-x64, Fuse.linux-arm64, Fuse.osx-arm64, Fuse.linux-musl-x64, Fuse.linux-musl-arm64 and Fuse.any. The Linux native clients run on glibc 2.27 and later. On Windows, the native client is the fuse.exe in the tools directory, so Git Bash, PowerShell and cmd all run it.
  • The build id in each request is the product version plus the module id of fuse.dll. The native client reads that module id from the fuse.dll installed with it. A running 5.1.0 engine answers the first 5.2.0 request by restarting, and the client starts a 5.2.0 engine, so the request does not fail.
  • In the native client, fuse engine <root> prints that the engine runs from fuse.dll on the .NET runtime and exits with 2. Clients start the engine; there is no supported reason to run that command by hand.
  • When a client starts the engine and has no runtime directory of its own, as the native client does not, it looks for the dotnet host on PATH if neither DOTNET_HOST_PATH nor DOTNET_ROOT names one.
  • For a test project on Microsoft.Testing.Platform, fuse test reads counts from the run summary and each failed test's message and stack frames from the run output. It answers in the VSTest form: a FAILED entry for each failure, then fuse: F failed, P passed in T s. In 5.1.0 a passing run printed fuse: tests passed in T s. A failing run printed the last 30 lines of output and exited with code E and produced no results. Commands shows the forms.
  • A starting engine deletes copies of other builds when no running engine holds them and they are more than ten minutes old. Each running engine marks its copy with a lock file. In 5.1.0 Fuse deleted only copies last written more than seven days earlier, so each build could leave a copy for a week.

Fixed #

  • In a repository whose global.json selects Microsoft.Testing.Platform, fuse test with arguments no longer adds VSTest's --logger, --results-directory, -nologo and -tl:off. This includes fuse test --filter-class Name, the form the pre-shell hook writes for dotnet test --filter-class Name. In 5.1.0 Fuse added the VSTest switches, so each such run failed with exit code 5 and ran no test.
  • Fuse decides whether dotnet test uses Microsoft.Testing.Platform from the test.runner value in the global.json nearest the working directory, searching up to the repository root. That is how the dotnet CLI reads it. In 5.1.0 Fuse read only the root global.json and treated any mention of the platform name as selecting it.
  • When every file named to fuse check or the fuse_check tool is one Fuse cannot check, such as a mistyped path or a file in another language, Fuse answers fuse: none of the files named in the check is a C# source file of a project in this repository: <files> and exits with 2. In 5.1.0 it answered fuse: no errors introduced (0 file(s) checked) and exited with 0, which read as a pass. InvalidPath gives the message.
  • A file renamed since HEAD is compared with the errors HEAD had under its old name. An error that existed before the rename is therefore not reported as introduced. Git status reports a rename as a deleted file and a new file; Fuse treats the new file as a rename of a deleted file when they share at least half their lines. In 5.1.0 it reported every error HEAD had in a renamed file as introduced.

5.1.0 #

Released 2026-09-29. Compared with 5.0.0.

The shell hook event is renamed to pre-shell, so repositories must run fuse init again. Errors in files the agent did not edit gain a cause line. Two agents can build in one repository without breaking each other's build, and several checks and selections that missed or over-selected in 5.0.0 are fixed.

Upgrading from 5.0.0 #

  1. Update the tool: dotnet tool update -g Fuse.
  2. Run fuse init again in each repository where you use Fuse. The hook event that rewrites dotnet build and dotnet test is pre-shell, and settings written by 5.0.0 call fuse hook <harness> pre-bash, which 5.1.0 answers with a usage line on standard error and exit code 0. Until you run fuse init, the harness runs dotnet build and dotnet test unchanged. fuse init replaces Fuse's own hook entries and keeps everything else (Running fuse init again). It also adds .fuse/ to .gitignore, so commit that change with the settings.
  3. Do nothing about the engine, the background process that answers every command. The first request from the 5.1.0 client reaches the running 5.0.0 engine, which answers with a restart and exits, and the client starts a 5.1.0 engine and sends the request again. No request fails (details).

Then check whether anything you run depends on these changes:

  • Codex approvals. For Codex, the pre-shell hook rewrites and approves only a command that is one dotnet build or dotnet test with plain arguments, and gives any other command no answer, so Codex asks you about it as usual. 5.0.0 rewrote dotnet build and dotnet test after any separator and approved the whole command line, so a command such as dotnet build && curl x | sh ran without your approval.
  • fuse test --all with other arguments prints an error, runs nothing and exits with 2. 5.0.0 dropped --all and ran what the other arguments named. Pass the arguments without --all to choose the scope.
  • Output text. A script or agent instruction that matches Fuse's output has to match the new wording:
Command5.0.0 printed5.1.0 prints

fuse checkno new errorsfuse: no errors introduced
fuse checkwhole projects boundchecked whole projects

A check compiles the edited files and the files that use a declaration the edit changed, and reports the errors HEAD did not have (How it works). Test selection picks the tests the changed code can reach (How it works).

Added #

  • fuse init adds .fuse/ to the root .gitignore, creating the file when there is none, unless a line already names the folder. The .fuse folder is reserved for files Fuse may keep in a repository, such as an index; 5.1.0 writes nothing there (The .fuse folder).
  • An error in a file the agent did not edit is followed by a cause line: changed: or removed: and the header, on one line, of the declaration change that put the file in the check, as the working tree has it or as HEAD had it. An answer holds at most ten cause lines, and the summary ends with N cause(s) left out when a printed error lost its cause to that cap.
  • fuse build and fuse test take a per-repository lock while they write build output. Two agents building or testing through Fuse therefore run one after the other instead of making MSBuild fail with MSB3021, MSB3027 or CS2012 on a file the other holds. A client that has to wait says so once on standard error. A client that cannot take the lock says why and runs anyway. The arguments fuse build passes to dotnet build, including its implicit restore, are unchanged. The build lock explains the order.
  • engine.log names every request by its kind, such as CheckFiles Calc.cs took 15 ms, and writes one line of per-phase times for it, so a slow check or test run can be traced to its phases (Reading a phase line).

Changed #

  • The hook event that rewrites dotnet build and dotnet test is pre-shell, and fuse init writes it for Claude Code, Gemini CLI, Codex and the OpenCode plugin.
  • fuse init and fuse mcp outside a git repository say fuse: not inside a git repository; Fuse compares your changes with HEAD, so it needs one, the message fuse check gives.
  • Test selection includes fewer tests that do not reach the change. Splitting a field declaration into two, or adding a variable to one, selects the tests that reach those fields rather than every test that reaches the type.
  • A formatting-only or comment-only edit inside a type header, parameter type or conversion no longer counts as a declaration change for test selection. An edit above a nested delegate does not count as a change to that delegate either.
  • The engine's pipe requests and responses have a different shape. An engine of another build, a running 5.0.0 engine included, answers the first request with a restart and exits, and the client starts an engine of its own build.

Fixed #

  • A hook and the MCP server read their input as UTF-8, so a repository whose path or file names are not ASCII is checked from a harness whose console uses another code page. 5.0.0 failed to parse the payload and reported nothing.
  • A hook payload that names an empty working directory runs in the harness's own working directory. In 5.0.0 that payload crashed the hook.
  • A hook payload that is valid JSON but not an object exits with 0 and no output, with a line in hook.log. That is how every other internal hook failure is handled.
  • A check compares declarations with each project's own preprocessor symbols, once per target framework, so a declaration change inside #if DEBUG or #if NET8_0_OR_GREATER checks the files that use it. 5.0.0 read such a region as inactive and reported no errors in its callers.
  • Removing a using directive checks the files that use the edited file's types, because the declarations' text is unchanged while what their type names resolve to is not. An added using still checks only the edited file.
  • Adding a constructor with parameters to a class that had only the implicit one checks every file that constructs the class, so each broken new C() is reported. 5.0.0 checked no other file.
  • A check finds a change to a type's parameterless constructor, such as making public C() internal, when a static constructor follows it in the file, which 5.0.0 missed. A formatting-only edit inside an explicit interface name no longer counts as a declaration change.
  • When a whole project is checked because more than 500 files are in reach, an analyzer error in an edited file is reported once. In 5.0.0 it could appear twice.
  • In the same whole-project check, file(s) checked counts each source file once. It no longer adds generated files or the same file again for a second target framework.
  • A file named to fuse check in another letter case than it has on disk, on Windows, is checked as the file git knows. 5.0.0 read it at HEAD under the other spelling, found nothing, and reported the errors HEAD has as introduced.
  • A file a hook names outside the repository is left out of that request's change set. In 5.0.0 it could make git fail and drop the request's other edits.
  • A file a hook names under bin or obj is left out of the change set. In 5.0.0 it could remove the generated file from the HEAD side of the check.
  • A project with a NuGet restore warning, such as a package advisory, is no longer reported as a project Fuse could not load, so Fuse answers in a repository whose restore logs a warning.
  • A restore needed answer names the project to restore in its command, so it also works for a project the solution leaves out.
  • Test selection selects tests reached by several edits it missed in 5.0.0. They are a body edit to an explicit interface implementation that shares its name and parameter types with another member, and an edit to a delegate declared at namespace level.
  • Changing a parameter modifier (ref, out, in, params or this) selects tests that reach the member. It also selects tests that reach the member's type, because callers may need the new modifier at the call site.
  • Changing class to struct, or record to record struct, selects the tests that reach that type. Test selection missed both forms in 5.0.0.
  • A change to the usings inside a namespace, and not only at the top of the file, selects the tests that reach the file's types.
  • When the test project's build output holds an older build of a project its tests load, a run without MSBuild emits the current project instead of running the older copy. This can happen after dotnet build Lib when Lib.Tests references Lib. In 5.0.0 a test that the working tree should fail could pass against the old copy.
  • When one test project does not build and others do run, fuse test prints the other projects' results first, then the failed project's build errors, and exits with 1. In 5.0.0 it printed only the projects that ran, so a passing project could hide the failed build.
  • fuse test --all with other arguments prints fuse: --all runs every test and cannot be combined with other arguments; pass the arguments without --all to choose the scope on standard error, runs nothing and exits with 2.
  • An analyzer or source generator the repository builds itself is loaded from a copy in the state directory, so a running engine no longer holds its file open and a real build that rebuilds it no longer fails with MSB3021 or MSB3027.
  • If a check arrives just as the engine finishes loading a dependent project in the background, the check includes that project. In 5.0.0 it could see the project as loaded but leave it out of the check, missing errors there.
  • A request that a hook gives up on while projects load no longer leaves those projects out of later checks. In 5.0.0 every later check of their files said no errors introduced until the next reload.
  • After a commit or branch switch, a re-evaluation that a cancelled or failed request left undone is finished by the next request, and the baseline is read at the new HEAD. In 5.0.0 later checks compared with the old HEAD and reported errors HEAD has as introduced.
  • When git status fails while the engine reads the changes again, after HEAD moved, a watcher error or more than 300 changed files, the engine keeps HEAD and the changed files it knew, and the next request asks git again. 5.0.0 had already taken the new HEAD and emptied its list of changed files, so later checks left out the files changed before the failure.
  • Git's file list and status are read NUL-separated, so a file whose name holds a quote, a backslash or a control character is found and checked under its own name.
  • Renaming, moving or deleting a folder whose name holds a dot, such as Company.Feature, is followed like any other folder, and a project file that moved with it re-evaluates the projects.
  • A project that fails to load in the background is tried again after the projects reload or a restore, and only one background load runs at a time.

Security #

  • For Codex, whose answer to the pre-shell hook also approves the command, the hook rewrites only a command that is one dotnet build or dotnet test with plain arguments (Codex).

5.0.0 #

Released 2026-09-25.

5.0.0 is a complete rewrite. It shares the name and the NuGet package with Fuse 4.x and nothing else. No command, file, setting or MCP tool of 4.x carries over, 5.x reads nothing 4.x wrote, and there is no migration path. Treat 5.0.0 as a new tool: remove what 4.x left in your repositories (Moving from 4.x) and set Fuse up again with fuse init.

Fuse 5 keeps a warm Roslyn compilation of a .NET repository and gives coding agents the compiler errors their edits introduced, affected-test runs, and compact build output, through agent hooks and a three-tool MCP server.

Added #

  • fuse init registers hooks for the harnesses a repository uses: Claude Code, Cursor, Gemini CLI, Codex and GitHub Copilot CLI. It registers a plugin with OpenCode and the MCP server with VS Code.
  • fuse hook <harness> <event> runs the hook events. A post-edit check reports only introduced errors. A pre-shell hook rewrites dotnet build and dotnet test to their Fuse equivalents. A stop check sends the agent back once while its changes leave errors HEAD did not have.
  • fuse check reports errors in the working tree that HEAD did not have, including breaks in dependent projects. It includes errors from analyzers that can report an error.
  • fuse test runs the tests the changes can reach. When it is safe, it runs them from a shadow copy of the last build with changed assemblies emitted in memory. fuse test --all runs everything. With dotnet test arguments, it runs exactly that scope. The output lists failures only.
  • fuse build runs dotnet build and prints only errors.
  • fuse mcp serves fuse_check, fuse_test and fuse_build.
  • One engine runs per repository. It starts on demand, runs from a private copy of its binaries, and exits after 30 idle minutes. There is nothing to configure. Fuse writes nothing inside the repository except the hook settings that fuse init creates.

Moving from 4.x #

Fuse 4.x was an indexer: it kept an index of the repository in a .fuse folder and served its own MCP tools. Fuse 5 uses none of what 4.x wrote. Most of it is only unused files, but two entries still act on your agent, so remove all of it:

  1. Update the tool: dotnet tool update -g Fuse.
  2. In each repository, remove what 4.x wrote, as the table below lists.
  3. Run fuse init in each repository to register the 5.x hooks (Connect your agent).
What 4.x wroteWhereWhat to do
The .fuse folder, which held the 4.x index fuse.dbThe repository rootDelete the folder. Fuse 5 neither reads nor writes it; left in place, it is residue that takes disk space and does nothing. Keep the .fuse/ line in .gitignore: from 5.1.0, fuse init adds it when it is missing, because the folder is reserved for files a later Fuse may keep there.
fuse.jsonThe repository root, usually committedDelete it. Fuse 5 has no configuration file.
Claude Code hooks running fuse check --delta --fast and fuse gate.claude/settings.jsonDelete both entries. fuse init does not, because it replaces only commands that start with fuse hook. Under Fuse 5, fuse gate prints the usage text and exits with 2, which Claude Code takes as a stop hook refusing to let the agent finish.
A guidance block that starts with <!-- fuse:begin and a 4.x version, such as <!-- fuse:begin v4.4 -->, and ends with <!-- fuse:end -->CLAUDE.md, AGENTS.md or .github/copilot-instructions.md, and for a user-scope install ~/.claude/CLAUDE.md or the AGENTS.md in the Codex, OpenCode or Kilo Code configuration folder; for Cursor, the file .cursor/rules/fuse.mdcDelete the block, markers included, and delete .cursor/rules/fuse.mdc whole. A script or CI step that runs a 4.x command has to be rewritten against Commands. Fuse 5 has no fuse index, fuse find or fuse mcp install, and its fuse check and fuse test take other arguments and print other output than the 4.x commands of the same names.

Versions before 5.0.0 #

Fuse 1.0.0 to 4.4.0, released from 2026-04-09 to 2026-07-30, are deprecated. They get no fixes, security fixes included, and no support, and this documentation does not describe them. Their release notes stay on the GitHub releases page and in CHANGELOG.md at v4.4.0. To leave one, follow Moving from 4.x.
