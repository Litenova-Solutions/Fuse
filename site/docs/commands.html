Commands

All documentation pages

Every fuse command takes arguments, prints an answer, and exits with a code. This page lists all three for each command. When a command cannot answer, its message is listed in Messages and fixes.

This page is for you when you read what Fuse printed, whether you ran the command yourself or you look at what a hook sent your agent, and when you script Fuse or connect it to another tool.

Before it, Getting started sets Fuse up in your repository and shows what the common commands print.

In short

  • Three commands do the work. check reports the errors your changes introduced, test runs the tests your changes affect, and build runs the real build and prints only its errors.
  • Every command works on the git repository that holds your current directory, compares the working tree with HEAD, and reads no configuration.
  • When Fuse answered and found nothing to fix, the exit code is 0. When it answered and found something to fix, it is 1. When it could not answer, it is 2.
  • Hooks and the MCP server give agents the same text the commands print, without the tree stamp. What you see in a terminal is therefore what the agent reads.

Overview #

fuse is one executable. check, test and build are its three operations. init sets a repository up, uninit takes Fuse out of it again, status shows the engine and the changed files, session registers an external writer as a session, and stop stops the engine. hook runs the operations for a harness, and mcp serves them to an MCP host. Both give the same text the command line prints, so what you see in a terminal is what the agent reads.

Every command works on the git repository that holds your current directory. A hook instead works on the repository of the files its payload names. Each command compares the working tree, the files on disk, with HEAD, the commit you have checked out, and reads no configuration.

$ fuse help
fuse - faster .NET build and test loop for AI coding agents

  fuse init [--instructions]  register Fuse's hooks with the agent harnesses this repository uses
                            (--instructions: also add a Fuse section to AGENTS.md)
  fuse uninit               remove what fuse init wrote, stop this repository's engine and delete its state
  fuse check [files...] [--max-errors <n>|--all-errors] [--json]
                            errors the working tree has that HEAD does not, across dependent projects
  fuse test [args...]       run the tests affected by your changes (with args: the tests those dotnet test arguments name)
  fuse test --all           run every test
  fuse test --failed        rerun the tests that failed in the last recorded run
  fuse build [args...] [--max-errors <n>|--all-errors] [--json] [--warnings] [--changed]
                            dotnet build, printing its errors
  fuse status [--json]      show the engine and the changed files
  fuse session begin <name> --paths <pattern> [<pattern>...]
                            register an external writer as a session for its path patterns
  fuse session end <name>   end the registration
  fuse stop [--all]         stop this repository's engine (--all: every engine); the next command starts one
  fuse mcp                  stdio MCP server (fuse_check, fuse_test, fuse_build) for MCP hosts that run no hooks
  fuse hook <harness> <event>   the command registered hooks run

Exit codes #

The exit code tells your script, or a harness, which of three things happened. Either Fuse answered and all is well, Fuse answered and something needs fixing, or Fuse could not answer.

CodeMeaning
0Fuse answered and found nothing to fix: no errors introduced, the tests passed, or the build succeeded.
1Fuse answered and found something to fix: errors introduced, a test failed, or a build failed.
2Fuse could not answer, so the output says why and what to run, as Messages and fixes lists. A usage failure also exits with 2 and prints the usage on standard error (Usage failures), for example an unknown command or option, or a flag combined with arguments it cannot take.
130Ctrl+C stopped the command.

fuse hook exits with 0 in every case but one. The Claude Code post-edit hook exits with 2 to wake the agent, as fuse hook describes.

fuse init #

This command registers Fuse's hooks with every harness your repository uses, and the MCP server with VS Code. It also adds .fuse/ to the root .gitignore (The .fuse folder). It detects a harness by its folder or file in the repository root, and when it finds none it sets up Claude Code. Connect your agent lists what it detects and writes, and what happens when you run it again.

$ fuse init
wrote .claude/settings.json
wrote .gitignore
fuse: hooks registered by Fuse 5.7.0; after each edit your agent gets the compiler errors the edit introduced, `dotnet test` runs the affected tests, and `dotnet build` prints only its errors

Outside a git repository, and in a repository where git knows no .csproj file, it exits with 2. It also exits with 2 when a settings file it has to change is not valid JSON (fuse: <file> is not valid JSON (<reason>); fix or remove it, leaving the file as it was) or cannot be written (fuse: could not write <file> (<reason>), leaving no temporary file). It first prints the wrote lines for the files it wrote before the failure.

A settings file that is empty, or that holds only comments, counts as an empty object. The closing line names the Fuse version that registered the hooks. When you run the command again after an upgrade, it prints the new version even when every file is unchanged.

fuse init --instructions #

This flag also writes a Fuse section into the instruction files your agents read, so an agent knows the commands before a hook first answers it. The section goes into AGENTS.md, which the command creates when your repository has none. It also goes into CLAUDE.md when that file exists and does not import @AGENTS.md, because Claude Code reads CLAUDE.md, and into GEMINI.md when that file exists. The section sits between the lines <!-- fuse:begin --> and <!-- fuse:end -->. A file without them gets the section at its end. Running the command again replaces only what sits between them and keeps the file's line endings. Subagents and parallel agents shows the section.

$ fuse init --instructions
wrote .claude/settings.json
unchanged .gitignore
wrote AGENTS.md
wrote CLAUDE.md
fuse: hooks registered by Fuse 5.7.0; after each edit your agent gets the compiler errors the edit introduced, `dotnet test` runs the affected tests, and `dotnet build` prints only its errors

When a file's section is already current, the command prints unchanged for it, as it does for a settings file. Any other argument prints usage: fuse init [--instructions] and exits with 2.

fuse uninit #

This command removes what fuse init and fuse init --instructions wrote. It covers every harness, whether your repository still uses it or not. It then stops your repository's engine and deletes its state directory (where it is).

  • In a shared settings file, it takes out only the handlers that run fuse hook. In Claude Code's settings it also takes out the Bash(fuse build:*) and Bash(fuse test:*) permissions. Every other entry stays, and the command deletes a file left with nothing in it.
  • The files that belong to Fuse are deleted whole: .github/hooks/fuse.json, .opencode/plugins/fuse.js and the Muse Code bundle .muse/plugins/fuse.
  • It also takes the fuse server out of .vscode/mcp.json, the .fuse/ line out of .gitignore, and the section between <!-- fuse:begin --> and <!-- fuse:end --> out of AGENTS.md, CLAUDE.md and GEMINI.md. It deletes a file that held nothing else.

The command also deletes a folder the deletions leave empty. Session registrations are deleted with the state directory.

$ fuse uninit
wrote .claude/settings.json
deleted .gitignore
deleted AGENTS.md
fuse: stopped the engine for /home/you/shop
fuse: deleted the engine's state in /home/you/.local/share/fuse/repos/3f2a9c1d7e5b8a60
fuse: removed Fuse from this repository; `dotnet tool uninstall -g Fuse` removes the tool itself

Muse Code keeps its own copy of a plugin it installed. After removing the bundle, the command therefore also prints fuse: Muse Code keeps the plugin it installed: run `muse plugins remove fuse` once. In a repository with nothing fuse init wrote, it changes no file and prints fuse: this repository has nothing fuse init wrote.

When no engine runs, the stop line reads fuse: no engine runs for <root>. When the state is already gone, the command prints fuse: no engine state to delete. When the state cannot be deleted, it prints fuse: could not delete the engine's state in <state> (<reason>); delete it once no fuse command runs.

Outside a git repository it exits with 2. It also exits with 2 when a settings file it has to change is not valid JSON or cannot be written, with the same messages as fuse init. Any argument prints usage: fuse uninit and exits with 2. The fuse tool stays installed. To remove it, run dotnet tool uninstall -g Fuse.

fuse check #

fuse check [files...] [--max-errors <n>|--all-errors] [--json]

This command reports the compiler errors the working tree has that HEAD does not. It covers the checked files, and every file in the same project or a dependent one that uses a declaration the checked files changed.

  • Without files, it checks every source file (.cs, .razor, .cshtml) that differs from HEAD: modified, added, or deleted. Added covers untracked files that git does not ignore. Files under bin, obj, .git and node_modules are skipped.
  • With files, it checks those files. Give a path relative to your current directory, or an absolute path. A named file is checked even when it matches HEAD. The command leaves out a file that is not a source file, or that no project owns. When none of the named files is a source file a project owns, the check is refused (InvalidPath).
  • With a directory or a pattern, it checks a scope. An argument that is a directory that exists, or that holds * or ?, scopes the whole call. The check then covers the changed sources under each directory and pattern, the named files alongside them, and what they reach. A directory or pattern matches within the changed sources, while a file is taken as named. Every directory, pattern and file must match at least one C# source a project owns. One that matches none refuses the whole call, as does an expansion past the 2000 sources one scoped check covers (InvalidPath).

Three flags shape the answer.

  • --max-errors <n> shows at most n errors, where n counts from 1 to 100000. Without a flag the command prints the first 20.
  • --all-errors shows every error, and cannot be combined with --max-errors.
  • --json prints one JSON object per error instead of text lines, with the summary as the last line.

Without a flag the engine sends at most 200 errors. --max-errors <n> sends and prints at most n. --all-errors and --json send and print every error.

After -- every token is a file, even one that looks like an option. The command refuses an unknown option, a bad count, and a combined pair on standard error with the usage, and exits with 2 (Usage failures). --warnings is not a check flag. For warnings, run fuse build --warnings.

The command waits up to 10 minutes for the engine to finish loading the repository. How it works describes what the check does.

$ fuse check
removed: public int Add(int a, int b) (2 error(s))
App/Program.cs(3,30): error CS1061: 'Calc' does not contain a definition for 'Add' and no accessible extension method 'Add' accepting a first argument of type 'Calc' could be found (are you missing a using directive or an assembly reference?)
Lib.Tests/CalcTests.cs(6,54): error CS1061: 'Calc' does not contain a definition for 'Add' and no accessible extension method 'Add' accepting a first argument of type 'Calc' could be found (are you missing a using directive or an assembly reference?)
fuse: 2 error(s) introduced in 2 file(s) (App, Lib.Tests); Lib declarations changed, 2 dependent project(s) checked; tree 9f2c41aa07b3 over 3 changed file(s)

Reading the output #

The output has four kinds of line.

  • Error lines, one per introduced error, as path(line,column): error ID: message, with the path relative to the repository root and forward slashes. This is the format dotnet build uses, so tools that read build errors read these too. The engine returns at most 200 errors, ordered by file and position. The command prints the first 20, or what the flags say.

    Every check also writes every error it was sent to last-check-results.txt in the state directory. The file is replaced each time, so you can read the rest there. Its first line is fuse check: N error(s) introduced with the tree stamp the summary carries. Then comes every error flat, without group headers, and ... and N more error(s) the engine did not send when the engine held errors back.

  • Group headers and cause lines. Errors that share a cause print under one header, removed|changed: <declaration> (N error(s)). The members print as plain error lines without a cause of their own. When more errors were found than fit, each group first shows up to two members, and its header counts what it holds back as (N error(s), first M shown). Ungrouped errors fill the rest.

    An error with no shared cause keeps its cause line. The line is indented by two spaces and holds the declaration on one line without its body: changed: with the changed declaration as the working tree has it, or removed: with the removed declaration as HEAD had it. A field is quoted as its modifiers, type and name, as in changed: public long Limit, and a constant with its value.

    An error in a checked file itself gets no cause line, and neither does an analyzer error. When any change in the check can break code without naming it (a type header, a delegate, a global using or an assembly attribute), no error in the answer gets one. Past the group headers the answer holds at most ten cause lines.

  • Generated lines, indented by two spaces under an error about a type or member that a file the build generates declares, once per file. Each reads generated: <path> declares it, and Fuse reads that file as the last build wrote it; if it is generated from changed code, run fuse build to write it again (errors about generated code).
  • The summary line, last, in one of two forms:
    • fuse: N error(s) introduced in M file(s), followed by , first P shown when more were found than fit, then the projects the errors are in, in parentheses. Then come the parts below, ; checked <paths> and what it reaches for a scoped check, ; tree <hash> over C changed file(s), and ; all N in <path>, which names the results file when errors were left out. N, M and the projects count every error the check found, including those past what the engine sent. A --json summary never names the results file, because the objects above it already hold every error.
    • fuse: no errors introduced (F file(s) checked), where F counts the checked files and the files the check reached. A scoped check instead reads fuse: no errors introduced in <paths> and what it reaches (F file(s) checked). An answer to a session with other sessions' errors left out reads fuse: no errors introduced by this session's edits (F file(s) checked; ...).

The summary ends with any of these parts, separated by semicolons. In the second form they sit inside the parentheses, after F file(s) checked, as in fuse: no errors introduced (3 file(s) checked; Lib declarations changed, 2 dependent project(s) checked; tree 9f2c41aa07b3 over 3 changed file(s)).

PartMeaning
P declarations changed, K dependent project(s) checkedThe projects where a checked file changed a declaration, and how many projects that depend on them the check searched.
checked whole projects: Lib because Lib/Calc.cs (removed: ...)More than 500 files were in reach, so the check compiled the reached projects whole. It names up to 3 projects with up to 2 of the changed files that forced each and their causes. What does not fit counts as ; and N more in the engine log.
C cause(s) left outMore than ten printed errors had a cause past the group headers, so C of them print without one.
left out N analyzer(s) that read the whole project, which the stop hook and fuse check run: AOnly the post-edit hook prints this part. It left out the compilation-wide analyzers A.
analyzers did not finish in N file(s) or project(s) in time, ...The check stopped its analyzers before its client's wait ran out, so analyzer errors in N files or projects may be missing. Their compiler errors are complete.
errors in N file(s) not compared with other sessions' edits, ...The errors in N files were reported without being attributed to sessions, so some of them may be other sessions'.
N non-C# file(s) changed, which Fuse does not check: <paths>The changed files Fuse does not check. This part comes last on clean and error answers alike, and names the first 5 paths, counting the rest as ... and M more. With named files it still covers the whole tree, not the named scope.

After the parts, every fuse check summary names the tree the command ended on: ; tree <12 hex> over N changed file(s). On a clean answer it sits inside the parentheses. Hook and MCP answers carry no stamp.

With --json each error prints as one JSON object with file, line, column, code and message. It adds cause when the error has one, and generated when a generated file declares what the error is about. line and column are left out for a general error. The results file is still written:

$ fuse check --json
{"file":"App/Program.cs","line":3,"column":30,"code":"CS1061","message":"'Calc' does not contain a definition for 'Add' and no accessible extension method 'Add' accepting a first argument of type 'Calc' could be found (are you missing a using directive or an assembly reference?)","cause":"removed: public int Add(int a, int b)"}
fuse: 1 error(s) introduced in 1 file(s) (App); tree 9f2c41aa07b3 over 3 changed file(s)

An error counts as introduced when HEAD has fewer errors with the same file, id and message than the working tree. Line numbers are ignored, so an error that only moved is not reported. A file renamed since HEAD is compared with the errors HEAD had under its old name. Errors are compiler errors, warnings the project treats as errors, and analyzer diagnostics at error severity. Warnings are not reported.

When an error was introduced, the exit code is 1. When none was, it is 0. When Fuse could not answer or the arguments did not parse, it is 2.

fuse test #

fuse test
fuse test --all
fuse test --failed
fuse test [dotnet test arguments]

This command runs tests and prints only the failures. It has four forms.

  • fuse test runs the tests affected by the working-tree changes, which are the tests the changed code can reach, as How it works describes. When a test project has build output and only C# sources changed since, it runs without MSBuild.
  • fuse test --all runs every test project whole, and builds each with MSBuild. Test projects that need a container runtime are left out when none answers, and the summary names them.
  • fuse test --failed reruns the tests that failed in the last recorded run.
    • It cannot be combined with --all or any other argument. With one, it prints fuse: --failed reruns the tests that failed last time and cannot be combined with other arguments; pass the arguments without --failed to choose the scope on standard error, runs nothing, and exits with 2.
    • When no run is recorded yet, it prints fuse: no test run is recorded yet; run fuse test first and exits with 2.
    • When the last run came from your own dotnet test arguments, it prints fuse: the last test run was from dotnet test arguments, so its failures cannot be rerun; run fuse test and exits with 2.
    • When the last run had no failures, it prints fuse: the last test run had no failures and exits with 0.
    • When the failed tests are in no test project of the repository anymore, it prints fuse: none of the tests that failed last time is in a test project in this repository and exits with 2 (No failures to rerun).

    On success the summary reads reran N test(s) that failed last time in M test project(s). It adds a ; left out X, which is not a test project in this repository clause per project that no longer is one, and the filter clauses below when the rerun widened.

    When none of the recorded failures still runs, it prints fuse: none of the N test(s) that failed last time ran; they may have been renamed or removed and exits with 1.

  • fuse test with dotnet test arguments runs what the arguments name, as follows.
    • Arguments that only say where the tests are and how to build them run the first form, limited to the test projects the paths name, which the summary names. These are a directory, a project file or a solution file, or --project and --solution; -c and --configuration; -f and --framework; --no-build; --no-restore; -v and --verbosity; --nologo and -nologo; -tl and its values.
    • When you pass a configuration or a framework, every run builds with MSBuild.
    • When a path names no test project, the command is refused with fuse: none of the paths given names a test project in this repository: <paths> and exit code 2.
    • With any other argument, the command runs dotnet test with those arguments in the current directory and adds result reporting. On Microsoft.Testing.Platform, a first argument that names a directory, a project file or a solution file is passed as --project or --solution, the form it requires, while on VSTest it stays positional. A --results-directory value is passed as a full path, with a Git Bash spelling such as /c/... read as its Windows path. Every other argument passes unchanged.
    • After the first --, no token is read as a Fuse option, even --all and --failed, and the -- itself is stripped. For example, fuse test -- --all runs dotnet test --all with that argument.
    • --all cannot be combined with other arguments. For example, fuse test --all --filter Name=A prints fuse: --all runs every test and cannot be combined with other arguments; pass the arguments without --all to choose the scope on standard error, runs nothing, and exits with 2.
    • A near miss of a Fuse option is refused with fuse: '<token>' is not a fuse test option; did you mean '<option>'? on standard error with the usage, exiting with 2. Every other token goes to dotnet test.

Every form takes the build lock. Runs without MSBuild each run from a copy of their own, and give the lock up while they run, so test runs from several agents run at the same time. Runs with MSBuild hold the lock until their last dotnet test process exits. The affected, --all and --failed forms wait up to 10 minutes for the engine's plan. A client that waits for the lock ends on Ctrl+C only once the lock is free.

When the pre-shell hook rewrote your command, the command first prints a notice on standard error: fuse: dotnet test routed to fuse test (tests affected by your changes; fuse test --all runs every test). A fuse test you typed prints none.

$ fuse test
FAILED Lib.Tests.CalcTests.Multiplies
  Assert.Equal() Failure: Values differ
  Expected: 6
  Actual:   7
  at Lib.Tests.CalcTests.Multiplies() in Lib.Tests/CalcTests.cs:line 9
fuse: 1 failed, 0 passed in 2.8 s; ran 1 test(s) affected by your changes out of 2; fuse test --all runs everything; without MSBuild

Reading the output #

Each failed test prints FAILED and its name, then its message (up to 12 lines) and up to five stack frames inside the repository, indented by two spaces. Failures that share their message's first line print under one N failure(s) with the same first message line: ... header, which cuts the line at 160 characters. The members keep their full text.

The first 10 failures print in detail. The next 100 print by name only, under also failed (N):. A line ... and N more counts the rest.

Every test run also writes all its failures, grouped by project, to last-test-results.txt in the state directory. The file is replaced each time, and holds the failures flat and without group headers. When failures or names were left out, the summary ends with ; all F in <path> naming it. Beside it, last-test-results.json holds the run projects with their absolute paths and each test's verdict and duration, failures first, at most 20,000 tests. It serves fuse test --failed and the runs that put failures first. A file that cannot be read counts as no record.

The summary line is fuse: F failed, P passed in X.X s, with , S skipped added when tests were skipped. Then comes what ran, then how it ran.

What ranWhen
ran N test(s) affected by your changes out of T; fuse test --all runs everythingfuse test
ran every test in N test project(s)fuse test --all
reran N test(s) that failed last time in M test project(s)fuse test --failed
ran the tests your dotnet test arguments namefuse test with arguments

When the pre-shell hook rewrote the command, it passed the agent's session with --session. The plan then leaves out the changes only other sessions wrote (a session's own tests). The first form adds ; left out N changed file(s) only other sessions wrote before ; fuse test --all runs everything. When nothing is left, it prints fuse: no C# changes by this session since HEAD, so no test is affected; left out N changed file(s) only other sessions wrote (fuse test --all runs everything). You do not pass --session yourself. Without it the plan covers every change.

Test projects that need a container runtime are left out of the affected and --all plans when none answers. The summary names them: ; skipped N test(s) in P1, P2 (no container runtime). A project needs a container runtime when any of its package references is Testcontainers or starts with Testcontainers.. Runs from your own dotnet test arguments pass to dotnet test verbatim, with no pre-flight.

On the command line, when the last recorded run left 1 to 100 failures inside a VSTest method selection, those tests run first as their own stage, and their failures print before the rest runs. The final summary counts each test once. A project whose recorded failures name theory rows, a platform run, and a whole-project run stay one stage.

N and T count test methods from source, by test attribute, without running test discovery. The failed and passed counts come from the test run. When a test project runs whole, the first form adds the reason in parentheses, for example (whole projects where App uses the changed code and runs behind an application host). The reasons are:

  • <application> uses the changed code and runs behind an application host
  • <application>'s entry point calls the changed code
  • <member> is called by an application host or a framework
  • top-level statements changed
  • <file> changed, for a Razor file
  • a test file without classes changed
  • a test project changed outside any class
  • <project> runs on a test framework Fuse cannot filter, for a Microsoft.Testing.Platform project whose framework Fuse does not know

When a selection held more names than a filter carries, the summary says what ran instead: ; ran whole test classes in Lib.Tests, because a test filter holds at most 2000 names. A platform filter holds 200 names.

How it ran is without MSBuild, without MSBuild for N of M project(s) or built with MSBuild. The form with arguments leaves it out.

When no test runs, or a test project does not build #

When no test runs, the command prints one of these lines and exits with 0:

fuse: no C# changes since HEAD, so no test is affected (fuse test --all runs everything)
fuse: no test is affected by the changes (out of T); fuse test --all runs everything
fuse: no test is affected by the changes (out of T); the changes compile to the same code as HEAD; fuse test --all runs everything
fuse: no test projects in this repository

When every selected test needs a container runtime and none answers, the command starts no process, prints fuse: no test ran: N test(s) selected in P need a container runtime, and none is running; start Docker or Podman and run fuse test again, and exits with 1.

When a test project does not build, the command prints the build's errors and fuse: test build failed with N error(s) in T s in the format of fuse build, and exits with 1. When other test projects ran, their results come first and each failed build follows them. The last line is therefore the failed build, even when every test that ran passed.

A test project on Microsoft.Testing.Platform writes no TRX file. Fuse therefore reads the counts from the run summary it prints, and each failed test's message and stack frames from its output. The answer has the same form as above. The project runs with its framework's own filter. Without the global.json opt-in, Fuse builds it, then starts its test application directly, once per target framework.

A project with a .NET Framework target runs through dotnet test instead, because that target has no runtimeconfig.json to start it from. So does a project whose started target exits without printing results. A filtered run that ran no test is answered as a run that exits with 8, below. In a repository whose global.json selects Microsoft.Testing.Platform, fuse test with arguments passes them on without VSTest's logger options, which the test application would reject.

Three kinds of run print the last 30 lines of the output and fuse: the test run of <project> exited with code E and produced no results in T s, and exit with 1: a run whose summary counts an error, such as an argument the test application rejects; a run that printed no summary; and any test run that exits with a code other than 0 without results and without an error line. For fuse test with arguments the line names the run dotnet test and appends (no result file in <dir>).

A passing run without a summary prints fuse: tests passed in T s; and the summary. A run that exits with 8, the platform's code for a run in which no test ran, prints only one line and exits with 1: fuse: no test matched the dotnet test arguments (exit code 8) for fuse test with arguments, or fuse: the test run of <project> ran no test (exit code 8).

The exit code is 1 when a test failed, a test project did not build, or the run was blocked. It is 0 when the tests passed or no test was affected, and 2 when Fuse could not answer or the arguments did not parse.

fuse build #

fuse build [dotnet build arguments] [--max-errors <n>|--all-errors] [--json] [--warnings] [--changed]

This command runs the real dotnet build in your current directory with the arguments unchanged, implicit restore included. It adds -nologo -tl:off -v:q -clp:ErrorsOnly;NoSummary so that MSBuild prints only errors. It also adds a file log with -fl9 and -flp9, which it reads and deletes. Inside a repository it takes the build lock. Outside one it runs without it.

Its own options are --max-errors <n>, --all-errors, --json, --warnings and --changed. They shape the answer and never reach dotnet build.

  • --max-errors <n> shows at most n errors, where n counts from 1 to 100000. Without a flag the command prints the first 20.
  • --all-errors shows every error, and cannot be combined with --max-errors.
  • --json prints one JSON object per error instead of text lines, with the summary as the last line.

Every other argument goes to dotnet build unchanged, as does every token after --, even one that looks like a Fuse option. A near miss of a Fuse option, a bad count, and a combined pair are refused on standard error with the usage, exiting with 2 (Usage failures). The near miss reads fuse: '<token>' is not a fuse build option; did you mean '<option>'?.

When the pre-shell hook rewrote your command, the command first prints a notice on standard error: fuse: dotnet build routed to fuse build (first 20 errors; fuse build --all-errors for every error). A fuse build you typed prints none.

$ fuse build
App/Program.cs(3,30): error CS1061: 'Calc' does not contain a definition for 'Add' and no accessible extension method 'Add' accepting a first argument of type 'Calc' could be found (are you missing a using directive or an assembly reference?)
Lib.Tests/CalcTests.cs(6,54): error CS1061: 'Calc' does not contain a definition for 'Add' and no accessible extension method 'Add' accepting a first argument of type 'Calc' could be found (are you missing a using directive or an assembly reference?)
fuse: build failed with 2 error(s) in 1.1 s; tree 9f2c41aa07b3 over 3 changed file(s)

Unlike fuse check, this is the whole build. It reports every error the solution has, including errors HEAD already has. It prints each error once, with its path relative to the repository root and without MSBuild's trailing project tag: up to 20 of them, or what --max-errors and --all-errors say. The last line is one of:

  • fuse: build succeeded in T s
  • fuse: build failed with N error(s) in T s, with , first M shown when more were found than fit
  • fuse: build failed (exit code E) in T s, after the last 30 lines of the build's output, when the build failed and no line of its output parses as an error

Each form ends with ; N warning(s) when the build logged warnings. On builds of 10 seconds or more it adds the slowest-tasks part below. It ends with ; tree <hash> over C changed file(s), naming the tree the command ended on. When errors were left out, it also names the results file: ; all N in <path>. A --json summary never names the results file, because the objects above it already hold every error.

A build of 10 seconds or more adds the three slowest tasks summed over every project and the three slowest projects, in parentheses after the warning count. In this example of the format, the build spent its time compiling:

fuse: build succeeded in 95.0 s (slowest tasks summed over projects: Csc 120.4 s, ResolveAssemblyReference 6.2 s, Copy 3.1 s; slowest projects: Api 60.2 s, Api.Tests 41.0 s, Domain 20.5 s)

Under an error MSB3073, which says that a command a target ran exited with a code other than 0, the answer prints the last lines the command printed. It prints at most 20, indented by two spaces, such as a generator's exception and its first stack frame:

Api/Api.csproj(40,5): error MSB3073: The command "dotnet getdocument --assembly Api.dll" exited with code 11.
  Generating document named 'v1'.
  System.InvalidOperationException: Duplicate audit action 'Create' on AuditController.
     at Api.Audit.Register(String action) in Api/Audit.cs:line 12
fuse: build failed with 1 error(s) in 14.2 s

Under an error for a file another process holds open (MSB3021, MSB3026 or MSB3027), the answer prints who holds it and what to do, indented by two spaces. It prints locked: <file> is held by <name> (pid <n>); stop that process, then run the build again. When the holder is a build server, it prints locked: <file> is held by <name> (pid <n>), a build server; run dotnet build-server shutdown, then run the build again instead. When MSBuild names no holder, it prints locked: <file> is being used by another process; stop the running application or build that holds it, then run the build again. --json omits the line and carries the holder as lockedBy instead.

When the build fails with CS2001 on a source file that no longer exists, because another agent moved it while the build ran, the command runs the build once more. It prints fuse: a source file moved while the build ran, so it ran again above the answer. How it works describes the file log.

--warnings lists the warnings after the errors, each indented by two spaces, up to 20 of them. The rest count as ... N more warning(s) in <path>, naming the results file, or ... N more warning(s) not shown outside a repository. A warning that is also an error prints once, as an error. Without the flag, warnings are only counted in the summary.

Every build writes every error and warning to last-build-results.txt in the state directory. The file is replaced each time. Its first line is fuse build: N error(s) with the tree stamp the summary carries. Then comes every error and, under ## warnings, every warning. With --json the errors are also written as JSON lines to last-build-results.json.

With --json each error prints as one JSON object with file, code and message. It adds line and column except for general errors, and lockedBy as <name> (pid <n>) when another process holds the file. A failed build with no parseable error prints the output tail before the summary, as text mode does. With --warnings the warnings still print as text lines.

With --changed the command builds only the projects that own files changed since HEAD and their dependents, reduced to the highest projects. It runs one dotnet build per project under one lock, each with the same extra arguments. It first prints what it builds: fuse: building M project(s) for N changed file(s) (tree <hash>): A, B. It adds ; changes in C when the changed projects differ from the built ones, and ; U changed file(s) in no project when some changed files no project owns.

Each project then answers as build (<name>). When several built, a last line counts the failures: fuse: F of M project(s) failed. With no C# changes the command builds nothing. It prints fuse: no C# changes since HEAD; nothing to build (tree <hash>) and exits with 0.

When the selection cannot be trusted, the command builds the whole solution instead and says why first. That happens when project files changed, or when no changed file is owned. It prints fuse: project files changed (A.csproj); building the whole solution instead, or fuse: N changed file(s) in no project; building the whole solution instead.

--changed outside a git repository is refused, because without HEAD there is nothing to compare with. A whole fuse build still runs there.

The exit code is 0 when the build succeeded, and 1 when it failed. It is 2 when Fuse could not answer or the arguments did not parse.

fuse status #

fuse status [--json]

This command shows whether an engine runs for your repository, how many files differ from HEAD, and the limits past which a large tree slows checks down. It never starts an engine. Past a short wait it reads the tree from git instead.

$ fuse status
fuse: engine running for /home/you/shop (pid 1234), 512 MB; idle exits after 30 min
fuse: 3 changed file(s) since HEAD; tree 9f2c41aa07b3; HEAD 1a2b3c4d5e6f
fuse: large-tree limits: past 300 changed files a sync reloads projects; past 500 files in reach a check binds whole projects; commit or run fuse stop and let the next check reload when checks feel slow

The first line says whether an engine runs: fuse: engine running for <root> (pid <pid>), <MB> MB; idle exits after 30 min, fuse: engine for <root> did not answer in 2 s, or fuse: no engine runs for <root>; the next check starts one. The second line counts the changed files and stamps the tree: fuse: N changed file(s) since HEAD; tree <hash>; HEAD <12 hex>. When more than 300 files changed, a warning line comes before the limits line: fuse: warning: N changed files is past the 300-file reload point; checks reseed from git and reload projects, so they slow down - commit soon.

With --json the command prints one object with these fields:

FieldMeaning
enginerunning, stopped, or unknown when an engine exists but did not answer in time.
pidThe engine process, left out without a running engine.
memoryMBThe engine's working set in megabytes, left out without a running engine.
changedFilesHow many files differ from HEAD.
headHEAD, left out when the repository has no commits yet.
treeThe tree stamp: 12 hex characters over what the changed files hold.
reloadAt300: past this many changed files a sync reloads projects.
wholeProjectAt500: past this many files in reach a check compiles whole projects.

In a repository it exits with 0, and outside one with 2. Any other argument prints fuse: status takes [--json]; '<token>' is not one with the usage and exits with 2.

fuse session #

fuse session begin <name> --paths <pattern> [<pattern>...] | fuse session end <name>

This command registers an external writer as a session for its path patterns. An external writer is a program that writes files without sending a hook payload. The registration lets a stop hook tell that writer's half-written errors apart from the stopping session's. Beginning a name that is already registered replaces its patterns and restarts its 4 hours.

$ fuse session begin worker-a --paths "src/WorkerA/**"
fuse: session worker-a registered for 1 path pattern(s); files under them count as that session's until fuse session end worker-a or 4 hours pass
$ fuse session end worker-a
fuse: session worker-a ended; its files now count as no session's

A name holds 1 to 64 letters, digits, -, _ and .. A pattern is read relative to the repository root with forward slashes. ** as a whole segment matches any run of segments, while * and ? match inside one segment. No segment is ... A pattern without wildcards names a file or a directory subtree. A pattern holds at most 256 characters, a session at most 32 patterns, and 64 sessions can be registered at once.

Ending a name that is not registered prints fuse: no registered session named <name> and exits with 2. Anything other than the two forms prints the usage on standard error and exits with 2 (InvalidPath, Usage failures).

Registrations live in registered-sessions.tsv in the state directory. fuse uninit deletes them with the state, while fuse stop keeps them. A plain fuse check still reports every error, registered or not.

fuse stop #

This command stops the engine of the repository that holds your current directory. It asks the engine to stop, as a client of another build does, and waits up to 10 seconds for it to exit. When the engine has not exited, the command kills the process the engine log names as the last engine that started, if that process is still a dotnet or fuse process. It never starts an engine. The next command or hook starts a new one. Stop the engine after changing an analyzer your repository builds itself, to give its memory back at once, or when it stops answering (Stopping or restarting the engine).

$ fuse stop
fuse: stopped the engine for /home/me/src/my-repo

When no engine runs, it prints fuse: no engine runs for <root>. When the engine had to be killed, it prints fuse: the engine for <root> did not stop within 10 s of being asked, so its process <pid> was killed. Both exit with 0.

fuse stop --all does the same for every repository that Fuse keeps a state directory for and that still exists. It prints one line for each engine it stopped, and fuse: no engine runs when there was none. Any other argument prints the usage and exits with 2.

fuse mcp #

This command runs an MCP server over standard input and output, for an MCP host without hooks. The server finds the repository from its working directory on every call, so the host has to start it inside the repository. Connect your agent shows how to register it.

A max_errors that is no count of 1 to 100000 is refused with fuse: max_errors takes a count of 1 to 100000. all with failed is refused with fuse: failed reruns the tests that failed last time and cannot be combined with all; set only one of them. Both are error results.

fuse hook #

usage: fuse hook <claude|cursor|gemini|codex|copilot|opencode|muse> <post-edit|pre-shell|stop>

This is the command every installed hook runs. You do not run it yourself, except to see what a hook would answer, as Getting started does. It reads the harness's JSON payload from standard input as UTF-8, and answers in that harness's format, which Connect your agent shows for each one. The harness is claude, cursor, gemini, codex, copilot, opencode or muse. Any other harness or event prints the usage line on standard error and exits with 0, without reading standard input. --help before or after the harness and event does the same.

EventWhat it does
post-editChecks the source files the edit wrote and reports introduced errors.
pre-shellRewrites dotnet build and dotnet test in a shell command to fuse build and fuse test.
stopChecks every change when the agent tries to finish, and sends it back once while its own edits introduce errors or a project needs a restore.

post-edit #

This event reads the edited paths from the payload's tool input: file_path, filePath, path or notebook_path, and the files an apply_patch patch adds, updates, deletes or moves to. It keeps the .cs, .razor and .cshtml files, and runs fuse check on them. Relative paths resolve against the payload's cwd, or the first of its workspace_roots. When the payload names neither, they resolve against the hook's own working directory.

Claude Code runs the hook in the background. There the hook waits up to 280 seconds for the engine to finish loading, covering at most two checks: the first answer, and one confirmation against the tree as it stands before an answer with errors is delivered. It writes the check's output to standard error, and exits with 2, which wakes the agent. Every other harness runs the hook inline, so the agent waits for it. There the hook answers only once the engine has loaded, waits up to 50 seconds, and writes its answer as JSON to standard output.

When the payload names the agent's session (what each harness sends), the check is answered to that session. Errors that other sessions' edits caused without it are left out, and the summary counts them, as in ; 1 error(s) from other sessions' edits left out. When every error found is another session's, the answer is clean and the hook stays silent. How it works describes how an error is attributed.

pre-shell #

This event reads the command from the tool input's command. It rewrites dotnet build and dotnet test (also dotnet.exe) where a command segment starts: at the beginning, or after &&, ||, ;, | or a line break. cd Lib && dotnet build -c Release becomes cd Lib && fuse build -c Release. Variable assignments before the verb are kept, so DOTNET_CLI_UI_LANGUAGE=en dotnet test becomes DOTNET_CLI_UI_LANGUAGE=en fuse test.

An assignment counts when its value has no whitespace, quote, backtick, separator, redirection or parenthesis. A command without either verb is left alone. When the payload names the agent's session, and its id holds only letters, digits and - _ . : /, fuse test gets --session and the session, as in fuse test --session claude:<id>. It then runs the tests that session's edits affect (a session's own tests).

Claude Code, Gemini CLI and OpenCode get the rewritten command. Cursor, GitHub Copilot CLI, Codex and Muse Code get it only when the whole command is one dotnet build or dotnet test with plain arguments, after plain assignments if any, because their answer also approves the command (Codex).

stop #

This event checks every change in the working tree, waiting up to 280 seconds for the engine. When the payload names the agent's session, the check covers only that session's files and what they reach, and is answered to that session. It sends the agent back with the errors its own edits cause, alone or with another session's, and with the errors in changes no session is credited with. They are followed by Fix these errors before finishing. The working tree has them and HEAD does not, and no other session's edits cause them on their own.

Errors another session's edits cause on their own are left out and counted in the summary, counting only those in reach. When they are all there is, the agent finishes. A subagent's edits count as its parent's once the subagent has stopped (the stop hook and subagents). In Claude Code the same command runs as the SubagentStop hook, so a subagent is sent back for its own errors.

When the payload names no session, the hook sends the agent back with every error and Fix these errors before finishing. The working tree has them and HEAD does not; another agent editing this working tree may have caused some of them. For a project that needs a restore, it sends the restore message alone. When the payload says the agent is already continuing because of an earlier stop hook (stop_hook_active is true, or loop_count is above 0), the hook lets the agent finish. It therefore sends an agent back at most once in a row, and cannot trap it in a loop.

What a hook never does #

A hook reports only introduced errors and a missing restore. Every other outcome, including a loading engine, a timeout and an internal failure, exits with 0 and prints nothing, or {} where the harness expects JSON. A hook therefore never breaks the agent's session. A payload that is not valid JSON or not a JSON object, and an exception, are written to hook.log in the state directory. A Claude Code hook whose payload comes from Cursor does nothing, because Cursor also runs Claude Code's settings. The Cursor hook answers there.

fuse --version and fuse help #

fuse --version (or fuse version) prints the product version:

$ fuse --version
5.7.0

fuse help (or --help, -h, or no arguments) prints the usage shown at the top of this page to standard output and exits with 0. Every command takes --help (or -h) before any --. It prints that command's usage to standard output and exits with 0, running nothing: no root lookup, no engine, no build and no lock. fuse hook --help is the exception. It prints the hook usage to standard error, still with 0 and without reading standard input. An unknown command prints the top-level usage to standard error and exits with 2.

fuse engine <root> is the engine process itself. Clients start it, so there is no reason to run it by hand. The native client refuses it with exit code 2, because the engine runs only from fuse.dll on the .NET runtime.

Environment #

Fuse has no configuration file and no environment variables of its own. When a client starts the engine, it looks for the dotnet host in DOTNET_HOST_PATH and DOTNET_ROOT, the variables the .NET SDK sets, then in the runtime's own directory, then on the PATH. The native client has no runtime directory, so it uses the variables or the PATH. Every child process Fuse starts gets DOTNET_CLI_TELEMETRY_OPTOUT=1, DOTNET_NOLOGO=1 and DOTNET_CLI_UI_LANGUAGE=en, so its output is in English and Fuse can parse it.

Fuse needs the .NET 10 SDK, git on the PATH, and restored projects. It writes the harness settings fuse init creates, the instruction files fuse init --instructions updates, and the state directory in your local application data. It writes nothing else.
