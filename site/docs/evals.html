Evals

All documentation pages

The evals in evals/Fuse.Evals measure whether Fuse is right and how fast it is, by comparing every answer with a real dotnet build or dotnet test. This page explains what each suite measures and how to run it.

This page is for a contributor whose change touches checking, test selection or performance, and who has to show its effect, and for anyone who wants to know how the published numbers were produced.

After reading it you can run the suite a change needs, read its result file, and update the pages that quote the numbers. Benchmarks has the published numbers.

evals/Fuse.Evals is a console project with three main suites, correctness, test selection and latency, and a light attribution suite. Every benchmark goes through the fuse executable, the way an agent calls it, and every answer is compared with the truth from a real dotnet build or dotnet test. Each run of a suite writes one JSON file to evals/results, and the published numbers, the chart and the site quote the newest file of each suite and repository.

Run an eval #

Build Fuse first; the suites run src/Fuse/bin/Release/net10.0/fuse (or fuse.exe), and the Debug build when there is no Release build.

dotnet build Fuse.slnx -c Release
dotnet run --project evals/Fuse.Evals -c Release -- correctness fixture --mutations 2
repo <fuse>\evals\.work\fixture, solution Fixture.sln: 3 code project(s), 2 test project(s); fuse <fuse>\src\Fuse\bin\Release\net10.0\fuse.exe
[correctness] fixture: HEAD build...
[correctness] HEAD build exit 0, 0 error(s), 1.1 s
[correctness] fuse warm-up: fuse: no errors introduced (0 file(s) checked) (1158 ms)
[correctness] 1/2 agree-clean  truth=  0 fuse=  0   5184 ms  change-return-type src/Services/ReportBuilder.cs
[correctness] 2/2 agree        truth=  2 fuse=  4    505 ms  remove-member src/Services/OrderService.cs
[correctness] fixture: 2 cases, 1 breaking, false green 0, false-red cases 0, unverifiable errors 2, deferred by csc 0, message mismatches 0, partial 0, exact 2, file agreement 2, tree clean True
wrote evals\results\correctness-fixture-20260929-0452.json

<fuse> stands for the path of the Fuse checkout, shortened here. In the second case the build reported 2 errors in Services and Fuse reported 4: the build's 2, and 2 in projects that reference Services. MSBuild skipped those projects because Services failed, so the suite counted Fuse's errors there as unverifiable rather than contradicted.

Delete the result file of a short run. Every run writes a new file, which becomes the newest for its suite and repository and the one chart reads. Commit a result file only from a full run.

Commands #

$ dotnet run --project evals/Fuse.Evals -c Release
usage: Fuse.Evals <suite> <repo> [--mutations N] [--seed S] [--solution path] [--fuse path]
                  [--cache file] [--truth-dir dir] [--cache-out file] [--part all|checks|main|agents]
       Fuse.Evals truth <correctness|selection> <repo> --out file [--shard K --shards N] [--cache file]
       Fuse.Evals key <correctness|selection> <repo> [--mutations N] [--seed S]
       Fuse.Evals chart
       Fuse.Evals clone <repo>
       Fuse.Evals clean
  suite: correctness | selection | latency | all
  repo:  fixture (generated under evals/.work/fixture), a pinned repository name, or a path to a git repository
  truth: runs shard K of N of the truth side (the real dotnet build or dotnet test) and writes it to a file; the
         suite run merges the files in --truth-dir and runs what is still missing. Without them it reads and
         writes evals/.work/truth/<suite>-<repo>.json, so a second run on the same tree measures only Fuse
  key:   prints the key the truth is cached under: suite, repository tree, seed, count, SDK and eval code
  --part: for latency, what to measure: all (the default); checks, the checks alone; main, the checks and
         the test rounds; agents, the multi-agent scenario after the cold checks and body edits
  clone: NodaTime | Jellyfin | CommunityToolkit, checked out at the pinned commit under
         %LOCALAPPDATA%/fuse/evals/repos (outside this repository, so its build settings do not leak in)
  clean: deletes %LOCALAPPDATA%/fuse/evals, which holds every checkout; the generated fixture in
         evals/.work/fixture and the result files in evals/results stay
  • <suite> <repo> runs correctness, selection, latency, or all three in that order, on one repository. <repo> is fixture, the name of a pinned repository that has been cloned, or a path to any git repository.
    • --mutations N: the number of cases, 30 by default for correctness and 10 for selection. The latency suite has a fixed size.
    • --seed S: the seed of the random choice of edits, 1 by default, so a run with the same seed on the same commit makes the same edits.
    • --solution path: the solution the truth side builds, relative to the repository. The default is the pinned solution, or the only .sln or .slnx file in the repository root.
    • --fuse path: the fuse executable to measure.
    • --cache file, --truth-dir dir, --cache-out file: where the truth comes from and goes, as The truth side describes. By default the truth is read from and written to evals/.work/truth/<suite>-<repo>.json.
    • --part: for the latency suite, what to measure: all, the default; checks, the checks alone, which the managed client's run on GitHub Actions uses; main, the checks and the test rounds; or agents, the multi-agent scenario, after the cold checks and the body edits it is compared with. A part leaves what it does not measure null.
  • truth <suite> <repo> runs one shard of the truth side of the correctness or selection suite and writes it to --out. --shard K --shards N picks shard K of N, numbered from 0; --cache file skips what that file already holds.
  • key <suite> <repo> prints the key the truth of that suite on that repository is cached under.
  • clone <repo> checks NodaTime, Jellyfin or CommunityToolkit out at its pinned commit in fuse/evals/repos/<repo> under the user's local application data (%LOCALAPPDATA% on Windows). A checkout already at that commit is left alone. The checkouts live outside the Fuse repository because a repository without its own Directory.Packages.props would inherit Fuse's and fail to restore.
  • chart renders site/assets/benefits.svg from the newest correctness and selection file of each repository: one panel for fuse check against dotnet build and one for fuse test against dotnet test, with every time and speedup rounded as the results are, each command's range, mean and P95 under its median, a header with the Fuse logo, what Fuse is, its website and repository, and a last line with the version and date measured and the benchmarks page, so the chart says what it is when shared on its own.
  • clean deletes fuse/evals under the local application data, which holds the checkouts. The result files stay, and so does the generated fixture under evals/.work/fixture; delete that folder by hand to regenerate it.

Before a suite runs, the tool restores the solution and every project under the repository that the solution leaves out, because Fuse reads every project in the working tree and does not answer while one is unrestored.

The suites discard changes. Every suite needs a clean working tree, fails otherwise, and discards each change it makes with git checkout -- . and git clean -fdq. Run the suites only on a checkout you do not work in.

evals/Fuse.Evals/PinnedRepo.cs holds the pins and the labels the chart draws. The four open-source repositories are the published set. FluentValidation is the small one: a library, an extension project that depends on it, one test project for three target frameworks, and a benchmark project. The generated fixture, five projects with 22 tests, is for a quick run on your own machine and is not published. Jellyfin is pinned to its final commit before it moved to Roslyn 5, because from then on its analyzer project needs a newer compiler than the SDK the evals run on. The Community Toolkit is measured because its test projects reach separate parts of the code, which lets test selection narrow.

The fixture is generated in evals/.work/fixture on its first use and reused afterwards: two libraries (Core, and Services, which references it), a console app (App, which references Services) and two xUnit test projects (Core.Tests and Services.Tests), committed to git and built. It writes its own global.json, Directory.Build.props, Directory.Build.targets and Directory.Packages.props, so Fuse's own build settings do not apply to it. Its commit id changes each time it is generated, while its content stays the same.

Suites #

The truth side #

The correctness and selection suites compare Fuse with a truth side: a real dotnet build or dotnet test of HEAD and of each case. The truth does not depend on Fuse, so it is a stage of its own, and a run measures only Fuse when the truth is already known.

  • The plan. The cases are drawn from the repository's tree, the seed and the requested count alone, never from Fuse's answers, so every machine draws the same cases.
  • The truth file. The plan and the answers for HEAD and each case are kept in one file per suite and repository, with the place each answer was measured. Its key is the suite, the repository's git tree, the seed, the count, the SDK version, and a hash of the eval code that draws the cases and runs the truth side; a change to any of them starts a new file.
  • Shards. truth fills one shard of the file. In the selection suite with more than one shard, shard 0 runs HEAD's full test run alone and the cases go round the other shards; otherwise shard 0 also runs HEAD and the cases go round every shard. The suite run merges the shard files and runs whatever is still missing.

Correctness #

The correctness suite measures whether fuse check reports the errors a real build reports.

  1. The truth side builds the solution at HEAD and keeps the errors HEAD already has.
  2. Each case is one generated edit, or with a probability of 0.3, two or three edits in different projects: removing, renaming or re-parameterizing a method, making it private, duplicating its signature, changing its return type, removing a using directive, or deleting a file.
  3. The truth side runs dotnet build on the solution with the case's edits, and takes the build's errors beyond HEAD's as the truth.
  4. The suite builds HEAD, then for each case makes the edits, runs fuse check on the edited files, resets the tree, and matches Fuse's errors with the truth by position (file, line and column).

A Fuse error at a truth position with a different id or message is a message mismatch. A Fuse error with no truth at its position is unverifiable when it is in a project MSBuild skipped because a project it references failed, deferred when the compiler skipped it (see Benchmarks), and contradicted otherwise. A truth error without a Fuse error at its position is missed. Each case gets a verdict:

VerdictMeaning
agreeFuse reported every error the build did.
agree-cleanNo error on either side.
partialSome errors missed.
false-redAn error contradicted.
false-greenThe build reported introduced errors and Fuse reported none.
fuse-failedFuse did not answer.

Test selection #

The selection suite measures whether fuse test runs every test a change makes fail.

  1. The truth side builds the solution at HEAD, runs every test project with dotnet test one at a time, and stops when a test project writes no results, because a missing project would hide misses.
  2. Each case is one behavior edit in a method body of a code project: flipping a comparison, shifting an integer constant by one, dropping a statement, or negating a boolean return. An edit with which the solution does not build is skipped when the plan is drawn.
  3. For each case, the truth side runs one dotnet test of the whole solution, as a user runs it after an edit: it builds what changed and runs the test projects in parallel. Its time is the dotnet test time the benchmarks quote. The truth is the tests that fail after the edit and did not fail at HEAD. A case whose run wrote fewer TRX files than HEAD's is listed in projectsWithoutResults.
  4. The suite builds HEAD, then for each case makes the edit, waits 500 ms, runs fuse test, and resets the tree.

A case is caught when every truth failure is among the failures fuse test printed, missed when one is not, no-failure when the edit failed no test, and unverified when a truth failure is not printed because fuse test cut its list of names (... and N more).

Latency #

The latency suite times fuse check and fuse test the way an agent waits for them, and reads the engine's phase line for each call from engine.log.

  1. It builds HEAD, as a repository an agent works in has been built, and picks a public method with a block body in one of the two code projects with the most dependents, the one whose name the other projects mention most.
  2. It times a check of the clean tree with a cold engine, and a check of a body edit with a cold engine, which loads the owning project.
  3. It times 15 body edits (a statement added to the method) and 10 signature edits (the method renamed), each followed by fuse check on the file, then 10 checks of the unchanged tree and 5 fuse test rounds after body edits.
  4. It reads the engine's working set, then runs the multi-agent scenario. Run as --part agents, it first runs one unmeasured fuse test round, so the scenario starts from an engine that has loaded the test projects, as it does after the test rounds.

Multi-agent scenario #

The latency suite ends with four scenarios for several agents in one repository:

  • Writers. Up to four clients each edit a file in a different code project ten times and check it, all at once, while a fifth client checks and runs the tests three times. The engine's gate phase shows whether requests queue behind each other, and gateByHolder groups those waits by what held the request lock longest during each one.
  • Builds. Three clients run fuse build at once, five times. A collision is an output line with MSB3021, MSB3026, MSB3027 or CS2012, and the pass bar is zero.
  • Rounds. Three fuse test rounds: a body edit in one project, a body edit in a second project whose tests differ, and a second edit to the same file. The result records which test projects each round planned.
  • Attribution. One pair of writers from the attribution suite, recorded with the other scenarios.

Attribution suite #

The attribution suite measures whether an agent that shares a working tree with another is told the other's errors (sessions). It needs no truth and runs no tests, so it takes minutes on a repository. Up to three times, writer A renames a public method in one of the two code projects with the most dependents, and writer B adds a statement naming an undeclared variable to a file in another project that calls the method, a different file each time. Each writer's edit then goes through the Claude Code post-edit hook, once without a session id and once with one per writer. The result file counts, over the errors the answers print, each writer's own errors and the other writer's errors in each arm, the errors the answers left to the other session, and the wall time of the hooks in each arm.

dotnet run --project evals/Fuse.Evals -c Release -- attribution fixture

With sessions, a writer should be told none of the other's errors and all of its own. A run that tells a writer the other's error, or loses one of its own, is a defect.

On GitHub Actions #

Times depend on what else the machine is doing, so the recorded results come from .github/workflows/evals.yml, which runs every job on a fresh windows-latest runner that runs nothing else. Add the evals label to a pull request to run the latency suite on the four open-source repositories. Start the workflow from the Actions tab to choose the repositories and the suites; it runs the three main suites by default, and the attribution suite only when the suites input names it, as ["attribution"]. Its fresh-truth input ignores the cached truth, for a run after a flaky test made a truth answer wrong. What to run says which suites a change needs.

  • Build. One job builds Fuse and publishes the native client, and every other job downloads that build, so every result file records the same fuseBuild.
  • Latency. Two jobs per repository run the latency suite with the native client: one the checks and the test rounds, followed by the checks alone with the managed client on the same runner, the other the multi-agent scenario. A merge job puts the multi-agent result into the first job's file.
  • Truth. The truth side of the correctness and selection suites runs in shards, one job each, more of them on the larger repositories. A shard whose truth is already in the Actions cache under its key does nothing.
  • Measure. One job per suite and repository merges the shards with the cached truth, measures Fuse on its own runner, writes the result file, and saves the merged truth to the cache.

A measure or latency job's artifact evals-<repo>-<suite> holds results/, the file to commit to evals/results in place of the older one, managed/, the managed client's latency file, which goes to evals/results/managed in the same way and is the comparison Benchmarks quotes, truth/, the merged truth, and runner.txt, which names the runner image, processor, memory and SDK. Each truth shard's artifact holds its shard and its own runner.txt, and a latency artifact also holds runner-agents.txt, the runner of the multi-agent scenario. Runners of the same image can have different processors, so compare two builds within one job, as the latency jobs do, rather than across jobs.

Result files #

A suite writes evals/results/<suite>-<repo>-<yyyyMMdd-HHmm>.json, with the local time of the run. The repository keeps only the newest file of each suite and repository; older files stay in git history. Every file records:

  • suite, repo: what ran on which repository.
  • commit: the commit the repository was measured at.
  • fuseBuild: the build of fuse that was measured, as <version>/<module id>, the same id the engine compares.
  • treeCleanAfter: whether the suite left the working tree clean.

Correctness files also hold seed, requested and cases; breaking and neutral (cases whose build reported errors beyond HEAD's, or none); falseGreen, falseRedCases, falseRedErrors (contradicted errors), partialMisses, exactAgreement and fileAgreement (cases whose errors are in the same files); unverifiableErrors, deferredByCompilerErrors and messageMismatchErrors; causeLines, causeBytes and outputBytes (cause lines, their size and the whole output's size); fuseUnanswered (cases where fuse check exited with neither 0 nor 1); fuseMedianMs and buildMedianSeconds; fuseStats and dotnetStats (see below); headBuildErrors; truthKey and truthOrigins; and details, one object per case with its edits, the truth and Fuse errors, each classification list, its verdict, and its times.

Selection files also hold seed, requested, cases, withFailures, missedCases, unverifiedCases, missedTests and unverifiedTests; totalTests (the tests in a full run at HEAD); meanSelectedFraction (the mean share of those tests fuse test ran); fuseMedianSeconds and dotnetMedianSeconds; fuseStats and dotnetStats; skippedNonCompiling and projectsWithoutResults; truthKey and truthOrigins (the key of the truth and where its answers were measured); and details, one object per case with its edit, the truth and Fuse failures, Fuse's counts and summary line (fuseSummary), the misses, both times and its verdict.

Latency files also hold the target file and method and referencingFilesInOtherProjects; coldCleanMs and coldBodyEditMs; part, the --part it ran, whose unmeasured fields are null; bodyEdit, signatureEdit, warmUnchanged and testRound, each p50, p95, max and n in milliseconds; signatureEditSample, the summary line of the first signature edit; bodyEditPhases, signatureEditPhases, warmUnchangedPhases and testRoundPhases, the same statistics per engine phase plus outsideEngine, the time the client spent outside the engine's request; multiAgent, with writers (whose unanswered counts checks that exited 2 and notRun checks that exited with any other code outside 0 and 1), builds, rounds and attribution (one pair, as attribution files hold them; null when no method has a caller in another project whose break the check reports); and engineWorkingSetMb.

Attribution files hold pairs, each with the renamedIn file, the method, the brokenIn file, ownWithoutSessions, otherWithoutSessions, ownWithSessions, otherWithSessions, leftToOtherSessions, and msWithoutSessions and msWithSessions, the wall time of both writers' hooks in each arm; the same counts summed over the pairs; the statistics of each arm's time; and treeCleanAfter.

fuseStats and dotnetStats describe how the Fuse command's and the dotnet command's times spread over the cases, in seconds: n, fastest, median, mean, standardDeviation (the sample standard deviation), p95, slowest and total. The chart and Benchmarks quote them next to each median.

Medians are over the cases, and the average of the two middle values for an even count. Percentiles use the nearest-rank method: P95 of 10 or 15 samples is the slowest one.

Quoting the numbers #

The rule in AGENTS.md binds every page that quotes a benchmark: numbers come from files in evals/results, and each results table names the files it comes from. Counts are quoted exactly. Times, sizes and percentages are rounded half up: seconds to two decimals below 10 s and one decimal from 10 s, milliseconds and megabytes to whole numbers, percentages to at most one decimal. A speedup is the dotnet median divided by the Fuse median, to one decimal.

After committing the result files of a full run, delete the older file of the same suite and repository, run chart, and update every page that quotes the numbers:

  • the root README.md;
  • site/index.html, site/docs/benchmarks.html and site/docs/index.html;
  • the questions in site/docs/how-it-works.html, and the load time in the Timeout section of site/docs/messages.html;
  • site/assets/og.png, whose text quotes the check speedup.
