Evals

All documentation pages

The evals in evals/Fuse.Evals measure whether Fuse is right and how fast it is, by comparing every answer with a real dotnet build or dotnet test. This page explains what each suite measures and how to run it.

This page is for a contributor whose change touches checking, test selection or performance, and who has to show its effect, and for anyone who wants to know how the published numbers were produced.

After reading it you can run the suite a change needs, read its result file, and update the pages that quote the numbers. Benchmarks has the published numbers.

In short

  • Every suite runs the real fuse executable and compares its answers with a real dotnet build or dotnet test.
  • Correctness, test selection and latency are the main suites, and attribution, analyzers, scale and stale are lighter suites that need no truth.
  • The recorded numbers come from GitHub Actions runners that run nothing else, because times depend on what else the machine is doing.
  • Each run writes one JSON file to evals/results, and a short run's file becomes the newest, so commit result files only from full runs.
  • Run the suite your change touches, and attach the result to the pull request.

evals/Fuse.Evals is a console project with three main suites, correctness, test selection and latency, and the lighter attribution, analyzers, scale and stale suites. Every benchmark goes through the fuse executable, the way an agent calls it, and every answer is compared with the truth from a real dotnet build or dotnet test. Each run of a suite writes one JSON file to evals/results, and the published numbers, the chart and the site quote the newest file of each suite and repository.

Run an eval #

Build Fuse first; the suites run src/Fuse/bin/Release/net10.0/fuse (or fuse.exe), and the Debug build when there is no Release build.

dotnet build Fuse.slnx -c Release
dotnet run --project evals/Fuse.Evals -c Release -- correctness fixture --mutations 2
repo <fuse>\evals\.work\fixture, solution Fixture.sln: 3 code project(s), 2 test project(s); fuse <fuse>\src\Fuse\bin\Release\net10.0\fuse.exe
[correctness] fixture: HEAD build...
[correctness] HEAD build exit 0, 0 error(s) in the truth (local)
[correctness] fuse warm-up: fuse: no errors introduced (0 file(s) checked) (1158 ms)
[correctness] 1/2 agree-clean  truth=  0 fuse=  0   5184 ms  change-return-type src/Services/ReportBuilder.cs
[correctness] 2/2 agree        truth=  2 fuse=  4    505 ms  remove-member src/Services/OrderService.cs
[correctness] fixture: 2 cases, 1 breaking, false green 0, false-red cases 0, unverifiable errors 2, deferred by csc 0, message mismatches 0, partial 0, exact 2, file agreement 2, tree clean True
wrote evals\results\correctness-fixture-20260929-0452.json

<fuse> stands for the path of the Fuse checkout, shortened here. In the second case the build reported 2 errors in Services and Fuse reported 4: the build's 2, and 2 in projects that reference Services. MSBuild skipped those projects because Services failed, so the suite counted Fuse's errors there as unverifiable rather than contradicted.

Delete the result file of a short run. Every run writes a new file, which becomes the newest for its suite and repository and the one chart reads. Commit a result file only from a full run.

  • <suite> <repo> runs correctness, selection, latency, attribution, analyzers, scale or stale, or all, which is the first three in that order, on one repository. <repo> is fixture, analyzer-fixture, scale-fixture, the name of a pinned repository that has been cloned, or a path to any git repository.
    • --mutations N: the number of cases, 30 by default for correctness and 10 for selection. The latency suite has a fixed size.
    • --seed S: the seed of the random choice of edits, 1 by default, so a run with the same seed on the same commit makes the same edits.
    • --solution path: the solution the truth side builds, relative to the repository. The default is the pinned solution, or the only .sln or .slnx file in the repository root.
    • --fuse path: the fuse executable to measure.
    • --cache file, --truth-dir dir, --cache-out file: where the truth comes from and goes, as The truth side describes. By default the truth is read from and written to evals/.work/truth/<suite>-<repo>.json.
    • --part: for the latency suite, what to measure: all, the default; checks, the checks alone, which the managed client's run on GitHub Actions uses; main, the checks and the test rounds; or agents, the multi-agent scenario, after the cold checks and the body edits it is compared with. A part leaves what it does not measure null.
    • --failed-rounds: for the selection suite on the fixture, three fix-and-rerun rounds with fuse test --failed after the cases, and a fourth round with the results files deleted, which runs nothing. On any other repository, or without the flag, the result file records why the rounds were skipped instead.
    • --projects N --files M --changed K: for the scale suite, the size of the generated fixture: class libraries, class files per library, and changed files. The defaults are 30, 200 and 1500; a smoke run is --projects 2 --files 10 --changed 5.
  • truth <suite> <repo> runs one shard of the truth side of the correctness or selection suite and writes it to --out. --shard K --shards N picks shard K of N, numbered from 0; --cache file skips what that file already holds.
  • key <suite> <repo> prints the key the truth of that suite on that repository is cached under.
  • clone <repo> checks FluentValidation, NodaTime, Jellyfin or Polly out at its pinned commit in fuse/evals/repos/<repo> under the user's local application data (%LOCALAPPDATA% on Windows). A checkout already at that commit is left alone. The checkouts live outside the Fuse repository because a repository without its own Directory.Packages.props would inherit Fuse's and fail to restore.
  • chart renders site/assets/benefits.svg from the newest correctness and selection file of each repository:
    • one panel for fuse check against dotnet build and one for fuse test against dotnet test, with every time and speedup rounded as the results are, and each command's range, mean and P95 under its median.
    • a header with the Fuse logo, what Fuse is, its website and repository.
    • a last line with the version and date measured and the benchmarks page, so the chart says what it is when shared on its own.
  • clean deletes fuse/evals under the local application data, which holds the checkouts. The result files stay, and so does the generated fixture under evals/.work/fixture; delete that folder by hand to regenerate it.

Before a suite runs, the tool restores the solution and every project under the repository that the solution leaves out, because Fuse reads every project in the working tree and does not answer while one is unrestored.

The suites discard changes. Every suite needs a clean working tree, fails otherwise, and discards each change it makes with git checkout -- . and git clean -fdq. Run the suites only on a checkout you do not work in.

Suites #

The truth side #

The correctness and selection suites compare Fuse with a truth side: a real dotnet build or dotnet test of HEAD and of each case. The truth does not depend on Fuse, so it is a stage of its own, and a run measures only Fuse when the truth is already known.

  • The plan. The cases are drawn from the repository's tree, the seed and the requested count alone, never from Fuse's answers, so every machine draws the same cases.
  • The truth file. The plan and the answers for HEAD and each case are kept in one file per suite and repository, with the place each answer was measured. Its key is the suite, the repository's git tree, the seed, the count, the SDK version, and a hash of the eval code that draws the cases and runs the truth side; a change to any of them starts a new file.
  • Shards. truth fills one shard of the file. In the selection suite with more than one shard, shard 0 runs HEAD's full test run alone and the cases go round the other shards; otherwise shard 0 also runs HEAD and the cases go round every shard. The suite run merges the shard files and runs whatever is still missing.

Correctness #

The correctness suite measures whether fuse check reports the errors a real build reports.

  1. The truth side builds the solution at HEAD and keeps the errors HEAD already has.
  2. Each case is one generated edit, or with a probability of 0.3, two or three edits in different projects: removing, renaming or re-parameterizing a method, making it private, duplicating its signature, changing its return type, removing a using directive, or deleting a file.
  3. The truth side runs dotnet build on the solution with the case's edits, and takes the build's errors beyond HEAD's as the truth.
  4. The suite builds HEAD, then for each case makes the edits, runs fuse check on the edited files, resets the tree, and matches Fuse's errors with the truth by position (file, line and column).

A Fuse error at a truth position with a different id or message is a message mismatch. A Fuse error with no truth at its position is unverifiable when it is in a project MSBuild skipped because a project it references failed, deferred when the compiler skipped it (see Benchmarks), which includes the flow analysis errors the compiler places on a declaration (CS0161, CS0171, CS0177 and CS0843), and contradicted otherwise. A truth error without a Fuse error at its position is missed. Each case gets a verdict:

VerdictMeaning
agreeFuse reported every error the build did.
agree-cleanNo error on either side.
partialSome errors missed.
false-redAn error contradicted.
false-greenThe build reported introduced errors and Fuse reported none.
fuse-unansweredFuse did not answer.
results-incompleteThe answer was capped and its results file does not hold every error the summary counts.
unmeasuredFuse answered but the engine logged no check: line or no phase line for the check, so its counts are missing.

Each case also records what the check cost: how many files it checked, how many documents binding them bound, whether it bound whole projects, whether it answered from the answer it kept, and for how many files it reused the errors of an earlier check.

A capped answer proves its completeness with its results file: the file holds every error the summary counts, and a missing file or a short count is a results-incomplete verdict rather than a silent gap. When the file is complete, the case is classified on the file's errors, not on the ones the answer printed, so an error the answer left out of its printed list is not counted as missed.

Test selection #

The selection suite measures whether fuse test runs every test a change makes fail.

  1. The truth side builds the solution at HEAD, runs every test project with dotnet test one at a time, and stops when a test project writes no results, because a missing project would hide misses.
  2. Each case is one behavior edit in a method body of a code project: flipping a comparison, shifting an integer constant by one, dropping a statement, or negating a boolean return. An edit with which the solution does not build is skipped when the plan is drawn.
  3. For each case, the truth side runs one dotnet test of the whole solution, as a user runs it after an edit: it builds what changed and runs the test projects in parallel. Its time is the dotnet test time the benchmarks quote. The truth is the tests that fail after the edit and did not fail at HEAD. A case whose run produced fewer result units than HEAD's, TRX files or executed test assemblies on Microsoft.Testing.Platform, is listed in projectsWithoutResults.
  4. The suite builds HEAD, then for each case makes the edit, waits 500 ms, runs fuse test, and resets the tree.

A case is caught when every truth failure is among the failures fuse test printed, missed when one is not, no-failure when the edit failed no test, unverified when a truth failure is not printed because fuse test cut its list of names (... and N more), and results-incomplete when a capped answer's results file does not hold every failure the summary counts.

Each case also records what the run planned and ran: how many tests it selected and ran, how many test projects it planned and how many ran, how many ran without MSBuild and how many built with it, how many ran whole and why, which filters collapsed, and how many test processes the plan implies. It records whether the edit changed compiled code, and how many symbols the member walk visited.

On the fixture the suite then measures two edits that change no compiled code, a comment and a local rename, each with fuse test on its own: what it selected and ran for it. On any other repository the result file records why those cases were skipped instead.

With --failed-rounds on the fixture, the suite ends with three fix-and-rerun rounds: three tests broken across two projects, one fixed, then the rest fixed, each fix followed by a full fuse test and a rerun with fuse test --failed, and a fourth round with the results files deleted, which runs nothing. Each round records how many tests failed before it, how many the full run selected, how many the rerun ran, and how many it avoided, with both times. Without the flag, on any other repository, or on a build without fuse test --failed, the result file records why the rounds were skipped instead.

Latency #

The latency suite times fuse check and fuse test the way an agent waits for them, and reads the engine's phase line for each call from engine.log.

  1. It builds HEAD, as a repository an agent works in has been built, and picks a public method with a block body in one of the two code projects with the most dependents, the one whose name the other projects mention most.
  2. It times a check of the clean tree with a cold engine, and a check of a body edit with a cold engine, which loads the owning project.
  3. It times 15 body edits (a statement added to the method) and 10 signature edits (the method renamed), each followed by fuse check on the file, then 10 checks of the unchanged tree and 5 fuse test rounds after body edits.
  4. Between the body and signature edits it measures five edits that change no compiled code, each on the pristine target on its own: a comment, a local rename, a reformat, a using sort and trailing whitespace. Each is measured as a check and, where the part runs tests, as a test round. An edit the target does not allow, such as a using sort in a file with fewer than two usings, is recorded with its reason instead of failing the repository.
  5. It reads the engine's working set and its peak, waits 50 seconds for the engine to return the memory its requests freed, reads the working set again, then runs the multi-agent scenario. Run as --part agents, it first runs one unmeasured fuse test round, so the scenario starts from an engine that has loaded the test projects, as it does after the test rounds.

Multi-agent scenario #

The latency suite ends with seven scenarios for several agents in one repository:

  • Writers. Up to four clients each edit a file in a different code project ten times and check it, all at once, while a fifth client checks and runs the tests three times. The engine's gate phase shows whether requests queue behind each other, and gateByHolder groups those waits by what held the request lock longest during each one.
  • Builds. Three clients run fuse build at once, five times. A collision is an output line with MSB3021, MSB3026, MSB3027 or CS2012, and the pass bar is zero.
  • Rounds. Three fuse test rounds: a body edit in one project, a body edit in a second project whose tests differ, and a second edit to the same file. The result records which test projects each round planned.
  • Scopes. The same body edit in a file a test project uses, planned four ways: a plain fuse test, a test directory, a test project and --no-build; then every test with fuse test --all; then a code directory that names no test project, which the product refuses. Each form records what it planned and selected and how it ran, so the plans compare form against form.
  • Attribution. One pair of writers from the attribution suite, recorded with the other scenarios.
  • Stops. A body edit in one file of each code project, up to 20, then a fuse check of every change, as a stop hook makes, and five more, each after another body edit in the first file.
    • A repeat compiles the file that changed and can keep the others' errors from the earlier check (errors kept from an earlier check); the result records the most files one repeat kept, from the engine log's check: line.
    • It also records three checks of the same tree with no edit in between (stopsUnchangedRepeat), which answer from the kept answer, each with its wall time and how many documents it bound, 0 for a kept answer.
  • Tests. A body edit in a file a test project uses, then one fuse test that is not measured, so the engine and the copies are ready, one fuse test on its own, and two started together, each after another body edit. Two runs that took turns would take about twice as long as one; runs without MSBuild from their own copies (each run holds its own copy) overlap.

Attribution suite #

The attribution suite measures whether an agent that shares a working tree with another is told the other's errors (sessions). It needs no truth and runs no tests, so it takes minutes on a repository.

Up to three times, writer A renames a public method in one of the two code projects with the most dependents, and writer B adds a statement naming an undeclared variable to a file in another project that calls the method, a different file each time. Each writer's edit then goes through the Claude Code post-edit hook, once without a session id and once with one per writer.

The result file counts, over the errors the answers print:

  • each writer's own errors and the other writer's errors in each arm.
  • the errors the answers left to the other session.
  • the wall time of the hooks in each arm.
dotnet run --project evals/Fuse.Evals -c Release -- attribution fixture

With sessions, a writer should be told none of the other's errors and all of its own. A run that tells a writer the other's error, or loses one of its own, is a defect.

Each run ends with one pair where the second writer never sends a hook: its directory is registered as its session with fuse session begin instead, and writer A's stop is measured while the registration holds and again after fuse session end. While registered, A's stop should leave the external writer's errors to it; after the end they count as no session's again. On a build without fuse session the result file records why the pair was skipped instead. Registrations expire after 4 hours, which the suite does not wait out, so expiry is never measured.

Analyzers suite #

The analyzers suite measures what an analyzer that reads the whole project costs (compilation-wide analyzers). It generates analyzer-fixture under evals/.work: an analyzer project whose compilation start binds every invocation of the project again and again until two seconds have passed, standing in for a package of such analyzers on any runner, and an app project of 300 files that uses it, its rule SLOW001 at error severity.

It runs one cold check, then five post-edit hooks and five checks of one edited file, and two checks of twenty edited files. It then adds a class the analyzer forbids, with a compiler error in it, and reads the engine's peak and idle memory. It needs no truth and runs no tests, so it takes minutes.

dotnet run --project evals/Fuse.Evals -c Release -- analyzers analyzer-fixture

The engine should find the analyzer compilation-wide, fuse check should report both errors, and the post-edit hook should report the compiler error, leave out SLOW001 and name the analyzer. A run where any of these fails is a defect.

Scale suite #

The scale suite measures what a check of a large tree costs, on the generated scale-fixture (Repositories). It changes 1,500 files, spread evenly across the projects, kills the engine, and runs one cold fuse check of every change: its wall time, the files it checked, and the engine's peak and idle memory. It needs no truth and runs no tests. The fixture is a linear scale-down of an observed tree of about 15,000 files with about 3,700 changed, so the full-scale number is an extrapolation, quoted with the factor, never as measured.

dotnet run --project evals/Fuse.Evals -c Release -- scale scale-fixture

A body edit in one class binds no other file, so the check loads the changed files' owners and no dependent. The verdict is answered when the check exited 0 or 1, out-of-memory when it named it or the engine died with exit 2, and unanswered otherwise.

Stale suite #

The stale suite measures whether a fixed post-edit error is delivered again. It breaks one file with a statement naming an undeclared name, reports it through the Claude Code post-edit hook, fixes it without another hook, checks, and then asks the stop hook. Stale is an error the stop delivers that the current tree no longer has. It needs no truth and runs no tests, and it runs only on your own machine: the workflow has no job for it.

dotnet run --project evals/Fuse.Evals -c Release -- stale fixture

The stop should deliver no stale error: the fix is already on disk when it runs, so anything it delivers beyond the current tree's errors is a defect. The result file records the post-edit, check and stop errors, whether the stop blocked, the stale errors it delivered, and whether it rechecked.

On GitHub Actions #

Times depend on what else the machine is doing, so the recorded results come from .github/workflows/evals.yml, which runs every job that measures on a fresh windows-latest runner that runs nothing else. Add the evals label to a pull request to run the latency and analyzers suites on the four open-source repositories.

Start the workflow from the Actions tab to choose:

  • its repos input names the repositories as a JSON array, default ["FluentValidation", "NodaTime", "Jellyfin", "Polly"], and its suites input names the suites as a JSON array, default ["correctness", "selection", "latency"].
  • To run one suite on one repository, start it with repos as ["NodaTime"] and suites as ["latency"].
  • The attribution, analyzers and scale suites run only when the suites input names them.
  • Its fresh-truth input ignores the cached truth, for a run after a flaky test made a truth answer wrong.
  • Its latency_parts input names the latency parts as a JSON array, default ["main", "agents"], and one part alone skips the merge.

What to run says which suites a change needs.

  • Build. One job builds Fuse and publishes the native client, and every other job downloads that build, so every result file records the same fuseBuild.
  • Latency. Two jobs per repository run the latency suite with the native client: one the checks and the test rounds, followed by the checks alone with the managed client on the same runner, the other the multi-agent scenario. A merge job puts the multi-agent result into the first job's file.
  • Truth. The truth side of the correctness and selection suites runs in shards, one job each, more of them on the larger repositories. For correctness there is 1 shard on the fixture and FluentValidation, 2 on NodaTime and Polly, and 4 on Jellyfin; for selection 1 on the fixture and FluentValidation, 4 on NodaTime and Polly, and 6 on Jellyfin. A shard whose truth is already in the Actions cache under its key does nothing.
  • Scale. One job generates the scale fixture, changes a quarter of its files, and measures one cold check with the native client, uploading evals-scale-fixture-scale. Like the attribution job, it runs only when the suites input names it.
  • Measure. One job per suite and repository merges the shards with the cached truth, measures Fuse on its own runner, writes the result file, and saves the merged truth to the cache. Each suite and repository is its own call of .github/workflows/evals-suite.yml, so a measure job starts as soon as its own shards finish, not when the slowest repository's do.

A measure job's artifact evals-<repo>-<suite> holds:

  • results/, the file to commit to evals/results in place of the older one.
  • truth/, the merged truth.
  • engine-logs/, the engine and hook logs of the measured repository.
  • runner.txt, which names the runner image, processor, memory and SDK.

The merged latency artifact evals-<repo>-latency holds results/ and managed/, the managed client's latency file, which goes to evals/results/managed in the same way and is the comparison Benchmarks quotes, with runner.txt and runner-agents.txt, the runner of the multi-agent scenario; the per-part latency artifacts also hold engine-logs/. Each truth shard's artifact holds its shard and its own runner.txt.

Runners of the same image can have different processors, so compare two builds within one job, as the latency jobs do, rather than across jobs.

Result files #

A suite writes evals/results/<suite>-<repo>-<yyyyMMdd-HHmm>.json, with the local time of the run. The repository keeps only the newest file of each suite and repository; older files stay in git history. Every file records:

  • suite, repo: what ran on which repository.
  • commit: the commit the repository was measured at.
  • fuseBuild: the build of fuse that was measured, as <version>/<module id>, the same id the engine compares.
  • treeCleanAfter: whether the suite left the working tree clean.

Correctness files also hold:

  • seed, requested and cases.
  • breaking and neutral (cases whose build reported errors beyond HEAD's, or none).
  • falseGreen, falseRedCases, falseRedErrors (contradicted errors), partialMisses, exactAgreement and fileAgreement (cases whose errors are in the same files).
  • unverifiableErrors, deferredByCompilerErrors and messageMismatchErrors.
  • causeLines, causeBytes and outputBytes (cause lines, their size and the whole output's size).
  • the sums filesChecked, documentsBound and filesWithReusedErrors, and keptAnswerHits.
  • fuseUnanswered (cases where fuse check exited with neither 0 nor 1).
  • unmeasuredCases, resultsIncompleteCases and cappedCasesComplete (whether every capped answer's results file holds every error).
  • fuseMedianMs and buildMedianSeconds.
  • fuseStats and dotnetStats (see below).
  • headBuildErrors.
  • truthKey and truthOrigins.
  • details, one object per case with its edits, the truth and Fuse errors, each classification list, its verdict, its times, and what the check cost: filesChecked, documentsBound (0 for a kept answer), wholeProjectsBound, keptAnswerHit, filesWithReusedErrors, printedErrors, totalErrors and resultsFileErrors.

Attribution files hold pairs, each with the renamedIn file, the method, the brokenIn file, ownWithoutSessions, otherWithoutSessions, ownWithSessions, otherWithSessions, leftToOtherSessions, and msWithoutSessions and msWithSessions, the wall time of both writers' hooks in each arm; the same counts summed over the pairs; the statistics of each arm's time; external, a list holding one pair with the renamedIn file, the method, the brokenIn file, otherWithRegistration, blockedWhileRegistered, blockedAfterEnd, expiredShielding (always null: registrations expire after 4 hours, which the suite does not wait out), msWithRegistration, msAfterEnd and note, with externalSkipped; and treeCleanAfter.

Scale files hold filesTotal, filesChanged, projectsTotal and projectsLoaded; checkMs, filesChecked and wholeProjectsBound; enginePeakWorkingSetMb and engineIdleWorkingSetMb; scaleFactor (15000 divided by the files, 2.5 at the recorded size), checkMsPer1kChanged and verdict. Full-scale numbers are extrapolated with the factor, never quoted as measured.

Stale files hold the target file; postEditErrors and postEditMs; checkErrors and checkMs; stopErrors, stopMs and stopBlocked; staleDelivered (stop errors absent from a fresh check; 0 means the stop rechecked), staleLines and rechecked.

Analyzers files hold files, the app project's file count; compilationWide, whether the engine log names the analyzer compilation-wide, and planLine, that log line; coldCheckMs; postEditHook, checkOneFile and checkManyFiles (over manyFiles files), each p50, p95, max and n in milliseconds; reportedByCheck and leftOutByHook, the two answers to the forbidden class; and enginePeakWorkingSetMb and engineIdleWorkingSetMb.

fuseStats and dotnetStats describe how the Fuse command's and the dotnet command's times spread over the cases, in seconds: n, fastest, median, mean, standardDeviation (the sample standard deviation), p95, slowest and total. The chart and Benchmarks quote them next to each median.

Medians are over the cases, and the average of the two middle values for an even count. Percentiles use the nearest-rank method: P95 of 10 or 15 samples is the slowest one.

Quoting the numbers #

The rule in AGENTS.md binds every page that quotes a benchmark: numbers come from files in evals/results, and each results table names the files it comes from. Counts are quoted exactly. Times, sizes and percentages are rounded half up: seconds to two decimals below 10 s and one decimal from 10 s, milliseconds and megabytes to whole numbers, percentages to at most one decimal. A speedup is the dotnet median divided by the Fuse median, to one decimal.

After committing the result files of a full run, delete the older file of the same suite and repository, run chart, and update every page that quotes the numbers:

  • the root README.md;
  • site/index.html, site/docs/benchmarks.html and site/docs/index.html;
  • the attribution costs in site/docs/how-it-works.html, and the load time in the Timeout section of site/docs/messages.html;
  • site/assets/og.png, whose text quotes the check speedup.
