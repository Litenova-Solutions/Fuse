About Fuse #

What is Fuse? #

A .NET tool that makes dotnet build and dotnet test faster for AI coding agents. It keeps your solution loaded in the background, reports only the compiler errors an edit caused, runs only the tests the edit affects, and prints only the errors of a build.

Why does Fuse exist? #

Agents check their work by running dotnet build and dotnet test, often dozens of times in one task. Each run is slow, lists old errors next to new ones, and prints far more than the agent needs. With several subagents, the builds also use a lot of memory and fail on each other's locked files.

Fuse removes that wait. On the benchmark repositories a check took 0.07 to 1.04 seconds where dotnet build took 1.78 to 12.8 seconds, and fuse test was 1.4x to 4.4x faster than dotnet test (Benchmarks). All agents in a repository share one Fuse process, and their builds take turns.

Is Fuse for people or for agents? #

Agents. The hooks run Fuse without the agent asking, and the output is only what an agent needs to act on. You run fuse init once, and can use the commands to try Fuse or see what the agent gets. For your own editing, your IDE is the better tool.

What does Fuse cost? #

Mainly memory. Fuse keeps the loaded projects in memory until it has been idle for 30 minutes: 256 MB to 795 MB in the benchmarks, and more on a machine with more memory. Each git worktree runs its own copy. The first edit that affects other projects has to load them, which took up to 92.2 s on Jellyfin, and agents in one repository wait for each other's checks. What Fuse costs lists every cost.

Which harnesses does Fuse support? #

Fuse supports Claude Code, Cursor, Gemini CLI, Codex, GitHub Copilot CLI and OpenCode through hooks, and VS Code agent mode and any other MCP host through fuse mcp. Claude Code and OpenCode are tested end to end. The others follow each harness's documented hook format and are covered by payload tests. Connect your agent lists what fuse init writes for each one.

Does Fuse need configuration? #

No. Run fuse init once in the repository and it writes the hook settings for each harness it finds. Fuse has no configuration file and no environment variables of its own. It needs the .NET 10 SDK and restored projects; if a restore is missing, it says so and names the dotnet restore command to run.

Does Fuse send my code or data anywhere? #

No. Everything runs locally, and Fuse has no telemetry and makes no network calls of its own. It never edits your code; the only files it writes in your repository are the hook settings and the .gitignore line from fuse init. Commands Fuse runs for you, such as dotnet build, act as they normally would.

Which platforms does Fuse run on? #

Windows, Linux and macOS, with the .NET 10 SDK. CI builds and tests Fuse on all three; the benchmarks come from one Windows machine.

What can Fuse not check? #

Fuse checks C# only. A check cannot see custom MSBuild targets that change compiler inputs or IL weaving, and it runs compilation-end analyzers only when it compiles whole projects, which happens past 500 files in reach; fuse build runs the real build. Test selection is static, so a test that reaches code only through reflection may not be selected. Limits lists every case.

What comes next for Fuse? #

Even faster feedback. We are exploring an index of the solution that survives restarts, so that Fuse can answer the moment an edit is saved instead of first loading the projects. Fuse does not index code today; the changelog will say when it does.

Fuse and other tools #

Which tools overlap with Fuse? #

Fuse does three jobs for an agent: it reports the compiler errors the changes introduced, in every project they can break; it runs the tests the changes can reach; and it prints only the errors of a build. Other tools do one of these jobs, or part of one, and most are built for a person in an editor or for CI rather than for an agent's hooks. We know of no other tool that does all three for an agent.

The table lists the kinds of tool people compare Fuse with, and examples of each as of September 2026. The benchmarks compare Fuse with dotnet build and dotnet test only, not with these tools.

How is Fuse different from dotnet build? #

dotnet build starts MSBuild, builds the projects and lists every error, including errors that already exist. Fuse keeps the solution compiled in memory and reports only the errors an edit introduced, so it answers sooner: in the benchmarks the median check took between 0.07 and 1.04 seconds where the median dotnet build took between 1.78 and 12.8 seconds. It does not replace the build; fuse build runs the real dotnet build.

How is Fuse different from a language server (LSP)? #

A language server gives an editor, or an agent's harness, the errors, warnings, completion and navigation for the files it has open, over the Language Server Protocol (LSP). For C# that is csharp-ls, which Claude Code's csharp-lsp plugin runs, or the Roslyn language server behind the C# extension for VS Code, which OpenCode runs. In a harness that runs one, the agent gets the diagnostics of the file it just edited. Fuse answers a narrower question, which errors did the changes introduce, and differs in four ways:

  • Compared with HEAD. A language server reports the errors a file has now. It has no notion of HEAD, the commit you have checked out, so an error that was already committed looks the same as one the edit caused. Fuse reports only the errors HEAD does not have.
  • Across projects. An edit that renames a public method breaks its callers in other files and other projects, which the agent has not opened, so it hears of them at the next build. Fuse finds the files that use each changed declaration, checks them, and names the change that broke each one.
  • Before the agent finishes. Fuse's stop hook checks every change once more before the agent ends its turn, and sends it back once if errors remain.
  • Tests and builds. A language server does not run tests or builds. Fuse runs the affected tests and prints only the errors of a build.

A language server does things Fuse does not: completion, go to definition, find references, hover, rename and warnings. Fuse reports errors only and has no navigation. What a check does describes Fuse's side in full.

Can I use Fuse and a language server together? #

Yes. They do not conflict: the language server gives the agent navigation and the diagnostics of the file it edited, and Fuse gives it the introduced errors across projects and the affected tests. Each loads the solution in its own process, so the machine holds two copies of it in memory; Benchmarks gives the memory Fuse's engine used. An error in the edited file can reach the agent from both.

How is Fuse different from Roslyn MCP servers? #

An MCP server gives the agent tools it can call. Roslyn-based servers such as SharpLensMcp, RoselineMCP and AgenticDotNet, and Serena, which drives language servers, offer many tools for navigation, refactoring and diagnostics. The agent has to decide to call them, and their diagnostics tools list the errors the code has; none that we know of compares with HEAD.

Fuse runs from hooks, so every edit is checked without the agent calling anything. Its MCP server has three tools, fuse_check, fuse_test and fuse_build, for hosts that run no hooks, such as VS Code agent mode. A navigation server and Fuse can run side by side.

How is Fuse different from code search and indexing tools? #

Code search and indexing tools, such as COA CodeSearch, code graph MCP servers and Serena's symbol tools, build an index of the code so an agent can find where something is defined and used, and read fewer files before it edits. Fuse does not index or search the code today. It answers after an edit: which errors did it introduce, and which tests can it break. The two kinds of tool work at different points of a task and can run together.

How is Fuse different from test impact analysis tools? #

Test impact analysis tools choose which tests to run for a change:

  • dotnet-affected selects the projects a change affects, from the project graph, to build and test only those in CI.
  • dotnet-tia selects the tests a git diff can reach, from Roslyn references, as a command for CI.
  • NCrunch and Live Unit Testing in Visual Studio Enterprise run tests continuously in the IDE, and use the code coverage of earlier runs to choose the tests a change affects.

Fuse selects tests from the code as written, like dotnet-tia, so it needs no earlier run. It runs when the agent runs dotnet test, which the pre-shell hook rewrites to fuse test. It selects from the changes against HEAD, skips MSBuild when only C# sources changed, and prints only the failures. Static selection misses a test that reaches the code only through reflection or configuration; Limits says when to run fuse test --all, and How Fuse selects tests gives the steps.
