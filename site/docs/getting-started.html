Getting Started

All documentation pages

This tutorial installs Fuse, sets it up in a small sample repository, and shows what it reports for an edit that breaks a caller and for an edit that fails a test, and what its hooks send the agent.

This page is for a developer trying Fuse for the first time, who has used dotnet and git before.

After it run fuse init in your own repository, and read Connect your agent for the harness you use.

You need the .NET 10 SDK, git, and access to NuGet to restore the sample's packages. The commands are for bash; on Windows, run them in Git Bash. The output on this page is from a run of Fuse 5.1.0 on Windows, and every path in it is relative to the repository.

1. Install Fuse #

Fuse is a .NET tool, installed from NuGet like any other:

dotnet tool install -g Fuse
fuse --version
5.1.0

dotnet tool install -g puts fuse in ~/.dotnet/tools (%USERPROFILE%\.dotnet\tools on Windows). That folder has to be on your PATH, and also on the PATH of the harness that runs the hooks, because every hook runs the command fuse.

2. Create a sample repository #

The sample is the smallest repository that shows what Fuse is for: a library Lib with a class Calc, a console app App that calls it, and an xUnit test project Lib.Tests that tests it. App and Lib.Tests are dependent projects of Lib, so an edit in Lib can break code in both.

mkdir fuse-sample
cd fuse-sample
git init
dotnet new sln -n Sample
dotnet new classlib -n Lib -o Lib
dotnet new console -n App -o App
dotnet new xunit -n Lib.Tests -o Lib.Tests
dotnet sln add Lib App Lib.Tests
dotnet add App reference Lib
dotnet add Lib.Tests reference Lib
rm Lib/Class1.cs Lib.Tests/UnitTest1.cs

Create Lib/Calc.cs:

namespace Lib;

public class Calc
{
    public int Add(int a, int b) => a + b;

    public int Multiply(int a, int b) => a * b;
}

Replace the contents of App/Program.cs with:

using Lib;

Console.WriteLine(new Calc().Add(2, 3));

Create Lib.Tests/CalcTests.cs:

namespace Lib.Tests;

public class CalcTests
{
    [Fact]
    public void Adds() => Assert.Equal(5, new Calc().Add(2, 3));

    [Fact]
    public void Multiplies() => Assert.Equal(6, new Calc().Multiply(2, 3));
}

Create .gitignore, so that build output is not part of the working tree Fuse compares:

bin/
obj/

3. Commit and build #

Fuse compares the working tree with HEAD, the commit you have checked out, so the repository needs a commit. Everything in that commit is the baseline: whatever errors it has are not the agent's, and Fuse will never report them.

Fuse also needs restored projects, and it never restores on its own. dotnet build restores the packages and builds once. The build also gives the test project build output, which later lets fuse test run the tests without starting MSBuild.

git add -A
git commit -m "Add the sample"
dotnet build

4. Register the hooks #

fuse init
wrote .claude/settings.json
fuse: hooks registered; after each edit your agent gets the compiler errors the edit introduced, `dotnet test` runs the affected tests, and `dotnet build` prints only its errors

fuse init looks in the repository root for each harness's folder, such as .cursor/ or .gemini/, and writes that harness's settings. The sample has none, so it set up Claude Code, which is the default. Connect your agent shows the file it wrote and what every other harness gets.

Run a first check:

fuse check
fuse: no errors introduced (0 file(s) checked)

Nothing differs from HEAD yet, so there was nothing to check. This first call also started the engine, the background process that keeps the projects compiled for this repository. Every later command and hook in this repository reuses it, until it has been idle for 30 minutes.

5. Break a caller #

Now make the kind of edit an agent makes all the time: rename a method. Change Add to Plus in Lib/Calc.cs, so the file reads:

namespace Lib;

public class Calc
{
    public int Plus(int a, int b) => a + b;

    public int Multiply(int a, int b) => a * b;
}

Lib itself still compiles. The code that breaks is in the other two projects, which still call Add. Check again, and print the exit code:

fuse check
echo "exit code $?"
App/Program.cs(3,30): error CS1061: 'Calc' does not contain a definition for 'Add' and no accessible extension method 'Add' accepting a first argument of type 'Calc' could be found (are you missing a using directive or an assembly reference?)
  removed: public int Add(int a, int b)
Lib.Tests/CalcTests.cs(6,54): error CS1061: 'Calc' does not contain a definition for 'Add' and no accessible extension method 'Add' accepting a first argument of type 'Calc' could be found (are you missing a using directive or an assembly reference?)
  removed: public int Add(int a, int b)
fuse: 2 error(s) introduced in 2 file(s) (App, Lib.Tests); Lib declarations changed, 2 dependent project(s) checked
exit code 1

Fuse found both broken callers, although neither file was edited. It works that out from the edit itself:

  1. The edit removed a declaration, Add, so it can break code in other files. (A change inside a method body cannot, and there the check would have stopped at Lib/Calc.cs.)
  2. Fuse searched Lib and the projects that depend on it for code that uses Add, and found App/Program.cs and Lib.Tests/CalcTests.cs.
  3. It compiled those files and kept only the errors HEAD does not have.

The indented line under each error is the cause: the declaration change that broke that file, here Add as HEAD had it. An agent reading an error in a file it never touched sees at once which of its edits to look at. The last line counts the errors, names the projects they are in, and says how far the check reached. Exit code 1 means Fuse found errors to fix; Commands describes every part of the output.

6. See what the hooks send the agent #

You ran fuse check by hand. In a real session nobody runs it: the harness runs Fuse's hooks, and each hook sends the agent the same text. To see what the agent would receive, send a hook the JSON its harness sends. Claude Code runs the post-edit hook after every edit, with the edited file in the payload:

echo '{"tool_input":{"file_path":"Lib/Calc.cs"}}' | fuse hook claude post-edit; echo " [exit code $?]"
App/Program.cs(3,30): error CS1061: 'Calc' does not contain a definition for 'Add' and no accessible extension method 'Add' accepting a first argument of type 'Calc' could be found (are you missing a using directive or an assembly reference?)
  removed: public int Add(int a, int b)
Lib.Tests/CalcTests.cs(6,54): error CS1061: 'Calc' does not contain a definition for 'Add' and no accessible extension method 'Add' accepting a first argument of type 'Calc' could be found (are you missing a using directive or an assembly reference?)
  removed: public int Add(int a, int b)
fuse: 2 error(s) introduced in 2 file(s) (App, Lib.Tests); Lib declarations changed, 2 dependent project(s) checked [exit code 2]

Claude Code runs this hook in the background while the agent keeps working. Exit code 2 tells Claude Code to wake the agent and show it this text. An edit that introduces no error prints nothing and exits with 0, so the agent hears from Fuse only when there is something to fix.

When the agent tries to finish, the stop hook checks every change once more and, if errors remain, sends the agent back with them:

echo '{}' | fuse hook claude stop
{"decision":"block","reason":"App/Program.cs(3,30): error CS1061: 'Calc' does not contain a definition for 'Add' and no accessible extension method 'Add' accepting a first argument of type 'Calc' could be found (are you missing a using directive or an assembly reference?)\n  removed: public int Add(int a, int b)\nLib.Tests/CalcTests.cs(6,54): error CS1061: 'Calc' does not contain a definition for 'Add' and no accessible extension method 'Add' accepting a first argument of type 'Calc' could be found (are you missing a using directive or an assembly reference?)\n  removed: public int Add(int a, int b)\nfuse: 2 error(s) introduced in 2 file(s) (App, Lib.Tests); Lib declarations changed, 2 dependent project(s) checked\nFix these errors before finishing; HEAD does not have them, so your changes introduced them."}

Before the agent runs a shell command, the pre-shell hook rewrites dotnet build and dotnet test to their Fuse equivalents, so the agent gets the short output and the affected tests without having to know Fuse exists:

echo '{"tool_input":{"command":"dotnet test"}}' | fuse hook claude pre-shell
{"hookSpecificOutput":{"hookEventName":"PreToolUse","updatedInput":{"command":"fuse test"}}}

7. Run the affected tests #

Undo the rename, then make an edit that compiles but is wrong. Restore the file:

git restore Lib/Calc.cs

Then edit the Multiply line in Lib/Calc.cs to read:

    public int Multiply(int a, int b) => a * b + 1;

This edit changes only a method body, so it cannot break a caller, and the check stops at the edited file:

fuse check
fuse: no errors introduced (1 file(s) checked)

It does break a test. Run the affected tests:

fuse test
echo "exit code $?"
FAILED Lib.Tests.CalcTests.Multiplies
  Assert.Equal() Failure: Values differ
  Expected: 6
  Actual:   7
  at Lib.Tests.CalcTests.Multiplies() in Lib.Tests/CalcTests.cs:line 9
fuse: 1 failed, 0 passed in 2.8 s; ran 1 test(s) affected by your changes out of 2; fuse test --all runs everything; without MSBuild
exit code 1

Fuse ran one of the two tests, Multiplies, because it is the only test that reaches Multiply. Adds cannot fail because of this edit, so it did not run. The output holds only the failure, with the assertion and the line in the test.

without MSBuild at the end says how the tests ran: instead of rebuilding with MSBuild, Fuse compiled the changed Lib from memory into a copy of the test project's build output and ran the tests from that copy. When the agent runs dotnet test, the pre-shell hook turns it into this command.

8. Clean up #

git restore Lib/Calc.cs

The engine exits on its own after 30 idle minutes. Delete the fuse-sample folder when you are done. Fuse's own files for it, such as its logs, are in your local application data, as Troubleshooting describes.

Next steps #

  • Run fuse init in your own repository, and read Connect your agent for what it writes for your harness.
  • Read Limits before you rely on a clean answer, especially in a repository with custom build logic.
  • Read How it works for what happened behind each step of this tutorial.
