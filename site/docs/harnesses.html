Connect Your Agent

All documentation pages

Fuse connects to the agent tools in your repository through one command, fuse init. This page shows what that command detects, which file it writes for each harness, what each hook answers, and how you run Fuse from an MCP host without hooks instead.

This page is for you when you have run, or are about to run, fuse init in your repository and want to know what it set up and why.

After reading it you can check the settings fuse init wrote, tell which Fuse behavior your harness gets, and connect an MCP host by hand.

In short

  • One command, fuse init, detects the harnesses in your repository and writes the hook settings for each one.
  • Fuse connects an agent through 3 hooks: post-edit reports the errors an edit introduced, pre-shell rewrites dotnet build and dotnet test to fuse build and fuse test, and stop checks every change before the agent finishes.
  • In Cursor, GitHub Copilot CLI, Codex and Muse Code, Fuse rewrites only one plain dotnet build or dotnet test.
  • VS Code agent mode and any other MCP host run Fuse as an MCP server instead of running hooks.
  • When you run fuse init again, it updates only its own entries and leaves everything else alone.

How Fuse connects to an agent #

Your AI agent runs inside a harness, which is one of Claude Code, Cursor, Gemini CLI, Codex, GitHub Copilot CLI, OpenCode or Muse Code. Each harness can run a command when something happens while the agent works, and it calls such a command a hook. Fuse uses 3 events, and every hook it registers runs fuse hook <harness> <event>:

EventWhen it runsWhat Fuse does
post-editAfter your agent edits or writes a fileFuse checks the edited C# files and tells the agent about any error the edit introduced.
pre-shellBefore your agent runs a shell commandFuse rewrites dotnet build and dotnet test to fuse build and fuse test in the projects the command names, so the agent gets short output and only the affected tests. The rewritten command prints a notice on standard error that names the rewrite.
stopWhen your agent tries to finishFuse checks every change. When errors remain, it sends the agent back once.

Because the harness runs these hooks, your agent needs neither to know that Fuse exists nor to remember to call it. Fuse answers it only when an edit introduced an error or when a project needs a restore. For the detail of each event, see Commands.

A command that the pre-shell hook rewrote names the rewrite on standard error before it runs:

fuse: dotnet test routed to fuse test (tests affected by your changes; fuse test --all runs every test)
fuse: dotnet build routed to fuse build (first 20 errors; fuse build --all-errors for every error)

When you type fuse build or fuse test yourself, it prints no notice. The hook rewrites only a bare dotnet or dotnet.exe at the start of a command. A full path to dotnet.exe therefore runs as written. fuse uninit removes the hooks.

When you work in VS Code agent mode, it runs no hooks. For VS Code agent mode and for any other MCP host, Fuse runs as an MCP server instead. The agent then calls its tools when it decides to.

What fuse init detects and writes #

fuse init looks in your repository root for each harness's folder or file and writes settings for every harness it finds. When it finds no harness, it sets up Claude Code. It also adds .fuse/ to the root .gitignore (see The .fuse folder).

HarnessDetected byFile writtenEvents
Claude Code.claude/ or CLAUDE.md, or no other harness and no .vscode/.claude/settings.jsonpost-edit, pre-shell, stop (also for subagents)
Cursor.cursor/.cursor/hooks.jsonpost-edit, pre-shell, stop
Gemini CLI.gemini/ or GEMINI.md.gemini/settings.jsonpost-edit, pre-shell, stop
Codex.codex/.codex/hooks.jsonpost-edit, pre-shell, stop
GitHub Copilot CLI.github/copilot-instructions.md or .github/hooks/.github/hooks/fuse.jsonpost-edit, pre-shell, stop
OpenCode.opencode/, opencode.json or opencode.jsonc.opencode/plugins/fuse.jspost-edit, pre-shell, stop
Muse Code.muse/.muse/plugins/fuse/.muse-plugin/plugin.json, which you install and approve nextpost-edit, pre-shell, stop
VS Code agent mode.vscode/.vscode/mcp.jsonno events; the MCP server

4 harnesses rewrite fewer commands. Cursor, GitHub Copilot CLI, Codex and Muse Code apply a rewritten command only together with an allow answer. That answer runs the command without asking you. Fuse approves only a command it rewrote whole, so in those harnesses it rewrites only one plain dotnet build or dotnet test, as the Codex note below describes. Every other command runs as the agent wrote it, with neither the build lock nor test selection.

A repository that holds only .vscode/ gets only .vscode/mcp.json and no Claude Code settings. In a repository with every harness's folder and .vscode/, fuse init writes 8 settings files and .gitignore and prints the step Muse Code still needs:

$ fuse init

wrote .cursor/hooks.json
wrote .gemini/settings.json
wrote .codex/hooks.json
wrote .github/hooks/fuse.json
wrote .opencode/plugins/fuse.js
wrote .muse/plugins/fuse/.muse-plugin/plugin.json
wrote .vscode/mcp.json

fuse: hooks registered by Fuse 5.7.0; after each edit your agent gets the compiler errors the edit introduced, `dotnet test` runs the affected tests, and `dotnet build` prints only its errors
fuse: Muse Code loads hooks from an installed plugin: run `muse plugins install .muse/plugins/fuse --scope project` and `muse plugins approve fuse` once, and `muse plugins update fuse` after a later fuse init

The settings blocks below show the files from that run, and current builds write them as shown.

fuse init --instructions also writes a Fuse section into AGENTS.md. When CLAUDE.md and GEMINI.md exist, it writes the section into them too, so each agent knows the commands from the start (fuse init --instructions).

Claude Code #

{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write|MultiEdit",
        "hooks": [
          {
            "type": "command",
            "command": "fuse hook claude post-edit",
            "asyncRewake": true,
            "timeout": 300
          }
        ]
      }
    ],
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "fuse hook claude pre-shell",
            "timeout": 10
          }
        ]
      }
    ],
    "Stop": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "fuse hook claude stop",
            "timeout": 300
          }
        ]
      }
    ],
    "SubagentStop": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "fuse hook claude stop",
            "timeout": 300
          }
        ]
      }
    ]
  }
}
  • post-edit runs in the background (asyncRewake). The agent therefore keeps working while the check runs, and the hook can wait for the engine to finish loading. When the edit introduced errors, the hook writes them to standard error and exits with 2. That exit wakes the agent and shows it the text.
  • pre-shell answers {"hookSpecificOutput":{"hookEventName":"PreToolUse","updatedInput":{...}}}, carrying over every field of the original tool input with the rewritten command. It sets no permission decision, so the rewritten command follows your normal permission rules.
  • stop answers {"decision":"block","reason":"..."} with the errors. When there are no errors, it prints nothing. It runs for the Stop event and, since Fuse 5.4.0, for SubagentStop. Fuse therefore sends a subagent back for the errors its own edits cause before it hands its work back. Once the subagent has stopped, its parent counts its edits as its own (the stop hook and subagents). Run fuse init again to add SubagentStop to settings that an earlier version wrote.

When the settings' permissions.allow list lets the agent run dotnet build or dotnet test without asking (Bash(dotnet:*), Bash(dotnet *), or a rule that starts with Bash(dotnet build or Bash(dotnet test), fuse init adds Bash(fuse build:*), Bash(fuse test:*), or both. Without that addition, the rewritten command would ask for permission where the original did not. A narrower rule, such as one for dotnet test on one project, still gains the rule for every fuse test.

Cursor also runs the hooks from Claude Code's settings. A Claude Code hook whose payload comes from Cursor does nothing, so the Cursor hooks answer in a Cursor session. To get them, create .cursor/ and run fuse init again.

Cursor #

{
  "version": 1,
  "hooks": {
    "postToolUse": [
      {
        "command": "fuse hook cursor post-edit",
        "matcher": "Write",
        "timeout": 60
      }
    ],
    "preToolUse": [
      {
        "command": "fuse hook cursor pre-shell",
        "matcher": "Shell",
        "timeout": 10
      }
    ],
    "stop": [
      {
        "command": "fuse hook cursor stop",
        "timeout": 300
      }
    ]
  }
}
  • post-edit answers with {"additional_context":"..."}. Cursor runs it inline, so your agent waits for it. The hook therefore does not wait for an engine that is still loading, and it waits up to 50 seconds for the answer. The stop hook reports the edits that post-edit skipped.
  • pre-shell answers {"permission":"allow","updated_input":{...}} with the rewritten command, carrying over every other field of the tool input. Cursor takes the replacement only with an allow answer, so Fuse rewrites only one plain dotnet build or dotnet test (see the note above). When Fuse does not rewrite a command, it gets no answer and runs as written.
  • stop answers {"followup_message":"..."}. When there are no errors, it answers {}.

Gemini CLI #

Gemini CLI measures its timeouts in milliseconds.

{
  "hooks": {
    "AfterTool": [
      {
        "matcher": "write_file|replace",
        "hooks": [
          {
            "name": "fuse-check",
            "type": "command",
            "command": "fuse hook gemini post-edit",
            "timeout": 60000
          }
        ]
      }
    ],
    "BeforeTool": [
      {
        "matcher": "run_shell_command",
        "hooks": [
          {
            "name": "fuse-dotnet",
            "type": "command",
            "command": "fuse hook gemini pre-shell",
            "timeout": 10000
          }
        ]
      }
    ],
    "AfterAgent": [
      {
        "hooks": [
          {
            "name": "fuse-stop",
            "type": "command",
            "command": "fuse hook gemini stop",
            "timeout": 300000
          }
        ]
      }
    ]
  }
}
  • post-edit answers {"hookSpecificOutput":{"hookEventName":"AfterTool","additionalContext":"..."}} inline, as in Cursor.
  • pre-shell answers {"hookSpecificOutput":{"hookEventName":"BeforeTool","tool_input":{"command":"..."}}}, and Gemini CLI merges that answer over the tool's arguments.
  • stop answers {"decision":"deny","reason":"..."}. When there are no errors, it answers {}.

Codex #

{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "^apply_patch$",
        "hooks": [
          {
            "type": "command",
            "command": "fuse hook codex post-edit",
            "timeout": 60
          }
        ]
      }
    ],
    "PreToolUse": [
      {
        "matcher": "^Bash$",
        "hooks": [
          {
            "type": "command",
            "command": "fuse hook codex pre-shell",
            "timeout": 10
          }
        ]
      }
    ],
    "Stop": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "fuse hook codex stop",
            "timeout": 300
          }
        ]
      }
    ]
  }
}
  • post-edit reads the edited files from the apply_patch patch and answers {"hookSpecificOutput":{"hookEventName":"PostToolUse","additionalContext":"..."}} inline.
  • pre-shell answers with {"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"allow","updatedInput":{"command":"..."}}}. For which commands it answers, see the note below.
  • stop answers {"decision":"block","reason":"..."}. When there are no errors, it answers {}.

Why Codex rewrites fewer commands. Codex applies a rewritten command only together with an allow decision. That decision runs the command without asking you. Fuse approves only what it rewrote whole, so it answers only when one dotnet build or dotnet test with plain arguments forms the entire command, such as dotnet test --no-build.

A command that is not one plain build or test, such as cd Lib && dotnet build or one with a pipe, a redirection, a quote, $, a backtick or a line break, gets no answer. That command goes through Codex's approval as the agent wrote it, with neither the build lock nor test selection.

GitHub Copilot CLI #

{
  "version": 1,
  "hooks": {
    "postToolUse": [
      {
        "type": "command",
        "matcher": "edit|create",
        "bash": "fuse hook copilot post-edit",
        "powershell": "fuse hook copilot post-edit",
        "timeoutSec": 60
      }
    ],
    "preToolUse": [
      {
        "type": "command",
        "matcher": "bash|powershell",
        "bash": "fuse hook copilot pre-shell",
        "powershell": "fuse hook copilot pre-shell",
        "timeoutSec": 10
      }
    ],
    "agentStop": [
      {
        "type": "command",
        "bash": "fuse hook copilot stop",
        "powershell": "fuse hook copilot stop",
        "timeoutSec": 300
      }
    ]
  }
}
  • post-edit reads the tool arguments, which Copilot CLI may send as a JSON string, and answers {"additionalContext":"..."} inline.
  • pre-shell answers {"permissionDecision":"allow","modifiedArgs":{...}} with the rewritten command, carrying over every other argument. Copilot CLI substitutes arguments only with an allow answer, so Fuse rewrites only one plain dotnet build or dotnet test (see the note above). When Fuse does not rewrite a command, it gets no answer, and Copilot CLI uses its default behavior.
  • stop answers {"decision":"block","reason":"..."}. When there are no errors, it answers {}.

OpenCode #

OpenCode runs JavaScript plugins rather than commands. fuse init therefore writes .opencode/plugins/fuse.js, a plugin that starts fuse hook opencode <event> for each tool event and applies the answer. That plugin carries both plugin formats: OpenCode 2 calls its setup function, and OpenCode 1 calls its server function.

  • post-edit runs after the edit, write, multiedit, patch and apply_patch tools. It sends the tool call's sessionID as session_id and appends the errors to the tool's result, which the agent reads next.
  • pre-shell runs before the shell and bash tools, where it sets the rewritten command on the tool's arguments.
  • stop runs when a session finishes a turn (session.execution.succeeded in OpenCode 2 and session.idle in OpenCode 1). When errors remain, it sends the agent the stop hook's text as a prompt, once. The next finished turn of that session then ends whatever the result.

The plugin allows 10 seconds for pre-shell, 60 seconds for post-edit and 300 seconds for stop. It treats a failure or a timeout as no answer.

Muse Code #

Muse Code runs hooks only from plugin bundles. A bundle is a folder with a manifest that Muse installs into its own cache. fuse init writes the bundle .muse/plugins/fuse, and its manifest belongs to Fuse and is written whole:

{
  "schemaVersion": 1,
  "name": "fuse",
  "displayName": "Fuse",
  "version": "1.0.0",
  "description": "Compiler errors your edits introduced, affected tests and compact build output for .NET, from fuse.codes.",
  "compat": {
    "source": "native",
    "manifestDir": ".muse-plugin"
  },
  "capabilities": {
    "skills": [],
    "commands": [],
    "hooks": [
      {
        "id": "post-edit",
        "event": "PostToolUse",
        "command": [
          "fuse",
          "hook",
          "muse",
          "post-edit"
        ],
        "timeoutMs": 60000,
        "statusMessage": "Checking the edit with Fuse"
      },
      {
        "id": "pre-shell",
        "event": "PreToolUse",
        "command": [
          "fuse",
          "hook",
          "muse",
          "pre-shell"
        ],
        "timeoutMs": 10000
      },
      {
        "id": "stop",
        "event": "Stop",
        "command": [
          "fuse",
          "hook",
          "muse",
          "stop"
        ],
        "timeoutMs": 300000,
        "statusMessage": "Checking every change with Fuse"
      }
    ],
    "mcpServers": [],
    "reminders": []
  }
}

Muse loads the hooks only after you install the bundle in the project and approve them. Run the install and approve commands below once in the repository, and run muse plugins update fuse after a later fuse init. fuse init prints the same step:

muse plugins install .muse/plugins/fuse --scope project
muse plugins approve fuse

Muse installs a project plugin only in a workspace you trust. It asks you to trust that workspace first. muse plugins list shows fuse with active=true once the plugin runs.

  • post-edit runs after every tool, since a plugin hook has no tool matcher. Fuse acts only after the edit_file, write_file and apply_patch tools, so a tool that only reads a file neither checks it nor credits it to the session. Fuse reads the file from path, relative to the payload's cwd, and answers {"decision":"block","reason":"..."} inline. Muse shows the model the reason and goes on with the turn. It does not show additionalContext for this event.
  • pre-shell reads the shell tool's command, where the tool is powershell on Windows. It answers {"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"allow","updatedInput":{...}}}, keeping the tool's other fields, such as description and workdir. Muse rejects updatedInput without an allow decision. As in Codex, Fuse therefore answers only when the whole command is one dotnet build or dotnet test with plain arguments.
  • stop answers {"decision":"block","reason":"..."}. When there are no errors, it answers {}. Muse sends stop_hook_active as the string "true" or "false". Fuse reads either form.

Fuse registers no SubagentStop hook for Muse, because Muse fires that event for its own helper agents many times in a turn. Fuse therefore does not check a Muse subagent's stop (Sessions).

Sessions in one working tree #

A session is one agent's run as its harness identifies that run in a hook payload. When the post-edit payload names a session, the post-edit hook tells that agent only the errors its own edits cause. It leaves out the errors from other agents' edits in the same working tree, with a count (how an error is attributed).

Fuse prefixes each session id with the harness's name, so two harnesses never share a session. The stop hook checks every change. When the payload names a session, it blocks only on the errors that session's edits cause and on those in changes that no session is credited with.

The pre-shell hook passes the session to fuse test, and that command runs the tests that session's edits affect (a session's own tests).

HarnessSession id Fuse readsA subagent
Claude Codesession_id, and agent_id inside a subagent (Claude Code 2.1.69 and later)A session of its own, from the parent's session_id and its agent_id
Cursorconversation_idA session of its own, because Cursor gives a subagent a conversation of its own
Gemini CLIsession_idThe parent's session, because the payload has nothing that tells them apart
Codexsession_id, and agent_id inside a subagentA session of its own, from the parent's session_id and its agent_id
GitHub Copilot CLIsessionId, or session_id in its PascalCase eventsThe parent's session, because the payload has nothing that tells them apart
OpenCodeThe tool call's sessionID, which the plugin sends as session_idA session of its own, because OpenCode runs a subagent in a child session with its own id
Muse Codesession_idA session of its own whose id does not name its parent, so its edits never count as its parent's

A payload without an id, a blank one, or one longer than 256 characters or holding a control character counts as no session. The hook then reports every error, as for a harness that sends none.

To set up and check work that several agents share, see Subagents and parallel agents.

VS Code agent mode #

VS Code runs no hooks. fuse init therefore registers Fuse's MCP server instead. The agent then has 3 tools, fuse_check, fuse_test and fuse_build, and calls them when it decides to rather than after every edit.

  • fuse_check takes the files to check and max_errors, which shows at most that many errors, from 1 to 100000, instead of the default 20.
  • fuse_test takes all to run every test and failed to rerun the tests that failed in the last recorded run. The two cannot be combined.
  • fuse_build takes target, which names the project or solution to build.
{
  "servers": {
    "fuse": {
      "type": "stdio",
      "command": "fuse",
      "args": [
        "mcp"
      ],
      "cwd": "${workspaceFolder}"
    }
  }
}

Other MCP hosts #

Any MCP host can run the same server as the command fuse with the argument mcp, over standard input and output and with the repository as its working directory. The server finds the repository from its working directory on every call, so an MCP host that starts servers elsewhere has to set the directory, as cwd does above. For the tools, their arguments and a transcript of a session, see Commands.

Running fuse init again #

Run fuse init again after you update Fuse, so the settings and the OpenCode plugin match the installed version. Run it again after you add a harness's folder to the repository. It updates those files in place:

  • In the settings files shared with other tools (.claude/settings.json, .cursor/hooks.json, .gemini/settings.json, .codex/hooks.json and .vscode/mcp.json), it removes Fuse's own entries, both the handlers whose command starts with fuse hook and the fuse MCP server, and writes them again. It keeps every other entry. It reads the file with comments and trailing commas allowed and writes it back as plain JSON, so it keeps no comments.
  • .github/hooks/fuse.json, .opencode/plugins/fuse.js and .muse/plugins/fuse/.muse-plugin/plugin.json belong to Fuse, and Fuse writes them whole. Because Muse Code reads its installed copy, run muse plugins update fuse after fuse init changes the manifest.
  • .gitignore changes only when it has no line about the .fuse folder (The .fuse folder).
  • When a file already holds exactly what fuse init would write, it stays as it was. The output then names it with unchanged instead of wrote, so a second run in the same repository prints unchanged .claude/settings.json.

As an example, take a Claude Code settings file that holds a comment, a formatter hook and a dotnet test allowance:

{
  // The team's formatter hook.
  "permissions": {
    "allow": ["Bash(dotnet test:*)"]
  },
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [{ "type": "command", "command": "dotnet format --include $CLAUDE_FILE_PATHS" }]
      }
    ]
  }
}

fuse init keeps the formatter hook and drops the comment. It adds Bash(fuse test:*) because dotnet test was allowed, and it adds its own hooks after the others:

{
  "permissions": {
    "allow": [
      "Bash(dotnet test:*)",
      "Bash(fuse test:*)"
    ]
  },
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "dotnet format --include $CLAUDE_FILE_PATHS"
          }
        ]
      },
      {
        "matcher": "Edit|Write|MultiEdit",
        "hooks": [
          {
            "type": "command",
            "command": "fuse hook claude post-edit",
            "asyncRewake": true,
            "timeout": 300
          }
        ]
      }
    ],
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "fuse hook claude pre-shell",
            "timeout": 10
          }
        ]
      }
    ],
    "Stop": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "fuse hook claude stop",
            "timeout": 300
          }
        ]
      }
    ],
    "SubagentStop": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "fuse hook claude stop",
            "timeout": 300
          }
        ]
      }
    ]
  }
}

The .fuse folder #

Fuse reserves the .fuse folder in the repository root for files it may keep inside a repository, such as an index. Fuse 5 writes nothing there today, while Fuse 4 kept its index there. fuse init adds .fuse/ to the root .gitignore and creates that file when there is none, so that folder is never committed:

  • The line goes at the end, in the line endings the file already uses, and the rest of the file stays as it was.
  • A file that already has a line about the folder, such as .fuse, /.fuse/, **/.fuse or !.fuse/, stays unchanged, so a repository that chose to commit the folder keeps that choice.
  • fuse init prints wrote .gitignore only after it changed the file.

Tested versions #

  • Fuse 5.0.0 was run manually end to end with Claude Code 2.1.282 and with OpenCode 2.0.15.
  • Fuse 5.2.4's sessions were run end to end with Claude Code 2.1.288, with 2 sessions at once and with 2 subagents of one session, and with OpenCode 2.0.21, with up to 4 sessions at once and with 2 subagents of one session.
  • Fuse 5.4.0 was run end to end with Muse Code 1.4.10 on Windows, where the post-edit report, the rewritten dotnet build and the blocked stop each reached the model.

Unit tests cover every harness's answers and the files fuse init writes. The Cursor, Gemini CLI, Codex and Copilot CLI adapters, and the OpenCode 1 plugin format, follow each harness's documented hook format. The plugin's JavaScript has no tests of its own.
