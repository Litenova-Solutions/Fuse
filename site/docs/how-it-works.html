How Fuse Works

All documentation pages

Fuse answers two questions for a coding agent in a .NET repository: which compiler errors did the changes introduce, and which tests can the changes break. It answers both from a background process that keeps the solution loaded, so the agent does not wait for a full build. All agents and subagents in the repository share that process.

This page is for anyone who wants to know what happens between an agent's edit and Fuse's answer, and why Fuse is built that way: a user deciding how far to trust a clean answer, or a contributor starting on the code.

How to read it: the first two sections explain the idea in plain terms. Each later section starts with a summary and then gives the exact rules. Architecture maps this behavior to the code, and Limits lists what it cannot see.

The idea: compare two versions #

Every answer Fuse gives compares two versions of the repository:

HEAD

The commit you have checked out: the code as it was before the current changes.

Working tree

Your files as they are on disk, with every edit the agent has made since.

An error is introduced when the working tree has it and HEAD does not. Fuse reports only introduced errors, so an error that already existed at HEAD is never reported, whoever caused it. The same comparison decides which tests to run: only code that differs from HEAD can make a test fail that passed before.

Comparing with HEAD is also why Fuse needs no configuration. It does not need to be told what the agent is working on, because the difference between the two versions is exactly that.

How an agent reaches Fuse #

Fuse has three surfaces. All three run the same three operations (check, test and build) and print the same text.

  • Hooks. A harness, such as Claude Code or Cursor, runs a command when an event happens in the agent's session. fuse hook <harness> <event> is that command. The post-edit hook checks the files an edit wrote. The pre-shell hook rewrites dotnet build and dotnet test in a shell command to fuse build and fuse test. The stop hook checks every change before the agent finishes, and sends it back once if errors remain. The agent does not have to decide to call anything. OpenCode runs JavaScript plugins instead of commands, so fuse init writes a plugin that forwards the same events to fuse hook opencode.
  • The command line. fuse check, fuse test and fuse build, for people and for agents that run shell commands.
  • The MCP server. fuse mcp serves the three operations as the tools fuse_check, fuse_test and fuse_build to an MCP host (the application that runs an MCP client) that has no hooks, such as VS Code agent mode.

fuse init registers the hooks with each harness the repository uses; Connect your agent lists what it writes.

The engine: one warm process per repository #

dotnet build starts MSBuild, evaluates every project and compiles what changed, on every call. Most of that work gives the same result from one edit to the next. Fuse does it once and keeps the result: a long-lived process, the engine, holds the evaluated and compiled projects in memory and answers each request from them. Every command and hook runs in a short-lived client that sends one request to the engine and prints the answer.

  1. A hook or command startsa short-lived fuse client.
  2. The client finds the enginefor this repository, and starts one if none runs.
  3. The engine answersfrom projects it already has in memory.
  4. The client prints the answerand exits; the engine keeps running.
  • One engine per repository. The engine is the process fuse engine <root>. The first client that finds no engine for its repository starts one and waits up to 15 seconds for it to accept connections. The engine exits after 30 minutes without a request, when the repository directory disappears, or when a client of another build connects.
  • Which repository. The root is the nearest directory that holds .git (a directory, or a file in a worktree or submodule). It is resolved through junctions, symbolic links, subst drives and 8.3 short names, so every spelling of a path reaches the same engine. A hash of the root's path names the engine's pipe, a mutex that lets one engine run per root, and the state directory. Every agent and subagent working under one root shares its engine. A git worktree is a root of its own, so each worktree gets its own engine, state directory and build lock, and agents in separate worktrees never wait for each other.
  • Client and engine always run the same code. Each pipe connection carries one request and one response, each a line of UTF-8 JSON. A request names its case in a request property, such as CheckFiles or PlanAffectedTests, and a response names its case in a status property, such as CheckAnswered or Unanswered. Every request carries the client's build id: the product version and the module id of fuse.dll, the assembly the engine runs, which changes with every build. The native client (below) reports the module id of the fuse.dll installed with it. The engine reads the build id before the rest of the request. When it differs, the engine answers Restart and exits, and the client starts an engine of its own build and sends the request again. That is why updating Fuse needs no action for running engines, and why the protocol needs no version negotiation.
  • The engine never blocks the installed tool or the harness. The engine runs from a private copy of the tool's files in <local application data>/fuse/engine/<version>-<module id>, so it never locks the installed tool and dotnet tool update works while engines run. Each engine holds a lock file in its copy while it runs. When an engine starts, it deletes every copy of another build that no engine holds and that is more than ten minutes old, the time a client may still need to start the engine from a copy it has just made. On Windows the engine starts without inheriting the client's handles and outside the client's job object, so a harness that ends its hook's processes does not end the engine, and an inherited output handle does not keep the hook's pipe open. On Linux and macOS it gets its own standard streams and calls setsid to leave the client's session. The pipe accepts connections from the current user only.
  • State lives outside the repository. Fuse's files for a repository live in <local application data>/fuse/repos/<id>, where <id> is the first 16 hexadecimal digits of the SHA-256 of the root path: engine.log, hook.log, the build lock, test results, the copies used for test runs without MSBuild, the copies of the repository's own analyzers, and a root file with the repository's path. Once a day, a starting engine deletes the state directories whose repository no longer exists and that nothing wrote to for a day, such as those of deleted temporary repositories. Fuse writes nothing inside the repository except the settings and the .gitignore line fuse init writes. Troubleshooting gives the path on each operating system.
  • One request at a time. The engine answers checks and test plans one at a time, behind a request lock, because each one brings the shared compilations up to date before it reads them. A test plan holds the lock only while it brings them up to date and selects the tests; it copies build output and emits the changed assemblies after it releases the lock, from the compilations as they were when it selected, so a check from another agent does not wait for the emit. When a client disconnects before its answer, because the agent or its harness gave up, the engine cancels that request, so the lock passes to the next one. engine.log names every request and gives one line of per-phase times (reading a phase line).
  • The client is native code. On Windows x64, Linux x64, Linux Arm64 and macOS Arm64, the fuse command is the native client: the client compiled ahead of time to native code, so a hook starts no .NET runtime and compiles nothing before it sends its request. The engine loads MSBuild and the repository's analyzers at run time, which native code cannot do, so the native client always starts it as dotnet fuse.dll engine <root> from the fuse.dll installed with it. On every other platform fuse runs fuse.dll on the .NET runtime, as dotnet tool run fuse and a tool manifest do everywhere.
  • Nothing starts where there is nothing to check. A client starts an engine only in a repository where git knows a .csproj file (tracked, or untracked and not ignored). In any other repository a command or hook costs at most two git ls-files calls and starts nothing.

How the engine keeps the projects current #

In short: the engine reads every project file once, compiles a project only when a request needs it, holds a compiled copy of each loaded project at HEAD and on disk, and folds each edit into both.

  • Evaluation. At start the engine lists every .csproj git knows about and evaluates each with MSBuild, without running targets, using the .NET SDK the repository's global.json selects. A multi-targeted project is evaluated once per target framework and the results are joined. The result, the project graph, says which projects own a source file, which projects depend on a project (its dependent projects), which projects hold tests (an IsTestProject property or a reference to a test framework package), and which are applications (an Exe or WinExe output type, or the Web SDK).
  • Loading on demand. After evaluation, the engine loads only the projects that own uncommitted changes. A request loads the projects it needs with Roslyn's MSBuildWorkspace, used only as a loader: its TryApplyChanges writes to disk, so Fuse never calls it. Before loading, the engine checks that every project involved has been restored (its project.assets.json exists) and answers restore needed with the command to run when one has not; it never restores on its own. After each request the engine loads, in the background, the dependents of the projects with uncommitted changes, one project at a time and outside the request lock, so a later check that has to reach them does not wait. A dependent that fails to load there, for example because it is not restored, is tried again once the projects reload or a restore writes its project.assets.json.
  • Analyzers the repository builds itself. Roslyn keeps an analyzer assembly open while it is loaded, and the engine runs for up to 30 idle minutes. An analyzer or source generator the repository builds itself (a project referenced with OutputItemType="Analyzer") would stay locked in its bin folder, and the next real build of that project would fail with MSB3021 or MSB3027. The engine therefore loads every analyzer inside the repository from a copy in the state directory, and a rebuilt analyzer gets a fresh copy when projects next reload. Package and SDK analyzers load from where they are, because no build writes them.
  • Two views. The engine holds two immutable Roslyn solutions of the loaded projects: the current one, with every file as it is on disk, and the baseline, with every changed file at its HEAD content. Both use the project files as they are on disk. The baseline changes only when HEAD moves or projects load, so its compilations and errors stay cached from one edit to the next.
  • Staying current. A file watcher marks changed paths, and every request also reads the files its client names (the hooks name the files an edit wrote), before the watcher reports them. A path counts as changed when its content differs from the file at HEAD, ignoring line endings; bin, obj, .git and node_modules are skipped. A change to a .csproj, .props, .targets, .editorconfig, .globalconfig, global.json or packages.lock.json file re-evaluates the projects. A commit or branch switch, an overflow of the file watcher, or more than 300 changed paths in one sync makes the engine read git status again and reload the projects it had loaded, because patching that many files one at a time costs more than reloading. When the request that started such a reload is cancelled or fails before the reload finishes, the next request does it.

What a check does #

A check compiles the changed files in both views and keeps the errors only the working tree has. Most edits stop there. Only an edit that changes a declaration, something other files can refer to, can break another file, and then Fuse finds and checks exactly the files that use it.

  1. Targetsthe changed or named C# files.
  2. Compare with HEADkeep errors HEAD does not have.
  3. Declarations changed?if not, the check ends here.
  4. Reachfind the files that use what changed.
  5. Reporttheir introduced errors, each with its cause.
  1. Targets. A check covers the files its client names, or every source file (.cs, .razor, .cshtml) that differs from HEAD. A file no evaluated project owns is skipped, and a check whose named files are all skipped is refused rather than answered as a pass. Each target is compiled with Roslyn in the current view, and when it has errors, in the baseline too. An error is introduced when the baseline has no match for it: the same file, id and message, counted, with line numbers ignored, so an error that only moved is not reported. A file new since HEAD that shares at least half of its lines with a file deleted since HEAD is a rename, and is compared with the errors HEAD had under the old name.
  2. Declaration changes. Each target's declarations are compared with HEAD from syntax alone: types, members, delegates, using directives and file-level attributes. Bodies, formatting, comments and the initializers of fields that are not constants are left out. The comparison runs once per target framework with that project's preprocessor symbols, so a declaration inside #if DEBUG or #if NET8_0_OR_GREATER counts where it is compiled. An edit that changes no declaration, such as a body edit or an added using, cannot break another file, and the check ends there.
  3. Reach. Otherwise the dependents of the projects with declaration changes are loaded, and each changed declaration is resolved to its symbol in the baseline. Roslyn's SymbolFinder finds the files that reference it, implement or override it, or derive from its type, across the owning project and its dependents. Some changes break code that never names them, so they reach further:
    • A removed or changed constructor also reaches every type that derives from its type, because a derived constructor calls it without naming it. An added constructor reaches every use of the type's constructors, the implicit parameterless one included, which it replaces, and every type that derives from the type.
    • An added member reaches the users of same-named members of its type and its base types, because an added overload can make a call ambiguous, and for an interface or abstract type, every implementation.
    • An added type reaches every file that mentions its name, because it can clash with a type of the same name, and a changed Razor file (.razor, .cshtml) reaches every file that mentions the file's name.
    • An added, changed or removed conversion operator also reaches every file that mentions its type's name, because the reference search does not return the places an implicit conversion is applied.
    • A removed using directive can change what the file's type names resolve to without changing their text, so it reaches every file that names one of the file's types.
    • A changed type header (attributes, modifiers, kind, type parameters, primary constructor, constraints or base types), a delegate, a global using or an assembly attribute can break code that never names it, so it reaches every file in the owning project and its dependents.
  4. Candidates. The reached files, the candidates, are compiled the same way as the targets, in parallel. Past 500 candidates the check compiles the reached projects whole instead, and the summary says checked whole projects.
  5. What counts as an error. Compiler errors, warnings the project treats as errors, and analyzer diagnostics whose configured severity is error (through .editorconfig, .globalconfig, WarningsAsErrors or TreatWarningsAsErrors). Only the analyzers that can report an error under the project's configuration run, so an analyzer whose diagnostics are all warnings costs nothing. Warnings are never reported.
  6. Causes. An error in a candidate is followed by one line naming the declaration change that put its file in the check: changed: and the declaration as the working tree has it, or removed: and the declaration as HEAD had it. The line holds the declaration's header on one line, without its body or members. A field is its modifiers, type and name, without its initializer unless it is a constant, whose value is part of what other files see. An agent that reads an error in a file it did not edit sees which of its edits caused it without tracing it back. A file that several changes reach names the first of them, taking the changed files in path order and each file's changes in the order HEAD declares them, then the declarations only the working tree has. An error in a target, an analyzer error and an error reached by a broad change get no cause line. Each answer holds at most ten, and the summary says how many were left out.

The engine returns at most 200 errors per answer, ordered by file and position, and the client prints the first 20.

How Fuse selects tests #

The affected tests are the tests a change can reach. Selection is built around one rule: a missed failing test is the one outcome it must avoid, while running extra tests only costs time. So wherever a step cannot decide, it selects more.

  1. Changed code. Each changed file is compared with HEAD from syntax, bodies included. That gives the changed declarations: added and changed members, types whose header changed or that lost a member, changed top-level statements, and every type in a file whose usings or file-level attributes changed. A changed declaration inside a test project selects its test, or its whole class when it is not a test method.
  2. Type walk. A graph of which types name which, built from syntax with extension methods matched by method name, is walked backwards from the types that hold the changed declarations to every test class that can reach them. It compiles nothing: it costs a parse of each file, and each file's part of the graph is cached until the file changes. Matching by name can only select extra tests, never fewer.
  3. Member walk. When at most 40 test classes are reachable, a second walk narrows the selection to test methods. It follows Roslyn references backwards from each changed member, through callers, overridden members and the interface members a member implements, and stops after 300 symbols or 8 seconds, in which case the type walk's answer stands. A reference in a test method selects that test; a reference elsewhere in a test class selects the class and the classes that derive from it.
  4. Application hosts. Some code in an application is called by an application host or a framework rather than by the repository's own code: a controller, a message handler, a hosted service, an entry point. Neither walk can follow such code to a test by name, because an integration test reaches it through HTTP, a mediator or the host. So reaching it selects every test project that depends on the application, whole. Changed top-level statements and changed Razor files (.razor, .cshtml) select every test project that depends on their project the same way.
  5. Filter. Each selection becomes a VSTest filter, FullyQualifiedName~ per test or class, which dotnet test receives. A filter longer than 8,000 characters is collapsed to class prefixes, and then to no filter, so it can run more tests than selected but never fewer.

The summary counts tests from source, by test attribute (xUnit, NUnit, MSTest and TUnit), without running test discovery. A test project on Microsoft.Testing.Platform (opted in through global.json) runs whole and builds with MSBuild, because its filter syntax differs per test framework.

How Fuse runs tests without MSBuild #

dotnet test on a project first runs MSBuild to build it. When the test project already has build output and only C# sources changed since, that build is mostly wasted: the engine already has the changed code compiled in memory. Fuse then skips MSBuild:

  1. Copythe test project's build output into the state directory.
  2. Emitthe changed assemblies from memory into that copy.
  3. Rundotnet test on the copied test assembly.

The emitted assemblies include the assemblies in the test project's closure that depend on the changed ones, and carry the embedded resources of their last built assembly, because the compilation Roslyn loads does not include the resources MSBuild adds. In the code this is called a shadow run; the output says without MSBuild.

An assembly counts as changed when its project has a source file newer than the project's build output, or when the copy in the test project's build output is not that build output: missing, or different in length or write time. MSBuild keeps the write time when it copies an assembly into a test project's output, so the copy differs when the project was built on its own after the test project, as dotnet build Lib does when Lib.Tests references Lib. The emitted assembly then replaces that older copy.

A run without MSBuild needs every project the test assembly loads to have build output, no project file or import newer than that output, and no file other than a source file newer than it in the project directories, such as a resource or content file the emitted assembly would not carry. Freshness is judged by timestamps. When a condition fails, or a changed project does not compile, Fuse runs dotnet test on the project, which builds it with MSBuild and reports the build errors.

Runs without MSBuild write no build output, so they run in parallel, one process per target framework. Runs with MSBuild share obj and bin folders across projects, so they run one after another. A run without MSBuild that produces no results goes through MSBuild instead. Results are read from the TRX files dotnet test writes.

Builds and the build lock #

Every process that builds a repository writes the same obj and bin files. Two builds at once make one of them fail with MSB3021 or MSB3027 on a file the other holds open, or with CS2012 on an output both are writing. When several agents work in one repository, their builds overlap, and each collision fails a build that would have succeeded on its own.

fuse build and fuse test therefore take a per-repository lock for as long as they write build output, so builds through Fuse take turns:

  • fuse build holds it around its dotnet build. fuse test holds it from before it asks the engine for a plan until its last dotnet test process exits, because preparing the plan writes the copies for runs without MSBuild.
  • The lock is the file build.lock in the state directory, opened exclusively, and the operating system releases it when the client that holds it exits or is killed, so a crashed client cannot leave it held.
  • A client that finds it held retries every 200 ms for as long as it is held and says once on standard error that it is waiting. A client that cannot open the state directory runs without the lock and says why on standard error, so a build is never refused because of the lock.

The arguments fuse build passes to dotnet build are the caller's, unchanged, including the implicit restore, so a package reference added a moment earlier still resolves.

The engine takes no lock: it writes nothing into the working tree, a check does not build, and it loads the repository's analyzers from copies. A dotnet build that does not go through Fuse takes no lock either; the pre-shell hook rewrites an agent's dotnet build and dotnet test so that they do.

When Fuse cannot answer #

When Fuse cannot answer, the answer carries one of eight codes and a message that names the fix: not a repository, no projects, loading, restore needed, load failed, timeout, invalid path, internal. Commands print the message and exit with code 2, and the MCP server marks the result as an error. Messages and fixes lists every message.

A hook must never break the agent's session. It reports introduced errors and a missing restore, and nothing else. Every other outcome exits 0 and prints nothing the agent reads (a stop hook that lets the agent finish prints the empty answer its harness expects, such as {}), and an exception or a payload that is not valid JSON is written to hook.log in the state directory. A post-edit hook that a harness runs inline, which is every harness except Claude Code, does not wait for an engine that is still loading, so the stop hook reports the first edits after the engine starts.

Privacy and footprint #

  • Everything runs locally. Fuse has no telemetry and makes no network calls of its own.
  • Fuse never edits your code and never runs dotnet restore on its own.
  • The only files Fuse writes in your repository are the hook settings from fuse init. Its logs and other state are stored in your local application data folder.
  • In a repository without a .csproj file, hooks return at once and no engine starts.
  • Fuse has no configuration file and no environment variables of its own.
