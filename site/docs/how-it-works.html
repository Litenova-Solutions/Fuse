How Fuse Works

All documentation pages

Fuse answers 2 questions for a coding agent in a .NET repository: which compiler errors the changes introduce, and which tests the changes can break. It answers both from a background process that keeps the solution loaded, so the agent does not wait for a full build. All agents and subagents in the repository share that process.

This page is for anyone who wants to know what happens between an agent's edit and Fuse's answer, and why Fuse is built that way. That is a user deciding how far to trust a clean answer, or a contributor starting on the code.

How to read it: the first 2 sections explain the idea in plain terms. Each later section starts with a summary and then gives the exact rules. Architecture maps this behavior to the code, and Limits lists what it cannot see.

In short

  • Fuse compares your working tree with HEAD and reports only the errors your changes introduced.
  • One warm engine process per repository keeps your projects loaded, so each check answers without a full build.
  • A check compiles the changed files, then the files that use the changed declarations, and names the change behind each error.
  • Fuse runs only the tests your changes can reach, skips MSBuild when only C# sources changed, and runs builds one at a time behind one lock per repository.

HEAD and the working tree #

Every answer Fuse gives compares 2 versions of the repository:

HEAD

The commit you have checked out: the code as it was before the current changes.

Working tree

Your files as they are on disk, with every edit the agent has made since.

When the working tree has an error and HEAD does not, that error is introduced. Fuse reports only introduced errors, so an error that already existed at HEAD is never reported, no matter who caused it. The same comparison decides which tests run: only code that differs from HEAD can fail a test that passed before.

Comparing with HEAD is also why Fuse needs no configuration. The difference between the 2 versions already says what the agent is working on.

Surfaces #

Fuse has 3 surfaces. All 3 run the same 3 operations (check, test and build) and print the same text.

  • Hooks. A harness, the agent host that runs Fuse's hooks, such as Claude Code or Cursor, runs a command when an event happens while the agent works. fuse hook <harness> <event> is that command.
    • The post-edit hook checks the files an edit wrote.
    • The pre-shell hook rewrites dotnet build and dotnet test in a shell command to fuse build and fuse test.
    • The stop hook checks every change before the agent finishes. When errors that the agent's own edits cause remain, it sends the agent back once. In Claude Code a subagent's stop runs the same hook, so a subagent fixes its own errors before it hands its work back.

    The agent never calls a hook itself; the harness runs each one on its event. OpenCode runs JavaScript plugins instead of commands, so fuse init writes a plugin that forwards the same events to fuse hook opencode. Muse Code runs hooks only from a plugin bundle, so fuse init writes one that you install and approve once (Muse Code).

  • The command line is fuse check, fuse test and fuse build, for people and for agents that run shell commands.
  • The MCP server is fuse mcp, which serves the 3 operations as the tools fuse_check, fuse_test and fuse_build to an MCP host (the application that runs an MCP client) that has no hooks, such as VS Code agent mode.

fuse init registers the hooks with each harness the repository uses. Connect your agent lists what it writes.

One warm process per repository #

dotnet build starts MSBuild, evaluates every project and compiles what changed, on every call. Most of that work gives the same result from one edit to the next, so Fuse does it once and keeps the result. The result lives in a long-lived process, the engine, which holds the evaluated and compiled projects in memory and answers each request from them. Every command and hook runs in a short-lived client, which sends one request to the engine and prints the answer.

  1. A hook or command startsa short-lived fuse client.
  2. The client finds the enginefor this repository, and starts one if none runs.
  3. The engine answersfrom projects it already has in memory.
  4. The client prints the answerand exits; the engine keeps running.
  • One engine per repository. The engine is the process fuse engine <root>. The first client that finds no engine for its repository starts one and waits up to 15 seconds for it to accept connections. After 30 seconds without a request, the engine compacts its memory and returns the freed memory to the operating system, so an idle engine holds only the loaded projects, not the peak of its largest check. When 30 minutes pass without a request, when the repository directory disappears, or when a client of another build connects, the engine exits.
  • Which repository. The root is the nearest directory that holds .git (a directory, or a file in a worktree or submodule). Fuse resolves it through junctions, symbolic links, subst drives and 8.3 short names, so every spelling of a path reaches the same engine. A hash of the root's path names the engine's pipe, the mutex that lets one engine run per root, and the state directory. Every agent and subagent working under one root shares its engine. A git worktree is a root of its own, so each worktree gets its own engine, state directory and build lock, and agents in separate worktrees never wait for each other.
  • Client and engine always run the same code.

    Each pipe connection carries one request and one response, each a line of UTF-8 JSON. A request names its case in a request property, such as CheckFiles or PlanAffectedTests. A response names its case in a status property, such as CheckAnswered or Unanswered.

    Every request carries the client's build id: the product version and the module id of fuse.dll, the assembly the engine runs. That module id changes with every build. The native client (below) reports the module id of the fuse.dll installed with it. The engine reads the build id before the rest of the request. When it differs, the engine answers Restart and exits. The client then starts an engine of its own build and sends the request again. You therefore do nothing about running engines when you update Fuse, and the protocol needs no version negotiation.

  • The engine never blocks the installed tool or the harness.

    The engine runs from a private copy of the tool's files in <local application data>/fuse/engine/<version>-<module id>, so it never locks the installed tool and dotnet tool update works while engines run. Each engine holds a lock file in its copy while it runs. When an engine starts, it deletes every copy of another build that no engine holds and that is more than 10 minutes old. The 10 minutes are the time a client may still need to start its engine from a copy it has just made.

    On Windows the engine starts without inheriting the client's handles and outside the client's job object. A harness that ends its hook's processes therefore does not end the engine, and an inherited output handle does not keep the hook's pipe open. On Linux and macOS it gets its own standard streams and calls setsid to start a session of its own. The pipe accepts connections from the current user only.

  • State lives outside the repository. Fuse's files for a repository live in <local application data>/fuse/repos/<id>, where <id> is the first 16 hexadecimal digits of the SHA-256 of the root path:
    • engine.log, hook.log and the build lock.
    • sessions.tsv (which session wrote each changed file).
    • registered-sessions.tsv (the sessions a launcher registered).
    • The baseline folder (HEAD's kept errors, keyed by commit and configuration).
    • Test results.
    • The copies used for test runs without MSBuild.
    • The copies of the repository's own analyzers.
    • A root file with the repository's path.

    Once a day, a starting engine deletes every state directory whose repository no longer exists and that nothing wrote to for a day. That removes the state of deleted temporary repositories, for example. Fuse writes nothing inside the repository except the settings and the .gitignore line fuse init writes. Troubleshooting gives the path on each operating system.

  • One request at a time.

    The engine answers checks and test plans one at a time, behind a request lock, because each one brings the shared compilations up to date before it reads them. A test plan holds the lock only while it brings them up to date and selects the tests. It copies build output and emits the changed assemblies after it releases the lock, from the compilations as they were when it selected, so a check from another agent does not wait for the copying and emitting.

    When a client disconnects before its answer arrives, the engine cancels that request, so the lock passes to the next one. The client disconnects when the agent or its harness gives up waiting. engine.log names every request and gives one line of per-phase times (reading a phase line).

  • The client is native code. On Windows x64, Linux x64, Linux Arm64 and macOS Arm64, the fuse command is the native client, which is the client compiled ahead of time to native code. A hook therefore starts no .NET runtime and compiles nothing before it sends its request. The engine loads MSBuild and the repository's analyzers at run time. Native code cannot do that, so the native client always starts the engine as dotnet fuse.dll engine <root> from the fuse.dll installed with it. On every other platform fuse runs fuse.dll on the .NET runtime, as dotnet tool run fuse and a tool manifest do everywhere.
  • Nothing starts where there is nothing to check. A client starts an engine only in a repository where git knows a .csproj file (tracked, or untracked and not ignored). In any other repository a command or hook costs at most 2 git ls-files calls and starts nothing.
  • HEAD's errors are kept on disk.

    The baseline side of a check depends only on HEAD and the configuration, so a check stores its finished baseline results in the state directory. The first check after an engine restart reads them instead of binding HEAD again.

    The key covers the commit, the Roslyn build, and per project its evaluation inputs, its restore output, its analyzer assemblies, its additional files and its global analyzer options, plus every .editorconfig and .globalconfig file. A result is therefore read only when all of those are as they were. Anything unreadable, or kept under another key, is ignored and computed again. A result whose analyzers did not finish is never kept. The log line baseline: N stored result(s) read for HEAD <12 hex>; M computed says how many of each a check read.

  • A new HEAD is analyzed in the background. After HEAD moves, the engine computes the new baseline's compilation-wide analyzer results between requests, one loaded project at a time. The first check that needs them then finds them running or done instead of starting them. The warming run holds the request lock only while it chooses the next project, so requests are served while a project warms. When HEAD moves again, the run stops. The log names each warmed project (baseline warm: <project> compilation-wide analyzers done in <ms> ms) and a run cut short (baseline warm: skipped, HEAD moved again).

Projects and compilations #

In short, the engine reads every project file once and compiles a project only when a request needs it. It holds a compiled copy of each loaded project at HEAD and on disk, and folds each edit into both.

  • Evaluation. At start the engine lists every .csproj git knows about. It evaluates each with MSBuild, without running MSBuild targets, using the .NET SDK the repository's global.json selects. It evaluates a multi-targeted project once per target framework and joins the results. The result, the project graph, says which projects own a source file, which projects depend on a project (its dependent projects), which projects hold tests (an IsTestProject property or a reference to a test framework package), and which are applications (an Exe or WinExe output type, or the Web SDK; never a test project).
  • Loading on demand.

    After evaluation, the engine loads only the projects that own changed files. A request loads the projects it needs with Roslyn's MSBuildWorkspace, which serves only as a loader. Its TryApplyChanges writes to disk, so Fuse never calls it. Before loading, the engine checks that every project involved has been restored, which means its project.assets.json exists. When one has not, it answers restore needed with the command to run. It never restores on its own.

    After each request the engine loads the dependents of the projects that own changed files in the background, one project at a time and outside the request lock, so a later check that reaches them does not wait. After loading each one it also builds its compilation, so a later check reuses that too. The log names each one (preloaded <project> compilation in <ms> ms). A project whose compilation does not build still counts as loaded. The next check that needs it builds the compilation itself. When a dependent does not load there, because it is not restored for example, the engine tries it again once the projects reload or a restore writes its project.assets.json.

  • Analyzers the repository builds itself. Roslyn keeps an analyzer assembly open while it is loaded, and the engine runs for up to 30 idle minutes. An analyzer or source generator the repository builds itself, which is a project referenced with OutputItemType="Analyzer", would otherwise stay locked in its bin folder. The next real build of that project would then fail with MSB3021 or MSB3027. The engine therefore loads every analyzer inside the repository from a copy in the state directory. A rebuilt analyzer gets a fresh copy when projects next reload. Package and SDK analyzers load from where they are, because no build writes them.
  • Two views. The engine holds 2 immutable Roslyn solutions of the loaded projects: the current one, with every file as it is on disk, and the baseline, with every changed file at its HEAD content. Both use the project files as they are on disk. The baseline changes only when HEAD moves or projects load, so the engine reuses its compilations and errors from one edit to the next.
  • Staying current.

    A file watcher marks changed paths, and every request also reads the files its client names. The hooks name the files an edit wrote, so the request reads them before the watcher reports them. A path counts as changed when its content differs from the file at HEAD, ignoring line endings. Paths under bin, obj, .git and node_modules are skipped. A change to a .csproj, .props, .targets, .editorconfig, .globalconfig, global.json or packages.lock.json file re-evaluates the projects.

    After a commit or branch switch, after an overflow of the file watcher, or when one sync finds more than 300 changed paths, the engine reads git status again and reloads the projects it had loaded. Patching that many files one at a time costs more than reloading. When the request that started such a reload is cancelled or stops before the reload finishes, the next request performs it. The engine also remembers every path it applied, as the touched set. Without a bound it would grow forever in a long-lived engine, so past 2000 paths the next sync re-evaluates the projects and resets it. The log then says touched set passed 2000 paths; re-evaluating projects and resetting it.

  • Generated files. A project can compile a file that a build writes into its bin or obj folder, such as an API client generated from another project's output. Such a generated file is not in git, so HEAD has no content of its own for it. Both views hold it as the last build wrote it. The watcher skips obj, so every request compares each generated file's length and write time with the ones from when the engine last read it. It reads the file again when a build has written it since.

Check #

A check compiles the changed files in both views and keeps the errors only the working tree has. For most edits the check ends there. Only an edit that changes a declaration can break another file, because only a declaration is something other files can refer to. Fuse then finds and checks exactly the files that use it.

  1. Targetsthe changed or named C# files.
  2. Compare with HEADkeep errors HEAD does not have.
  3. Declarations changed?if not, the check ends here.
  4. Reachfind the files that use what changed.
  5. Reporttheir introduced errors, each with its cause.
  1. Targets.

    A check covers the files its client names, or every source file (.cs, .razor, .cshtml) that differs from HEAD. A file that no evaluated project owns is skipped. A check whose named files are all skipped is refused rather than answered as a pass. Roslyn compiles each target in the current view, and also in the baseline when the target has errors.

    An error is introduced when the baseline has no match for it. A match is the same file, id and message, counted, with line numbers ignored, so an error that only moved is not reported. A file new since HEAD that shares at least half of its lines with a file deleted since HEAD is a rename. It is compared with the errors HEAD had under the old name.

    A check can also cover a folder or a pattern with fuse check <dir|pattern>, where each directory, file or pattern is a spec. Any existing directory or */? makes the whole call scoped, and files may be mixed with folders and patterns. Its targets are the changed C# sources the specs match that a project owns. A spec that matches none is refused rather than answered as clean. A call whose specs expand past the 2000 sources one scoped check covers is refused too. The summary names the scope (; checked <paths> and what it reaches, or no errors introduced in <paths> and what it reaches when clean).

  2. Declaration changes. Each target's declarations are compared with HEAD from syntax alone: types, members, delegates, using directives and file-level attributes. Bodies, formatting, comments and the initializers of fields that are not constants are left out. The comparison runs once per target framework with that project's preprocessor symbols, so a declaration inside #if DEBUG or #if NET8_0_OR_GREATER counts where it is compiled. An edit that changes no declaration, such as a body edit or an added using, cannot break another file. The check then ends there.
  3. Reach. Otherwise the engine loads the dependents of the projects with declaration changes, and resolves each changed declaration to its symbol in the baseline. Roslyn's SymbolFinder finds the files that reference it, implement or override it, or derive from its type, across the owning project and its dependents. Some changes break code that never names them, so they reach further:
    • A removed or changed constructor also reaches every type that derives from its type, because a derived constructor calls it without naming it. An added constructor reaches every use of the type's constructors, including the implicit parameterless one it replaces, and every type that derives from the type.
    • An added member reaches the files that use same-named members of its type and its base types, because an added overload can make a call ambiguous. For an interface or abstract type, it reaches every implementation.
    • An added type reaches every file that mentions its name, because it can clash with a type of the same name. A changed Razor file (.razor, .cshtml) reaches every file that mentions the file's name.
    • An added, changed or removed conversion operator also reaches every file that mentions its type's name, because the reference search does not return the places an implicit conversion is applied.
    • A removed using directive can change what the file's type names resolve to without changing their text, so it reaches every file that names one of the file's types.
    • A changed type header (attributes, modifiers, kind, type parameters, primary constructor, constraints or base types), a delegate, a global using or an assembly attribute can break code that never names it, so it reaches every file in the owning project and its dependents.
  4. Candidates. The reached files, the candidates, are compiled the same way as the targets, in parallel. Past 500 candidates the check compiles the reached projects whole instead. The summary then says which projects, and whose edits forced it: checked whole projects: Lib because Lib/Calc.cs (removed: ...); App because .... It names at most 3 projects and 2 files per project in path order, and counts the rest as ; and N more in the engine log. The log's check: line holds the full uncapped list after whole projects:.
  5. Errors kept from an earlier check.

    A file's compiler errors and the errors of the analyzers that run file by file depend on its own text, on the declarations of its project and of the projects it references, and on the project configuration. When none of them changed since an earlier check compiled the file, the check takes that check's errors for it instead of compiling it again. A change inside a method body elsewhere leaves the declarations as they were, so a stop hook that checks many files again after a few edits compiles again only the files whose errors those edits can change.

    The compilation-wide analyzers (below) read every file's bodies, so their errors are never kept this way. Only a check of every change keeps errors this way, as the stop hook, fuse check without files and the MCP tool make. Finding out that the declarations are unchanged costs more than it saves in a check of the files an edit just wrote. The engine log's check: line says how many files had their errors kept ((12 with errors reused from an earlier check) is an example of the format).

  6. Answers kept from an earlier check.

    When nothing an answer depends on has changed since an earlier check of the same scope for the same session and analyzer run, the check answers with that check's result without compiling anything again. The scope is the same files, paths or every change. The answer depends on each changed file's contents, HEAD, the configuration the projects were evaluated under, the baseline, which a generated file written again also moves, and which sessions wrote each changed file. The log then holds only check: kept answer. An answer whose analyzers did not finish is never kept, because it holds only what finished in time. The engine keeps the last 8 answers in memory. It forgets them when it exits.

    A check of every change first applies every changed file to both views again and compares each with what the disk holds now. When a file cannot be read or still disagrees, the check still answers from its snapshot, but the answer is not kept. The log then says check: N changed file(s) could not be read from disk, so this answer is not kept. Past 500 changed files the kept answer is skipped outright, because hashing every file costs more than the reuse saves. The log then says check: kept answer skipped, N changed file(s) past 500.

  7. What counts as an error. Errors are compiler errors, warnings the project treats as errors, and analyzer diagnostics whose configured severity is error (through .editorconfig, .globalconfig, WarningsAsErrors or TreatWarningsAsErrors). Only the analyzers that can report an error under the project's configuration run. An analyzer whose diagnostics are all warnings therefore never runs. Warnings are never reported.
  8. Analyzers that read the whole project.

    Roslyn analyzes one file on a fresh copy of the compilation. It runs every analyzer's compilation start actions again for each file. Most analyzers only look up a few types there. An analyzer that walks every file of the project there, or that registers actions that run once per compilation, therefore performs a whole-project pass for each file a check compiles.

    The first time a check compiles a file of a project, the engine runs every analyzer on that file and times each one. An analyzer with compilation start or compilation actions that took a second or more is a compilation-wide analyzer. The time comes from a second run, because the first run also pays for compiling the analyzers' code. From then on it runs once over the whole compilation, and every file of the check, and of every later check until an edit changes the project, takes its errors from that one run. The others keep running file by file.

    The engine log names each compilation-wide analyzer and the time it took on one file. The engine decides again when the project's configuration changes.

  9. The post-edit hook leaves compilation-wide analyzers out.

    A run over the whole compilation takes as long as compiling the project, so the post-edit hook leaves the compilation-wide analyzers out. Its summary names them. The stop hook, fuse check and the MCP tool run them.

    The baseline runs the same analyzers as the working tree under the same deadline, so the post-edit hook leaves the compilation-wide analyzers out of the baseline too. When the baseline's analyzers did not finish in a file, the working tree's analyzer errors in that file are not reported, because they cannot be told apart from errors HEAD already has. Its compiler errors are compared and reported. An error HEAD already has is never reported as introduced.

  10. A background post-edit answer is confirmed before it is delivered. A harness that runs the post-edit hook in the background delivers its answer late, after the agent has made more edits. An answer with errors is therefore checked again against the working tree as it stands before the hook returns it. When the working tree no longer reports the errors, the hook exits 0 with no output. The errors were already fixed. A hook the harness runs inline answers from one check. The wait covers at most 2 checks: the first answer plus one confirmation. hook.log records every confirmed delivery and every drop.
  11. Analyzers stop before the client gives up. Each request carries how long its client waits for the answer: 50 seconds for a post-edit hook that runs inline, 280 seconds for one that runs in the background and for the stop hook, 10 minutes for fuse check and the MCP tool. The harness allows 300 seconds. The 20 seconds left over are the time the hook needs to deliver the answer before the harness ends it. When 80% of that wait has passed, the check stops its analyzers and answers with every compiler error and the analyzer errors found so far. The summary then says in how many files or projects the analyzers did not finish. Without that stop, an analyzer that runs too long would make the client give up, and the check would answer nothing.
  12. Runs over a whole compilation outlive the check. A run of the compilation-wide analyzers over a whole compilation, and the run of every analyzer over a project bound whole, belong to that compilation, not to the check that started them. When the check's deadline passes, or its client stops waiting, the run goes on in the engine. The next check of the same compilation then takes its result instead of starting again. A newer compilation of the same project, after an edit, stops the older compilation's run. The engine therefore analyzes at most one compilation per project in each view, current and baseline, at a time.
  13. A reached project the views do not hold leaves the check unanswered.

    When a reached project has no project in one of the views, answering would silently narrow the check. The engine therefore derives both views again once. What is still missing leaves the check unanswered with fuse: could not load <project>: the check reached <name> but the engine's view does not hold it (the projects the view holds are named in engine.log) and exit 2, instead of answering partially. Hooks report nothing for it, as for every failure but a missing restore.

    A check whose views missed a reached project, or whose reach names a file on disk with no document in the current view, writes a check coverage: reached <names>; current holds <names>; baseline holds <names>[; recovered after rebuilding the views][; candidates without a document: <paths>] line to the log. That line names what each view held. When neither holds for a check, the check logs nothing.

  14. Causes.

    Under an error in a candidate, one line names the declaration change that put its file in the check. It holds changed: and the declaration as the working tree has it, or removed: and the declaration as HEAD had it. The line holds the declaration's header on one line, without its body or members. A field is its modifiers, type and name, without its initializer unless it is a constant, whose value is part of what other files see. An agent that reads an error in a file it did not edit sees which edit caused it without tracing it back.

    In a file that several changes reach, each error names the change whose declaration its message quotes. An error about a renamed method and one about a renamed interface member in the same file therefore each name their own change. An error that quotes none of them names the first change: the changed files in path order, each file's changes in the order HEAD declares them, then the declarations only the working tree has. An error in a target, an analyzer error and an error reached by a broad change get no cause line. Each answer holds at most 10 cause lines. The summary says how many were left out.

  15. Errors about generated code. When an error is about a type or member that a generated file declares, a line under it names the file: generated: Api/obj/Contract/Client.cs declares it, and Fuse reads that file as the last build wrote it; if it is generated from changed code, run fuse build to write it again. A member the agent just added to the generator's source is missing from the file until a build writes it again. Such an error can therefore mean only that the file still holds the last build's content. After fuse build, the next check reads the new file. The line appears once per file in an answer.
  16. Sessions.

    When several agents edit one working tree, the post-edit hook and the stop hook tell each agent only the errors its own edits cause. A session is one agent's run as its harness identifies it in the hook's payload (what each harness sends). A subagent the harness identifies on its own is a session of its own. The engine records which sessions wrote each changed file, in sessions.tsv in its state directory. It forgets a file once the file matches HEAD again.

    The check still reads the whole working tree. Then, for each error in a file the session did not write together with another session, the engine compiles that file again in a view of the working tree with the files only other sessions wrote put back at HEAD. An error that is still there is the session's own.

    An error that is gone is compiled once more, in a view with the files only this session wrote put back at HEAD. When it is still there, other sessions' edits caused it without this one, so it is left out of this session's answer, and the summary counts it (1 error(s) from other sessions' edits left out). When it is gone too, it needs both sessions' edits, so it is reported.

    An error in a file several sessions wrote, and an error in a file no session is credited with, because a shell command, a generator or a tool without a post-edit hook changed it, is reported to every session whose check finds it. A check without a session, from the command line, the MCP server or a harness that names none, reports every error.

    A process outside every harness can be registered too. fuse session begin <name> --paths <pattern> ... counts every changed file under its patterns as that session's until fuse session end <name> or 4 hours pass. Such a session is an ordinary session in attribution, so other sessions are not told the errors its edits cause on their own. Re-beginning a name replaces its patterns and restarts its 4 hours. A fuse check with no session still reports every error.

  17. The stop hook and subagents.

    The stop hook checks every change in the working tree and answers to the session that stops. When it answers to a session, it binds only that session's own files, the files it wrote together with another session, and the files no session is credited with, plus what they reach, and then attributes. A session that no changed file is credited to leaves nothing out. It blocks on the errors that session's edits cause, alone or with another session's, and on the errors in changes no session is credited with. Under them it says Fix these errors before finishing. The working tree has them and HEAD does not, and no other session's edits cause them on their own.

    An error another session's edits cause on their own is left to that session, which may still be writing the file. The summary counts only those in reach. The N file(s) checked count covers the session's targets and candidates, not the whole working tree. fuse check, the MCP tool and a stop with no session are unchanged. They cover every change.

    A subagent's session id starts with its parent's, followed by / and the subagent's own id. While the subagent runs, its edits count as another session's, so its parent's stop never blocks on half-written work. Once the subagent's own stop hook has run, it writes no more, and from then on its parent session counts its edits as its own. What the subagent left broken is the parent's to fix. The engine records a stopped session in sessions.tsv too. A harness that names no session gets every error at its stop hook, with the line another agent editing this working tree may have caused some of them.

  18. The cost of sessions. The views cost time only while another session has written a file of its own, because each view compiles the projects whose files it puts back a second time. In the attribution suite, the median post-edit hook took 504 ms with sessions and 98 ms without on FluentValidation, 1,706 ms and 328 ms on NodaTime, whose core project the views compiled again, 3,340 ms and 172 ms on Jellyfin, and 753 ms and 166 ms on Polly (attribution-FluentValidation-20261029-1937.json, attribution-NodaTime-20261029-1938.json, attribution-Jellyfin-20261029-1939.json, attribution-Polly-20261029-1938.json). Past 40 files to decide, the remaining errors are reported without being compiled again, and the summary then counts them. It says errors in N file(s) not compared with other sessions' edits, so some of them may be other sessions'.

Errors that share their cause print under one header that names it once. The header is changed: <declaration> (N error(s)), or removed: ... for a removed declaration, with (N error(s), first M shown) when the cap cuts the group. Grouped members print no cause line, since the header names it. Member error lines keep their shape at column 0. last-check-results.txt stays flat with every error.

The engine returns at most 200 errors per answer by default, ordered by file and position, and the client prints the first 20. --max-errors and --all-errors raise both limits.

Test selection #

The affected tests are the tests a change can reach. Selection follows one rule: a missed failing test is the one outcome it must avoid, while running extra tests only costs time. Wherever a step cannot decide, it therefore selects the wider set.

  1. Changed code. Each changed file is compared with HEAD from syntax, bodies included. That gives the changed declarations: added and changed members, types whose header changed or that lost a member, changed top-level statements, and every type in a file whose usings or file-level attributes changed. A changed declaration inside a test project selects its test. When it is not a test method, it selects its whole class and the tests that call it.
  2. Same code.

    A changed declaration that compiles to the same code as HEAD's seeds neither walk. A local rename is one, and var against the explicit type is another. Its header must read the same with bodies stripped, and its bodies the same after every local, parameter and range variable name is replaced with the order it is first seen in and every local type with the type it names. Only a method, constructor, operator or conversion, and a property or indexer without an initializer, can qualify. A field, an event, a type and anything without a body still select their tests.

    Anything the comparison cannot read counts as changed:

    • a name under nameof
    • an inferred member name
    • a captured argument
    • a query
    • a signature or attribute change
    • anything that fails to bind

    The log says how many declarations of how many qualified. When every changed declaration did, the plan selects no tests.

  3. Type walk. A graph of which types name which, built from syntax with extension methods matched by method name, is walked backwards from the types that hold the changed declarations to every test class that can reach them. It compiles nothing. It costs a parse of each file, and each file's part of the graph is cached until the file changes. Matching by name can only select extra tests, never fewer.
  4. Member walk.

    When at most 100 test classes are reachable, a second walk narrows the selection to test methods. It follows Roslyn references backwards from each changed member, through callers, overridden members and the interface members a member implements. It stops after 300 symbols or 8 seconds, in which case the type walk's answer stands.

    The log records each attempt with its statistics: test selection: member walk completed in M ms, S symbol(s), C test class(es) reachable, P pattern(s) selected; selecting at member level, the over budget variant ending in selecting at class level, and test selection: N test classes reachable; selecting at class level past the gate. A reference in a test method selects that test. A reference elsewhere in a test class selects the class and the classes that derive from it, and the walk goes on to that member's callers. A test that reaches the change through a helper class, such as a shared builder, is therefore selected too.

  5. Application hosts. Some code in an application is called by an application host or a framework rather than by the repository's own code: a controller, a message handler, a hosted service, an entry point. Neither walk can follow such code to a test by name, because an integration test reaches it through HTTP, a mediator or the application host. So reaching it selects every test project that depends on the application, whole. Changed top-level statements and changed Razor files (.razor, .cshtml) select every test project that depends on their project the same way.
  6. Filter.

    Each selection becomes a VSTest filter, FullyQualifiedName~ per test or class. dotnet test receives it in a runsettings file, as RunConfiguration/TestCaseFilter passed with --settings, so its length does not count against the command line. Fuse writes the file to the run's folder in the state directory and deletes it after the run. When the project names its own runsettings file in RunSettingsFilePath, the written file is a copy of it with the filter added. A filter the project's file already has keeps applying.

    A filter holds at most 2,000 patterns. A selection with more is collapsed to class prefixes, and then to no filter, so it can run more tests than selected but never fewer. The summary names the projects where a collapse happened, and the engine log records each collapse.

For a session's own tests, the pre-shell hook passes the session whose dotnet test command it rewrites, as fuse test --session claude:<id>, when that id holds only letters, digits and - _ . : /. The plan then leaves out the changed files that only other sessions wrote, so a subagent runs the tests its own edits affect, against the working tree as it is. Files the session wrote, files several sessions wrote and files no session is credited with stay in. The summary says how many files it left out: left out 2 changed file(s) only other sessions wrote is an example of the format. A person who runs fuse test passes no session. The plan then covers every change.

Tests that need a container runtime are left out when no runtime answers. A test project that references Testcontainers starts its databases from containers, so when no container runtime answers, its tests would fail before they run. The plan leaves such projects out of affected and --all plans and names them in the summary. When everything selected needed a runtime, no process starts, and the answer says to start Docker or Podman and run fuse test again. The engine probes docker info then podman info, 2 seconds each, and trusts the answer for 5 minutes. A run with test-choosing arguments goes to dotnet test with no pre-flight.

Every counted run writes the last run's record, last-test-results.json, beside the text file in the state directory. It holds each test's verdict and duration, failures first, at most 20,000 tests. A corrupt file counts as no record. A result without a recognized verdict is stored as skipped, never as a pass. fuse test --failed reruns the recorded failures. An affected run consults the record for failed-first ordering.

With failed first, when the last run on the command line recorded between 1 and 100 failures inside a VSTest method selection, those tests run first as their own stage. Their failures print before the rest runs. The 2 stages record once from their combined results, so the final summary counts each test once. Platform runs, whole-project runs, and selections with no recorded failure run unchanged in one stage. A project whose split would name a theory row does too, so each row is counted once. The MCP tool answers once with the full text.

The summary counts tests from source, by test attribute (xUnit, NUnit, MSTest and TUnit), without running test discovery. A test project on Microsoft.Testing.Platform builds with MSBuild and runs with its framework's own filter. xUnit v3 and TUnit take theirs as arguments, and MSTest and NUnit take the VSTest filter.

Without the global.json opt-in, Fuse builds such a project once and starts each target the build wrote directly. Only 2 kinds of project run through dotnet test instead, without building again:

  • one with a .NET Framework target, which has no runtimeconfig.json to start it from
  • one whose started target exits without printing results, because it is not a test application that runs itself (an NUnit or MSTest project can reference the platform without being one).

Test runs without MSBuild #

dotnet test on a project first runs MSBuild to build it. When the test project already has build output and only C# sources changed since, that build is mostly wasted, because the engine already has the changed code compiled in memory. Fuse then skips MSBuild:

  1. Copythe test project's build output into a copy in the state directory.
  2. Emitthe changed assemblies from memory into that copy.
  3. Rundotnet test on the copied test assembly, with the project's runsettings.

The emitted assemblies are the changed ones plus the assemblies in the test project's dependency closure that depend on them. They carry the embedded resources of their last built assembly, because the compilation Roslyn loads does not include the resources MSBuild adds. In the code this is called a shadow run. The output says without MSBuild.

A dependent is emitted again only when a project it depends on changed its declarations. Those are the surfaces plus parameter names and defaults, which callers can name or inline although the surface leaves them out. Otherwise the shadow folder keeps the image already in place. The log says so per dependent (test plan: Lib.Tests: not emitting Lib.Tests again; Lib compiles to the same declarations as HEAD). Anything undecidable counts as a change.

A kept image is still emitted again on a fresh copy, whose build output can predate HEAD. It is also emitted again when a referenced project declares differently than when the image was written, even while it declares the same as HEAD, because the kept image was compiled against an intermediate state. The emitter records each referenced project's declaration fingerprint when it writes a dependent.

dotnet test on an assembly does not evaluate the project, so it would not read the project's RunSettingsFilePath. Fuse passes that file itself, in the runsettings file that carries the filter, so a run without MSBuild has the parallelism, timeouts and environment variables a run with MSBuild has. Relative paths in it (ResultsDirectory, TestAdaptersPaths and MSTest's SettingsFile) are made absolute against the project's file's folder.

An assembly counts as changed when its project has a source file newer than the project's build output, or when the copy in the test project's build output is not that build output. That means missing, or different in length or write time. MSBuild keeps the write time when it copies an assembly into a test project's output, so the copy differs when the project was built on its own after the test project, as dotnet build Lib does when Lib.Tests references Lib. The emitted assembly then replaces that older copy.

A run without MSBuild needs every project the test assembly loads to have build output, no project file or import newer than that output, and no file other than a source file newer than it in the project directories, such as a resource or content file the emitted assembly would not carry. Freshness is judged by timestamps. When a condition does not hold, or a changed project does not compile, Fuse runs dotnet test on the project, which builds it with MSBuild and reports the build errors.

Runs without MSBuild write no build output, so they run in parallel, one process per target framework. Runs with MSBuild share obj and bin folders across projects, so they run one after another. A run without MSBuild that produces no results goes through MSBuild instead. Results are read from the TRX files dotnet test writes.

Because each run holds its own copy, each test project, per target framework, has numbered copies under shadow/<project>/ in the state directory. They are numbered g1, g2 and so on. A run holds the copy it runs from until it ends, with a lock file inside it that the operating system releases when the client exits or is killed. A plan never writes a copy a run holds.

It prepares the newest copy again when no run holds it, so files already in place are not written again. Otherwise it starts a new copy. It deletes the older copies no run holds. Runs from several agents therefore run at the same time, each from the files it started with. A test host never holds a file in the repository's bin folder open, which would make the next build fail on it.

Builds and the build lock #

Every process that builds a repository writes the same obj and bin files. Two builds at once make one of them fail with MSB3021 or MSB3027 on a file the other holds open, or with CS2012 on an output both are writing. When several agents work in one repository, their builds overlap. Each collision then fails a build that would have succeeded on its own.

fuse build and fuse test therefore take a per-repository lock for as long as they write build output, so builds through Fuse take turns:

  • fuse build holds it around its dotnet build. fuse test takes it before it asks the engine for a plan, because preparing the plan writes the copies for runs without MSBuild. Once its runs without MSBuild hold their copies (each run holds its own copy), it gives the lock up while they run, so another agent's fuse build or fuse test goes ahead meanwhile. Before a run with MSBuild it takes the lock again and keeps it until its last dotnet test process exits. fuse test with dotnet test arguments builds with MSBuild, so it holds the lock throughout.
  • The lock is the file build.lock in the state directory, opened exclusively. The operating system releases it when the client that holds it exits or is killed, so a crashed client cannot leave it held.
  • A client that finds it held retries every 200 ms for as long as it is held and says once on standard error that it is waiting. A client that cannot open the state directory runs without the lock and says why on standard error, so a build is never refused because of the lock.

fuse build passes its arguments to dotnet build unchanged, including the implicit restore, so a package reference added a moment earlier still resolves.

What fuse build prints is the build's errors, one line each. When you run fuse build, it also adds a file log to the build: MSBuild's file logger 9 at normal verbosity with its performance summary. The log is written to the state directory (the temporary folder outside a repository) and deleted once read. A test run with MSBuild adds it too. When the build produced warnings, the summary line counts them (; 42 warning(s)), read from the same log. Without --warnings warnings are counted, never listed. The log adds 2 more things the errors alone leave out:

  • Under an error MSB3073, which says only that a command an MSBuild target ran exited with a code other than 0, the answer prints the last lines that command printed, at most 20, such as a code generator's exception and its first stack frame.
  • A build of 10 seconds or more ends its summary line with the 3 slowest tasks, their times summed over every project, and the 3 slowest projects. The compiler task, Csc, includes the analyzers and source generators it runs. Projects build in parallel, so a task's sum can exceed the build's own time. A slow build says how to read it.

When a build fails with CS2001 on a source file that no longer exists, another agent moved or deleted it while MSBuild compiled the file list it had evaluated. fuse build then runs the build once more, which evaluates the file list again, and prints fuse: a source file moved while the build ran, so it ran again above the answer.

The engine takes no lock. It writes nothing into the working tree, a check does not build, and it loads the repository's analyzers from copies. A dotnet build that does not go through Fuse takes no lock either. The pre-shell hook rewrites an agent's dotnet build and dotnet test so that they do.

Failure handling #

When Fuse cannot answer, the answer carries one of 9 codes and a message that names the fix: not a repository, no projects, loading, restore needed, load failed, timeout, invalid path, no registered session, internal. Commands print the message and exit with code 2. The MCP server marks the result as an error. Messages and fixes lists every message.

A hook must never break the agent's session. It reports introduced errors and a missing restore, and nothing else. Every other outcome exits 0 and prints nothing the agent reads. A stop hook that lets the agent finish prints the empty answer its harness expects, such as {}. An exception or a payload that is not valid JSON is written to hook.log in the state directory. A post-edit hook that a harness runs inline, which is every harness except Claude Code, does not wait for an engine that is still loading. The stop hook therefore reports the first edits after the engine starts.

Privacy and footprint #

  • Everything runs locally. Fuse has no telemetry and makes no network calls of its own.
  • Fuse never edits your code and never runs dotnet restore on its own.
  • The only files Fuse writes in your repository are the hook settings from fuse init, and with fuse init --instructions its section in AGENTS.md and the other instruction files your agents read. Its logs and other state are stored in your local application data folder.
  • In a repository without a .csproj file, hooks return at once and no engine starts.
  • Fuse has no configuration file and no environment variables of its own.
