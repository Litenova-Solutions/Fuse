Limits

All documentation pages

Fuse is faster than a build because it does less than a build. This page lists what it therefore cannot see, and where its answer differs from dotnet build and dotnet test, each with what to do about it.

This page is for anyone about to rely on a clean answer from Fuse, especially in a repository with custom build logic, code generation, or tests that load code at run time.

After reading it you know when to run the real build (fuse build) or every test (fuse test --all) before you finish a change.

Fuse answers from a Roslyn compilation of what MSBuild's evaluation describes, and compares the working tree (the files on disk) with HEAD (the commit you have checked out). It does not see what lies outside that model. Two commands always give the complete answer: fuse build runs the real build, and fuse test --all runs every test.

Scope and requirements #

  • C# only. Fuse evaluates .csproj projects and checks .cs, .razor and .cshtml files. Visual Basic and F# projects are not evaluated. Build those with dotnet build.
  • The .NET 10 SDK, git and restored projects. Fuse runs git from the PATH and never runs dotnet restore. When a project is not restored, it answers with the command to run (RestoreNeeded).
  • Only changes against HEAD. An error that is already committed is part of HEAD and is never reported, and neither is an error that exists at HEAD and in the working tree alike. Run fuse build to see every error the solution has.
  • A repository needs a commit. With no commit, every file counts as added, so every error counts as introduced. Commit once before relying on a check.
  • Platforms. CI builds and tests Fuse on Windows, Linux and macOS (.github/workflows/ci.yml); the benchmarks come from one Windows machine.
  • Letter case in paths on macOS. Fuse compares paths ignoring case on Windows and exactly on Linux and macOS. The default macOS volume ignores case, so a file named to fuse check in another letter case than it has on disk is not matched to the file git knows. Name files as they are spelled on disk; hooks already do.

What a check does not see #

  • Compile inputs outside evaluation. A check compiles the sources, references, analyzers and options that MSBuild's evaluation lists, without running targets. Custom targets that change what the compiler receives, source generators that read files outside the project's additional files, and IL weaving (rewriting assemblies after the compiler runs) are invisible to it. What to do: in such a repository, run fuse build before finishing a change.
  • Changes to build configuration. Both of Fuse's views, the working tree and HEAD, use the project files as they are on disk. A change to a .csproj, .props, .targets, .editorconfig, .globalconfig or global.json file on its own is not compared with HEAD, and the files it affects are checked only when they changed too. What to do: run fuse build after changing build configuration.
  • Compilation-end analyzers. Analyzers that report only after seeing the whole project run only when a check compiles whole projects, which happens past 500 files in reach, or when the analyzer is a compilation-wide analyzer, which runs over the whole compilation. Otherwise fuse build reports them.
  • The post-edit hook leaves out compilation-wide analyzers. An analyzer that reads the whole project in its compilation start or compilation actions runs once over the whole compilation, which takes as long as compiling the project, so the post-edit hook leaves it out and names it in its summary. Its errors reach the agent at the stop hook, or from fuse check.
  • Analyzers that do not finish in time. A check stops its analyzers when 80% of its client's wait has passed and answers with every compiler error and the analyzer errors found so far. The summary says in how many files or projects the analyzers did not finish. What to do: run fuse build, which runs every analyzer, and see A slow analyzer to find which analyzer is slow.
  • Warnings. A check reports errors only: compiler errors, warnings the project treats as errors, and analyzer diagnostics configured as errors.
  • Matching. An error counts as introduced when HEAD has fewer errors in the same file with the same id and message. An edit that removes one error and causes an identical one in the same file reports nothing.
  • Differences from the build's wording. The build compiles a dependent project against reference assemblies, which leave out private members, while Fuse compiles against the source. After a member is made private, the build says "does not contain a definition" and Fuse says "is inaccessible due to its protection level", at the same position. This difference is behind the one error Fuse missed in the benchmarks.
  • Generated files. A file a build writes into a project's bin or obj folder, such as a generated API client, is read as the last build wrote it, in both views (generated files). A change to it is not compared with HEAD, and it does not reach the files that use it: they are checked only when they change too. After a change to the code a file is generated from, the file lacks that change until a build writes it again, and an error about it names the file. What to do: run fuse build, then check again.
  • Which agent made an edit. When several agents edit one working tree, the post-edit hook and the stop hook tell each session only the errors its own edits cause (sessions), and they know only the edits a post-edit hook reported. An edit made by a shell command, a generator or a tool without a post-edit hook is credited to no session, so its errors go to every agent whose check finds them. Gemini CLI and GitHub Copilot CLI send the parent's session id from a subagent, so a subagent and its parent count as one session there. The command line and the MCP server send no session, so their checks report every error. In a file two sessions wrote, a cause line can name the other session's declaration change. A file stays credited to the sessions that wrote it until a check sees it match HEAD, so a file reverted and written again between two checks still counts the earlier sessions among its writers, and its errors go to each of them. A subagent's edits count as its parent's only once its own stop hook has run, which only Claude Code's SubagentStop hook does. In Codex, Cursor and OpenCode a subagent stays a session of its own, so its parent's stop hook does not block on the errors it leaves; the subagent's own stop hook is what holds it to them. An error that another session's edits cause on their own does not block a stop, so a working tree can end with errors that an agent still writing, or one that gave up, leaves behind. Deciding whose an error is adds time to each post-edit hook while another session has written files of its own, close to a second on a repository the size of NodaTime. What to do: give agents that edit the same files at the same time separate tasks, and run fuse check, which reports every error, once all agents have finished.
  • Output limits. An answer holds at most 200 errors, of which the command prints 20, and at most ten cause lines; its summary line still counts every error found. What to do: fix what is printed and check again, or run fuse build for the full list.

Test selection #

  • Static selection. Fuse selects tests from the code as written, without running it. A test that reaches the changed code only through reflection, a type name in a string or configuration, or an assembly loaded at run time is selected only when the change reaches an application host, which selects every test project that depends on the application. What to do: run fuse test --all before finishing a change that such tests cover.
  • Counts from source. The summary counts test methods from source, so a theory with several cases counts once, while the failed and passed counts come from the test run.
  • Microsoft.Testing.Platform. A test project on Microsoft.Testing.Platform (opted in through global.json) runs whole and builds with MSBuild, because its filter syntax differs per test framework. It writes no TRX file, so Fuse reads its counts and failures from what it prints; a run that crashes before its run summary is reported as a test run that exited with its exit code and produced no results, after the last 30 lines of the run's output. What to do: to run fewer of its tests, pass the framework's own filter, such as fuse test --filter-class Name for xUnit.

Test runs without MSBuild #

  • Resources and content files. A run without MSBuild takes resources and content files from the last real build. When any file other than a source file changed in a project directory since that build, Fuse builds with MSBuild instead, which is slower but complete.
  • Timestamps. Freshness is judged by timestamps, not content, so saving a resource file unchanged also sends the run through MSBuild.
  • Tests that share a fixed resource. Test runs from several agents run at the same time (each run holds its own copy). Integration tests that each start their own server, such as WebApplicationFactory and its in-memory test server, or that start their own containers, do not collide. Tests that bind a fixed port, use one database by a fixed name, or write one fixed file outside their output can collide with the same tests in another agent's run, and fail where they would pass alone. Fuse has no setting to run them one at a time. What to do: give each run its own port, database name or folder, for example from a random number or the process id.

Builds and the build lock #

  • Only builds through Fuse take the lock. A dotnet build run directly, by a person, a script, an IDE, or an agent in a harness without a pre-shell hook (Cursor and GitHub Copilot CLI), can still collide with a build Fuse runs. So can a test run with MSBuild that does not go through Fuse, whose test host holds the test assemblies in bin open until it ends. A test run without MSBuild through fuse test runs from a copy and holds nothing in bin. What to do: in a repository that several agents work in, run builds and tests through fuse build and fuse test.
  • What the pre-shell hook rewrites. The hook rewrites dotnet build and dotnet test where a command segment starts. dotnet msbuild, dotnet run, dotnet publish and scripts that call dotnet themselves run as they are. In Codex it rewrites only a command that is one dotnet build or dotnet test with plain arguments, so cd Lib && dotnet build runs there as it is (Codex).

The engine #

  • Analyzers the repository builds. The engine loads an analyzer the repository builds itself as it was when its project loaded. A rebuilt analyzer takes effect when projects next reload: after a project file change, a commit or branch switch, more than 300 changed files at once, or an engine restart. What to do: after changing an analyzer, restart the engine.
  • Memory. The engine keeps every project it has loaded in memory until it exits after 10 idle minutes, and never unloads one while it runs. A check on a large project can briefly take several times that; 30 seconds after its last request the engine compacts its memory and returns what the check freed to the operating system. In the benchmarks its working set once idle was 356 MB on the 15-project NodaTime and 947 MB on the 26-project Community Toolkit, and it peaked at 1,640 MB during checks, on runners with 16 GB of memory; the engine uses more on a machine with more memory. Each git worktree runs its own engine. What to do: on a machine short of memory, stop the engines you no longer need, as Stopping or restarting the engine describes.
  • Loading. The first request that reaches a project loads it; Benchmarks gives the load times. A post-edit hook in a harness other than Claude Code does not wait for loading, so the stop hook reports the first edits after the engine starts.
