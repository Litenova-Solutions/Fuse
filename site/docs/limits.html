Limits

All documentation pages

Fuse is faster than a build because it does less than a build. This page lists what it therefore cannot see, and where its answer differs from dotnet build and dotnet test, each with what to do about it.

This page is for anyone about to rely on a clean answer from Fuse, especially in a repository with custom build logic, code generation, or tests that load code at run time.

After reading it you know when to run the real build (fuse build) or every test (fuse test --all) before you finish a change.

Fuse answers from a Roslyn compilation of what MSBuild's evaluation describes, and compares the working tree (the files on disk) with HEAD (the commit you have checked out). It does not see what lies outside that model. Two commands always give the complete answer: fuse build runs the real build, and fuse test --all runs every test.

Scope and requirements #

  • C# only. Fuse evaluates .csproj projects and checks .cs, .razor and .cshtml files. Visual Basic and F# projects are not evaluated. Build those with dotnet build.
  • The .NET 10 SDK, git and restored projects. Fuse runs git from the PATH and never runs dotnet restore. When a project is not restored, it answers with the command to run (RestoreNeeded).
  • Only changes against HEAD. An error that is already committed is part of HEAD and is never reported, and neither is an error that exists at HEAD and in the working tree alike. Run fuse build to see every error the solution has.
  • A repository needs a commit. With no commit, every file counts as added, so every error counts as introduced. Commit once before relying on a check.
  • Platforms. CI builds and tests Fuse on Windows, Linux and macOS (.github/workflows/ci.yml); the benchmarks come from GitHub Actions windows-latest runners.
  • Letter case in paths on macOS. Fuse compares paths ignoring case on Windows and exactly on Linux and macOS. The default macOS volume ignores case, so a file named to fuse check in another letter case than it has on disk is not matched to the file git knows. Name files as they are spelled on disk; hooks already do.

What a check does not see #

  • Compile inputs outside evaluation. A check compiles the sources, references, analyzers and options that MSBuild's evaluation lists, without running targets. Custom targets that change what the compiler receives, source generators that read files outside the project's additional files, and IL weaving (rewriting assemblies after the compiler runs) are invisible to it. What to do: in such a repository, run fuse build before finishing a change.
  • Changes to build configuration. Both of Fuse's views, the working tree and HEAD, use the project files as they are on disk. A change to a .csproj, .props, .targets, .editorconfig, .globalconfig, global.json or packages.lock.json file on its own is not compared with HEAD, and the files it affects are checked only when they changed too. What to do: run fuse build after changing build configuration.
  • Compilation-end analyzers. Analyzers that report only after seeing the whole project run only when a check compiles whole projects, which happens past 500 files in reach, or when the analyzer is a compilation-wide analyzer, which runs over the whole compilation. Otherwise fuse build reports them.
  • The post-edit hook leaves out compilation-wide analyzers. An analyzer that reads the whole project in its compilation start or compilation actions runs once over the whole compilation, which takes as long as compiling the project, so the post-edit hook leaves it out and names it in its summary. Its errors reach the agent at the stop hook, or from fuse check.
  • Analyzers that do not finish in time. A check stops its analyzers when 80% of its client's wait has passed and answers with every compiler error and the analyzer errors found so far. The summary says in how many files or projects the analyzers did not finish. This also covers a file whose HEAD analyzers did not finish: the working tree's analyzer errors in that file are left out, because they cannot be told apart from errors HEAD already has. What to do: run fuse build, which runs every analyzer, and see A slow analyzer to find which analyzer is slow.
  • Warnings. A check reports errors only: compiler errors, warnings the project treats as errors, and analyzer diagnostics configured as errors.
  • Non-C# files. A changed file that is not C# is named in the summary, not checked: N non-C# file(s) changed, which Fuse does not check, with the first five paths. Hooks stay silent about them: a stop shows the note only when it already blocks, and a post-edit hook never shows it. What to do: build or test those files with their own tools.
  • Scoped checks cover 2000 sources. A fuse check over folders or patterns whose specs expand to more than 2000 sources is refused; name a smaller folder or pattern. What to do: split the scope, or check every change.
  • Matching. An error counts as introduced when HEAD has fewer errors in the same file with the same id and message. An edit that removes one error and causes an identical one in the same file reports nothing.
  • Differences from the build's wording. The build compiles a dependent project against reference assemblies, which leave out private members, while Fuse compiles against the source. After a member is made private, the build says "does not contain a definition" and Fuse says "is inaccessible due to its protection level", at the same position. This difference is behind the one error Fuse missed in the benchmarks.
  • Generated files. A file a build writes into a project's bin or obj folder, such as a generated API client, is read as the last build wrote it, in both views (generated files). A change to it is not compared with HEAD, and it does not reach the files that use it: they are checked only when they change too. After a change to the code a file is generated from, the file lacks that change until a build writes it again, and an error about it names the file. What to do: run fuse build, then check again.
  • Which agent made an edit. When several agents edit one working tree, the post-edit hook and the stop hook tell each session only the errors its own edits cause (sessions), and they know only the edits a post-edit hook reported. An edit made by a shell command, a generator or a tool without a post-edit hook is credited to no session, so its errors go to every agent whose check finds them. Gemini CLI and GitHub Copilot CLI send the parent's session id from a subagent, so a subagent and its parent count as one session there. The command line and the MCP server send no session, so their checks report every error. In a file two sessions wrote, a cause line can name the other session's declaration change. A file stays credited to the sessions that wrote it until a check sees it match HEAD, so a file reverted and written again between two checks still counts the earlier sessions among its writers, and its errors go to each of them. A subagent's edits count as its parent's only once its own stop hook has run, which only Claude Code's SubagentStop hook does. In Codex, Cursor, OpenCode and Muse Code a subagent stays a session of its own, so its parent's stop hook does not block on the errors it leaves; the subagent's own stop hook is what holds it to them. Muse Code fires its subagent stop for its own helper agents many times in a turn, so Fuse registers none there, and a Muse subagent's errors are held by no stop hook. A session registered with fuse session begin lasts 4 hours or until fuse session end; while it is live, files under its patterns count as its session's and their errors are left out of other sessions' answers, and a stale registration shields real errors until it expires. An error that another session's edits cause on their own does not block a stop, so a working tree can end with errors that an agent still writing, or one that gave up, leaves behind. Deciding whose an error is adds time to each post-edit hook while another session has written files of its own, over a second on a repository the size of NodaTime. What to do: give agents that edit the same files at the same time separate tasks, and run fuse check, which reports every error, once all agents have finished.
  • Output limits. An answer holds at most 200 errors by default, of which the command prints 20, and at most ten cause lines; its summary line still counts every error found. What to do: fix what is printed and check again, pass --max-errors or --all-errors for more, or run fuse build for the full list.

Test selection #

  • Static selection. Fuse selects tests from the code as written, without running it. A test that reaches the changed code only through reflection, a type name in a string or configuration, or an assembly loaded at run time is selected only when the change reaches an application host, which selects every test project that depends on the application. What to do: run fuse test --all before finishing a change that such tests cover.
  • Same-code detection fails closed. An edit that compiles to the same code as HEAD selects no tests, but only when the comparison can prove it. Anything it cannot read - a query, a nameof, an inferred member name, a captured argument, a field or event, anything that fails to bind - counts as changed and selects its tests. What to do: nothing; the extra tests are the safe side.
  • Container detection is package-based. A test project is left out without a runtime when any PackageReference equals Testcontainers or starts with Testcontainers., ignoring case. The probe is docker info then podman info, 2 seconds each, trusted for 5 minutes per engine process, so starting a runtime is noticed at the next plan past the wait. Tests that need a database they do not start from containers, or any other service, are not detected. What to do: start the service before fuse test.
  • Counts from source. The summary counts test methods from source, so a theory with several cases counts once, while the failed and passed counts come from the test run.
  • Microsoft.Testing.Platform. A test project on Microsoft.Testing.Platform builds with MSBuild and never runs from a shadow copy. It runs with its framework's own filter: xUnit v3 and TUnit as their arguments, MSTest and NUnit as the VSTest filter in a runsettings file, and a project whose framework Fuse does not know runs whole. An xUnit v3 or TUnit filter holds at most 200 names; past that, whole test classes run, and the summary says so. It writes no TRX file, so Fuse reads its counts and failures from what it prints; a run that crashes before its run summary is reported as a test run that exited with its exit code and produced no results, after the last 30 lines of the run's output. Without the global.json opt-in, Fuse builds the project once and starts each target directly; a project with a .NET Framework target, or one whose started target exits without printing results, runs through dotnet test instead, which takes longer.

Test runs without MSBuild #

  • Resources and content files. A run without MSBuild takes resources and content files from the last real build. When any file other than a source file changed in a project directory since that build, Fuse builds with MSBuild instead, which is slower but complete.
  • Timestamps. Freshness is judged by timestamps, not content, so saving a resource file unchanged also sends the run through MSBuild.
  • Tests that share a fixed resource. Test runs from several agents run at the same time (each run holds its own copy). Integration tests that each start their own server, such as WebApplicationFactory and its in-memory test server, or that start their own containers, do not collide. Tests that bind a fixed port, use one database by a fixed name, or write one fixed file outside their output can collide with the same tests in another agent's run, and fail where they would pass alone. Fuse has no setting to run them one at a time. What to do: give each run its own port, database name or folder, for example from a random number or the process id.

Builds and the build lock #

  • Only builds through Fuse take the lock. A dotnet build run directly, by a person, a script, an IDE, or an agent whose command its harness's pre-shell hook did not rewrite (in Cursor, GitHub Copilot CLI, Codex and Muse Code only one plain command is rewritten; VS Code agent mode has no hooks), can still collide with a build Fuse runs. So can a test run with MSBuild that does not go through Fuse, whose test host holds the test assemblies in bin open until it ends. A test run without MSBuild through fuse test runs from a copy and holds nothing in bin. What to do: in a repository that several agents work in, run builds and tests through fuse build and fuse test.
  • What the pre-shell hook rewrites. The hook rewrites dotnet build and dotnet test where a command segment starts. dotnet msbuild, dotnet run, dotnet publish and scripts that call dotnet themselves run as they are. In Cursor, GitHub Copilot CLI, Codex and Muse Code it rewrites only a command that is one dotnet build or dotnet test with plain arguments, so cd Lib && dotnet build runs there as it is (Codex).

The engine #

  • Analyzers the repository builds. The engine loads an analyzer the repository builds itself as it was when its project loaded. A rebuilt analyzer takes effect when projects next reload: after a project file change, a commit or branch switch, more than 300 changed files at once, or an engine restart. What to do: after changing an analyzer, run fuse stop (stopping the engine); the next command starts an engine that loads the new analyzer.
  • Memory. The engine keeps every project it has loaded in memory until it exits after 30 idle minutes, and never unloads one while it runs. A check on a large project can briefly take several times that; 30 seconds after its last request the engine compacts its memory and returns what the check freed to the operating system. In the benchmarks its working set once idle was 423 MB on the 40-project Jellyfin and 504 MB on the 15-project Polly, and it peaked at 1,091 MB during checks, on runners with 16 GB of memory (latency-FluentValidation-20261029-1855.json, latency-NodaTime-20261029-1858.json, latency-Jellyfin-20261029-1907.json, latency-Polly-20261029-1904.json); the engine uses more on a machine with more memory. Each git worktree runs its own engine. What to do: on a machine short of memory, stop the engines you no longer need, as Stopping or restarting the engine describes.
  • Loading. The first request that reaches a project loads it; Benchmarks gives the load times. A post-edit hook in a harness other than Claude Code does not wait for loading, so the stop hook reports the first edits after the engine starts.
  • Large-tree points. Past 300 changed files a sync reads git status again and reloads the loaded projects; past 500 files in reach a check binds whole projects; past 2000 applied paths the next sync re-evaluates the projects and resets the touched set. fuse status prints the first two as the large-tree limits. What to do: commit, or run fuse stop and let the next check reload when checks feel slow.
  • Kept answers need a quiet tree to hash. Past 500 changed files a check skips the kept answer, because hashing every file costs more than the reuse saves, and an answer bound from text that no longer matches disk is served but not kept. What to do: nothing; the check still answers.
  • HEAD's kept state. The engine keeps HEAD's finished baseline errors on disk per commit and configuration, and warms a new HEAD's compilation-wide analyzer results in the background. Either is dropped silently when it no longer applies: an unreadable store entry is computed again, and a warm cut short by another commit stops. What to do: nothing; both only cost time.

Deferred improvements #

These speedups were considered for this release and deliberately not built. Each is listed so you do not expect it.

  • Concurrent checks still answer one at a time. Requests are not coalesced: each check binds its own scope behind the request lock.
  • Builds still run one per waiter. The build lock takes turns but shares no result: each fuse build runs its own dotnet build.
  • Checks still bind whole files. A body edit binds its files whole, not only the changed spans.
  • Attribution still re-binds. Deciding which session an error belongs to compiles the files with errors again in narrowed views; no view is reused between checks.
  • Tests still run in plan order. Slow tests are not split into their own runs, and one request gets one answer with one summary; only the tests that failed last time run first as their own stage, whose failures print before the rest runs on the command line.
  • No executed-code record. Fuse records no per-test coverage, so the application rule is decided from source, not from the handlers each test ran.
  • Each run starts its own test host. No warm host is kept between runs, nothing is patched into a running host, and emitted images are written to the shadow copies, not served from memory.
  • Failures at HEAD are still reported. fuse test does not compare failures with HEAD; a test that already failed at HEAD fails the run the same as an introduced one.
  • Agents do not share runs. Two agents that select the same tests each run them in their own processes.
  • Compilation-wide analyzers rerun per compilation. An analyzer that reads only declarations still runs again after a body edit; its result is not reused across compilations.
  • Every selected test runs again. A passing test is never answered from an earlier run: when it is selected again, it runs again, even when nothing it reads changed.
  • Application hosts still select whole projects. A change that reaches an application runs every test project that depends on it; Fuse does not narrow them to the tests that start the application.
  • Each run prepares its own copies. Nothing mirrors build output in the background ahead of a test run; each fuse test prepares its shadow copies itself, under the build lock.
