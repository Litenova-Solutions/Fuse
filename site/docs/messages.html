Messages and Fixes

All documentation pages

When Fuse cannot answer, it prints fuse: and one of the messages on this page, and exits with 2. Each message names its fix. Usage failures also exit with 2. The rerun and container lines at the end are answers: each names its own exit code.

This page is for anyone who got one of these messages from a command, an MCP tool, or a hook, and wants to know what caused it and what to run.

If there was no message at all, for example a hook that says nothing, read Troubleshooting instead.

Each message has a code, which the MCP server and the hooks act on. The MCP server returns every one as an error result. A hook reports RestoreNeeded, because the agent can fix it by running the command, and stays silent on the rest, because a hook never breaks the agent's session. Text in angle brackets varies.

NotARepository #

fuse: not inside a git repository; Fuse compares your changes with HEAD, so it needs one

Cause. fuse check, fuse test, fuse status, fuse session, fuse stop, fuse init and fuse uninit print it on standard error, and fuse mcp returns it, when the working directory is in no git repository. For an MCP server, that is the directory it was started in. fuse build runs outside a repository; only fuse build --changed needs one.

Fix. Run the command inside the repository, or run git init and commit.

NoProjects #

fuse: no C# projects (.csproj) in this repository, so Fuse has nothing to check
fuse: no C# project could be evaluated: <path>: <MSBuild message>

Cause. Git knows no .csproj file in the repository (the second line is fuse init's), the project files git knows are missing from disk, or MSBuild could evaluate none of them.

Fix. Add or commit a project. For the second line, fix the project file the message names, which dotnet build also fails on.

Loading #

fuse: Fuse is still loading this repository; the next check will include these changes

Cause. The engine answers a check with this while it is still evaluating the repository or loading the projects that own uncommitted changes, when the check asked not to wait. Only the post-edit hook of a harness other than Claude Code asks that, because the agent waits for that hook, and it stays silent on this answer.

Fix. None; the stop hook and the next check cover the changes.

RestoreNeeded #

fuse: restore needed: run `dotnet restore Lib/Lib.csproj` (Lib/Lib.csproj not restored)

Cause. A project the request needs, or a project it references, has no project.assets.json, the file dotnet restore writes. The message names the first such project, adds and the same for each project listed when there are more, and lists up to three. It names a project rather than the solution, because a solution can leave out the project that is missing its restore.

Fix. Run the command it names for each project listed. Fuse never restores on its own. Every hook reports this message too, so an agent sees it and can run the command.

LoadFailed #

fuse: could not load <project>: <message>
fuse: could not load <project>: the check reached <name> but the engine's view does not hold it (the projects the view holds are named in engine.log)
fuse: Fuse could not evaluate the repository's projects: <message>
fuse: git failed <action> in <root> (<git's message>); the repository may be damaged, see `git status` and `git fsck`
fuse: git cannot read <path> at HEAD; the repository may be damaged (run `git fsck`)
fuse: git cannot list the repository's files (<git's message>); see `git status`

Cause. A project could not be loaded (a missing project reference or an SDK that does not resolve, which dotnet build also fails on), the evaluation failed, or git could not read the repository. A NuGet restore warning, such as a package advisory, does not count as a failure. The second line means a check reached a project the engine's views do not hold, even after rebuilding them once; the check fails rather than answer partially. Hooks stay silent on it.

Fix. Run dotnet build on the project to see the same failure, or git status and git fsck for the git messages. For the second line, run the command again.

Timeout #

fuse: the Fuse engine did not answer within <seconds> s
fuse: the request is cancelled

Cause. The engine did not answer within the command's limit:

CallerLimit
fuse check, fuse test and the MCP tools600 s
The Claude Code post-edit hook and every stop hook280 s
The other post-edit hooks50 s

A request that reaches projects the engine has not loaded waits for them to load. The second line is the engine's answer when a request is cancelled while it runs.

Fix. Run the command again; the engine keeps loading in between. Troubleshooting shows how to see what it is doing.

InvalidPath #

fuse: a file named in the check is empty; name each file by its path
fuse: "<file>" named in the check is not a valid path
fuse: none of the files named in the check is a C# source file of a project in this repository: <files>
fuse: none of the paths given names a test project in this repository: <paths>
fuse: "<spec>" in the check matches no changed C# source file of a project in this repository
fuse: the paths named in the check expand to <N> source files, more than the 2000 a scoped check covers; name a smaller folder or pattern
fuse: "<name>" is not a valid session name; use 1 to 64 letters, digits, -, _ or .
fuse: "<pattern>" is not a valid path pattern; use forward slashes, * and ? inside a segment, ** as a whole segment, no .. segment
fuse: a session holds at most 32 path patterns, not <N>; name fewer
fuse: at most 64 sessions can be registered at once; end one with fuse session end <name>
fuse: "<pattern>" is outside this repository; name a pattern inside it

Cause. fuse check and the fuse_check tool print it when a file argument is empty or blank, is not a string, or is not a path (for example because it holds a NUL character), and check nothing. The third form means every named file is something Fuse cannot check: a path that does not exist, a file of another language, or a C# file outside every project. It lists up to five of them. When at least one named file is a C# source of a project, the check runs on those, and its file(s) checked count leaves the others out. The fourth form is fuse test with arguments that only name where the tests are, when none of them is a test project file, a solution listing one, or a directory holding one. The fifth and sixth forms are a scoped fuse check: one directory or pattern matched no changed C# source a project owns, or one file is no C# source of a project, refusing the whole call even when the other specs matched, or the specs expanded past 2000 sources. The rest are fuse session: a name or pattern the engine cannot register, more than 32 patterns on one session, more than 64 sessions at once, or a pattern outside the repository.

Fix. Name each file by its path, relative or absolute, and check that the path is spelled as it is on disk. For a scoped check, name a smaller folder or pattern. For a session, pick a name of 1 to 64 letters, digits, -, _ or ., and patterns inside the repository.

NoRegisteredSession #

fuse: no registered session named <name>

Cause. fuse session end prints it when no session with that name is registered, and ends nothing.

Fix. Check that the name is spelled as it was begun, or register it with fuse session begin.

Internal #

fuse: internal error: <message> (details in <state directory>/engine.log)
fuse: the Fuse engine closed the connection (see <state directory>/engine.log)
fuse: the Fuse engine sent an answer this client cannot read (<reason>; see <state directory>/engine.log)
fuse: could not connect to the Fuse engine: <message>
fuse: could not start the Fuse engine: <message>
fuse: the Fuse engine sent no check result (<response>); run the command again
fuse: the Fuse engine sent no test plan (<response>); run the command again

Cause. Something failed inside Fuse. could not connect to the Fuse engine: it did not start within 15 s means the engine process did not open its pipe.

Fix. Read the lines of engine.log the message names, then run the command again. Troubleshooting lists the details to collect for a bug report.

Usage failures #

fuse: check takes files and [--max-errors <n>|--all-errors] [--json]; '<token>' is not one
fuse: '<token>' is not a fuse build option; did you mean '<option>'?
fuse: '<token>' is not a fuse test option; did you mean '<option>'?
fuse: --max-errors takes a count of 1 or more; use --all-errors for every error
fuse: --max-errors takes a count of 1 to 100000, not '<text>'
fuse: --all-errors and --max-errors cannot be combined; choose one
fuse: --all runs every test and cannot be combined with other arguments; pass the arguments without --all to choose the scope
fuse: --failed reruns the tests that failed last time and cannot be combined with other arguments; pass the arguments without --failed to choose the scope
fuse: status takes [--json]; '<token>' is not one
fuse: max_errors takes a count of 1 to 100000
fuse: failed reruns the tests that failed last time and cannot be combined with all; set only one of them

Cause. The arguments did not parse, so the command ran nothing: no root lookup, no engine start, no build and no lock. fuse check refuses every -- option it does not take; fuse build and fuse test pass unknown tokens to dotnet and refuse only a near miss of one of their own options, naming the option it meant. A --max-errors with no count or 0 is refused, as is one with text that is no count of 1 to 100000, as are --all-errors with --max-errors, --all and --failed with any other argument, and anything but --json to fuse status. A fuse test --session with no id prints fuse: --session takes the session's id; you never pass that flag yourself, the pre-shell hook does. The last two lines are the MCP server's, returned as error results. On the command line each refusal prints on standard error and exits with 2; the --session, --all and --failed lines print alone, and the rest print with the command's usage. fuse init, fuse uninit, fuse stop, fuse mcp and fuse session with arguments they do not take print only their usage there: usage: fuse init [--instructions], usage: fuse uninit, and usage: fuse session begin <name> --paths <pattern> [<pattern>...] | fuse session end <name>, while fuse stop and fuse mcp print their own usage block. So does an unknown command, which prints the top-level usage.

Fix. Read the usage line and run the command again.

No failures to rerun #

fuse: no test run is recorded yet; run fuse test first
fuse: the last test run was from dotnet test arguments, so its failures cannot be rerun; run fuse test
fuse: the last test run had no failures
fuse: none of the tests that failed last time is in a test project in this repository
fuse: none of the <N> test(s) that failed last time ran; they may have been renamed or removed

Cause. fuse test --failed reruns the failures of the last recorded run, and there is nothing to rerun: no run is recorded yet, the last run came from your own dotnet test arguments, which are recorded without their project and cannot be rerun, the last run had no failures, the failed tests are in no test project of this repository anymore, or none of them ran, because they were renamed or removed. The first, second and fourth lines exit with 2, the third with 0, and the last with 1.

Fix. Run fuse test or fuse test --all to record a run, then rerun its failures.

No container runtime #

fuse: no test ran: <N> test(s) selected in <P> need a container runtime, and none is running; start Docker or Podman and run fuse test again

Cause. Every selected test needs a container runtime and neither Docker nor Podman answered, so no process started. The command exits with 1. The affected and --all plans leave such projects out and name them in the summary (fuse test); this line is for a plan with nothing else to run.

Fix. Start Docker or Podman and run fuse test again.

Other lines on standard error #

These two lines are not failures: the command goes on after printing them.

fuse: waiting for another build or test in this repository
fuse: running without the per-repository build lock: <reason>

fuse build and fuse test print the first once when another client holds the build lock, and keep waiting. They print the second when the state directory cannot be written, and build without the lock.
