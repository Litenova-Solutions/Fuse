Subagents and parallel agents

All documentation pages

An agent can hand work to subagents, run in the background, or share a repository with other agents. This page shows what Fuse tells each of them, how their test runs and builds share the machine, and how to check work that several agents wrote, as a peer or as a judge that settles workers' slices.

This page is for a developer who runs more than one agent in a repository: subagents an agent starts, background agents, several agent sessions in one working tree, agents in separate git worktrees, or workers a judge settles.

After reading it you can set up a repository for them with fuse init, know which errors each agent is told about, check fanned-out work before you merge it, and settle external workers as a judge with sessions, scoped checks and changed-only builds.

What each agent is told #

Every agent in one working tree (the files on disk) talks to the same engine, the background process that keeps the repository's projects compiled. Each agent runs as a session: its run as its harness identifies it in a hook's payload. Fuse remembers which sessions wrote each changed file, and answers each session for itself:

  • The post-edit hook tells a session the errors its own edits cause, alone or together with another session's edits.
  • The stop hook checks only that session's scope: the files its own edits wrote, files it wrote together with another session, and files no session is credited with, plus the files they reach. It blocks the session's finish on the errors those cause. Errors that live only in another session's files are never bound; errors only another session's edits cause inside the reach are left to that session, and the summary counts them.
  • An edit no post-edit hook reported, such as one a shell command, a code generator or a tool without a hook made, is credited to no session, so its errors go to every agent whose check finds them.

How it works explains how Fuse decides whose an error is, and Limits lists the cases it cannot separate.

Subagents in each harness #

Whether a subagent is a session of its own depends on what its harness sends. When it is, its parent is not told about its errors while it runs, so a half-written file of a working subagent does not interrupt its parent. When the harness also runs Fuse's stop hook as the subagent finishes, the subagent is sent back to fix its own errors first, and from then on its edits count as its parent's.

Where a subagent's stop is not checked and its edits never count as its parent's, nothing holds it to the errors only its edits cause. In those harnesses, have the subagent run fuse check before it finishes, and have the parent run it once every subagent is done. Connect your agent lists the id each harness sends.

Fanning work out #

Fanning out means one agent, the orchestrator, splits a task among several workers that run at once. These habits keep each worker's answers its own and the result checked:

  1. Give workers separate files. An error in a file two sessions wrote is told to both, so workers that share files get each other's errors.
  2. Have each worker check its own work. A worker runs fuse test before it hands its work back. The pre-shell hook rewrites its dotnet test to fuse test --session <its session>, which runs the tests its own edits can break and leaves out the changes only other sessions wrote (a session's own tests). It runs fuse check too where its harness does not check its stop.
  3. Write through edit tools, not shell commands. A file a worker writes with a shell command is credited to no session, so its errors reach every agent.
  4. Check the whole result at the end. Once the workers are done, the orchestrator runs fuse check, which reports every error the changes since HEAD (the commit checked out) introduced, whoever wrote them, and fuse test, or fuse test --all for every test. In Claude Code its own stop hook also covers the edits of the subagents that have stopped. When the workers write from outside any harness, settle them as a judge instead (Judges and workers).

Judges and workers #

A judge is the agent or launcher that starts workers, gives each its own paths, and settles their work at the end. A worker that edits through a harness is a session already, so the judge's stop leaves its errors to it. A worker that writes from outside any harness, such as a program, a code generator or a tool without hooks, is credited to no session, so its half-written errors would block the judge. Register each such worker as a session before you start it:

fuse session begin worker-3 --paths "src/Workers/Third/**" "src/Shared/**"
fuse: session worker-3 registered for 2 path pattern(s); files under them count as that session's until fuse session end worker-3 or 4 hours pass

While the registration lasts, every changed file under its patterns counts as that worker's session, so the judge's stop leaves that worker's half-written errors to it. A plain fuse check still reports every error in the tree, whoever wrote it.

  • End the registration when the worker stops. fuse session end worker-3 prints fuse: session worker-3 ended; its files now count as no session's, so the judge's next check sees them as work to settle. Ending an unknown name prints fuse: no registered session named worker-3 and exits 2.
  • Re-begin to change the paths or keep a slow worker. Beginning a live name again replaces its patterns and restarts its 4 hours. Past 4 hours a registration expires on its own, and its files count as no session's. Fuse does not watch whether the worker's process still runs, so end a worker that finished early.
  • Keep the names and patterns small. A name holds 1 to 64 letters, digits, -, _ or .. A pattern is relative to the repository root, with ** as a whole segment, * and ? inside a segment, no .. segment, and at most 256 characters. One session holds at most 32 patterns, and 64 sessions can be live at once.
  • Registrations live outside the repository. They are kept in the state directory, so they survive an engine restart. fuse stop keeps them, and fuse uninit deletes them with the rest of the state.

Commands lists both forms and every refusal.

Checking one worker's paths #

A scoped check is a worker's "my paths, my errors" query: fuse check with a directory or a pattern checks the changed sources under it and what they reach. Any argument that is a directory that exists, or holds * or ?, scopes the whole call, and files, directories and patterns can be mixed:

fuse check src/Workers/Third/

The answer holds the errors in the changed sources under that folder, and the errors they cause in files outside it, each with the cause line that names the change. The summary names the scope: with errors it carries ; checked src/Workers/Third and what it reaches before the tree stamp, and a clean scope reads fuse: no errors introduced in src/Workers/Third and what it reaches (3 file(s) checked; tree 9f2c41aa07b3 over 5 changed file(s)).

A scope that matches no changed C# source is refused instead of answering clean, which would read as no errors introduced:

fuse: "docs/**" in the check matches no changed C# source file of a project in this repository

Each refusal exits 2. A scope that expands past 2000 source files is refused too, so name a smaller folder or pattern. Commands lists every form.

To split the errors into per-worker briefs, add --json: fuse check --json prints one JSON object per error, with file, line, column, code and message, plus cause and generated when the error has them, and the summary as the last line. The judge groups the objects by file and hands each worker its own.

Building only what changed #

Once the workers are done, fuse build --changed builds only the projects that own files changed since HEAD (the commit checked out) and their dependents, reduced to the highest projects, because building one builds what it references. Each project builds with the same extra arguments you passed:

fuse: building 2 project(s) for 5 changed file(s) (tree 9f2c41aa07b3): App, Lib.Tests
fuse: build (App) succeeded in 3.2 s; tree 9f2c41aa07b3 over 5 changed file(s)
fuse: build (Lib.Tests) succeeded in 2.8 s; tree 9f2c41aa07b3 over 5 changed file(s)
fuse: 0 of 2 project(s) failed

With nothing changed it builds nothing and exits 0: fuse: no C# changes since HEAD; nothing to build (tree 9f2c41aa07b3). When the selection cannot be trusted, because project files changed or no changed file belongs to a project, it says so first and builds the whole solution instead: fuse: project files changed (Lib/Lib.csproj); building the whole solution instead. Commands lists every form.

Checking the tree before a large commit #

Before a large commit, fuse status shows what the tree holds: whether an engine runs for the repository, how many files differ from HEAD, and the tree stamp that command-line checks and builds carry:

fuse: engine running for C:/Repo (pid 1234), 512 MB; idle exits after 30 min
fuse: 87 changed file(s) since HEAD; tree 9f2c41aa07b3; HEAD a1b2c3d4e5f6
fuse: large-tree limits: past 300 changed files a sync reloads projects; past 500 files in reach a check binds whole projects; commit or run fuse stop and let the next check reload when checks feel slow

fuse status never starts an engine: when none answers within 2 seconds it reads the tree from git instead. Past 300 changed files it also warns that checks reseed from git and slow down, and tells you to commit soon. With --json it prints one object with engine, pid, memoryMB, changedFiles, head, tree, reloadAt and wholeProjectAt. Commands lists every form.

Tests and builds at once #

Several agents' fuse test runs overlap. A run without MSBuild runs from a copy of the test project's build output that it holds until it ends, and fuse test gives up the per-repository build lock once its runs hold their copies, so another agent's test run or build does not wait for it. A run that has to build with MSBuild takes the build lock, so those runs take turns (How Fuse runs tests without MSBuild).

Integration tests that each start their own server or containers run side by side safely. Tests that bind a fixed port, or use one database by a fixed name, can collide with the same tests in another agent's run (Limits).

fuse build takes the build lock, so agents' builds take turns instead of failing on each other's files. When a build fails because another agent moved a source file while it ran, it runs once more (fuse build). Agents in Cursor and GitHub Copilot CLI get no pre-shell hook, so ask them to run fuse build and fuse test instead of dotnet build and dotnet test. To build only the changed projects and their dependents, run fuse build --changed (Building only what changed).

Agents in separate worktrees #

A git worktree is a second working tree of the same repository, in its own folder. To Fuse each worktree is a repository root of its own, with its own engine, state directory and build lock, so agents in different worktrees never share an engine, never see each other's errors, and never wait for each other's builds.

  • Each engine keeps the projects it loaded in memory until it has been idle for 30 minutes (Limits), so several worktrees with warm engines hold several times that memory. fuse stop in a worktree you are done with gives its memory back at once.
  • Fuse never runs dotnet restore, so a new worktree needs one before its first check; until then a check answers with the command to run.
  • Run fuse init in a worktree only when its settings files differ from the main working tree's; committed settings are already there.

Telling agents about Fuse #

The hooks work without any instructions, but an agent uses the commands better when it knows them, and a subagent starts with only the instructions files. fuse init --instructions writes a Fuse section into AGENTS.md, creating the file when the repository has none, into CLAUDE.md when that file exists and does not import @AGENTS.md, and into GEMINI.md when that file exists. The section sits between <!-- fuse:begin --> and <!-- fuse:end -->; running the command again replaces only what is between them and keeps the rest of the file (fuse init --instructions).

<!-- fuse:begin -->
## Fuse

This repository uses [Fuse](https://fuse.codes) to check .NET changes. Its hooks run on their own; these commands are for when you need them.

- After each edit, Fuse tells you the compiler errors that edit introduced. Fix them before you go on.
- Run `fuse test` to run the tests your changes can break; `fuse test --all` runs every test. `dotnet test` is rewritten to `fuse test`.
- `fuse test` skips test projects that need a container runtime when none is running, and says so; start Docker or Podman to run them.
- Fuse checks C# only; `fuse check` names changed files in other languages, which your repository's own gates cover.
- Run `fuse build` instead of `dotnet build`: it prints only the errors, and waits for another agent's build instead of colliding with it.
- When you finish, Fuse checks every change since HEAD (the commit checked out) and sends you back for the errors your edits introduced. `fuse check` runs the same check when you want it sooner.
- When several agents work in this working tree, each is told the errors its own edits cause, and `fuse test` runs the tests its own edits affect.
- If Fuse stops answering, `fuse stop` stops its engine; the next command starts a new one.
<!-- fuse:end -->

Stopping the engine #

fuse stop asks the repository's engine to stop, and kills its process when it has not exited within 10 seconds. fuse stop --all does the same for the engine of every repository Fuse keeps state for. The next command or hook starts a new engine. Stop it after changing an analyzer the repository builds itself, to give memory back when you are done with a worktree, or when it stops answering (fuse stop).
