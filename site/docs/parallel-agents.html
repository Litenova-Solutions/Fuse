Subagents and parallel agents

All documentation pages

An agent can hand work to subagents, run in the background, or share a repository with other agents. This page shows what Fuse tells each of them, how their test runs and builds share the machine, and how to check work that several agents wrote.

This page is for a developer who runs more than one agent in a repository: subagents an agent starts, background agents, several agent sessions in one working tree, or agents in separate git worktrees.

After reading it you can set up a repository for them with fuse init, know which errors each agent is told about, and check fanned-out work before you merge it.

What each agent is told #

Every agent in one working tree (the files on disk) talks to the same engine, the background process that keeps the repository's projects compiled. Each agent runs as a session: its run as its harness identifies it in a hook's payload. Fuse remembers which sessions wrote each changed file, and answers each session for itself:

  • The post-edit hook tells a session the errors its own edits cause, alone or together with another session's edits.
  • The stop hook blocks a session's finish on the same errors, and on errors in changes no session is credited with. Errors another session's edits cause on their own are left to that session, and the summary counts them.
  • An edit no post-edit hook reported, such as one a shell command, a code generator or a tool without a hook made, is credited to no session, so its errors go to every agent whose check finds them.

How it works explains how Fuse decides whose an error is, and Limits lists the cases it cannot separate.

Subagents in each harness #

Whether a subagent is a session of its own depends on what its harness sends. When it is, its parent is not told about its errors while it runs, so a half-written file of a working subagent does not interrupt its parent. When the harness also runs Fuse's stop hook as the subagent finishes, the subagent is sent back to fix its own errors first, and from then on its edits count as its parent's.

Where a subagent's stop is not checked and its edits never count as its parent's, nothing holds it to the errors only its edits cause. In those harnesses, have the subagent run fuse check before it finishes, and have the parent run it once every subagent is done. Connect your agent lists the id each harness sends.

Fanning work out #

Fanning out means one agent, the orchestrator, splits a task among several workers that run at once. These habits keep each worker's answers its own and the result checked:

  1. Give workers separate files. An error in a file two sessions wrote is told to both, so workers that share files get each other's errors.
  2. Have each worker check its own work. A worker runs fuse test before it hands its work back. The pre-shell hook rewrites its dotnet test to fuse test --session <its session>, which runs the tests its own edits can break and leaves out the changes only other sessions wrote (a session's own tests). It runs fuse check too where its harness does not check its stop.
  3. Write through edit tools, not shell commands. A file a worker writes with a shell command is credited to no session, so its errors reach every agent.
  4. Check the whole result at the end. Once the workers are done, the orchestrator runs fuse check, which reports every error the changes since HEAD (the commit checked out) introduced, whoever wrote them, and fuse test, or fuse test --all for every test. In Claude Code its own stop hook also covers the edits of the subagents that have stopped.

Tests and builds at once #

Several agents' fuse test runs overlap. A run without MSBuild runs from a copy of the test project's build output that it holds until it ends, and fuse test gives up the per-repository build lock once its runs hold their copies, so another agent's test run or build does not wait for it. A run that has to build with MSBuild takes the build lock, so those runs take turns (How Fuse runs tests without MSBuild).

Integration tests that each start their own server or containers run side by side safely. Tests that bind a fixed port, or use one database by a fixed name, can collide with the same tests in another agent's run (Limits).

fuse build takes the build lock, so agents' builds take turns instead of failing on each other's files. When a build fails because another agent moved a source file while it ran, it runs once more (fuse build). Agents in Cursor and GitHub Copilot CLI get no pre-shell hook, so ask them to run fuse build and fuse test instead of dotnet build and dotnet test.

Agents in separate worktrees #

A git worktree is a second working tree of the same repository, in its own folder. To Fuse each worktree is a repository root of its own, with its own engine, state directory and build lock, so agents in different worktrees never share an engine, never see each other's errors, and never wait for each other's builds.

  • Each engine keeps the projects it loaded in memory until it has been idle for 30 minutes (Limits), so several worktrees with warm engines hold several times that memory. fuse stop in a worktree you are done with gives its memory back at once.
  • Fuse never runs dotnet restore, so a new worktree needs one before its first check; until then a check answers with the command to run.
  • Run fuse init in a worktree only when its settings files differ from the main working tree's; committed settings are already there.

Telling agents about Fuse #

The hooks work without any instructions, but an agent uses the commands better when it knows them, and a subagent starts with only the instructions files. fuse init --instructions writes a Fuse section into AGENTS.md, creating the file when the repository has none, into CLAUDE.md when that file exists and does not import @AGENTS.md, and into GEMINI.md when that file exists. The section sits between <!-- fuse:begin --> and <!-- fuse:end -->; running the command again replaces only what is between them and keeps the rest of the file (fuse init --instructions).

<!-- fuse:begin -->
## Fuse

This repository uses [Fuse](https://fuse.codes) to check .NET changes. Its hooks run on their own; these commands are for when you need them.

- After each edit, Fuse tells you the compiler errors that edit introduced. Fix them before you go on.
- Run `fuse test` to run the tests your changes can break; `fuse test --all` runs every test. `dotnet test` is rewritten to `fuse test`.
- Run `fuse build` instead of `dotnet build`: it prints only the errors, and waits for another agent's build instead of colliding with it.
- When you finish, Fuse checks every change since HEAD (the commit checked out) and sends you back for the errors your edits introduced. `fuse check` runs the same check when you want it sooner.
- When several agents work in this working tree, each is told the errors its own edits cause, and `fuse test` runs the tests its own edits affect.
- If Fuse stops answering, `fuse stop` stops its engine; the next command starts a new one.
<!-- fuse:end -->

Stopping the engine #

fuse stop asks the repository's engine to stop, and kills its process when it has not exited within 10 seconds. fuse stop --all does the same for the engine of every repository Fuse keeps state for. The next command or hook starts a new engine. Stop it after changing an analyzer the repository builds itself, to give memory back when you are done with a worktree, or when it stops answering (fuse stop).
