Troubleshooting

All documentation pages

This page covers each symptom a Fuse setup can show, with its cause and fix, then where Fuse keeps its logs, how you read them, and how you stop the engine.

This page is for you when your hooks stay silent, your checks run slowly, or your commands print an error, and you want to find out why.

If you have a message that starts with fuse:, look it up first in Messages and fixes, which lists every one.

In short

  • A hook stays silent when the edit is clean, so run fuse check to tell a clean edit apart from a hook that never ran.
  • Each section below names one symptom, its cause, and what you do about it.
  • Most problems show in engine.log or hook.log, both in the state directory.
  • Stopping the engine is safe: fuse stop stops it, and the next command starts a fresh one.

Most problems show in one of two logs in the repository's state directory. The engine writes engine.log for every request it serves, and a hook writes hook.log when it fails. Where the logs are gives the path.

A hook prints nothing #

Silence is usually correct. A hook prints an answer only when the edit introduced errors or when a project needs a restore.

A clean edit, an engine that is still loading, a timeout, and an internal failure all leave the agent with nothing to read. A stop hook still prints the empty answer its harness expects, such as {}. A hook stays silent in these cases so that it never breaks the agent's session.

To tell these cases apart:

  1. Run fuse check in the repository. When it reports errors that the hook did not print, the hook did not run or did not reach the engine; see The agent does not see the hooks.
  2. Read hook.log. It holds two things only: a payload that is not valid JSON, and an exception inside the hook. Each entry names the harness and the event. A timeout, or an answer the engine could not give, is never written there; run fuse check in the same repository to see it.
  3. Read the end of engine.log. A post-edit check appears as a CheckFiles request with the edited file names. A stop check appears as CheckChanges (reading a phase line).

A stale-looking answer #

An answer that names an error you already fixed is usually not stale. It was true when the engine computed it.

A harness that runs the post-edit hook in the background delivers its answer late, after you made more edits. The hook therefore checks the tree again before it returns errors, and drops the answer when the current tree no longer reports it (confirmed before it is delivered).

To tell the cases apart:

  1. Run fuse check. When it no longer reports the error, the tree moved on after the answer was computed, so nothing is wrong.
  2. Read hook.log. A background post-edit delivery is logged as <harness> post-edit delivered: ..., and a drop as <harness> post-edit dropped: ... (a check of the current tree did not report it). Each entry carries the answer's summary line. A stop that blocked is logged as <harness> stop blocked: ..., which tells it apart from a late post-edit delivery.
  3. Read the end of engine.log. check: kept answer means the answer was reused because nothing it depends on changed. If the tree had moved, the check would have bound again instead.

The agent does not see the hooks #

  • The harness's folder did not exist when fuse init ran. fuse init writes settings only for the harnesses it detects (detection). Create the folder first, for example .cursor/, then run fuse init again.
  • The harness cannot find fuse. Every hook runs the command fuse, so the tools directory (~/.dotnet/tools, or %USERPROFILE%\.dotnet\tools on Windows) must be on the PATH of the process that starts the harness, not only in your terminal.
  • Cursor with only Claude Code settings. Cursor also runs Claude Code's hooks. In a Cursor session Fuse ignores those hooks so that the Cursor hooks answer. Create .cursor/ and run fuse init again.
  • Muse Code runs no Fuse hook. Muse loads hooks only from an installed and approved plugin, so writing the bundle is not enough. After trusting the workspace in Muse, run muse plugins install .muse/plugins/fuse --scope project and muse plugins approve fuse in the repository. Run muse plugins update fuse after you run fuse init again. Once the plugin runs, muse plugins list shows fuse with active=true (Muse Code).

dotnet build and dotnet test run unchanged after updating from 5.0.0 #

Fuse 5.1.0 names the shell event pre-shell. Settings written by 5.0.0 call fuse hook <harness> pre-bash. Fuse 5.1.0 answers that call with a usage line on standard error and exit code 0, so the harness runs the command unchanged.

After updating, run fuse init again in each repository. It replaces Fuse's hook entries and the OpenCode plugin and keeps everything else (Running fuse init again).

The engine needs no action after an update. The first request from the updated client reaches the running engine of the earlier build, which answers Restart and exits. The client then starts an engine of its own build and sends the request again.

engine.log records the restart as client build <build> differs; exiting so the client can start a matching engine, with the client's build id in place of <build>. A 5.0.0 engine cannot read the build id of a 5.1.0 request and leaves the place empty. A 5.1.0 engine writes (none) there for a request that carries no build id, such as one from a 5.0.0 client.

Restore needed #

fuse: restore needed: run `dotnet restore Lib/Lib.csproj` (Lib/Lib.csproj not restored)

A project the request needs has no project.assets.json. Fuse never restores on its own. Run the command the message names for each project it lists (RestoreNeeded). Every hook reports this message too, so that the agent sees it and can run the command.

Not a repository, or no projects #

fuse: not inside a git repository means the working directory is in no git repository. For an MCP server, the directory is the one it was started in.

fuse: no C# projects (.csproj) in this repository means git knows no .csproj file there, tracked, or untracked and not ignored.

In such a repository every hook returns at once without starting an engine. That is by design.

To fix this, run Fuse inside a git repository with a C# project, and commit once.

The first answer after the engine starts is slow #

The engine loads projects when a request first needs them. A declaration change additionally needs every dependent project loaded. The first check after the engine starts, and the first declaration change in a large repository, wait for that load. Later requests reuse it. engine.log shows each load as loaded <project> in <ms> ms.

Harnesses other than Claude Code run the post-edit hook inline, so that hook never waits for an engine that is still loading. It prints nothing until the load finishes. The stop hook does wait, so it reports those edits before the agent finishes.

A command times out #

fuse: the Fuse engine did not answer within 600 s

The request waited longer than the command allows:

  • 600 s for fuse check, fuse test, and the MCP tools.
  • 280 s for the Claude Code post-edit hook and every stop hook.
  • 50 s for the other post-edit hooks.

Read the end of engine.log. loaded <project> lines mean the engine is still loading. Once the request finishes, its phases line shows where the time went.

Run the command again, because the engine keeps its progress between requests.

A slow analyzer #

left out 1 analyzer(s) that read the whole project, which the stop hook and fuse check run: Vendor.Analyzers/RegistrationAnalyzer

An analyzer package can make every check slow when it reads the whole project in its compilation start or compilation actions. One example is calling Compilation.GetSemanticModel on every file, which the Roslyn rule RS1030 warns analyzer authors against. Fuse runs such an analyzer once per compilation instead of once per file (compilation-wide analyzers). The post-edit hook leaves it out. When the engine first decides, the engine log names the analyzer:

analyzers of Shop.Application: 212 per file, 3 compilation-wide (Vendor.Analyzers/RegistrationAnalyzer 21480 ms on one file, ...)

A check line that ends in analyzers unfinished in N means an analyzer was still running when the check had to answer. So does a summary that says the analyzers did not finish in time.

To see which analyzer takes the time in a real build, build with -p:ReportAnalyzer=true -bl and open the binary log's Analyzer Summary, which lists each analyzer's time.

Report a slow analyzer to its authors with that summary. Until they fix it, fuse build runs it.

The engine keeps running the compilation-wide analyzers after the check answers, so a check of the same compilation soon after takes their errors (How it works).

Internal errors #

fuse: internal error: <message> (details in <state directory>/engine.log)

Something went wrong inside Fuse. engine.log holds the exception with its stack trace, on a line with failed:. could not connect to the Fuse engine and could not start the Fuse engine mean the client could not reach or start the engine process. engine.log then shows whether an engine started at all.

Run the command again. When the error persists, open an issue with the command, the message, the engine.log lines around the failure, and the output of fuse --version.

A build waits #

fuse: waiting for another build or test in this repository

Another fuse build or fuse test in the same repository holds the build lock, so this one waits until that run finishes. Waiting is what the lock is for.

When nothing else is running, a fuse process is still alive. The lock is released when that process exits.

fuse: running without the per-repository build lock: <reason> means the state directory cannot be written. The build then runs without that protection.

A fuse test whose runs all run without MSBuild holds the lock only while it plans, so a build waits for it only that long. A fuse test that builds with MSBuild holds the lock until its last test run ends.

A slow build #

A fuse build that takes 10 seconds or more ends its last line with the slowest tasks and projects (fuse build shows the format). Read that line this way:

  • Csc leads. The compiler, with the analyzers and source generators it runs, takes the time. To see which analyzer or generator takes it, build with -p:ReportAnalyzer=true -bl and open the binary log's Analyzer Summary.
  • Exec or a tool's own task leads. A command an MSBuild target runs, such as a code generator, takes the time. The slowest projects name the project that runs it.
  • ResolvePackageAssets, RestoreTask, or Copy lead. Restoring packages or copying output takes the time. When a build restores every time, pass --no-restore once packages are restored.

Task times are summed over every project, and projects build in parallel, so the times can add up to more than the build took.

When the same build is fast one time and slow the next, compare the last line of both runs.

Builds that wait for each other print fuse: waiting for another build or test in this repository first (A build waits). The waiting is not part of the times.

A command in the build fails #

Api/Api.csproj(40,5): error MSB3073: The command "dotnet getdocument --assembly Api.dll" exited with code 11.

An MSBuild target ran a command, such as a code generator, and the command exited with a code other than 0.

The lines under the error, indented by two spaces, are the last lines the command printed. An exception's type and message and its first stack frame usually say what to fix.

When no line follows the error, the command printed nothing, or its MSBuild target runs on a node whose lines Fuse could not match to the command. Run the command the error quotes yourself to see its output.

A locked file #

  locked: Lib/bin/Debug/net10.0/Lib.dll is held by MyApp (pid 1234); stop that process, then run the build again

The build failed with MSB3021, MSB3026, or MSB3027 because another process holds a file the build writes.

The indented line under the error names the file and the holder MSBuild reported, and says what unblocks it: stop that process and run the build again, or dotnet build-server shutdown when the holder is a build server.

When MSBuild names no holder, the line reads locked: <file> is being used by another process; stop the running application or build that holds it, then run the build again.

When two builds overlap, the fix is the same: run builds and tests through fuse build and fuse test, which take the build lock.

An error about generated code #

  generated: Api.Client/obj/Contract/Client.cs declares it, and Fuse reads that file as the last build wrote it; if it is generated from changed code, run fuse build to write it again

The error is about a type or member that a file the build generates declares. Fuse reads that file as the last build wrote it (errors about generated code).

When you changed the code the file is generated from, such as an API's controllers, run fuse build, which writes the file again. The next check reads the new file.

If the error remains after the build, it is a real error in the code that uses the generated file.

Reading fuse status #

fuse status reports whether an engine runs for the repository and how many files differ from HEAD. It never starts an engine to do so. It prints three lines: the engine, the tree, and the large-tree limits. Read them this way:

  • The engine line.
    • fuse: engine running for <root> (pid <n>), <m> MB; idle exits after 30 min names the running engine.
    • fuse: no engine runs for <root>; the next check starts one means none runs, which is normal after 30 idle minutes.
    • fuse: engine for <root> did not answer in 2 s means a pipe exists but no answer arrived in time, so the tree below was read from git instead. Run fuse stop and let the next command start a fresh engine.
  • The tree line. fuse: N changed file(s) since HEAD; tree <12 hex>; HEAD <12 hex> counts what differs from HEAD and prints the tree stamp. Past 300 changed files a warning line follows: checks reseed from git and reload projects. Commit soon.
  • The limits line. fuse: large-tree limits: past 300 changed files a sync reloads projects; past 500 files in reach a check binds whole projects; ... names the two points past which a large tree slows checks down. When checks feel slow and the count is past either point, commit, or run fuse stop and let the next check reload.

fuse status --json prints the same as one object with engine, pid, memoryMB, changedFiles, head, tree, reloadAt, and wholeProjectAt.

Where the logs are #

Fuse keeps its files for a repository in a state directory in your local application data, never in the repository:

Operating systemState directory
Windows%LOCALAPPDATA%\fuse\repos\<id>
Linux~/.local/share/fuse/repos/<id>, or $XDG_DATA_HOME/fuse/repos/<id> when that is set
macOS~/Library/Application Support/fuse/repos/<id>

<id> is the first 16 hexadecimal digits of the SHA-256 of the repository's root path. The first line of each engine.log names the repository its engine served. On Windows, this finds the directory of C:\src\my-repo:

Select-String -Path "$env:LOCALAPPDATA\fuse\repos\*\engine.log" -SimpleMatch "started for C:\src\my-repo (" -List | Select-Object -ExpandProperty Path

On Linux and macOS, search the engine.log files under the directory in the table for started for followed by the repository's path.

The state directory holds:

  • engine.log: one line per event the engine records, each with a timestamp. The engine moves a log larger than 4 MB to engine.log.1 when it starts.
  • hook.log: the failures of hooks run in this repository.
  • build.lock: the build lock.
  • results, shadow, and analyzers: test results while a run lasts, the copies used for test runs without MSBuild (shadow/<project>/g1 and so on, one per simultaneous run), and the copies of the repository's own analyzers.
  • build-*.log: the file log of a build that is running, deleted once the build ends.
  • sessions.tsv and registered-sessions.tsv: which session wrote each changed file, and the sessions a launcher registered with fuse session begin.
  • baseline and last-test-results.json: HEAD's kept errors by commit and configuration, and the last run's per-test verdicts, which fuse test --failed reruns.
  • last-check-results.txt, last-build-results.txt, and last-test-results.txt: every error, diagnostic, or failure the last run found, named by a capped summary.
  • root: the repository's path. Once a day, a starting engine deletes a state directory when its repository no longer exists and nothing wrote to the directory for a day.

The engine itself runs from a copy of the tool at fuse/engine/<version>-<module id> in the same local application data. A starting engine deletes the copies from other builds that no running engine holds.

Reading a phase line #

Every request ends with two lines: a request line, <request> took <ms> ms, and a phase line:

phases id=<client process id>-<n> kind=<request> [gateHolder=<holder>] <phase>=<ms> ... total=<ms>
  • id names the client process and its request count, so that you can match a line to the command that sent it.
  • kind is the request: CheckChanges (every change), CheckFiles (named files, which is what a post-edit hook sends), CheckPaths (a scoped check over folders or patterns), PlanAffectedTests (fuse test), PlanAllTests (fuse test --all), or PlanFailedTests (fuse test --failed), plus the session, build-plan and status requests, which are short.
  • When the request waited for the request lock, gateHolder names what held the lock longest during the wait: another request's kind, Preload (the background load or the baseline warm choosing its next project), or Initialization. The line leaves it out when nothing held the lock.
  • The phases follow in the order they ran, in milliseconds.
PhaseTime spent
gateWaiting for the requests ahead of it.
syncFolding the file changes since the previous request into both views.
loadLoading the projects that own the checked files, or for a test plan the projects it needs.
loadDependentsLoading the dependents of the projects with a declaration change.
bindTargets, surfaceDiff, referenceSearch, bindCandidatesThe steps of a check, as How it works describes them: compiling the targets, comparing declarations with HEAD, finding the files that use a changed declaration, and compiling those files.
bindUpdate, bindCompiler, bindAnalyzers, bindFrameworksThe parts of bindTargets: updating the compilation while binding, reading the compiler errors, running the analyzers, and how many documents were bound, one per target framework.
attributionFor a post-edit check answered to a session while another session has written files of its own: compiling the files with errors again, to leave out the errors other sessions' edits caused (sessions). Absent otherwise.
selectionSelecting the tests, including loading the projects they need.
mirror, emitPreparing the copies for runs without MSBuild, after the request lock is released: deciding which assemblies changed and copying the build output, then emitting the changed assemblies and writing them into the copies. An assembly that has not changed since the previous plan is not emitted again.
totalThe whole request from the moment it held the request lock, including a test plan's mirror and emit. The total is counted in system clock ticks, so on Windows a request that took less than about 16 ms shows total=0.0.

Kept answers and background work #

These lines record what a check reused and what the engine did between requests. Each link goes to the mechanism the line comes from.

  • check: kept answer - the check answered from an earlier check without compiling anything, because nothing the check depends on changed (answers kept from an earlier check).
  • check: kept answer skipped, N changed file(s) past 500 - past 500 changed files, the kept answer costs more hashing than it saves, so the check ran as usual.
  • check: N changed file(s) could not be read from disk, so this answer is not kept - the check answered from its snapshot, but the answer is not reused, because a changed file could not be read, or still disagreed with disk.
  • baseline: N stored result(s) read for HEAD <12 hex>; M computed - per check that read the store: how many HEAD results came from disk and how many were bound again.
  • baseline warm: <project> compilation-wide analyzers done in <ms> ms and baseline warm: skipped, HEAD moved again - the background warm after HEAD moved: one line per project warmed, and one when a newer commit cut it short.
  • preloaded <project> compilation in <ms> ms - the background load built a dependent's compilation after loading it.
  • check coverage: reached <names>; current holds <names>; baseline holds <names> - which reached projects each view held. It is written only when a view missed one (with ; recovered after rebuilding the views when the rebuild fixed it), or when the reach named a file on disk with no document (; candidates without a document: <paths>).
  • touched set passed 2000 paths; re-evaluating projects and resetting it - the next sync re-evaluates the projects, because the applied-paths set grew past its bound.
  • ; sessions: <id> N file(s), ... - the tail of a check: line: how many changed files each session wrote, most files first, at most 10 sessions before , and M more.
  • test selection: D of C changed declaration(s) compile to the same code as HEAD; selecting no tests for them - how many changed declarations seeded no tests (same code).
  • test selection: member walk completed in M ms, S symbol(s), C test class(es) reachable, P pattern(s) selected; selecting at member level - this line and the over budget variant ending in selecting at class level, plus test selection: N test classes reachable; selecting at class level past the 100-class gate.
  • test plan: <project>: not emitting <project> again; ... compiles to the same declarations as HEAD - per dependent whose shadow image was kept.
  • test plan: container runtime present; N gated project(s) planned - a plan ran while a container runtime answered, so gated projects were planned, not left out.
  • registered session <name> expired; its files count as no session's now - a fuse session begin registration reached its 4 hours.

Stopping or restarting the engine #

The engine exits on its own in three cases: after 30 minutes without a request, when its repository directory is deleted, and when a client of another build connects.

Ending the engine's process is safe: it holds no lock, it writes nothing into the repository, and the next command or hook starts a fresh engine.

To stop it yourself, run fuse stop in the repository. The command asks the engine to stop, and kills the engine's process when it has not exited within 10 seconds. fuse stop --all does the same for the engine of every repository Fuse keeps state for (fuse stop).

Stop the engine after changing an analyzer that the repository builds itself, when you want memory back at once, or when the engine stops answering.

When fuse stop cannot end the engine, end the process by hand. The engine is a dotnet process whose command line holds fuse.dll engine and the repository's root path. On Windows, this lists the running engines:

Get-CimInstance Win32_Process -Filter "Name='dotnet.exe'" | Where-Object CommandLine -like '*fuse.dll engine *' | Select-Object ProcessId, CommandLine

This stops the engine of C:\src\my-repo:

Get-CimInstance Win32_Process -Filter "Name='dotnet.exe'" | Where-Object CommandLine -like '*fuse.dll engine C:\src\my-repo' | ForEach-Object { Stop-Process -Id $_.ProcessId }

On Linux and macOS, end the process whose command line holds fuse.dll engine and the repository's path, for example with pkill -f and that text.
