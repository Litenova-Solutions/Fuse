How Fuse Works

Fuse answers two questions for a coding agent working in a .NET repository: which compiler errors did its edits introduce, and which tests can those edits break. It answers from a background process that keeps your solution loaded, so the agent does not wait for a full build.

Two terms come up on this page. The working tree is your files as they are on disk. HEAD is the commit you have checked out. Fuse calls an error introduced when the working tree has it and HEAD does not.

How the agent uses Fuse

A harness is an agent host such as Claude Code, Cursor or OpenCode. Most harnesses can run a command when an event happens, for example after the agent edits a file. That command is called a hook. fuse init registers Fuse's hooks with each harness the repository uses, so the agent needs no instructions and no tool to remember.

  • After an edit, Fuse checks the edited files and reports only the errors that edit introduced.
  • Before a shell command runs, Fuse rewrites dotnet build and dotnet test to fuse build and fuse test.
  • Before the agent finishes, Fuse checks every change once more. If the working tree has errors that HEAD does not, it sends the agent back once with the list.

An agent host without hooks, such as VS Code agent mode, uses fuse mcp instead. It is an MCP server (MCP is the Model Context Protocol, a standard way for agents to call tools) that serves the same three operations as the tools fuse_check, fuse_test and fuse_build.

What a check does

  1. Fuse keeps two views of your solution: the working tree and HEAD.
  2. Fuse compiles each changed file in both views and reports only the difference. An error that HEAD already has is never reported as introduced, and neither is an error that only moved to another line.
  3. If only method bodies changed, the check ends there. If declarations changed (types, method signatures, properties and similar), Fuse uses Roslyn, the .NET compiler platform, to find every file that uses, implements or derives from them. It searches the owning project and every dependent project, which is a project that references the changed one, and checks those files too.
  4. Fuse reports compiler errors, warnings that the project treats as errors, and analyzer diagnostics set to error. An analyzer is a code rule that runs during compilation. Only the analyzers that can report an error run.
  5. An error in a file the agent did not edit is followed by one line that names the declaration that changed and broke it, so the agent does not have to trace the error back.

How Fuse selects tests

The affected tests are the tests a change can reach.

  • Fuse builds a graph of which types refer to which types. It walks the graph backwards from the changed code to the test classes that can reach it. The graph comes from each file's syntax alone, and each file's part of it is cached until the file changes.
  • When only a few test classes are reachable, the selection narrows to individual test methods.
  • Controllers, handlers, hosted services and other code that runs behind an application host are reached through the application host, not by name. A change to that code selects every test project that depends on the application.

How Fuse runs tests without MSBuild

MSBuild is the build system behind dotnet build. Fuse skips it when it can. If the test projects have build output from an earlier build and only C# files have changed since then, Fuse copies the test output to a private folder, compiles the changed assemblies from memory into that copy, and runs the tests there. If anything else changed, such as a project file or a resource, Fuse runs a normal dotnet test on the affected projects.

The background engine

  • One engine process runs per repository. The first hook or command starts it, and it exits after 30 idle minutes.
  • At start the engine evaluates every project with MSBuild, without building. It compiles a project only when a change touches it.
  • A file watcher keeps the engine current. When you commit or switch branches, HEAD moves and the engine compares against the new HEAD.
  • A newer Fuse replaces an engine from an older version automatically.
  • Agents that build or test through Fuse in the same repository take turns, so they do not fail on each other's files. The engine loads the repository's own analyzers from a copy, so it never holds a file that a build needs to write.

Privacy and footprint

  • Everything runs locally. Fuse has no telemetry and makes no network calls of its own.
  • Fuse never edits your code and never runs dotnet restore on its own.
  • The only files Fuse writes in your repository are the hook settings from fuse init. Its logs and other state are stored in your local application data folder.
  • In a repository without a .csproj file, hooks return at once and no engine starts.
  • Fuse has no configuration file and no environment variables of its own.

Limits

  • Fuse checks C# only. It needs the .NET 10 SDK and restored projects.
  • A check compiles what MSBuild's evaluation describes. Custom MSBuild targets that change what the compiler receives, and IL weaving (rewriting compiled assemblies after the compiler runs), are invisible to it. fuse build runs the real build.
  • Compilation-end analyzers, which report only after they have seen the whole project, run only when a check compiles whole projects, which happens past 500 files in reach. Otherwise fuse build reports them.
  • Test selection reads the source code and does not run it. A test that reaches code only through reflection may not be selected.
  • Fuse is used day to day on Windows. The automated tests also pass on Linux and macOS.

Questions

What is Fuse?

Fuse is a .NET command-line tool that gives AI coding agents compiler feedback right after each edit. It keeps a repository's solution compiled in memory with Roslyn, reports the errors an edit introduced, runs the tests the edit can reach, and prints build output in a short form.

Which harnesses does Fuse support?

Fuse supports Claude Code, Cursor, Gemini CLI, Codex, GitHub Copilot CLI and OpenCode through hooks, and VS Code agent mode and any other MCP host through fuse mcp. Claude Code and OpenCode are tested end to end. The others follow each harness's documented hook format and are covered by payload tests.

Does Fuse need configuration?

No. Run fuse init once in the repository and it writes the hook settings for each harness it finds. Fuse has no configuration file and no environment variables of its own. It needs the .NET 10 SDK and restored projects; if a restore is missing, it says so and names the dotnet restore command to run.

Does Fuse send my code or data anywhere?

No. Everything runs locally, and Fuse has no telemetry and makes no network calls of its own. It never edits your code; the only files it writes in your repository are the hook settings from fuse init. Commands Fuse runs for you, such as dotnet build, act as they normally would.

How is Fuse different from dotnet build?

dotnet build starts MSBuild, builds the projects and lists every error, including errors that already exist. Fuse keeps the solution compiled in memory and reports only the errors an edit introduced, so it answers sooner: in the measurements the median check took between 0.18 and 0.70 seconds where the median dotnet build took between 1.14 and 4.48 seconds. It does not replace the build; fuse build runs the real dotnet build.

What can Fuse not check?

Fuse checks C# only. A check cannot see custom MSBuild targets that change compiler inputs or IL weaving, and it runs compilation-end analyzers only when it compiles whole projects, which happens past 500 files in reach; fuse build runs the real build. Test selection is static, so a test that reaches code only through reflection may not be selected.

Which platforms does Fuse run on?

Fuse needs the .NET 10 SDK. It is used day to day on Windows, and its automated tests also pass on Linux and macOS.
