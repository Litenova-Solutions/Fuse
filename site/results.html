Reading the Numbers

  • On NodaTime the generated changes reach core types, so every test still runs. The saving there comes from skipping MSBuild, not from selecting fewer tests.
  • On the Community Toolkit the generated changes reach one area at a time, so a small share of the tests runs: 12,449 tests in the repository, and the selection is per change, not per repository.
  • The signature-edit P95 includes the first such edit after the engine starts, which loads every dependent project. On Jellyfin and the Community Toolkit that first edit loads dozens of projects, which is why their P95 is in seconds.
  • NodaTime builds with warnings as errors, so each check there also runs the analyzers that can report a warning. That is why its body-edit check is slower than the small solution's.
  • When a project has a declaration error, the compiler stops before it binds method bodies or runs analyzers, and after any compiler error it skips its documentation checks. Fuse reports those errors at once; the evals count them as deferred, because the build reports them once the first error is fixed.
  • NodaTime's one missed error comes from the build compiling dependent projects against reference assemblies, which leave out private members. It reports "no definition" and one follow-on error where Fuse, compiling against source, reports "inaccessible".
  • In two NodaTime cases hundreds of tests fail, and fuse test lists at most 100 failing names, so those cases cannot be matched name by name. fuse test ran 42,689 of 42,700 tests in both.
  • Timings on this machine vary by about 150 ms between runs of the same build.

How It Was Measured

  • Correctness: generated edits that break or keep the build. An error the build reports and Fuse does not is "missed"; the reverse is "contradicted".
  • Test selection: generated behavior changes that make tests fail. Failing test names are compared exactly with a full dotnet test run.
  • Latency: repeated warm checks after body and signature edits, through the installed fuse command, plus a warm fuse test round and a three-client fuse build scenario.
  • Every result file records the commit of the repository it measured and the Fuse build that measured it, so a number here can be traced to the tree and the binary behind it.

The evals live in evals/Fuse.Evals, and every result file is in evals/results.
