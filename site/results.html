Results

On four repositories, Fuse checked an edit 2.3x to 10.0x faster than dotnet build and ran the affected tests 1.4x to 6.6x faster than dotnet test. It missed 1 compiler error in 120 generated cases (168 edits).

The four repositories are a small generated fixture solution and three open-source repositories: NodaTime, a date and time library; Jellyfin, a media server; and the .NET Community Toolkit, a set of libraries with one source generator for each supported compiler version. Each was measured against the real dotnet build and dotnet test.

Speed and accuracy

A warm check runs on an engine that is already running and has loaded the project. A body edit changes the inside of a method. A signature edit changes a declaration, so Fuse also checks the dependent projects. P50 and P95 are nearest-rank percentiles. P50 is the 8th fastest of the 15 body-edit checks, which is their median, and the 5th fastest of the 10 signature-edit checks. P95 is the slowest check of each kind.

Reading the numbers

  • In 8 of the 10 NodaTime cases the change reached NodaTime.TzdbCompiler, an application. Fuse cannot follow code that runs behind an application host to a test by name, so every test project that depends on the application ran whole: 42,689 tests ran and the other 11 of the 42,700 were skipped. That makes the share 80 percent on average, and the time saved there comes from running without MSBuild.
  • On the Community Toolkit each generated change reaches one area of the code, so only a small share of the 12,449 tests runs (13.7 percent on average). Fuse selects tests for each change, so the share depends on the change.
  • The signature-edit P95 is the slowest signature edit, the one that loads the dependent projects and searches them for the first time; at least half of the signature edits load nothing. The slowest load phase of a signature edit took 25,166 ms on Jellyfin, which checked 27 dependent projects, and 6,833 ms on the Community Toolkit, which checked 12, and the slowest referenceSearch phase took 26,915 ms and 26,823 ms.
  • NodaTime builds with warnings treated as errors, so each check there also runs the analyzers that can report a warning. That is why its body-edit check is slower than the small solution's.
  • The build reports fewer errors than exist in two situations, and the evals count the extra errors Fuse reports there as deferred or unverifiable, not as contradicted. When a project has a declaration error, the compiler stops before it checks method bodies or runs analyzers, and after any compiler error it skips its documentation checks (CS1570 to CS1592). Fuse reports those errors at once, and the build reports them only after the first errors are fixed, so they count as deferred. When a project fails to build, MSBuild skips every project that references it; an error Fuse reports in such a project counts as unverifiable, because the build has no answer there.
  • NodaTime's one missed error comes from a difference in how the build and Fuse compile dependent projects. One edit made DateAdjusters.AddPeriod private. The build compiles dependent projects against reference assemblies, which leave out private members, so it reported CS0117 "'DateAdjusters' does not contain a definition for 'AddPeriod'" at five places and the follow-on CS1503 "Argument 1: cannot convert from 'T'" at a sixth. Fuse compiles against the source and reported CS0122 "'DateAdjusters.AddPeriod(Period)' is inaccessible due to its protection level" at the same five places. The CS1503 error is the one it missed.
  • In two NodaTime cases 126 and 252 tests failed by name in a full run. fuse test prints the first 10 failures in detail and the next 100 by name, then counts the rest, so those two cases could not be matched name by name. In both, the whole suite ran: 42,689 tests ran and the other 11 were skipped.

How it was measured

  • Correctness: the suite makes generated edits, some that break the build and some that do not, and compares Fuse's errors with the errors a real dotnet build reports beyond the ones HEAD already has. Each case makes one edit, or two or three in different projects: 168 edits in the 120 cases. An error the build reports and Fuse does not is "missed". An error Fuse reports that the build does not have, and that the suite cannot account for as deferred or unverifiable, is "contradicted".
  • Test selection: the suite makes generated changes to behavior, some of which make tests fail. It compares the failing test names exactly with a full dotnet test run.
  • Latency: the suite runs the fuse executable built from this repository after 15 generated body edits and 10 signature edits, and times each warm check. It also times 10 checks of the unchanged tree, five fuse test rounds, and three scenarios for several agents in one repository: up to four clients editing and checking at once, three fuse build runs at once five times, and three fuse test rounds over two projects.
  • Every result file records the commit of the repository it measured and the Fuse build that measured it, so each number can be traced to the source and to the executable behind it.

The evals are in evals/Fuse.Evals, and every result file is in evals/results.
