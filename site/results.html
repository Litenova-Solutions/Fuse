Results

On four repositories, Fuse checked an edit 2.3x to 10.0x faster than dotnet build and ran the affected tests 1.4x to 6.6x faster than dotnet test. It missed 1 compiler error in 120 generated edits.

The four repositories are a small generated fixture solution and three open-source repositories: NodaTime, a date and time library; Jellyfin, a media server; and the .NET Community Toolkit, a set of libraries with one source generator for each supported compiler version. Each was measured against the real dotnet build and dotnet test.

Speed and accuracy

A warm check runs on an engine that is already running and has loaded the project. A body edit changes the inside of a method. A signature edit changes a declaration, so Fuse also checks the dependent projects. P50 is the median, and P95 is the time that 95 percent of the checks stayed under.

Reading the numbers

  • On NodaTime the generated changes reach core types, so most tests still run (80 percent on average). The saving there comes from skipping MSBuild, not from selecting fewer tests.
  • On the Community Toolkit each generated change reaches one area of the code, so only a small share of the 12,449 tests runs (13.7 percent on average). Fuse selects tests for each change, so the share depends on the change.
  • The signature-edit P95 includes the first such edit after the engine starts, which loads every dependent project. On Jellyfin and the Community Toolkit that first edit loads dozens of projects, which is why their P95 is in seconds.
  • NodaTime builds with warnings treated as errors, so each check there also runs the analyzers that can report a warning. That is why its body-edit check is slower than the small solution's.
  • The compiler reports fewer errors than exist in two cases. When a project has a declaration error, it stops before it checks method bodies or runs analyzers. After any compiler error, it skips its documentation checks. Fuse reports all of these errors at once, and the build reports the rest only after the first errors are fixed, so the evals count them as deferred.
  • NodaTime's one missed error comes from a difference in how the build and Fuse compile dependent projects. The build compiles against reference assemblies, which leave out private members, so it reports "no definition" and one follow-on error. Fuse compiles against the source, so it reports "inaccessible" instead.
  • In two NodaTime cases hundreds of tests fail, and fuse test lists at most 100 failing names, so those cases cannot be matched name by name. In both, fuse test ran 42,689 of the 42,700 tests.
  • Timings on this machine vary by about 150 ms between runs of the same build.

How it was measured

  • Correctness: the suite makes generated edits, some that break the build and some that do not, and compares Fuse's errors with a real dotnet build. An error the build reports and Fuse does not is "missed". An error Fuse reports and the build does not is "contradicted".
  • Test selection: the suite makes generated changes to behavior that make tests fail. It compares the failing test names exactly with a full dotnet test run.
  • Latency: the suite runs the installed fuse command repeatedly after generated body edits and signature edits, and times each warm check. It also times a warm fuse test round and a scenario where three clients run fuse build at once.
  • Every result file records the commit of the repository it measured and the Fuse build that measured it, so each number can be traced to the source and to the executable behind it.

The evals are in evals/Fuse.Evals, and every result file is in evals/results.
